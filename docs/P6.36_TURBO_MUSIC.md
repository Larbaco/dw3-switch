# P6.36 Music at normal speed while turbo is on (design)

Status (2026-10-29): **design only, no code.** Owner request 2026-10-28: the
music should not speed up in turbo. Goal note: [ROADMAP](ROADMAP.md) P6.36.
Related: [P6.4](P6.4_FAST_FORWARD.md), [P3.6](P3.6_AUDIO.md),
[P6.17](P6.17_VOLUME.md), [P6.22](P6.22_FIELD_CPU.md).

## Findings

**The tick.** The game drives libsnd by hand. `initSound`
(`vendor/dw3_decomp/src/engine/sound/sound.c`) sets `SS_NOTICK`, and the only
call to the sequencer is `SsSeqCalledTbyT()` at the end of `vsyncCallback`
(`vendor/dw3_decomp/src/engine/gfx/display.c`, line 37), installed by
`startVSyncCallback`. One vsync callback is one game frame, so turbo, which runs
more game frames per second (`port/include/port_turbo.h`,
`port/options/turbo.c`), runs more ticks per second. Nothing else in the port
ticks the sequencer. Ticks run on the game thread.

**What a tick does.** `SsSeqCalledTbyT` (`vendor/psyz/decomp/src/libsnd/sscall.c`)
calls `_SsVmFlush` and then `_SsSndPlay` for every playing track, which reads
MIDI events in `vendor/psyz/psyz/src/psyz/midiread_host.c`. A track consumes
`unk54` delta units per call; `unk54` is derived from resolution, tempo and the
vblank rate (`VBLANK_MINUS`, lines ~450-470). So tempo is "per call", and the
call rate is the only thing that sets song speed. The sequencer holds no
absolute position: a different call rate from now on is harmless.

**Pitch does not change.** The SPU mixer is wall-clock: `Psyz_SpuPullSamples`
(`psyz_spu.c`) is pulled at 44.1 kHz by the SDL callback (PC) or the audren
thread (`platforms/switch/psyz_backend/nx_audio.c`, core 1 since #331).
Samples, ADSR envelopes and the XA/CD input all run at 1x. In turbo today the
music has the right pitch and a faster tempo, and notes are keyed on and off
more often per second. The ROADMAP goal note says "tempo and pitch"; it is tempo
only.

**Music and SFX share the ticker, but most SFX are not on it.** Two kinds of
sound exist (`playSound`, `sound.c`):

| Kind | Path | Ticked? |
|---|---|---|
| One-shot effects (most SFX) | `SsUtKeyOn`, immediate voice, then the sample plays | No. They are triggered by game logic, so they already fire 2x-4x as often; each sound plays at 1x pitch and length |
| SEP tracks | `SsSepPlay`: all music, the win jingle (track 30), menu sounds (25/26/28), battle text blips (22/23) | Yes, same `SsSeqCalledTbyT` |

The port already classifies them: `dw3_port_audio_note_sequence`
(`port/include/port_audio.h`, patch 0060) knows if a track is music (the
exclusive flag) and routes it to bus 1, SFX tracks to bus 0. No per-track tick
exists in libsnd: `SsSeqCalledTbyT` walks all tracks.

**Wall clock vs game frames.** Nothing in libsnd needs the vblank. Tick sources
that can work: (a) the game thread, skipping or repeating the call from
`vsyncCallback` through a gate; (b) the mixer thread. (b) is rejected for now:
libsnd is not thread-safe (`_snd_ev_flag` is a re-entry guard, not a lock) and
the game thread calls `SsSepPlay`, `SsSepStop`, `SsUtKeyOn` from tasks. Calling
the tick under the audio lock would also need every game libsnd call under it.
(a) keeps all libsnd calls on one thread.

**What the game waits on.** A search of `vendor/dw3_decomp/src` finds exactly
these libsnd sequence calls: `SsSepOpen`, `SsSepClose`, `SsSepPlay`,
`SsSepSetVol`, `SsSepStop`, `SsSepSetDecrescendo` (in `fadeOutSound` only) and
the tick. **No game code reads sequence state** (no `SsIsEos`, no status calls),
and no code waits for a track to end. The only music waits are loading waits,
which are file-cache driven, not tick driven:

| Place | What it waits for | Tick dependent? |
|---|---|---|
| `battle/battle_mode/entrance.c` (0x1D3 entrance) | `SOUND.fadeOut(MUSIC(0x24,0))` then `loadBank(0x26)`, waits `isLoading()` | Only the fade length; it does not wait for the fade |
| `field/field_mode/field.c` ~l.592 | `loadBank`, `isLoading()`, then `playSound(FIELDSTG_state.music)` or `stopSound` | No. Exclusive `playSound` stops the previous music at once |
| `field.c` l.127 (encounter) | `SOUND.stopAll()` then `SOUND_ENCOUNTS` | No |
| `battle_script.c`, `digimon_change.c`, `normal_battle/menu.c`, gym, name entry, country select, title loader, memory card | `isLoading()` | No |
| `menus/title/splash.c`, `title/movie.c` | `stopAll()` before the movie | No |
| Win jingle / battle report (#215, #223) | The report does not wait for the jingle; it loops (`SEP loop count 127 seq=1 tr=14`) until the field's `playSound`/`stopAll` stops it ([P6.4](P6.4_FAST_FORWARD.md), battle report) | No wait, but see risk R1 |
| Movies / XA | Movies run at 1x (not turbo-gated); XA goes through `Psyz_CdPullSamples` in wall time | Not affected |

So nothing can deadlock or desync logically. The risks are audible: the game
changes tracks at game speed while the music plays at 1x.

**Turbo menus at 1.5x.** The game rate is `dw3_port_turbo_rate_x2()` (2 = 1x,
3 = menu 1.5x, `2*speed` otherwise). The gate must use that rate, not `speed()`
alone, so the music is still 1x in menus. Battle: `FIGHTSTG` runs at the full
speed except the menu cursor (1.5x); the same rate function covers it. Modes
that are never turbo (title, movies, `STSTATUS`) have rate 2 and the gate is a
pass-through there.

## Design

A **music tick gate** replaces the bare call in `vsyncCallback` (one small game
patch, `if (dw3_port_audio_tick_due()) SsSeqCalledTbyT();`, in the style of
patches 0051 and 0176). At rate 2 (1x) it always returns 1, so the output is
bit-identical to today and replays that do not use turbo are unchanged.

Two clock sources, same gate:

* `frames` (deterministic): a credit counter like
  `dw3_port_turbo_present_due()`; each game frame adds 2, a tick is due when the
  credit reaches `rate_x2`, so one tick in `speed` game frames. Correct when the
  host really reaches the set speed (PC pacer). Used by replays.
* `wall`: ticks are due at the region's vblank rate (60 NTSC, 50 PAL, from
  `VSYNC_STEP_*` / `Psyz_VideoStats`) measured with `Psyz_OsNowUs`. It may owe
  more than one tick (cap 2 per game frame, then drop the debt) and may owe none.
  This is what the Switch needs: P6.22 says real turbo speed there is "up to"
  the setting (the rasterizer bounds it), and `frames` would run the music
  slower than 1x when the game cannot keep up.

Turning turbo on or off resets the accumulator (no catch-up burst). Pause
(Options over a held battle, system pause) must not accrue debt: reset the
accumulator whenever the previous game frame was more than 250 ms ago.

### What is ticked at 1x

Phase 1 gates the whole call, so SEP SFX (menu sounds, text blips) follow the
music at 1x. Phase 4 splits them.

### Fades

`fadeOutSound` uses `SsSepSetDecrescendo(..., 0x80, 0x3C)`: 60 ticks, one
second. With the music at 1x and the game at 4x, the battle entrance and map
changes cover a quarter of the fade before the next `playSound` cuts the old
track, so the volume drops abruptly. Fix: the port scales the tick count by the
game rate while the gate is on, `60 * 2 / rate_x2` (15 at 4x), so the fade spans
the same game time as at 1x. Done through a tiny hook in `fadeOutSound`, off
when the option is off.

## Phases (smallest first)

1. **Gate with the `frames` source and the option.** Option row, gate patch,
   log lines, replay scenarios. PC proves the logic. The Switch gets it too but
   runs the `frames` clock (music slower than 1x if the game is under speed).
   Done when the `tick` lines show 15 ticks per 60 game frames at 4x and the
   existing turbo replays pass.
2. **`wall` clock and fade scaling.** Switch default `wall`, PC `wall` when the
   pacer is on. Fade scaling. OLED check at 2x, 3x, 4x, US and EU.
3. **Jingle handoff.** If R1 is judged bad on the OLED: hold the field music
   request until the jingle ends (cap 4 s), see owner question 2.
4. **SFX split (only if the owner wants fast SEP SFX).** PSY-Z gets a mask
   (for example `Psyz_SsSeqTickClass(music_only|sfx_only)`) so the gate ticks
   music tracks on the wall clock and SEP SFX tracks per game frame, using the
   bus class of `dw3_port_audio_note_sequence`. Touches `Larbaco/psyz` (a new
   pin). Not needed for the default answers below.

## Option and log lines

Option: Port options row **Turbo music**, key `turbo_music` in
`port_options.cfg` (P9.4; rows are in `port/options/port_options.c`, same style
as `music_volume`), values `1x` (the music keeps its tempo) and `Fast` (today),
default `1x`. Env override `DW3_TURBO_MUSIC=0|1` for tests. The row has no effect
when Fast-forward is OFF. Record it in `docs/PORT_OPTIONS.md`.

Logs (AGENTS.md rule 12), once per event, never per frame:

* `dw3-audio: music tick source=wall|frames|game rate=N/s game_rate=Nx` when
  turbo starts or stops, or the speed or menu rate changes (`game` = gate off).
* `dw3-audio: music tick window frames=F ticks=T wall_ms=M` once per second of
  turbo (a count line for the OLED).
* `dw3-audio: fade scaled 60 -> 15 ticks` per `fadeOutSound` in turbo.
* `dw3-audio: music tick debt dropped (N)` when the cap or the idle reset fires.
* Phase 3: `dw3-audio: jingle hold start` and `jingle hold end (ms=N reason=ended|cap)`.

## Risks

* **R1 Jingle cut short.** The report is quick at 4x (84 to 101 game frames, about
  0.4 s) and the jingle lasts seconds at 1x. The field's `playSound` stops it,
  as it stops everything today. Mitigation: phase 3 hold.
* **R2 Cut tracks and fades.** Hard cuts by `stopAll`, `loadSoundBankInto`
  (`SsSepStop` on every track of the closed slot) and exclusive `playSound` are
  unchanged but now interrupt a song that is mid-phrase. Fade scaling handles the
  main case; the rest sounds like a PS1 track change.
* **R3 `wall` is not deterministic.** Replays must use `frames`; a wall-clock
  gate must never run in the replay build. `DW3_TURBO_MUSIC_CLOCK=frames|wall`
  in the manifest env.
* **R4 Debt after hitches.** Loading hitches or a suspended Switch must not play
  a burst of ticks. Cap 2 per frame and the 250 ms reset.
* **R5 SEP SFX at 1x.** Menu sounds and text blips on SEP tracks (phase 1) play
  at 1x tempo while the text runs at 4x, so fast text may get fewer blips per
  line. Probably fine; revisit with phase 4.
* **R6 Play time.** `GAME.playTime` is advanced by the same vsync callback and
  is not touched by the gate.
* **R7 Callback order.** The gate must stay exactly where `SsSeqCalledTbyT` is
  now, so `_SsVmFlush` still runs after `GFX.vsyncFunc`.
* **R8 Idle voices.** `_SsVmFlush` runs inside the tick; with fewer ticks it runs
  less often. Watch `dw3-audio: health` voices-in-use (#188) on the OLED.
* **R9 Not verified here.** This is a code reading: no build, replay or listen.
  The 84/101 report frame counts come from P6.4; the jingle length is not
  measured. Measure it (frames between `seq=1 tr=14` start and `end-of-track`
  or the first loop jump) before owner question 2.

## Owner questions (recommended defaults first)

1. **SFX: fast or 1x?** Recommended: one-shot SFX stay as they are (triggered by
   the faster action, already 1x pitch). SEP SFX tracks (menu sounds, text
   blips) follow the music at 1x in phase 1. If you want them fast, phase 4.
2. **Win jingle.** Recommended: plays at 1x and the field music waits for it to
   end, with a 4 s cap (phase 3). Alternatives: let it be cut when the report
   ends (phase 1 behavior, simplest), or keep the jingle at the turbo speed as
   today.
3. **New track while the old one is mid-way.** Recommended: same as the game
   today, the new track starts at once and the old one stops (area change,
   battle start), with fades shortened by the game rate. Alternative: a
   crossfade in the port (not what the PS1 does, more work).
4. **Option and default.** Recommended: row `Turbo music` on `1x` by default,
   `Fast` restores today's sound.
5. **Menus at 1.5x.** Recommended: music 1x there too (the gate follows
   `rate_x2`).
