# P5.4 — Crash report to SD (2026-10-12, 2026-10-16, 2026-10-23)

PR 2 (2026-10-23) adds the next-boot notice and routes assert / abort /
libnx fatal / unannounced `exit` into the same report: see
[Report PR 2](#report-pr-2-2026-10-23-steps-67).

## Landed

- Switch user-exception handler (`__libnx_exception_handler`) writes a
  readable text report to **`sdmc:/switch/dw3/crash_report.txt`**.
- Sink is opened on the main thread at boot (`dw3_nx_crash_install` from
  `boot_main.c` after SD mount + log open). Soft default: handler always
  linked; **no forced fault** in release / preview NROs.
- **Startup latch (2026-10-16):** install rotates a report left over from
  the previous run to `sdmc:/switch/dw3/crash_report_prev.txt` (one kept)
  and logs `previous run crashed: version=… reason=… mode_file=…
  stage_file=…`, so repeating a crash no longer eats the previous copy.
  Archival copies stay the owner's evidence flow.
- After the SD write, the handler `svcBreak`s so Atmosphere creport can
  still capture the fault under `sdmc:/atmosphere/crash_reports/`.
- **Report PR 1 (2026-10-23), steps 1–5 of the error-report plan:**
  1. **Backtrace and module offsets.** `module_base` (the main module's
     text mapping, found with `svcQueryMemory` on our own code) and every
     code address as `base+0x…`. A frame-pointer backtrace of up to 16
     frames (`#00`…): each frame record is read only if it is 8-byte
     aligned and inside `[sp, end of the readable mapping that holds sp)`,
     and the chain must strictly increase, so the walk cannot fault inside
     the handler. Build identity: `git:` (commit at configure time) and
     `build_id:` (the GNU build-id read back from the loaded image).
  2. **`tools/symbolize_crash.py`** turns the offsets into `file:line
     function` (see below). `tools/build_switch_game.sh` prints the
     unstripped `.elf` it leaves next to the `.nro`.
  3. **Last log lines.** `nx_log.c` keeps the last 64 formatted log lines
     (256 bytes each) in a static ring; the handler copies them under
     `--- last log lines ---`. Lock-free: a line being written at the time
     is skipped and counted.
  4. **Crash marker in `dw3.log`.** After the report, one
     `[E][nx_crash.c][crash] CRASH … see sdmc:/switch/dw3/crash_report.txt`
     line is appended to `dw3.log`. `dw3.log` is now a raw libnx `FsFile`
     written with `fsFileWrite` at a tracked end offset (one write per
     line, like the old `fwrite` + `fflush`), so the handler can write to
     it without a stdio lock.
  5. **Readable context.** `mode_file` / `stage_file` keep the hex and add
     the overlay name (`0x207 (STSTATUS)`, `0x1e4 (WSTAG355)`) from the US
     or EU overlay table (`dw3_overlay_file_name`); `disc: US|EU`, and on
     EU `language: N (en|fr|it|de|es|jp-logo)` from `LANGUAGE`; `esr` is
     decoded (`data abort, read, translation fault L2`); all of x0–x28.
- Handler rules: no `malloc`, no stdio, no locks. Text is built with the
  helpers in `nx_crash_fmt.h` (no `vsnprintf`) into a static 32 KiB buffer
  and written in a few `fsFileWrite` calls (after the registers, after the
  backtrace, at the end), so a later step cannot cost the earlier ones.
  Stack use is a few hundred bytes of the 16 KiB `__nx_exception_stack`.
  A re-entry guard `svcBreak`s if the report itself faults.
- Options / mechanism notes (kernel path, Atmosphere creport + fatal, data
  to capture): [P5.4_ERROR_REPORT.md](P5.4_ERROR_REPORT.md).

## Report PR 2 (2026-10-23, steps 6–7)

### 6. Next-boot notice

When `dw3_nx_crash_install` finds a report from the previous run and
rotates it to `crash_report_prev.txt`, the next boot shows this panel right
after the EGL surface comes up, before the runtime check and the game:

```text
The last run crashed.

Version: 0.6.5-preview.29-20-g660c13b
Reason:  assert nx_crash.c:931 crash_force_assert:
         s_force_ptr != 0 && "DW3_FORCE_CRASH=assert"
Mode:    0x0 (none)
Stage:   0x0 (none)

Report saved to
sdmc:/switch/dw3/crash_report_prev.txt
Please attach it and dw3.log to a bug report.

Press A to continue (47)
```

- **All builds** (release, nxlink, force-crash). The fields come from the
  latch (`dw3_nx_crash_previous`), the same first 512 bytes it already
  logs as `previous run crashed: …`; the reason wraps under the value, at
  most three lines, cut with `...`.
- **Duration:** up to 60 s with a countdown (it was 8 s until preview.31-rc1,
  when the owner could not read the panel in time), or A / B / + (counted
  only after the first second, so the press that launched the NRO cannot
  skip it). A HOME / close request ends it at once (`appletMainLoop`), so
  the longer wait does not eat the ~15 s `appletLockExit` grace. A wall
  clock deadline plus a loop cap end it even if the pad or the clock
  misbehave: it **never blocks boot**. `dw3.log` records `crash notice:
  showing (…)` and `crash notice: timed out after 60010 ms (60 frames drawn)`
  or `… dismissed by a button …`.
- **Once per crash.** The rotation consumes `crash_report.txt` (the live
  sink is truncated right after it), so the boot after the notice finds an
  empty report and shows nothing. A boot without a previous report returns
  from `dw3_nx_crash_notice_show` before touching the GPU or the pad: the
  boot flow is unchanged (one flag test).
- **Drawing:** the cheapest path every build already has: the scissor
  clears (`dw3_nx_gpu_clear` / `dw3_nx_gpu_fill_rect`) the STR-restore bar
  uses, plus the HUD's 8×8 font (now `source/debug_overlay_font.h`), one
  clear per horizontal run of lit glyph pixels. No shader, texture or
  allocation. The panel is centred on the whole surface with an integer
  scale, 2 at 1280×720 (handheld) and 3 at 1920×1080 (docked); it is
  redrawn only when the countdown changes and the loop sleeps between
  polls. Nothing of the game is on screen yet, so the widescreen option
  does not apply; the screen is cleared to black when the notice ends.
- **English only.** The port has no localization system yet; the EU build
  shows the same English text.
- **Not shown** when there was no report: a crash before
  `dw3_nx_crash_install` opened the sink (an abort during libnx start-up),
  a fault on the KDebug path that skips our handler (creport only), a hang
  (no exception at all), or a failed rotation (logged as `crash report
  rotation failed`).
- **Limits:** a dock / undock during the 60 s is not followed (the system
  scales the frame; the game's present path picks the new size up right
  after). HOME during the notice is handled by the vsync pump once the
  game starts; the notice itself already stops on an exit request.

Layout and scale are host-tested (`nx_crash_notice.h`,
`tools/tests/test_crash_notice.py`); the drawing is in `nx_crash_notice.c`.

### Why there is no panel at the moment of the crash (2026-10-24)

The owner asked for the screen at the crash itself to wait for a button too.
Nothing of ours is drawn at that moment, and this was left that way on
purpose; the next-boot notice above is the readable screen (60 s, A).

- What shows at the crash is Horizon's own "software closed unexpectedly"
  dialog (creport ends the process with `Result 2168-0006`, User Break), and
  it waits for the OK button by itself.
- A panel of ours would have to draw from the faulting thread: the EGL
  context is current there, and `__libnx_exception_handler` runs on the
  16 KiB `__nx_exception_stack`, far less than mesa needs to clear, draw and
  swap. A GL call from a fault inside the driver (or with its lock held) hangs
  or faults again, and the handler would then lose the `svcBreak` that lets
  creport capture the crash. A watchdog thread could force the break, but the
  panel could not be verified: Ryubing does not deliver real data aborts, so
  only `DW3_FORCE_CRASH=sim` would run it, which skips exactly the dangerous
  part (a fault on a bad stack inside the driver).
- The report is already on the SD card before anything else happens, and the
  boot after the crash shows the notice. If a panel at the crash is still
  wanted, it needs a spike on the console first (own thread with a large
  stack, `eglMakeCurrent` handover, watchdog), not a blind change.

### 7. assert / abort / fatal / exit into the same report

The game image links with `-Wl,--wrap=` for `abort`, `__assert_func`,
`exit`, `diagAbortWithResult` and `fatalThrow` (`CMakeLists.txt`), so every
call to them from any input archive (our code, PSY-Z, newlib, libstdc++,
libgcc, mesa, libnx) goes to a stub in `nx_crash.c`. The stub stores x0–x30
and sp as they were at the call (x16/x17 through the stack), then branches
without a new frame to its C handler with the arguments intact. The handler
builds a `ThreadExceptionDump`: `pc` = the call instruction (`lr - 4`),
`lr`, `sp`, `fp` and x0–x28 from the call site, `error_desc 0x0 (none:
software abort, registers from the call site)`, `esr` / `far` 0. Then the
PR 1 path runs unchanged: report (backtrace walk from the caller's frame,
log tail), the `CRASH` line in `dw3.log`, and `svcBreak` so Atmosphere
creport still captures it. The one exception is an unannounced non-zero
`exit`: after the report and the `CRASH` line it still calls the real
`exit`, because it is an orderly exit whose `atexit` handlers flush dirty
flat saves and the option file (a `svcBreak` would drop them); creport
sees nothing for it. No malloc, stdio or locks; it runs on the
caller's stack below the saved sp, so the frames it walks are untouched.
The next boot's notice fires for these exactly as for a fault.

| Path | Callers in the linked `.elf` (US release, `objdump`) | Before | Now (`reason:`) |
|---|---|---|---|
| `assert()` → newlib `__assert_func` | 13: newlib's own `dtoa` / `mprec` internals (`Balloc succeeded`). Our code, PSY-Z and the decomp build with `NDEBUG` (CMake Release), so their `assert()`s are compiled out | stderr line, then `abort` | `assert mprec.c:N __multadd: Balloc succeeded` (basename, capped at 192 bytes); `svcBreak(BreakReason_Assert)` |
| `abort()` | 40: libstdc++ (`std::terminate`, so uncaught C++ exceptions too), the libgcc unwinder, mesa's shader compilers (`nv50_ir`, GLSL), `__assert_func`, `dw3_overlay_restore` strict mode (replay builds) | `raise(SIGABRT)` → `_exit(1)`: the NRO just closed, no report | `abort` |
| libnx `diagAbortWithResult` | 46: hid (`hidGetNpadStates*`, `padConfigureInput`), `appletGetMessage` / `appletProcessMessage`, `appletInitialize`, `__appInit`, heap / virtmem setup, `threadExit`, `randomGet` | `svcBreak(Panic, &rc)`: creport only | `fatal 0x00006159 (2345-0048, diagAbortWithResult)`; the Result stays the break payload |
| libnx `fatalThrow` | 3, all in mesa's Switch EGL (window surface creation, framebuffer validate, swap) | fatal:u error screen, no report at all | `fatal 0x… (2xxx-yyyy, fatalThrow)`, then `svcBreak` (creport) instead of the fatal screen |
| `exit(n)`, n ≠ 0 | mesa `_eglLog` (fatal), GLSL lexer `yy_fatal_error`, `glsl_to_tgsi`; crt0 when `main` returns non-zero | silent exit | `exit N`, then the real `exit` (no `svcBreak`), unless the boot host announced it (`dw3_nx_crash_allow_exit`: its logged GPU-init and runtime-setup failures stay a plain `exit(1)`, no report) |
| `exit(0)` | normal quit (`main` returns 0 after HOME), replay end, stage sweeps | unchanged | unchanged (`__real_exit`) |
| `__builtin_trap`, `brk`, bad pointers | CPU exception | PR 1 handler | unchanged (`user exception`) |

Not covered, and why:

- **Aborts before `main`** (`__appInit`, `__libnx_initheap`,
  `virtmemSetup`): the stub runs, but the SD card is not mounted yet, so the
  report only reaches `svcOutputDebugString` and creport; no file, no
  notice.
- **`_exit` / `__libnx_exit` called directly**: only `abort` and `exit`
  call them in this image, both wrapped.
- **`__stack_chk_fail`**: not linked (no `-fstack-protector`).
- **PSY-Z** has no fatal / panic helper; its only `assert()`s are in the
  SDL draw backend, which the Switch build does not link.
- **Calls inside the defining object** are not redirected by `--wrap`;
  none of the five symbols is called that way here (checked with
  `objdump`: every call goes to `__wrap_*`; the one direct `bl exit` is
  the stub's own `__real_exit`).
- **Two threads aborting at once** share one register save area; the
  re-entry guard `svcBreak`s the second, so the report may carry the first
  caller's reason with mixed registers. Not seen; noted.
- **Hangs** (no exception, no abort): P10.2 lifecycle work.

Side effect: an `abort()` now ends in `svcBreak` (creport, Atmosphere's
crash screen) instead of a silent `exit(1)` back to hbmenu. Under Ryubing a
replay run that hits the strict overlay `abort` now stops the emulator on
the break instead of a guest exit; its `FATAL overlay restore` line is
printed before, as before.

### Frame pointers

The backtrace follows the AArch64 frame-record chain (x29). devkitA64
GCC 15 at `-O2` already keeps frame records in every non-leaf function
(only leaf functions skip them, and the report's `lr` covers that frame).
The Switch CMake build now passes `-fno-omit-frame-pointer` explicitly so a
toolchain default or a later flag cannot silently break the backtrace.
**Cost: none.** A US release build with and without the flag has the same
`.text` size (5,859,792 bytes) and the same 1,448,842 instructions; only
address operands differ, from the git string. `-mno-omit-leaf-frame-pointer`
was not added: it would cost two instructions per leaf call for a frame
`lr` already gives. A function that ends in a tail call is not in the
chain (its caller's frame is), as with any frame-pointer unwinder; code
without debug info (crt0, libnx assembly) symbolizes to the nearest
function only.

## How to symbolize a report

Keep the `.elf` of every `.nro` you hand out: `tools/build_switch_game.sh`
leaves the unstripped `build/switch[-eu][-nxlink]/dw3-switch.elf` next to
the `.nro` and prints its path. Then:

```bash
python3 tools/symbolize_crash.py crash_report.txt build/switch-eu-nxlink/dw3-switch.elf
```

It prints `file:line function` (with inlined frames) for pc, lr, each
backtrace frame and the registers that point into code, plus the symbol
table's `name+offset` as a cross-check. Return addresses (lr and frames)
are looked up at `addr-4`, the call instruction. It checks the `.elf`'s
build-id (then the version and git strings) against the report and warns
on a mismatch; `--strict` exits 3 instead. addr2line comes from
`--addr2line`, `aarch64-none-elf-addr2line` on PATH or under `$DEVKITPRO`,
or the `devkitpro/devkita64` Docker image.

Reports written before this change have absolute addresses only: pass the
Atmosphere creport log of the same crash (`--creport
sdmc:/atmosphere/crash_reports/<n>_<program id>.log`; the module base comes
from its `dw3-switch + 0x…` lines, and its crashed-thread stack trace is
symbolized too) or `--base 0x…`.

**Use the `.elf` of the exact `.nro` that crashed.** The four preview
builds (US, EU, each normal and `-nxlink`) are laid out differently. Check
with the preview.30-rc6 OLED crash (owner, EU `-nxlink`, Items screen;
evidence `tmp/evidence/2026-10-22-preview30-rc6-oled/`): with the EU
`-nxlink` `.elf` and the creport base `0xb697c2000`, pc `base+0x1613ec` is
`getItemCategory` (`items.c:28`) called from `STSTATUS_drawItemScreen` ←
`STSTATUS_updateItemScreen` ← `executeTask` ← `dw3_game_main` ← `main`, which
is the bug patch 0069 fixed. The earlier manual reading,
`spriteDrawerDraw` (`sprite_drawer.c:148`), came from the EU **normal**
`.elf`, which puts a different function at that offset. The new
`build_id:` field and the symbolizer's check catch that mistake.

**Previews:** the release workflow publishes `dw3-switch-elf.zip` (US and US
nxlink `.elf` plus `BUILD_IDS.txt`) with each release, and the EU `.elf` zip
is uploaded by hand. Download it from the release, find the report's
`build_id:` in `BUILD_IDS.txt`, and pass that `.elf` to the symbolizer. See
[RELEASES](RELEASES.md#publishing-a-release). Releases up to preview.30 have
no `.elf` published.

## How to force a fault (debug build)

Soft default is **off**. The build script passthrough (`--force-crash`)
makes the smoke build one command:

```bash
./tools/build_switch_game.sh --nxlink --force-crash        # US
./tools/build_switch_game.sh --eu --nxlink --force-crash   # EU
```

Right after boot (`entering dw3_game_main()`), the NRO null-writes from a
small chain of functions (`crash_force_null_write` ← `crash_force_now` ←
`dw3_nx_crash_force_fault` ← `main`), so the report's pc, lr and frames
must symbolize to exactly those. Development-only environment, baked with
`DW3_NX_TEST_ENV` (the build script passes it through; Ryubing cannot pass
an environment to a homebrew NRO):

- `DW3_FORCE_CRASH_PUMPS=N` — fault at vsync pump N, inside the running
  game, instead of at boot (mode/stage names, a deeper backtrace and a
  fuller log tail);
- `DW3_FORCE_CRASH=sim` — call the handler directly with the thread's live
  registers instead of faulting. **Ryubing does not deliver a guest data
  abort to the libnx handler** (it stops the guest with
  `InvalidMemoryRegionException`; the report file stays empty), so the
  emulator can only exercise the report path this way. Hardware is the
  truth for the real fault path.
- `DW3_FORCE_CRASH=assert` — a failing `assert()` in `crash_force_assert`
  (the forced site re-includes `<assert.h>` without `NDEBUG`, so the macro
  is the real one even in the Release build);
- `DW3_FORCE_CRASH=abort` — `abort()` in `crash_force_abort`;
- `DW3_FORCE_CRASH=fatal` — `diagAbortWithResult(MAKERESULT(Module_Libnx,
  LibnxError_ShouldNotHappen))`;
- `DW3_FORCE_CRASH=exit` — `exit(3)`.

The four software paths behave the same in Ryubing and on hardware (no CPU
fault involved). Like `sim`, they exist only in `--force-crash` builds,
never in release or preview NROs.

```bash
DW3_NX_TEST_ENV=DW3_FORCE_CRASH_PUMPS=1500 ./tools/build_switch_game.sh --nxlink --force-crash
DW3_NX_TEST_ENV=DW3_FORCE_CRASH=sim,DW3_FORCE_CRASH_PUMPS=1500 ./tools/build_switch_game.sh --nxlink --force-crash
DW3_NX_TEST_ENV=DW3_FORCE_CRASH=assert ./tools/build_switch_game.sh --nxlink --force-crash
DW3_NX_TEST_ENV=DW3_FORCE_CRASH=abort,DW3_FORCE_CRASH_PUMPS=1500 ./tools/build_switch_game.sh --eu --nxlink --force-crash
```

The CMake option `DW3_NX_FORCE_CRASH` still works when configuring
directly (Docker/`tools/dk.sh` on this host):

```bash
./tools/dk.sh bash -c 'cmake -S platforms/switch -B /tmp/dw3-force-crash -G Ninja \
  -DCMAKE_TOOLCHAIN_FILE=/opt/devkitpro/cmake/Switch.cmake \
  -DDW3_NXLINK_STDIO=ON -DDW3_NX_FORCE_CRASH=ON && \
  cmake --build /tmp/dw3-force-crash -j"$(nproc)"'
```

Boot that `.nro` once, then pull `sdmc:/switch/dw3/crash_report.txt` and
`sdmc:/switch/dw3/dw3.log` over FTP / USB. Expect `reason: user
exception`, `esr: 0x92000046 (data abort, write, translation fault L…)`,
`far: 0x0`, a `build_id:`, `base+0x…` on pc / lr / frames, the last log
lines (ending in `DW3_NX_FORCE_CRASH: deliberate null write`) and the
`CRASH` line at the end of `dw3.log`. `mode_file` / `stage_file` are
`0x0 (none)` for the boot fault. A fresh Atmosphere report under
`sdmc:/atmosphere/crash_reports/` is expected too. On the *next* boot,
`dw3.log` gains the `previous run crashed:` latch line and the old report
is kept as `crash_report_prev.txt`. Reports written by preview.29 count two
pumps per VSync (fixed after it): halve its `vsync_pumps`, and its
`last_dt_us` spans 30 frames, not 60.
[PREVIEW26_CRASH_RECORDS.md](PREVIEW26_CRASH_RECORDS.md) already shows both
mechanisms producing files after real (unforced) crashes on the OLED.

Software-only report without a CPU fault (for host unit checks later):

```c
dw3_nx_crash_write_report("manual smoke");
```
