# P5.1 — Memory budget instrumentation

Status: **in progress**. Instrumentation (Switch `mem dbg:` line), a PC
equivalent, a host allocation audit and 2 h / 1 h PC soaks exist (see "PC audit
and soak"). The roadmap done-when, a 2-hour session flat **on the console**,
is still the owner's OLED check: tick P5.1 only after the checklist at the end
of this file.

## What is measured

| Bucket | Source | Notes |
|---|---|---|
| Game heap arena | `DW3_HOST_HEAP` (8 MiB BSS) | Walk `HEAP` list; used / free / high-water |
| File cache | `MEM_FILE_CACHE` tagged spans | Subset of the game heap |
| VRAM emulation (fixed) | Soft RGB555 (1 MiB) + `nx_gpu` RGBA pack (2 MiB) + overlay/stage host BSS (256+512 KiB) | Reserved size, not a growing allocator |
| libc (newlib) | `mallinfo().uordblks` | Host `malloc` (map preload buffer, misc); high-water tracked |

Map preload lives in libc, not the game heap (see `cdfs_read_field_tile`).
This instrumentation does **not** change cdfs or allocators.

## nxlink line (~1 Hz)

Sibling of `frame dt us=` / `mesh dbg:` (60 VSync pumps):

```
mem dbg: heap=1234K/8192K hw=1300K free=6800K fcache=200K/hw=250K vram=3840K libc=400K/hw=450K
```

| Field | Meaning |
|---|---|
| `heap=used/arena` | Occupied vs 8 MiB host arena (KiB) |
| `hw=` | High-water of heap used since boot |
| `free=` | Free-list span total |
| `fcache=` / `hw=` | `MEM_FILE_CACHE` used / high-water |
| `vram=` | Fixed VRAM-emulation footprint (KiB) |
| `libc=` / `hw=` | newlib allocated / high-water |

Before `initHeap`, the line reports `heap=n/a` and still shows vram/libc.

## On-screen HUD

When `DW3_NX_DEBUG_OVERLAY` is on, the same sample feeds two short lines
(`heap …`, `fc=… libc=…`). Visual only — no extra per-frame nxlink traffic.
See [DEBUG_OVERLAY.md](DEBUG_OVERLAY.md).

## How to use for the 2h flat check (later)

1. Build `--nxlink`, launch with NetLoader **Y** + `nxlink -s`.
2. Play field/battle for ~2 hours; leave the HUD visible or capture the log.
3. Compare early vs late `heap=… hw=` and `libc=… hw=`. Flat means used and
   high-water stop climbing after init / first map loads (small mode spikes
   that return are OK; a monotonic climb is not).
4. Do **not** tick P5.1 done until that session evidence exists.

## File cache slots (preview.31-rc1 crash)

The owner's preview.31-rc1 (EU, GPU renderer, OLED) crashed in the second
battle of a session of about two hours, in the battle report: SIGSEGV with
`far=0x4`, backtrace `requestFile` <- `waitForFile` <- `loadFile` <-
`getFileEntry` <- `STFGTREP_drawReport` (`file_cache.c:106`, `slot->file = file`).
`findFreeFileSlot` returns NULL when all `FILE_CACHE_SLOTS` (64) are used and
`requestFile` did not check. The log showed `fcache=1551K`, more than the whole
PS1 heap.

Cause (port, not psyz): on the PS1 the heap is 1.33 MB, and `allocMem` evicts
the least recently used file until an allocation fits, so the 64 slots never
filled. The host heap is 8 MiB (patch 0012), nothing evicts, and a long
session fills every slot. US has the same code, so US was affected too.

Fix (patch 0096): when no slot is free `requestFile` evicts the least recently
used loaded file, the policy `allocMem` already uses (queued or reading files
are never candidates), and takes its slot. With nothing to evict it logs and
aborts so the crash report names the cause. Evictions go to `dw3.log`
(`dw3-file-cache: all 64 slots taken, evicted ... (eviction N)`, the first 16,
then every 256th): if the owner sees these lines the cache did fill.

Test: patch 0095 adds `DW3_FILE_CACHE_SLOTS=<n>` (PC), and the replay scenarios
`us/eu-file-cache-full` run two forced battles with 16 slots. Without 0096 both
end in SIGSEGV in `requestFile`; with it both battles finish and the eviction
line is logged. Natural play: two battles use about 46 slots at most
(measured with a temporary counter), so the cache fills after several battles.
A small cache (20 slots) also changes some frames of `two-battles`, because
evicted files reload; that is why the hook is not set in other scenarios.

## PC audit and soak (2026-10-25, branch test/p5.1-memory-soak)

Tools (all PC only, off unless asked, no effect on replays):

| Tool | What it does |
|---|---|
| `DW3_MEM_LOG=<csv>` (`platforms/pc/src/mem_sampler.c`) | The PC `mem dbg:` line: every `DW3_MEM_LOG_EVERY` frames (default 600) one CSV row and one `dw3-mem:` stderr line with game heap used / free / high-water, file cache, mode-tag and locked heap bytes, glibc `mallinfo2` (in use, mmapped, arena), RSS, VmHWM, VmData, threads, open fds. The heap walk is the one of `nx_mem_budget.c` |
| `DW3_SOAK_ARM_EVERY=<frames>` + `DW3_SOAK_ARM_LIST=a;b;c` | Re-arms the Cheats one-shots in turn (`dw3_cheats_soak_arm`, same specs as `DW3_CHEATS_ARM`): warp, battle now, money, give item, fill bag. Needs `cheat_enabled=1` |
| `DW3_PC_FRAME_LIMIT=1` | Real 1x pacing. Under Xvfb the driver VSync does not block, so a plain run goes at about 2x (115 fps measured); this switches PSY-Z to its frame limiter |
| `tools/memaudit/soak.py` | One process under its own Xvfb, nice 10: a save phase (forced save screen, as `xr-save`), then Continue and a pad loop (walk, Cross, field menu, battle mash) with the warp / battle / money / item rotation every 2400 frames and auto-save on |
| `tools/memaudit/malloc_audit.c` | `LD_PRELOAD` malloc counter: every allocation after frame 3000 keyed by call stack, split game thread / other threads, with live-pointer tracking; written per 600-frame window. `soak.py --preload` runs with it |
| `tools/memaudit/report.py` | `mem`: table of first / last tenth, max and least-squares slope, plus an SVG chart. `audit`: symbolized sites by origin and by game mode |

```bash
cc -O1 -g -shared -fPIC -o libdw3_malloc_audit.so tools/memaudit/malloc_audit.c -ldl -lpthread
tools/memaudit/soak.py --version us --bin build/pc/dw3-pc --runtime ~/.cache/dw3-switch/runtime/us \
    --out /mnt/cabal/tmp/soak-us --hours 2          # 1x; --turbo 4 for faster, --preload for the audit
tools/memaudit/report.py mem /mnt/cabal/tmp/soak-us/mem.csv --svg soak.svg
```

### Allocation audit (host malloc, US, 0.8 h of game time at turbo 4, 169626 frames after frame 3000)

Result: **after init, no port or engine code allocates per frame.** Every
frame of the game thread does allocate (600 to 800 times), but all of it is
the PC-only `sdl3_gpu` renderer: SDL's Vulkan backend (`VULKAN_BindGraphicsPipeline`,
`VULKAN_DrawIndexedPrimitives`, `VULKAN_INTERNAL_BindGraphicsDescriptorSets`,
99.8% of 107 M allocations) and lavapipe's worker threads (26 M, other threads).
The Switch host has its own present path (`nx_gpu`) and none of this. Freed
as fast as allocated; the SDL descriptor-set bookkeeping holds 30 to 60
thousand live blocks and grows slowly (62k at the end), bounded by the arena
staying flat (below).

What is left on the game thread, by mode (allocations per frame without the
SDL GPU renderer; `audit-us-report.md` in the evidence folder has the stacks):

| Mode | per frame | Sites |
|---|---|---|
| field walk | 0.24 | `host_file_size` (fopen + fseek + fclose, a 4 KiB FILE buffer) from `cdfs_file_size` <- `readFile` <- `FIELDSTG_seekStream` / `updateFileCache`: one per file request, not per frame; `X11_PollEvent` (SDL, PC only) |
| battle | 0.07 | the same, `X11_PollEvent` |
| battle report | 0.19 | the same |
| field menu / status | 0.24 | the same |
| area change | bursts | `map_load` (one `malloc` of the whole map file, `map_release` frees it: one live buffer), overlay `readFile` requests |
| title | 14.9 | **title movie** (`STDWTITL_onSliceDecoded`): `rgb888_packed_to_5551` malloc/free per slice, 0.9 MB of churn per frame; the PSY-Z present path (`AllocRgb24Region`, `Draw_StoreImage`, vendor) mallocs a few MB per frame as well |

Fixed: `rgb888_packed_to_5551` (platforms/pc/src/psyz_dma_present.c, PC only)
now reuses one buffer; pixels are the same (replay suite below). Not fixed,
documented: `host_file_size` could be a `stat()` (port/cdfs, shared with the
Switch; saves a FILE and a 4 KiB buffer per file request, about 0.1 per frame
in the field; left alone because it cannot be checked on hardware here), the
vendor PSY-Z title movie allocations (PC renderer), and the SDL GPU churn.

Charts and CSV: `tmp/evidence/20261025-p51-memory/{us,eu}-soak/` (not in git).

Slopes (least squares over the whole run after 10 min) that look like growth,
and why they are not:

- **Game heap high-water, US +96 K/h:** it climbs in steps when a combination
  is seen for the first time (a new area or battle: 1770 -> 1782 -> 1797 -> 1810
  -> 1929 K) and is flat from minute 93 to 140 (slope +0 over that last 50 min;
  the used heap in the same window moves between 1.4 and 1.7 M and returns).
- **glibc in use +1153 K/h (US), +2867 K/h (EU):** the first hour loads each
  area's map buffer, overlay snapshot and textures once; the last 50 min of the
  US run are -490 K/h with the arena fixed at 94008 K. EU shows the same shape
  (arena 90.1 M from minute 26, 90.5 M at the end, +1007 K/h from 30 min on);
  a 1 h run cannot separate that from a slow climb, which is why the OLED check
  below is still needed. The SDL GPU descriptor cache (above) is a PC-only part
  of that.
- **RSS, US -47 M:** the last 15 min drop from 337 to 277 M while glibc in use
  and VmData stay flat. The desktop's swap was full (11.4 of 11.4 GiB), the
  kernel swapped pages out. Not a leak.
- Mode-tag heap and file cache move with the mode and return (battle and
  report load files, the next field frees them): the file cache never got
  near 64 slots in 61 battles, so #235's eviction was not exercised here; it
  is still covered by the `file-cache-full` scenarios.

Not covered: the PC build is the `sdl3_gpu` renderer on lavapipe, so the host
numbers (glibc 70 M against newlib 144 M on the Switch, RSS) are not the
console's; the game heap numbers are the same arena and the same code. The
Cheats rotation is a test aid, not a player's route; no cooking, card
battles, shops or training were visited. The soak lasts one session of the
loop (about 15 min of pad pattern, repeated), so it is deterministic.

### Owner checklist: 2 hour OLED / nxlink session (P5.1 stays unticked until done)

1. Build `./tools/build_switch_game.sh --nxlink` (US) and `--nxlink --eu` for
   EU; run each as its own session. HOME menu off, auto-sleep off, handheld on
   the charger, `nxlink -s` capture to a file (`nxlink -s dw3.nro 2>&1 | tee
   p51-us-<date>.log`), and keep `sdmc:/switch/dw3/dw3.log`.
2. Play 2 hours of wall time without restarting the NRO, at 1x (no R3
   fast-forward, or note how long it was on). Include at least: 8 or more
   random battles (win them, take the report), 10 or more area changes (doors
   and map exits), the field menu and Items / Status / Options screens a few
   times, Cards / Gym / Digimon Lab if reachable, three manual saves and
   auto-save ON for the area changes, one Continue from the title, and one
   sleep / wake cycle. Turn on Cheats > Battle now and Warp if the session
   needs more battles or areas per hour (it will be marked in the save).
3. Every 15 minutes write down the HUD line (Debug overlay) or take it from
   the log: `heap=` / `hw=`, `fcache=`, `libc=` / `hw=`.
4. Pass when: after the first 30 minutes `heap hw` and `libc hw` stop climbing
   (a rise below 1% of the arena, 80 K, over the last hour is noise; each
   new area or battle type may raise them once), `libc` used has no
   monotonic climb across the last hour, no crash report, no
   `dw3-file-cache: all 64 slots taken` followed by `FATAL`. Evictions lines
   are fine and worth keeping.
5. Report: the `mem dbg:` lines at minute 30, 60, 90, 120 (hw and used), the
   count of `dw3-file-cache` lines, total battles / area changes, the EU run
   language, whether the console slept, the paths of the logs. State what was
   not covered. Then tick P5.1.

For reference the rc7 sample is 144435K newlib hw, 1685K game heap hw and 1259K
file cache after 30 minutes; the PC soak above stabilizes at 1.9 M game heap
hw and 1.4 M file cache.
