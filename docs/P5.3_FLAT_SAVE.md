# P5.3 — Flat save host (2026-10-11)

## Landed

- Runtime save format is **one flat file per port** (`save0.bin` /
  `save1.bin`, 32 KiB) under the existing memcard directory, resident in
  RAM. `MemCardReadFile` / `MemCardWriteFile` are `memcpy` at offset.
- Flush is deferred: one rename-atomic write when a write section ends
  (next non-write `MemCard*` call) or on `memcard_host_shutdown`.
  Write goes to `saveN.bin.tmp`, then `remove(saveN.bin)` + `rename`
  (FAT/exFAT and Windows reject rename-over-existing with EEXIST).
- `MemCardGetDirentry` returns synthetic `size = 0x8000` when a save
  exists. `MemCardExist` / `MemCardAccept` do not walk directory frames.
- One-time migration from this port's `memcardN.mcr` → `saveN.bin` by
  DW3 product name (US/EU/JP), with the image renamed to `.mcr.bak` only
  after a successful extract. Corrupt/wrong-size `saveN.bin` is
  quarantined as `.bad` so migration can still run.
- PC and Switch hosts register `atexit(memcard_host_shutdown)` and call
  shutdown if `dw3_game_main` returns.
- No in-game emulator card import/export (P9.6 stays a separate tool).

## HOME / quit flush (2026-10-12)

Switch `boot_main` vsync now drains applet messages with `appletMainLoop`.
Current libnx `appletGetMessage` uses `eventWait(..., 0)` (non-blocking);
older notes that `appletMainLoop` hung the first frame applied to an older
SDK. On `ExitRequested` (HOME):

1. `dw3_nx_set_quit_requested()` → `Psyz_QuitRequested` becomes true so
   `dw3_game_main` returns.
2. `memcard_host_flush_all()` runs immediately (before teardown).
3. `appletLockExit` at boot gives ~15s for flush + leave `main` instead of
   an immediate force-kill; `appletUnlockExit` before return.

`atexit(memcard_host_shutdown)` and the post-`dw3_game_main` shutdown path
remain as a second line of defense.

## OLED preview.13 — EEXIST flush (2026-10-11)

In-game SAVE on flat `save0.bin` / `save1.bin` logged
`memcard flush FAILED ... (File exists)` then `STGMCARD_writeSave ...
status=3` (cartão bloqueado). Cause: `rename(tmp, saveN.bin)` on Switch
SD (FAT/exFAT) when the dest already existed; `flush_failed` left the
card looking locked for the rest of the session. Fix: unlink dest before
rename. On-disk `saveN.bin` from that session should still be the last
*successful* flush (pre-failed write); reboot after the fix clears the
runtime lock — do not FTP-delete saves.

## STGMCARD progress bar (option B, 2026-10-11)

Owner chose **B**: shorten the load/save panel duration on the port
only. Root cause was UI pacing, not flush latency:

- Decomp `panel.c` fills to ~95% over `MEMCARD_LOAD_FRAMES` /
  `MEMCARD_SAVE_FRAMES` (US: **1239** / **1266**), then phase 2 finishes
  over 20 frames (`start(panel, 2, 0x14)`).
- Engine still does one 128-byte sector per frame; flat `MemCard*` is
  `memcpy`, so real work ends after ~78–80 frames (~6% of the PS1 bar).

Port override (`port/patches/0043-PORT_HOST-stgcard-panel-frames.patch`):
under `PORT_HOST`, both constants are **100**. That is slightly above
sector count so the bar stays readable (~1.7 s at 60 Hz for phase 1 +
~0.3 s phase 2) without the ~1240-frame crawl. Non-`PORT_HOST` / PS1
matching builds keep the original defines. Flat-save flush policy and
on-disk layout are unchanged.

**Expected feel:** load/save bar rises nearly in step with sector I/O,
then a short smooth finish to 100% — no long crawl then sudden jump.

**Preview.17 OLED (2026-10-12):** owner confirmed option B felt correct for
**load and save** (tip `413efb8` / #84). Keep 100 frames.
