# P6.32 Map zoom and full-screen map (design proposal)

Status: **phase 0 spike and scaler PoC built (2026-10-27, section 7), awaiting
the owner's OLED look (section 8)**; the design below dates from 2026-10-25 and
the owner decisions are in section 5. The design sections 1 to 6 are unchanged
except where a note says "measured in phase 0". Roadmap entry:
[ROADMAP.md](ROADMAP.md) (P6.32). The 16:9 layout of the same screen is P6.1
(patch `0080`, see
[P6.1_WIDESCREEN.md](P6.1_WIDESCREEN.md#map-results-and-save-screens-patches-0080-0081-0082)).

Owner request (2026-10-24, translated): zoom in and out on the map, and a
full-screen map that uses the whole 16:9 picture.

## 1. Survey of the current code

Read-only, `vendor/dw3_decomp` at `b9caa6cf9648ec331762cacfc7256f5d97d81e0a`
(the pin in `port/patches/DECOMP_PIN`). Paths are under
`vendor/dw3_decomp/src/menus/field_menu/` unless noted. US and EU share the
source; the map code differs by version only in the hover bookkeeping
(`hoverX` exists only on EU) and in the draw code's EU-only mark frames.

### 1.1 Which mode and overlay

The Map is one entry of the field menu (`createFieldMenu`,
`engine/menu/field_menu.c`, inside `FIELDSTG`). Picking it runs the block
dissolve and `requestMode(MODE_STATUS)`, which loads the overlay **`STSTATUS`**
(US `0x1F9`, EU `0x207`; `include/menus/field_menu.h`). `STSTATUS_runScreens`
opens the screen picked in `FIELD_MENU_CHOICE` from the table
`STSTATUS_screens[2][7]` (`helpers.c`); for Map that is `STSTATUS_createMapScreen`.
When the task ends the field menu is recreated. The Map is therefore a
**task inside an overlay that also hosts Items, Status and the others**, with no
mode of its own.

### 1.2 Functions (`map_screen.c`, 346 lines)

| Function | What it does |
|---|---|
| `STSTATUS_createMapScreen(menu, extra)` | creates the task (`createTask(..., sizeof(StatusMapScreen), 4)`); layer `SCREEN_LAYER`, depth 5, `height = 0xF0` (240), `top = 0x10` (the map starts 16 px down). Picks the game half with `STSTATUS_areaFuncs.getGameHalf()`: first half `FILE_STATUS_BG` (`0x78A` US), second half `FILE_STATUS_BG + 2`; requests the area-name text (`TEXT_ASUKA_MAP` or `TEXT_AMATERASU_MAP`) |
| `STSTATUS_updateMapScreen` | the task: open (fade in, `ready = 1`), `TASK_RUN` calls `STSTATUS_runMapScreen`, `STSTATUS_showMapArea`, `STSTATUS_drawMapScreen` in that order, then the close |
| `STSTATUS_runMapScreen` | pad: speed `speedX` / `speedY` ramps 2 to 4 while a direction is held (`PAD_PRESSED`, `PAD_REPEATED`), calls `STSTATUS_moveMapCursor`; **Triangle closes** (`SOUND_MENU_CANCEL`, `TASK_KILL`). No other button is read |
| `STSTATUS_moveMapCursor(screen, dx, dy)` | the scroll rule (below) |
| `STSTATUS_showMapArea(screen, windows)` | finds the visited area under the cursor, plays `SOUND_MENU_CONFIRM` on entry, shows its name in `windows[0]`, above (y `0xB9`) or below (y `0x19`) depending on `hoverY` against `height / 2` |
| `STSTATUS_drawMapScreen` | draws the name box backing (sprite `0x3B` of `FILE_STATUS_SPRITES`), the animated cursor or hover mark, the home mark, the visited spots, the towns, and last the map |

### 1.3 Map image source

The map is **not a bare TIM**. It is frame 0 of a **sprite archive**
(`screen->archive = FILE_STATUS_BG << 16`, entry 0, read with
`FILE_CACHE.getEntry`) drawn by `SpriteDrawer` (`sprite.setTexture(0x280, 0)`,
`sprite.setAltClut(0x140, 0x100)`, `sprite.draw(archive, 0, x, y)`). A sprite
frame is a list of parts (texture page cells), so the picture is stitched from
cells in VRAM at draw time. The port already reads this layout:
`dw3_port_sprite_frame_bounds()` (`port/options/widescreen.c`) walks the frame's
part list to get its bounding box. The width is **392 px** (patch `0080`
notes). The height is not written anywhere in the source; the vertical scroll
range of 0 to `-0x60` (96 px) over a 224 px window (`height - top`) implies about
**320 px, to be measured** in phase 0 (**measured: 392 x 352**, section 7.2). Entry 1 (`archive1`) holds the town
sprites, entry 2 (`archive2`) the cursor, the home mark and the area marks.
Pixels are 4 or 8 bit CLUT data, never a 24-bit picture.

### 1.4 Cursor, markers, scrolling

All values are in map-screen pixels of the 320x240 logical picture.

- **Cursor** `cursorX`, `cursorY`: sprite frames `STSTATUS_cursorFrames[]` of
  `archive2`, 4 animation frames at 4-tick steps. Home mark: `homeX`, `homeY`,
  3 frames; the animation also calls `moveMapCursor(screen, 0, 1)` once per
  cycle (a quirk of the original, kept).
- **Markers** are sprites in map coordinates plus the scroll: visited areas
  `STSTATUS_data.spots[1..46]` drawn when `visited[i - 1]` is set; towns
  `STSTATUS_data.towns[]` from the list `STSTATUS_townList0`, filtered by
  `progress`; area ids by field map in `STSTATUS_mapAreas[]`.
- **Scrolling** is a rule on the cursor, not a camera. The cursor moves freely
  from the edge (x `0x16`, y `0xF`) to the screen middle (x `0xA0`, y
  `height / 2`); at the middle the cursor stops and the map scrolls instead
  (`scrollX` 0 to `-0x48`, `scrollY` 0 to `-0x60`), until the clamp; then the
  cursor goes on to the far edge (x `0x12A`, y `height - top - 0x1E`).
  The hit test in `STSTATUS_showMapArea` works in map space
  (`cursorX - scrollX`), a 6 to 18 px box on each spot. **The scroll limits are
  constants in `moveMapCursor`**: any other size or scale of map needs them
  changed, which is a logic change.

### 1.5 How patch `0080` centres it in 16:9

`port/patches/0080-PORT_HOST-p61-widescreen-map-screen.patch` (draw-time,
gated on `dw3_port_widescreen_menu_shift() > 0`; widescreen off is the PS1):

- `mapDrawScrollX()` reads the frame bounds and, if the map (392) fits in the
  picture (320 + 2 x 53 = 426), returns `offset = (320 - 392) / 2 - x0 = -36`;
  otherwise the PS1 `scrollX`.
- New macros `MAP_X(screen)` and `MAP_CURSOR_X(screen)` replace
  `screen->scrollX` and `screen->cursorX` in **every draw call** (cursor, hover
  mark, home mark, spots, towns, map). Cursor and scroll are still moved by the
  PS1 code, so the logic is untouched; only the x passed to the draw changes.
- `drawMapSides()` adds opaque black `POLY_F4`s on the map's rows beside the
  picture (17 px each side), in the map's own OT entry (`depth + 1`), to hide
  the menu background. The area-name box stays at its PS1 position.
- The vertical scroll is still live in 16:9: only the width fits.

Replay: `us-map-screen`, `eu-map-screen` (P6.15,
[P6.15_REPLAY_TESTS.md](P6.15_REPLAY_TESTS.md); `map_screen()` in
`tools/replay/gen_scenarios.py`): checkpoints `map-open`, `map-left`,
`map-right-a/b`, `map-right`, `map-up`, `map-down`, `map-left-up`, with
references from the patched build.

## 2. What "full-screen" and "zoom" can mean

Source resolution is the limit: the map is **392 x ~320 px**, 4/8-bit CLUT
sprite cells. The display is 426 x 240 logical (16:9), 4:3 is 320 x 240, and the
real output is 1280 x 720 / 1920 x 1080 through the present path.

| Reading | What it needs | Notes |
|---|---|---|
| **Fill the picture** (no zoom) | a backdrop instead of black in the 17 px strips, and the 16 px top band | draw-time only. Never shows more map than 392 x 224. Cheapest "full-screen" |
| **Fit whole map** (zoom out) | scale 0.75: 392 x 320 becomes 294 x 240, the whole map with no vertical scroll | non-integer; the cells must be scaled as quads. Leaves 66 px beside it in 16:9 |
| **Zoom in 2x** | 784 x 640 source on a 426 x 240 window: a pan | integer, so cells stay aligned and no seams. 2x of CLUT art is blocky, but it is the PS1 picture and the output is already scaled by the host |
| **Bilinear** | sampling filter on the scaled quads | only if the renderer filters per primitive; **not known** for PSY-Z, see below. A global present filter would blur the whole game, so it cannot be used for this |
| **Crop and pan** | a window over a bigger map, driven by the cursor | what the PS1 already does at 1x; at 2x the existing scroll limits (`-0x48`, `-0x60`) are too small: pan range needs to be 392 and 320 minus the window, a logic change |

What the renderers allow, from the repo's docs and code:

- **Scale in the game's own draw path.** `SpriteDrawer` draws sprite parts at
  1:1. The game scales panels with `PanelAnim` (horizontal scale about a pivot,
  P6.1 section on menu fades), so scaled primitives are an existing technique
  in `STSTATUS`. A textured quad is a primitive both the soft raster and the SDL3
  GPU path take, but **this is to confirm** in [PSYZ.md](PSYZ.md) and with a test
  before any design depends on it.
- **Filtering.** The PS1 GPU samples with nearest. Whether PSY-Z has a
  bilinear mode per texture page is unknown here; do not promise bilinear until
  phase 0 answers it. Integer 2x and nearest need nothing.
- **Seams.** A map made of cells scaled by a non-integer factor can show
  1-pixel gaps or overlaps between cells. 0.75 is the risky one; 2x is safe.
- **Clip.** A zoomed map must stay inside its window: use the layer's drawing
  area (a gutter-aware scissor, as P6.1 `UpdateScissor` did), not a black
  polygon, or the opaque rectangles of `0080` are overdrawn.
- **Soft raster** (the Switch software path) pays per pixel: a 2x full-screen
  quad covers about 426 x 240 pixels, the same as today's map layer plus the
  backdrop, so no new cost class. A 0.75 scale reads fewer pixels than 1x.
  Measure once (phase 0).

## 3. Options, least to most invasive

All options keep the **save format unchanged** (no new field in `GAME`) and sit
behind a Port option (key in `port_options.cfg`, P9.4), **off by default**, so
the default build keeps `0080` bit-identical.

### Option A: fill the picture, no zoom (least invasive)

Replace the black strips with the screen's own background (the pattern the
other field-menu screens use, patch `0053`), use the 16 px top band, and keep
1x. This delivers "full-screen" and no "zoom".

| Aspect | Option A |
|---|---|
| Patch scope | one patch in `map_screen.c`, replacing `drawMapSides()` with the background draw. No logic change; policy in `port/options/widescreen.c` |
| Risk | very low; draw-time, gated on the gutter. Needs no new pad button |
| Widescreen | built for 16:9; 4:3 is the PS1 layout unchanged |
| Controls (P9.8, P10.6) | none. Triangle (close) is the PS1 cancel and is not remapped by P9.8 |
| Replay | `map-screen` references change in 16:9 only (the strips); with widescreen off they must equal `main`, as `0080` already required |

### Option B: integer zoom steps with pan (moderate, recommended core)

Three states, cycled with a button: **1x** (today, default), **2x** (pan over
the map), and **fit** (whole map scaled to the screen height). Scaling is done in
`STSTATUS_drawMapScreen` by passing a scale and offset to each draw (spots,
towns, marks, cursor, map), through a small helper in `port/map_zoom/`. The
logic functions stay, with the cursor kept in 1x map space so
`STSTATUS_showMapArea` still hits the right spot; at 2x the view centres on the
cursor and the pan clamp is computed by the port, not by `moveMapCursor`. The
cursor is drawn at its map position times the scale.

| Aspect | Option B |
|---|---|
| Patch scope | two patches. First: hooks in `STSTATUS_runMapScreen` (read the zoom button) and `STSTATUS_drawMapScreen` (apply scale and offset), with the state in `StatusMapScreen` (task struct, rebuilt each open, not saved). Second: the area-name box placement at 2x. Policy in `port/map_zoom/`. `moveMapCursor` is wrapped, not edited: a call that would hit the scroll constants at 2x is replaced by the port's pan |
| Risk | medium. The cursor-to-map-space conversion must be exact or the area lookup drifts from the drawn spot. Non-integer fit needs the seam check. Nothing is written to `GAME` |
| Widescreen (P6.1) | 2x fills 426 x 240 fully (no strips). Fit leaves side bars; fill them as in option A. With widescreen off, 4:3 gets 2x and fit too, with the 320 window; nothing is 16:9-only |
| Controls (P9.8, P10.6) | button for the step: **L1 / R1** (Switch L / R) are not read in the map, or **Square** to cycle. L2 / R2 are also free. P9.8's confirm / cancel swap is not touched (Triangle stays "back"). HOTKEYS.md has no conflict: restart is the chord L1+R1+Start+Select, so a single L1 / R1 is free; fast-forward is R3 in field and battle only. Help text needs the button name; until P10.6 it is plain text, after it the glyph |
| Replay | new `us/eu-map-zoom` built like `map_screen()`: open, zoom in, pan to the four corners, fit, back, with `map-open` and the existing checkpoints unchanged when the option is off; one cursor-on-spot check at 2x that the area name appears (a `dw3:` log line for `spot`) |

### Option C: analog zoom, free pan (more invasive)

Continuous zoom (stick or shoulder held) from fit to 3x, free pan with the
right stick, a cursor independent of the scroll, and optional bilinear if the
renderer supports it.

| Aspect | Option C |
|---|---|
| Patch scope | three or more: input beyond the D-pad (right stick through `nx_input.c` and the PC pad), a pan/zoom state machine, scale on every draw, text box layout at every scale. Replaces the scroll rule of `moveMapCursor` for players who enable it, so the logic of the screen forks |
| Risk | high. Non-integer scales make seams on every cell boundary; the cursor, hit test and text box move in a continuous space; analog input must not reach the rest of the overlay |
| Widescreen | works in both; at fractional scales the 17 px strips and the fill have to follow |
| Controls | uses the right stick, which HOTKEYS.md does not assign in menus, plus a reset button; needs a P9.8 decision for the reset |
| Replay | stick input in `.rec` scripts must be supported first; checkpoints at fractional scales have no PS1 reference and rely on the patched build |

### Option D: port-drawn full-screen map view (most invasive)

A port-owned mode that reads the map frame, builds a single bitmap in host
memory from the VRAM cells, and shows it with the host's own texture path at
any scale, filtered, with its own cursor and labels, replacing the field-menu
Map entry or sitting next to it.

| Aspect | Option D |
|---|---|
| Patch scope | a new mode module in `port/ui/`, a hook in `STSTATUS_createMapScreen`, own text rendering for area names (the game's fonts and string loader would have to be reached) |
| Risk | highest. A second renderer for one screen, two code paths to keep in step with each overlay version; the VRAM cells must be read back, which is not a PSY-Z-agnostic operation on Switch |
| Widescreen | free |
| Controls | own focus and input layer (the game screen reads `PAD_*` itself) |
| Replay | host-drawn, so only the patched build can be a reference |

## 4. Decision: option D, as a new second screen (B is the fallback)

Owner decisions (section 5): build **option D**, a port-drawn full-screen map,
as a **new screen next to the game's own Map entry**, which stays exactly as it
is. Option **B** (integer zoom with pan inside the game's screen) is kept only as
the fallback if the phase 0 study below finds D not viable. Options A and C are
dropped (A is subsumed: the new screen has no black strips; C's analog
input was not asked for).

Why a second view and not a replacement (the rationale for answer 4):

| | New second screen (chosen) | Replacing the game's Map entry |
|---|---|---|
| What the player sees | Map entry works as on the PS1; Square opens the big map on top; Triangle/Square returns | Map entry opens the big map directly |
| Risk | The PS1 screen, its replay references and the 4:3 / widescreen-off behaviour are untouched; a failure of the new view falls back to the old screen | Every bug in the new view is a bug in the Map entry; needs the old screen's cursor and names reproduced before it can ship |
| Controls | One extra button on a screen that ignores it (`STSTATUS_runMapScreen` reads only the D-pad and Triangle) | None extra, but the PS1 behaviour is gone for those who enabled it |
| Cost | Needs an open and return path (below) | Hooks the field menu choice and the mode switch to `STSTATUS` |

### 4.1 How the new screen is opened and closed

- **Primary: from the game's Map screen, with Square** (PS1 Square: Switch Y,
  PC Z). The game screen stays alive, frozen, underneath; the port screen takes
  the pad. **Return: Triangle or Square** closes the new screen and the game's
  Map screen is exactly where it was (cursor, scroll, hover untouched); Triangle
  again closes that, as on the PS1.
- **Optional, a later phase: a field hotkey** (proposal: Select in the field,
  with no L/R/ZL/ZR held, the pattern of the Options-in-battle hotkey,
  [HOTKEYS.md](HOTKEYS.md)) that opens the new screen directly without the field
  menu. It needs the field to stand still while open (as patch `0165` did for
  battle), which is harder in the field (NPCs, timers, encounters); so it comes
  after the Map-screen route is accepted. Whether Select is free in the field
  must be verified in phase 0. **Return: the same key or Triangle**, back to the
  field with the game resumed.
- The cursor and visited-area data of the new screen are its own snapshot; it
  opens centred on the home mark or the current area. It never writes to the
  game's `StatusMapScreen` or to `GAME`.
- Where widescreen is off (4:3), the Square press is ignored and the feature is
  unavailable (owner: no zoom at 4:3).
- **No turbo.** The game's Map screen has no fast-forward and the owner wants it
  kept that way. Turbo is gated on the current mode file
  (`port/options/turbo.c`: only `FIELDSTG`, `FIGHTSTG` and `STFGTREP`), and the
  Map screen runs in `STSTATUS`, so it is already off there. The new screen is
  host-drawn at the display rate and independent of the game's speed; it also
  swallows the pad (R3 included) while open. For the optional field hotkey the
  field is not eligible-by-accident: opening the screen must force turbo off
  and ignore R3 until it closes, and a replay checkpoint covers it.

### 4.2 Phase 0 feasibility study for option D

Everything here is from reading the source; items marked **verify** need the
phase 0 spike (a build or a logged run).

**a) Where the map image comes from.** The map is frame 0 of the sprite archive
`FILE_STATUS_BG` (US `0x78A`), a list of texture-page cells, drawn by
`SpriteDrawer` with `setTexture(0x280, 0)` and `setAltClut(0x140, 0x100)`
(`map_screen.c`; section 1.3). The picture is therefore in **PS1 VRAM as 4- or
8-bit CLUT cells** while the game's Map screen is open, and the CLUT is in VRAM
too. The port already does the same trick for the title logo:
`port/options/title_logo_capture.c` walks a sprite sheet's frame parts
(`read_frame`), reads the cells back with `Draw_StoreImage` and resolves the
CLUT, then hands an RGBA bitmap to the overlay
(`dw3_pc_title_menu_set_logo_rgba`). The helper
`dw3_port_sprite_frame_bounds()` (`port/options/widescreen.c`) gives the frame
box. So **the extraction is a known technique, not a new one**. **Verify:** the
cells are in VRAM at the moment the new screen opens (they are drawn every
frame, so yes at the first draw); the exact height (about 320 px); the EU
sheet layout (US and EU share the code, the file ids differ); and that the
capture also works on the Switch, where VRAM is the soft RGB555 copy plus the
`nx_gpu` pack (the title logo is already captured on the Switch GLES overlay,
which is the proof of principle).

**b) How the host draws it.** Two native overlays exist, with one pattern:
Switch `platforms/switch/psyz_backend/nx_title_overlay.c` (GLES3, draws over the
game picture after the composite and before the debug HUD; its logo texture
already uses `GL_LINEAR`) and PC `platforms/pc/src/title_menu_overlay.c` (SDL3
GPU). The Switch file reuses CPU code from `platforms/pc/src/` (the options
cache, the overlay art), so the new screen follows that: **a shared CPU module
(state, capture, pan/zoom maths, marker list, scaler) plus a thin GL draw on the
Switch and a thin SDL3 draw on the PC**. The title overlay is drawn over the 4:3
viewport (`vx, vy, vw, vh`); the map view needs the **whole 16:9 picture** as its
viewport. **Verify** that the present hands the overlay that rectangle (the
game picture with its gutters) on both hosts. The overlay is native
resolution, so zoom and filtering cost nothing in the game's raster.

**c) Markers, cursor and player position.** The data needed is all in
`vendor/dw3_decomp` structures: `STSTATUS_data.spots[1..46]` (map coordinates
and hit sizes) with `visited[47]` (spot i at i - 1, in `StatusData`, part of the
game state), `STSTATUS_data.towns[]` filtered by `progress` and
`STSTATUS_townList0`, `STSTATUS_mapAreas[]` (area id by field map), and the home
mark `homeX, homeY` of the game's task. The current field area gives "you are
here". These are plain reads at open (a snapshot; the screen is frozen), so a
small accessor patch (`0147`) exports them as a flat array to `port/`. Marker
**art**: either capture the game's marker sprites from `archive1` / `archive2`
the same way as the map (runtime only, game-derived), or draw port markers
(simple shapes) so the screen has no dependence on them; with the fan-art map
(4.5) port markers are the natural choice. The cursor is port-drawn and moves
free of the PS1 scroll rule.

**d) Area names.** This is the hardest piece. The names are game text drawn by
the game's own text windows (US English; EU five languages; fonts in VRAM), so
the host cannot just print a string. Two ways: (1) **capture the name box**: run
the game's own lookup (`STSTATUS_showMapArea`'s hit test) for the new cursor and
read the text-window pixels back from VRAM into an RGBA strip drawn by the
overlay. All languages, the game's font, no string decoding. (2) A host font
plus the string loader (`TEXT_ASUKA_MAP`, `TEXT_AMATERASU_MAP`) and a glyph
table for the game's encoding; more code, and it has to handle five EU
languages. **Recommendation: (1).** **Verify** that text-window pixels can be
read after the game draws them, and that the box can be driven from a cursor
that is not the game's. This is the main risk of D; if it fails, the fallback is
B.

**e) Input focus and remap.** A pattern exists: while the port Options screen is
open over the field or battle, the host screen owns the pad and the game does not
see the frames (`port_field_options.h`: "no pad frame leaks into the game";
patches `0160`, `0165`). The new screen does the same through a
`dw3_port_map_view_tick()` called from `STSTATUS_runMapScreen` before its own
input. Buttons are PS1 **logical** buttons (after the host map in
[HOTKEYS.md](HOTKEYS.md)), so a binding like "open = Square, zoom = L1 / R1" is
one definition that holds on Switch (Y, L, R) and on PC (Z, Q, R) for US and EU,
and the host-level remap of P6.12 (physical to logical) composes with it for
free. P9.8's confirm / cancel swap does not touch Square, L1 or R1; Triangle
stays the cancel in both layouts. To be **remappable** before P6.12 exists, the
three actions (open, zoom out, zoom in) read from a small binding table in
`port/options/` with defaults Square, L1, R1, and optional file-only keys in
`port_options.cfg`; when P6.12 lands, its submenu lists these three rows. No
conflict in HOTKEYS.md: restart is the four-button chord, fast-forward is R3 and
only in field / battle. **Verify** that L1 / R1 / Square reach the Map screen on
the Switch (`nx_input.c` maps them) and on the PC.

**f) Memory budget (Switch).** [P5.1_MEMORY.md](P5.1_MEMORY.md): the fixed VRAM
emulation is about 3.8 MiB, the game heap is an 8 MiB arena, and the GLES
driver's heap already holds the title overlay's 16.2 MB atlas, released after
idle frames. The map view's costs: native RGBA of the map 392 x 320 x 4 = about
0.5 MB; an upscaled copy at 3x = 4.5 MB, at 4x (1568 x 1280) = 8 MB; the decoded
PNG of an asset pack is a transient of the same size. The view is **lazy** (built
on open, released after idle frames, the title overlay's policy), and the title
atlas is not needed in the field menu, so the peak does not stack on the title's.
Measure with the `mem dbg:` line (P5.1) in phase 0/5 before committing to 4x;
the numbers above are arithmetic, not measurements.

**g) The new-limits question (answer 5).** The PS1 clamps are exactly the image
bounds, not a margin: `scrollX` min `-0x48` = 392 - 320 and `scrollY` min `-0x60`
= 320 - 224, so **the map data does not extend beyond the 392 x ~320 frame**
(confirm with the bounds in phase 0; there is no hidden border art). What the
PS1 does limit is the **cursor**: it can reach map x 22 to 370 and starts at
y 15, so strips of about 22 px at the left and right and 15 px at the top are
**unreachable by the PS1 cursor**. **Verify** (a spot list check) whether any
spot or town lies in those strips. For the new screen: pan limits are the image
box at every zoom (no pan past the art), with an optional margin of half a spot
box so an edge spot can be centred; the cursor moves over the whole image
including the strips the PS1 cannot reach; at zoom levels where the whole map
fits (the fit step) the view is centred and does not pan. So "as far as
possible" means the full image, which is as far as the data goes; the extra
reach over the PS1 is the cursor strips.

### 4.3 Upscale and filtering survey (answer 6)

The source is a 392 x 320 CLUT picture; the screen shows it at 426 x 240
logical, output 1280 x 720 or 1920 x 1080. Costs are for the Switch (Tegra X1
GLES, no overclocking per AGENTS.md; a static screen) and the PC. None were
measured; shader costs are counted in texture samples.

| Method | Look | Cost on Switch | Notes |
|---|---|---|---|
| Nearest | crisp, but uneven pixel widths at non-integer zoom (shimmer when panning) | free (the present path today) | right at integer zoom only; the owner wants non-integer |
| Bilinear (`GL_LINEAR`) | smooth but soft and blurry at 2x or more | free (hardware) | the Switch title logo overlay already uses it; fine at 1.0 to 1.5x |
| Sharp-bilinear (integer nearest pre-scale, then bilinear on the remainder) | crisp pixel centres, clean edges at any zoom | 1 to 4 texture taps per pixel, trivial | **best generic fit for non-integer zoom with the unmodified art**; one small fragment shader (GLES) / SDL3 GPU shader |
| Lanczos2 or bicubic, once on the CPU | smooth and sharp, slight ringing | one pass at open: the title logo already does Lanczos2 300 x 136 to 720 x 326 (`title_logo_resample.c`); 392 x 320 to 1568 x 1280 is about 16 times more pixels (measure on the console) | cached texture; zero per-frame cost; reuse the existing code |
| xBR / HQx / ScaleFX (pixel-art scalers) | sharp diagonals on hard-edged sprites | GPU shader of 10 to 20 taps per pixel, fine at 1080p for one static quad; or once on the CPU | made for sprites with few colours and hard outlines; this map is painted, dithered CLUT art, where they tend to produce blotches, so **not recommended as default**; could be an optional style |
| Offline AI upscale (Real-ESRGAN-type, ncnn / PyTorch) of the user's extracted map, as a user-supplied pack | best quality, fixed size (typically 4x: 1568 x 1280) | none on the Switch: only a PNG decode at open (about 8 MB transient) and a texture | runs on the user's PC in seconds to minutes; see 4.5; the model must not move geometry, since markers use PS1 coordinates |
| Diffusion upscalers / img2img | may add detail | none on the Switch | risk of changing the layout (spot positions stop matching); owner-supplied only and checked against the marker overlay; on-device inference is not viable on the Switch CPU/RAM budget |

**Recommendation:** a default with no asset needed: **sharp-bilinear** of the
captured map at any zoom; **Lanczos2** (CPU, once) is the softer alternative if
the owner prefers that look; a **replacement picture** (4.5) when one is
present. Nearest stays as a "crisp" style at integer steps. These are styles
inside the single `map_view` option (answer 7), not new rows.

### 4.4 Zoom steps

Non-integer steps are wanted. Proposed ladder, as a scale of the source map:
**fit** (whole map in the viewport height: about 0.75; computed from the
viewport), **1.0**, **1.5**, **2.0**, **3.0**, and **4.0** (only when a
higher-resolution source or pack is loaded, otherwise capped at 3.0 so the
screen never magnifies beyond what the source can show). L1 steps down and R1
up (remappable); the zoom is about the cursor. Seams are not an issue: the map
is **one bitmap** built from the cells at open, drawn as a single quad, so the
cell-seam risk of options B and C does not exist in D.

### 4.5 Where the map picture comes from: two sources

The new screen takes its picture from the first of these that exists, and
works with none (the captured map, 4.2a):

1. **Original fan-art map, committed to the repo.** A new, original illustration
   of the world map, drawn to the same geometry as the PS1 map (aspect
   392:320 and the same marker positions in map space, so the PS1 spot table
   places the markers; or an own calibration table, `assets/map/markers.txt`,
   authored with the art). Proposed layout:
   - `assets/map/world_map.png` (the picture), `assets/map/LICENSE` (a
     permissive licence such as CC-BY 4.0 or CC0) and
     `assets/map/PROVENANCE.md`: artist, date, licence, and an explicit
     statement that **no extracted game image was used as an input in any
     step: no tracing over, no img2img, no upscaling of the original map or
     of any game art**.
   - Format: **PNG** (lossless, decoded to RGBA at open; the same transient as
     a user pack). Size target: 1568 x 1280 (4x), with a budget of **about 4 MB
     in git** (an optimised PNG of an illustration). If a texture-compressed
     format is wanted later (ETC2/ASTC on the Switch GLES), a tool can
     pre-convert it, but PNG stays the source of truth. The build packs it into
     the NRO romfs and the PC data directory, so there is nothing to install.
   - The picture is **not game data**, so it can go in git once the provenance
     file exists. AGENTS.md's rule "Do not vend game assets into git" and
     directive 5 ("Own-disc only") need a short **clarification** (proposed
     wording; applied to AGENTS.md on 2026-10-27, owner approved): *"Original
     artwork created for this port (fan art) may be committed under `assets/`
     if it has a LICENSE and a PROVENANCE.md stating that no extracted or
     derived game asset (no tracing, img2img or upscaling of game images) was
     used. Anything derived from the owner's disc, including upscales, stays out
     of git."*
2. **User-generated local pack, derived from the user's own disc.** Never
   committed and never shipped. A helper script (proposed `tools/map_pack/`)
   would: (a) dump the stitched map as a PNG into the user's own folder (from the
   running port with a hook, or by reading the disc file directly); (b) the user
   runs it through an upscaler of their choice (Real-ESRGAN-type models via
   ncnn-vulkan or PyTorch, or a pixel-art scaler), keeping aspect and
   orientation; (c) the user puts the result in the runtime `texture_packs/`
   folder ([TEXTURE_PACKS.md](TEXTURE_PACKS.md)) as `map/world_map.png`. The
   loader checks size and aspect, ignores a bad file, and falls back. The
   generated pack is the user's own derived data and stays on their SD card or
   disk.

Precedence: **user pack, then fan-art map, then captured-and-scaled map**. A
picture that does not match the PS1 marker geometry needs the calibration table;
the plan treats that as part of the fan-art task.

### 7.3 Where the picture comes from: the disc is readable, VRAM capture is the fallback

**Reading the map from the disc, before the screen opens: feasible, and done.**
The Map is two files per half of the game: the **sprite sheets** (`FILE_STATUS_BG`,
US `0x78A` = `STWMP0CS.BIN`, 3416 bytes; second half `+2` = `STWMP1CS.BIN`) and the
**images** (`+1` = `STWMP0TM.BIN`, 173640 bytes; second half `+3`), whose entry 0
is an archive of TIMs (some RLEN packed). The port reads them with `cdfs_read`
(the runtime tree, no game code involved), does what `TimLoader.loadArchive` does
(TIM `i` at VRAM `(0x280 + 0x40 i, 0)`, CLUT at `(0x140, 0x100)`) into a
**private 1 MiB VRAM**, and composes the frame with the same code as the live
capture. Result:

- **0 differing bytes** between the disc-built map and the live VRAM capture, on
  **US and EU**, on PC and in Ryubing (`DW3_MAP_VERIFY=1` prints
  `verify cache vs vram` / `verify vram vs disc`). The second half (Amaterasu) was
  decoded from the disc too (checked by eye; its VRAM comparison needs a save in
  the late game and is **not done**).
- It needs no game state, so it runs **before the screen exists**: a
  **background precompute** starts after the paths are known (PC: a `nice 19`
  pthread; Switch: a libnx thread on **core 2**, priority `0x3B`, 256 KiB stack;
  `DW3_MAP_PRECOMPUTE=0` turns it off on the PC). It builds both halves, writes
  the cache and **frees everything it allocated** (`precompute done ... RAM freed`).
- **Cache:** `map_<us|eu>_h<half>_s<scaler>.rgba` (header `DW3M`, version, size,
  origin, then RGBA). Switch `sdmc:/switch/dw3/cache/`, PC `<config dir>/cache/`
  (`DW3_CONFIG_DIR`, else the runtime folder). Derived from the user's disc:
  **never committed** (the folder is under the user's data, not the repo). Per
  region: 2 bases (0.5 MB each, scaler 0) + 4 scaled images (4.7 MB each: Lanczos2 and
  FSR 1 for both halves) = about **20 MB**. The sharp prescale is a 4-6 ms copy and
  is not cached.
- **At the open** the screen takes the cached base (8-13 ms) if it exists and falls
  back to the **VRAM capture** (12 ms, writes the cache for next time) when the
  precompute did not run or did not finish. Both give the same picture: the
  replay with and without precompute gives **identical captures** (0 px).

What a **full** precompute still needs (not in the PoC): a version stamp of the
disc in the cache header (today the key is region + half + scaler), an invalidation
when the scalers change (the header version covers a format change only), the
markers' art if the fan-art map is not the source, and **the area-name boxes**: the
names are game text drawn by the text windows, so they cannot be precomputed from the
two files without the string loader and the glyph renderer of the game
(`TEXT_ASUKA_MAP` / `TEXT_AMATERASU_MAP`); recommended stays option (1) of 4.2d,
capture the window when the game draws it.

### 7.4 The scalers (the owner's request): how they look and what they cost

All four are on the live screen, cycled with L2 / R2, the name is on screen and
`dw3-map: scaler X built in N ms` (or `loaded from cache in N ms`) goes to the log.
Source 392 x 352, CPU scalers produce **3x = 1176 x 1056**; the GPU draws it
bilinearly at any zoom (a 3x texture at 720p is 1:1 at zoom 1.0).

| Scaler | What it is | PC build time | Ryubing (x86 JIT, **not** console speed) | RAM / SD |
|---|---|---|---|---|
| Nearest | the 392 x 352 texture, GPU nearest | 0 | 0 | 0.5 MB texture |
| Sharp bilinear | **integer 3x nearest prescale on the CPU, then GPU bilinear** (the same result as the shader form, without a shader; it avoids a new SPIR-V shader on the PC and works the same on both hosts) | 4-6 ms | not logged (a copy) | 4.7 MB texture, no SD file |
| Lanczos2 | `title_logo_resample.c` (the title logo's resampler), 3x, once | **0.72 s** alone, 1.2-1.6 s under load | **5.2-5.6 s** | 4.7 MB texture, 4.7 MB SD |
| AMD FSR 1 | **EASU + RCAS on the CPU** (a C port of AMD's `ffx_fsr1.h`, MIT header kept in `map_view_core.c`), 3x, once; RCAS sharpness 0.2 stops | **0.36 s** alone, 0.8-1.0 s under load | **3.5-3.7 s** | 4.7 MB texture, 4.7 MB SD |
| Anime4K-style | **not done** (optional; the survey's argument stands: painted dithered art) | | | |

Why the FSR is on the CPU and not a shader: the PoC runs the same code on both
hosts and the screen is static, so a once-per-open CPU build cached on the SD costs
nothing per frame. A GPU FSR (EASU + RCAS in GLES on the Switch, SDL3 GPU on the PC)
would not need the 3x copy or the SD files and is the "real" form if the owner
picks FSR; it is a shader per host (a SPIR-V one needs `glslang`, absent here).
The same goes for a true sharp-bilinear fragment shader. **Timings on the console
were not taken**: the Ryubing numbers say the order (Lanczos2 slower than FSR, both
seconds, not milliseconds); the real A57 at the console's fixed clock (no
overclocking, AGENTS.md) is the OLED item. This is why the background precompute
exists: with a cache the first open of a scaler costs 6 ms of file read.

Look (comparison crop in `tmp/evidence/p632/scaler-compare.png`, git-ignored):
nearest shows the PS1 pixels and shimmers when panning at 1.25x; sharp bilinear keeps
the pixels crisp at 1.0 and 2.0 and cleans the 1.25 / 1.5 steps; Lanczos2 is the
softest and removes the blocky dither; FSR 1 sits between (sharper edges than
Lanczos2, slight edge enhancement). The decision is the owner's, after the OLED.

Build: the nxlink or release NRO of this PR (US or EU), widescreen ON (the

that has left the first town (the Map shows visited areas).

2. **Close it.** **X (Triangle)** or **Y** returns to the game's Map screen exactly
   as it was; X again leaves the Map as always. Check the old screen still works

3. **Cursor and zoom** (section 10: the D-pad pan became the cursor). D-pad or left stick moves the cursor, the view follows it; the **right stick** zooms smoothly
   (up in, down out, FIT to 3.0, any value between); **L / R** step the zoom (fit,

## 9. The reveal layer and the right-stick zoom (fix after preview.43)

Owner report (OLED, preview.43): the new screen showed the background and the
markers but **not the map the game reveals** (the lit land). Root cause: the
captured picture is **frame 0 of the map sheet only**, which is the dark,
fogged map. The game draws the lit pieces as **separate sprite cells** in
`STSTATUS_drawMapScreen` (`map_screen.c`), over that frame:

| Layer | Source | Visible when | Texture | Order |
|---|---|---|---|---|
| the dark map | entry 0 of the map file, frame 0 | always | `0x280,0` (+ CLUT `0x140,0x100`) | bottom |
| the lit towns (up to 22 cells, 24 to 104 px) | entry 1, frame `towns[i] - 1`, at `STSTATUS_towns[towns[i]]` | the list of `STSTATUS_getTowns(gameHalf, progress)` (a story-progress list, not exploration flags): 6, 11, 17 or 21 towns | `0x380,0x100` | over the map |
| the visited area icons (24 x 24, two cells) | entry 2, frame `STSTATUS_spots[i].sprite`, at `STSTATUS_spots[i]` | `visited[i - 1]`, from the map-area flags `0x2000 | map low byte` of the half | `0x300,0x100` | over the towns |
| the cursor and home mark | entry 2 | live | | top (left to the HUD ring) |

Both halves use the same layout (US files `0x78A` / `0x78B` and `0x78C` /
`0x78D`; EU `0x799`...). All cells have `abr = -1` (opaque) and VRAM colour 0 is
transparent. Patch `0146` now sends the list (kind, frame, x, y) to the port
with the sheets of entries 1 and 2; `port/map_view/map_view.c` draws the cells
from the live VRAM into the image with `dw3_mv_blit_frame` (same palette and
pixels as the game, then the scalers run on the whole picture), and the HUD
crosses are no longer used (the area icons are in the picture).

**Cache.** `map_<region>_h<half>_s0.rgba` stays the bare map (disc-built or
captured before the layer is added), so it never goes stale. The reveal layer
is composed per open (about 1 ms at 392 x 352). A scaled file (`_s2`, `_s3`)
now carries the **hash of the piece list** in its header (cache version 3) and
is used only for the same hash; otherwise it is rebuilt and overwritten
(`cache stale` / `cache miss` in the log). The precompute builds the bare map
(hash 0): the first Lanczos2 / FSR 1 of a save with revealed pieces is built on
the spot once per change of the list. Sharp bilinear and nearest are never
cached, so they always show the current layer.

**Right-stick zoom.** Up zooms in, down zooms out, smoothly (full tilt is 1.5
octaves per second: 1.0 to 3.0 in about a second), between FIT and 3.0, with
non-integer values and no snapping; L1 / R1 still step (from a smooth zoom to
the next table step). The Switch fills the right-stick bytes of the pad frame
(`nx_input.c`; the game reads only the left stick), the PC reads them from the
pad buffer; `dw3_map_view_set_zoom_stick`. Replays use two bits above the pad
mask (`0x10000` up, `0x20000` down).

**Logs (rule 12).** `dw3-map: reveal layer: N pieces from the game (T towns + A
visited areas drawn), D drawn, hash H`, `scaler X ... reveal hash H` (build, hit
or stale), `zoom source=stick|button ...`, `close after N frames (zoom: S stick
frames, B button presses, last source ...; reveal hash H)`.

Replay: `us-map-view` / `eu-map-view` expect the reveal line with at least one
piece drawn, the hash on the scaled images and both zoom sources; new
checkpoints `mv-stick-in` and `mv-stick-out`. Not verified on the OLED: the
stick feel and dead zone, the first Lanczos2 / FSR 1 time with revealed pieces
on the console, the EU Map (checked on the PC replay only).

## 10. The balloon, the cursor and the name box (owner, after preview.45)

Owner report (OLED, preview.45 EU, best scaler Nearest): the full-screen map is
missing three things the game's own Map screen has: the **balloon** (the
partner's face bubble over the current area), the **cursor** (the selection
marker the player moves between locations) and the **name box** of the selected
location ("Bulk Swamp / Bulk Bridge"). All three are now in the view, drawn
from what the game itself uses; nothing is redrawn by hand.

| Element | Where it comes from | How it is drawn |
|---|---|---|
| the balloon | marks sheet (entry 2 of the map file), frames `0x35 + homeFrame` (0..2, animated by the game), on the EU version `0x3B + homeFrame` when the cursor is not left of the home mark (the game turns the balloon to face the cursor) | composed once per open from the live VRAM into small RGBA images (`bank_build`, the same cell blit as the reveal layer, texture `0x300,0x100`, CLUT `0x140,0x100`, VRAM colour 0 transparent), drawn as a quad in **map space**: it scales and pans with the map at any zoom |
| the cursor | the same sheet: `0x32 + cursorFrames[cursorFrame]` free (the arrow), `0x38 + ...` when it is on a location (the hexagon, drawn on the spot) | same, drawn over the map and under the balloon (the game's depths) |
| the name box | **the game's own**: the frame sprite `FILE_STATUS_SPRITES` `0x3B` and the text window of `STSTATUS_showMapArea`, with the game's text, font, sound and (translated) strings | the patch keeps the game's cursor on the view's cursor (below), so the game draws the box into its own picture as it always does; the host leaves that rectangle of the picture to the game's pixels (up to four strips around it, scissor) and draws everything else over it. It is screen-space HUD like the game's: the same logical position (`y 0x14` or `0xB4`), 16:9-aware (`(x + gutter) / (320 + 2 * gutter)`), at the bottom while the cursor is in the top half of the picture |

**The cursor moves as in the game.** While the view is open the D-pad **and the
left stick** (the game's pad bits) move the cursor, at the game's speeds (2 px
a frame at the first press, then 3 and 4 while held), over the **whole map**
(the game's own cursor cannot reach some corners; the sprite is kept on the
map). It starts on the current area, like the game's. The **view follows the
cursor** (it only moves when the cursor gets into the outer 30% of the picture,
and never past the map's edge), so zoomed in you steer the cursor and the map
comes with it; there is no separate pan any more (the old D-pad pan is
gone: the cursor replaces it). The **right stick still zooms**, **L1 / R1** step
the zoom, **L2 / R2** the scaler, **Circle** hides the text **and the name box**,
**Triangle or Square** close. The cursor on a visited location is the game's own
hit test (`spot + 6 < x <= spot + 0x12`, the same for y), so the same name
comes up as on the game's Map.

How the game's name box follows the view's cursor (patch `0146`, `mapViewFrame`):
every frame the host returns the cursor's map position and where it is on the
320 x 240 menu picture; the patch sets `cursorX/Y` to the latter and the scroll
to `screen - map`, so `STSTATUS_showMapArea` (which uses `cursor - scroll`) finds
the same location the host did, plays the confirm sound, places and fills the
name window; `hoverY` is the cursor's screen row, so the box goes to the other
half of the picture. The game's own cursor and scroll are saved when the view
opens and put back when it closes.

**Logs (rule 12), each once per event.** `dw3-map: sprite bank: N of 12 frames
built (...)` (US builds 9: no turned balloon), `dw3-map: cursor on location
id=I (name id=I, spot at X,Y) cursor X,Y`, `dw3-map: cursor left location id=I,
free at X,Y`, `dw3-map: cursor at rest at X,Y, location id=I name id=I (view
centre X,Y)` (when a move ends; `id=0` is no location), `dw3-map: balloon at
sprite X,Y (image X,Y) on location id=I, frame 0x35|0x3b (plain|turned)`,
`dw3-map: name box shown for location id=I (name id=I) at the top|bottom of the
picture, logical x A..B y C..D`, `dw3-map: name box hidden (cursor on no
location | HUD off)`, `dw3-map: HUD on|off`. The location id is the spot index
(1..46) and also the string id passed to the game's name window.

### 10.1 Nearest is the default scaler

The owner chose **Nearest**. A fresh start (and the first open of a session)
now opens on Nearest; the scaler the player leaves it on is kept for the next
open of the session. Order of the L2 / R2 cycle: nearest, sharp bilinear,
Lanczos2, AMD FSR 1.

### 10.2 The CPU scalers no longer block input

Measured on the Switch (preview.45 log): Lanczos2 **6.4 s**, FSR 1 **2.1 s**
with the cache missing. They ran on the game thread, so the game (and the
buttons) stood still for that time: **not async before this change**. Now the
build (or the cache read) runs as a job on a worker thread: low priority on
the PC, core 2 on the Switch (`dw3_map_view_async_start`, two slots). The
screen keeps taking input; the old picture stays until the new one is ready
(the HUD says `SCALER 3/4: LANCZOS2  BUILDING, NEAREST STAYS`), a second request
while one builds is queued (the last one wins), a Nearest or Sharp request
cancels it, and closing the screen abandons it (the worker frees its own copy
of the map). The build, the cache hit and the cache write are logged as before
plus `scaler X requested (worker thread, input stays live)`. Both scalers are
kept; the cache files and the precompute are unchanged. `DW3_MAP_SYNC=1` forces
the old synchronous path (the replays use it: the frame at which the picture
changes must be fixed to compare screenshots).
