# P6.11 Internal resolution scaling: feasibility and design

Status: **step 1 (feasibility and design), 2026-10-31. No game behaviour change.** Step 2 (the
build) is queued after D1 to D5 ([OPTIONS_REORG](OPTIONS_REORG.md)). Owner request 2026-10-15
(the goal), 2026-10-31 (the turbo idea and the Options rule). Roadmap entry:
[ROADMAP P6.11](ROADMAP.md). Related: [P5.2 battle on the GPU](P5.2_BATTLE_GPU.md),
[P6.10 field on the GPU](ROADMAP.md), [P6.22 CPU time](P6.22_FIELD_CPU.md),
[P6.1 widescreen](P6.1_WIDESCREEN.md), [P6.4 turbo](P6.4_FAST_FORWARD.md),
[PC README](../platforms/pc/README.md).

## Verdict

| Question | Answer |
|---|---|
| Feasible on the Switch at **2x**? | **Yes**, for the 3D battle (the only 3D layer the Switch draws on the GPU today). Estimated GPU cost 1-3 ms handheld and under 1.5 ms docked per 16.7 ms frame; memory 3 MiB. Estimate, not measured: the OLED has no GPU-time number yet. |
| At **3x**? | **Yes on paper, tight handheld.** Estimated 2-6 ms handheld worst case, 1-2.5 ms docked; memory 7 MiB with the display-sized targets proposed here (36 MiB with the PC layout, not recommended). A handheld cap at 2x stays available as a per-platform limit if the OLED run disagrees. |
| Field, menus, movies, title? | **Nothing to scale.** The Switch draws them with the CPU rasterizer at 1x, and the field is 2D sprites and tiles: a 2D sprite at 3x is the same picture with bigger blocks. Scaling them on the CPU is out (the field is CPU-bound; 3x is 9x the pixels). |
| What the player gets | Smoother 3D edges and less shimmer in **battle**, and a battle picture that is 1:1 with the panel handheld (3x of the 426x240 widescreen picture is 1278x720). The vertices stay integer PS1 coordinates, so the polygon wobble stays. |
| Docked only? | **No.** Allow 1x/2x/3x in both modes. The GPU is about 2.5x faster docked, but the TV is where the 4.5x output stretch shows the most, so both modes benefit. Keep "handheld max 2x" ready as a one-line limit. |
| Turbo idea ("Native res while turbo") | **Justified by the logs, not only by taste.** The battle mesh flushes every game frame in turbo (the P6.22 deferral does not cover battle), so at 4x the GPU would do 4x the fill at Nx. Drop to 1x while turbo is on, with both targets allocated up front. |
| Recommended build | Six phases, about 12 to 16 worker days, [below](#7-phased-build-plan). Start with an OLED measurement build (phase 0, half a day) so the caps come from numbers. |

What this changes in the roadmap text: the done-when of P6.11 says "the GTE/3D path renders above
native on PC and Switch ... and the 2D/UI layers and widescreen patches still match soft
rendering". On the Switch the 2D/UI layers match soft by construction (they are soft). The
"3D path" is the battle mesh. If P6.10 later moves the field to the GPU, its 2D quads need no
scaling. See [the owner questions](#9-owner-questions).

## 1. What exists: the PC experiment

`DW3_PC_INTERNAL_RES=3` ([PC README](../platforms/pc/README.md)) calls
`Psyz_VideoSetInternalResolution(3)` in `platforms/pc/src/main.c` (it accepts only 3 today, and
prints `dw3-pc: experimental internal resolution 3x (960x720 for 320x240 content)`). The scaling
is in PSY-Z's `sdl3_gpu.c` (`vendor/psyz/psyz/src/platform/sdl3_gpu.c`); `sdl3_gl.c` has the same
design. The Switch does not use either file ([SWITCH_BACKEND](SWITCH_BACKEND.md)).

How it scales:

| Part | What PSY-Z does | Where |
|---|---|---|
| Vertices | **Not scaled in the data.** `Vertex` holds `short x, y` (`sdl3_draw.h`): integer PS1 screen coordinates, as the GTE and the game produced them. The scale is the **viewport** (`VRAM_W * n` by `VRAM_H * n`) and the scissor (`* n`). No GTE sub-pixel precision exists in this path; the rasterizer just samples the same integer triangles on a finer grid. | `DrawBatch` (about line 1921) |
| Render target | A second texture, `scaled_vram_render`, of `1024*n x 512*n` RGBA8, next to the native `vram_render`. | `CreateScaledVramTarget` |
| VRAM texture reads | Textures and CLUTs are still sampled from the **native** 1024x512 texture with `texelFetch`, so texels stay PS1 texels. | `psx.frag.glsl` |
| Coherence | After each batch the drawing area is nearest-downsampled back into the native VRAM (`SyncScaledVramToNative`), so anything that reads VRAM (the next frame's textures, `StoreImage`, the replay capture) sees a 1x picture. Writes by `LoadImage`, `ClearImage` and `MoveImage` are mirrored up with a nearest blit (`SyncNativeVramToScaled`). | lines 625 to 670 |
| Present | The display rectangle is blitted from the scaled target to the swapchain. | `PlatformBackend_Present` |
| Change at run time | `ApplyPendingInternalRes` at the next present: it **releases and creates** the scaled texture and re-blits all of VRAM. That is a one-time allocation hitch, which is why the turbo idea asks for both targets to exist up front. | line 722 |
| Limits | `PSYZ_INTERNAL_RES_MAX` 8, and `n` is lowered until `1024*n <= 16384`. | video.h, `AdjustInternalRes` |

What each layer does at 3x on the PC (the PC draws everything through this path):

| Layer | Result | Why |
|---|---|---|
| 3D polygons | Crisper edges, less crawl. Vertex wobble stays. | Same integer vertices on a finer grid. |
| 2D sprites, tiles, UI quads | Identical picture, N x N blocks. | The fragment shader fetches `floor(uv)` texels, so each texel becomes an N x N block. Axis-aligned quads at integer coordinates land on exact multiples of N: no half-pixel seams. |
| Slanted textured quads used as windows | Edge pattern differs from the PS1 rasterizer, by less than 1 PS1 pixel. | Same as the existing 1x GPU path; the difference shrinks with N. To be proven by the 2x replay family ([section 5](#5-replay-plan)). |
| Widescreen gutters (P6.1) | Work. The gutter texture is also `n` times larger (`GetGutterTarget`, `gutter_render_res`), and [P6.1_WIDESCREEN](P6.1_WIDESCREEN.md) records that it works with `DW3_PC_INTERNAL_RES`. | `sdl3_gpu.c` line 551 |
| Dithering | **Changes.** The shader indexes the 4x4 matrix with `gl_FragCoord & 3`, which is a fragment coordinate, so at N the pattern is N times finer than the PS1 one (smoother gradients, not the PS1 grid). Fix, if wanted: use `floor(gl_FragCoord / n) & 3`, so each PS1 pixel keeps its own value. Recommended: keep the finer one for the first cut (it is the natural look), and decide by eye on the OLED. | `psx.frag.glsl` line 42 |
| Movies | Unscaled. The 24-bit region goes through `rgb24_source` with `n = 1`. On the Switch the movie is converted to RGB555 and shown by the soft path. | `PlatformBackend_Present` |
| Native title and Options overlays, the full-screen map | Unrelated to the setting. They are host overlays drawn after the picture at output resolution (960x720 canvases on both hosts, [MENU_COMPOSITION_PLAN](MENU_COMPOSITION_PLAN.md); `nx_map_view.c`). The "retained canvas" is therefore independent of N. | `title_menu_overlay.c`, `nx_title_overlay.c` |
| 16-bit present (P6.22 pass 4) | Not involved: it is the path that uploads CPU VRAM as `R16UI`. The scaled target is RGBA8. | `nx_gpu.c` |
| `title_background_capture.c` | Only acts when `DW3_PC_INTERNAL_RES=3` (it reads the env var itself, and `title_menu_overlay.c` does the same for the window size). Both must be moved to the new setting in the build. | lines 119 and 274 |

Memory on the PC: the scaled texture is 8 MiB at 2x and 18 MiB at 3x, and the gutter texture is
the same size again (16 and 36 MiB). The PC test run below shows the resident set growing
by 18 and 33 MB.

## 2. What the Switch draws today

The Switch backend is native libnx ([SWITCH_BACKEND](SWITCH_BACKEND.md)), not the SDL3 GPU path:

| Layer | Drawn by | Resolution | Source |
|---|---|---|---|
| Field, menus, dialogue, HUD, title picture, movies (as RGB555) | PSY-Z CPU rasterizer into a 1024x512 RGB555 VRAM in RAM (`switch_gpu.c`), presented with an `R16UI` upload and a shader (P6.22 pass 4) | 1x, then stretched to 1280x720 (handheld) or 1920x1080 (docked) | `nx_gpu.c` `resolution_for_mode` |
| Battle 3D (`gpu-tex`, the default since preview.22) | GLES3 mesh FBO, 1024x512 RGBA8, plus a second one for the P6.1 gutters (`nx_mesh.c`); no depth buffer (painter's order from the OT) | 1x | `s_mesh_fbo`, `s_gutter_fbo` |
| Battle partner view, drawing areas smaller than the screen | Kept on the CPU rasterizer (`mesh_area_is_screen`) | 1x | P5.2 |
| Composite | The mesh is blitted to the output, then the CPU VRAM is drawn over it with a shader that drops black (`UI_FS`) | output | `dw3_nx_mesh_present` |
| Title menu and logo, Options, full-screen map | Native GL overlays | output | `nx_title_overlay.c`, `nx_map_view.c` |

Three consequences:

1. **The only thing a Switch internal resolution can scale is the battle mesh.** That is also the
   only 3D geometry on screen. The P6.22 profile of the field shows sprites, tiles and a few
   textured triangles for windows; none of it gains from a finer grid.
2. **The cost is in the mesh path only**, so the field, menus and turbo outside battle keep their
   present speed.
3. **Today's widescreen battle draws every batch twice** (`draw_batches` into the mesh FBO and
   again into the gutter FBO, `flush_locked`), and then blits the mesh FBO's display part over
   the gutter FBO's (`dw3_nx_mesh_present`). At Nx the second pass would double an Nx cost for
   nothing in the middle; it only needs the two side strips (see phase 2).

The output is stretched by the GPU: handheld 1280x720, docked 1920x1080. The 4:3 picture is
960x720 handheld (exactly 3x) and 1440x1080 docked (4.5x). The 16:9 widescreen picture
(53-pixel gutters, 426x240) is 3.005x handheld and 4.5x docked. So **3x is output-native handheld**
and 2x is a 1.5x stretch; docked, neither is an integer.

## 3. Numbers

### 3.1 PC measurement (2026-10-31)

Method: `build/pc/dw3-pc` (US, `a9c34c0`, only `main.c` patched locally to let the env var take 2
and 1; the patch is not in this PR), the recorded `us-two-battles.rec` (two forced battles, widescreen
on, the scenario's own env), Xvfb 1920x1080 with Mesa llvmpipe (`vulkan: No DRI3 support detected`:
Vulkan on the real GPU cannot present on Xvfb, so the "GPU" is the CPU), `nice -n 10`, one
`dw3-pc` at a time, `SDL_AUDIODRIVER=dummy`, 5000 frames to the end of the recording. The machine
was shared with other workers (load average 13 to 16), so absolute times move. The replay suite
was not run. Script and raw table: `tmp/evidence/20261031-p611-feasibility/` (git-ignored).

| Scale | Wall, 5000 frames (runs) | Per game frame | CPU time (user) | Resident set |
|---|---|---|---|---|
| 1x | 24.3, 24.4 s (33.1 s on the first, cold run) | 4.9 ms | 115 s | 204 MB |
| 2x | 42.7, 42.8, 44.2 s | 8.6 ms | 326 s | 222 MB |
| 3x | 67.5, 67.7, 68.7 s | 13.5 ms | 667 s | 237 MB |

Reading: the cost is **linear in pixels** (about +1.1 to 1.2 ms of wall per extra 1x of pixels,
about 14 ms of CPU, at both 2x and 3x), so the fill-rate is the cost and there is no big fixed
price per scale change. The absolute numbers say nothing about the Switch GPU: llvmpipe is a CPU
rasterizer. They support the shape of the estimate in 3.3, not its size. Turbo 4 or none made no
difference in the replay (it runs uncapped).

### 3.2 What the OLED logs already say

No log has a GPU time. What exists (handheld, 1280x720):

| Fact | Source |
|---|---|
| The battle mesh draws about 1300 triangles per game frame (69k to 80k per 60 frames) and costs the CPU about 0.25 to 0.45 ms per frame to submit (`flush_us` 14k to 26k per 60 frames). It runs at 60 fps (`frames_mesh=60`). | `tmp/evidence/2026-10-22-preview30-rc6-oled/dw3-234757.log`, `mesh dbg:` |
| At turbo 4x the same 60-frame window flushes the **same 79k triangles** with only 15 frames shown (`frames_mesh=15`): every game frame is drawn, not only the shown ones. The P6.22 pass-2 deferral covers the CPU rasterizer and says "Battle keeps the immediate path". So the GPU fill at 4x is 4x per second. | same log; `switch_gpu.c` line 767 |
| Battle at turbo ran about 180 to 190 game fps on the OLED (preview.25), against 70 to 80 in the field. | [P6.22](P6.22_FIELD_CPU.md), ROADMAP P6.10 |
| `present_us` is 5.6 to 12.5 ms per present while `swap_us` is only 0.5 to 0.6 ms, at 1x and at 4x, so the draw calls block (waiting for a free buffer) before the swap and `present_us` cannot be read as GPU cost. (Field scenes, preview.57, handheld.) | `tmp/evidence/20261031-ftp-console-logs/dw3.log`, `dw3.3.log`, `pace dbg:` |

So the 1x mesh path has headroom at 190 game fps, but **there is no measured GPU time**, and the
vsync hides it at 60 fps. Phase 0 fixes that with a turbo test (below): with "Native res while
turbo" off, the game fps at 4x in battle is the GPU's throughput at that scale.

### 3.3 Switch estimate

Inputs: the display-sized picture is 426x240 = 102 240 px at 16:9 (76 800 at 4:3). Overdraw in
battle is not measured; assume 2 to 4x (sky and floor planes plus models). The shader does two
dependent `texelFetch` (index word, then CLUT) for 4/8-bit textures, one for 16-bit, modulation
and dither. The Tegra X1 (Maxwell, 16 ROPs and 16 texture units) at the clocks the console sets
(published figures, not checked on this unit: handheld 307 to 460 MHz, docked 768 MHz; this port never changes them, rule 7) peaks at
about 4.9 Gtexel/s handheld and 12 Gtexel/s docked. At two fetches per fragment and a realistic
25 to 40 % efficiency (small triangles, blending, a driver-compiled integer shader), assume 0.6 to
1.0 Gfrag/s handheld and 1.5 to 2.4 Gfrag/s docked.

| Scale | Target (display-sized, with gutters) | Fragments per frame | GPU per frame handheld | GPU per frame docked | Bandwidth at 60 fps (about 16 B/frag) |
|---|---|---|---|---|---|
| 1x (today) | 426x240 | 0.2 to 0.4 M | 0.2 to 0.7 ms | 0.1 to 0.3 ms | under 0.4 GB/s |
| 2x | 852x480 | 0.8 to 1.6 M | 0.8 to 2.7 ms | 0.3 to 1.1 ms | 0.8 to 1.5 GB/s |
| 3x | 1278x720 | 1.8 to 3.7 M | 1.8 to 6.2 ms | 0.8 to 2.5 ms | 1.7 to 3.5 GB/s |

The shared memory bandwidth is about 21 to 25 GB/s, so 3x is 7 to 17 % of it at worst. Against
the 16.7 ms frame, 3x handheld uses 11 to 37 %; if the real efficiency is half of the low
assumption, it is still under one frame. The GPU works in parallel with the CPU thread, so the
budget is the GPU's alone. **This is an estimate with a factor of 2 of uncertainty in both
directions.** Battery and heat rise with the GPU load in handheld; that is for the owner to feel
(OLED row R7).

With the PC layout instead (a `1024*n x 512*n` target and an equally large gutter target, plus the
downsample blit to native after every batch) the same pixels cost more: 16 MiB at 2x and 36 MiB at
3x of render targets, plus a blit of up to `(320x240)*n*n` pixels per flush (0.7 M pixels at 3x).
That is the reason for the display-sized design below.

### 3.4 Memory

| Layout | 1x (today) | 2x | 3x |
|---|---|---|---|
| Mesh FBO + gutter FBO, VRAM-sized (the PC layout) | 2 + 2 MiB | 8 + 8 MiB | 18 + 18 MiB |
| **Proposed**: two display-sized wide targets (with the 53 px gutters) | n/a (the 1x pair below) | 1.6 + 1.6 MiB | 3.5 + 3.5 MiB |
| **Both** the 1x pair (VRAM-sized, as today) and the Nx pair, pre-allocated for the turbo switch | 4 MiB | 4 + 3.2 = 7.2 MiB | 4 + 7.0 = 11 MiB |

(RGBA8, 4 bytes per pixel; driver padding and tiling add a few percent.) The game's CPU-side VRAM
buffers stay as they are. How much GPU memory a homebrew in
applet mode may use is not documented in this repo; 11 MiB is small enough that the answer is
"fits" unless the console is already near its limit. Phase 0 logs it.

## 4. Design

### 4.1 Approach: which layers scale and which stay native

| Layer | Scales? | How |
|---|---|---|
| Battle 3D (mesh FBO) on the Switch | **Yes** | A display-sized RGBA8 target of `(display_w + 2*gutter) * n` by `display_h * n`. The vertex shader gets `u_scale = n` and the viewport and scissor are multiplied; the vertex data and the OT order are unchanged. There is no depth buffer, so nothing else is needed. |
| Battle 3D on the PC | **Yes** | The existing PSY-Z path (`scaled_vram_render`), with the changes in 4.4. |
| Field, menus, HUD, text, partner view, movies, title picture | **No** (native 1x) | CPU rasterizer on the Switch; on the PC they go through the same GPU path and are N x N blocks, which is visually identical. |
| Title menu, Options, full-screen map | Independent | Native overlays at output resolution. |
| Widescreen gutters | Follow the mesh | The wide target already contains them; the existing side-strip logic is kept at Nx. |

Output stage on the Switch: the mesh target is drawn to the output with **nearest at an integer
ratio and bilinear otherwise** (docked 1.5x for 3x; 2.25x for 2x), then the CPU VRAM layer is
drawn over it as today. The UI layer stays nearest, so text and sprites keep their pixel look
while the 3D behind them is finer. This is the same mix the PC 3x has.

Known look issue, to decide by eye: the **partner view** in the battle HUD (a 3D model in a
100x60 area) stays on the CPU rasterizer at 1x, so it will look coarser than the stage next to
it. Phase 4 can give it its own small Nx target; it is an optional polish.

### 4.2 Options rows (AGENTS.md rule 8)

Both are registry rows in the **Display** group, with `port_options.cfg` keys, label and message
line in the five languages. The next free registry indexes on `main` today are **28 and 29**
(`DW3_PORT_OPT_COUNT = 28` in `port/options/port_options.c`; take the next free ones when the
build starts, because D2 to D5 add rows first). Display holds 4 rows now
(`{0, 15, 22, 21}` in `port_options_groups.h`); two more make 6, which is the list's visible
count, so no scrolling until D5's Map scaler arrives.

| Row | Key | Values | Default | Applies | Notes |
|---|---|---|---|---|---|
| **Internal resolution** | `internal_res` | 0 = 1x (native), 1 = 2x, 2 = 3x | 0 (1x) | at once; the targets are allocated when the value changes, not per frame | Message line, English draft: "Smoother 3D in battle. Higher uses more battery." Per-platform limits: the PC offers 1x to 3x; the Switch offers 1x to 3x in both modes, with a clamp table (`handheld max`, `docked max`) that phase 0 sets from the OLED numbers. A value above the limit is clamped and logged. |
| **Native res while turbo** | `internal_res_turbo` | 0 = off, 1 = on | **1 (on)** | at once | Message line: "Fast-forward draws at 1x, then returns to your resolution." Greyed (and shown as 1x) when Internal resolution is 1x. |

Defaults: 1x keeps the original look (the replays and the OLED baseline do not move). Native res
while turbo defaults to on by the owner's request. Both rows are plain switches in the sense of
the registry: no new widget. The labels must fit the generator's 290 px (row label) and 236 px
(value) limits; "Internal resolution" and "Native res while turbo" are short enough, to be
confirmed by `tools/generate_pc_title_lettering.py` in the build.

Environment test aids (not options, per the rule): `DW3_INTERNAL_RES=1|2|3` forces the value for a
run (replaces `DW3_PC_INTERNAL_RES`, which stays as an alias on the PC for one release),
`DW3_INTERNAL_RES_TURBO=0|1`, and on the Switch `DW3_NX_TEST_ENV` accepts both.

### 4.3 Turbo: native resolution while fast-forward is on

Trigger: `dw3_port_turbo_speed() >= 2` (full fast-forward in the field, battle and results,
`port/options/turbo.c`). The menus' 1.5x turbo does not count; the Switch does not scale menus
anyway.

State machine, run once per game frame in `dw3_port_turbo_poll()` and applied **at the frame
boundary**, before the frame's first draw:

```
turbo off, scale N  --R3 to 2x/3x/4x-->  turbo on:  use 1x   log  dw3-res: turbo on -> 1x
turbo on            --R3 back to 1x-->   turbo off: use Nx   log  dw3-res: turbo off -> Nx
```

- **Both targets are allocated whenever the chosen scale is above 1x**: the 1x pair that exists
  today and the Nx pair of 3.4. The switch only changes which target the flush binds and which the
  present samples, plus one uniform. No allocation, no shader compile, no `glTexImage2D`: no
  hitch. The allocation happens when the Options row changes or at boot, and is logged once:
  `dw3-res: targets 3x 1278x720 x2 allocated in 1.2 ms (handheld)`.
- On the PC the PSY-Z change is to keep `scaled_vram_render` alive while `internal_res` is 1 for
  turbo, and make the change a variable flip plus one `SyncNativeVramToScaled` of the whole VRAM
  when it goes back up (a single blit of 1024x512, well under a millisecond on a GPU). Today
  `ApplyPendingInternalRes` frees and re-creates the texture, which is the hitch to avoid.
- On the Switch the mesh target is repainted by every battle frame, so the stale target needs no
  copy; the one case is a battle held under the Options screen (P9.7), where the held picture is
  in the old target: the switch waits until the next frame that draws, or re-presents the old
  target. Test case in the replay family.
- Logs, once per event, in the AGENTS.md rule 12 style: `dw3-res: set 2x (handheld)`,
  `dw3-res: clamp 3x -> 2x (handheld max)`, `dw3-res: turbo on -> 1x`, `dw3-res: turbo off -> 2x`,
  `dw3-res: targets ...`. The `mesh dbg:` line gains `res=N`.
- Honest note on the benefit: turbo outside battle has no mesh cost at all, so the row only
  matters in battle turbo. That is where the numbers show it matters (3.2).

Alternative that makes the row less necessary (phase 3, optional): **do not flush mesh frames that
turbo will not show**, the way P6.22 pass 2 does for the CPU rasterizer. The mesh draws on the GPU
into a target that is overwritten every frame, so skipping three of four frames looks safe,
but it needs the same care as pass 2 about what reads the target (the encounter transition,
`StoreImage`). If it works, turbo costs the same GPU per second as 1x at any scale, and the row
could default to off. It is a separate decision for the owner.

### 4.4 Other changes the build needs

- **PSY-Z (the `Larbaco/psyz` fork, a submodule bump called out in the commit):** the up-front
  allocation and variable flip above; lower the `AdjustInternalRes` cap to what the row offers;
  optionally the dither coordinate (`floor(gl_FragCoord / n)`); make `Psyz_VideoSetInternalResolution`
  callable before the window exists (it already defers to the next present).
- **PC:** replace the `main.c` env parsing (3 only) and the two `getenv("DW3_PC_INTERNAL_RES")`
  reads (`title_background_capture.c`, `title_menu_overlay.c`) with the port setting; the 1280x720
  3x window sizing becomes "when the setting is 3x and the window was not resized by the user".
- **Switch:** `nx_mesh.c` scale uniform, new targets, gutter pass restricted to the two side strips,
  `dw3_nx_mesh_present` blit filter, `nx_gpu.c` dock/handheld recreate (the EGL context is
  rebuilt on a dock change and drops every GL object, so the targets are recreated with the new
  mode's clamp and logged again), the `mem dbg` line gains the target bytes.
- **`port/`:** the two rows, the cfg keys, the turbo hook (`dw3_port_res_*`), the five-language
  strings. A new `port/options/internal_res.c`, platform-independent; the platforms provide
  `dw3_platform_set_internal_res(n)` and `dw3_platform_max_internal_res()`.

## 5. Replay plan

Replays pin **1x**. The runner already removes `DW3_PC_INTERNAL_RES` from the environment of
every scenario (`tools/replay/replay_tests.py`, the `env.pop` list); the build adds
`DW3_INTERNAL_RES` and `DW3_INTERNAL_RES_TURBO` to that list and every replay runs with an isolated
`DW3_CONFIG_DIR`, so the new keys sit at their defaults (1x). The acceptance for the whole
feature on the existing 315 scenarios is therefore "no reference changes", which the normal
`--changed` run proves for `port/` and `platforms/`; a PSY-Z change that touches the 1x path runs
the area sweep as rule 13 says.

A **2x scenario family**, new and small (about 12 recordings on EU, plus a US canary of 3):

| Scenario | What it proves |
|---|---|
| `*-res2x-title` | the title and the native overlays do not depend on the setting |
| `*-res2x-field-walk` | the field (2D) is the same picture at 2x, gutters included |
| `*-res2x-two-battles` | 3D at 2x; the widescreen gutters in battle; the report keeps the gutter |
| `*-res2x-battle-held` | the Options screen over a battle (P9.7), the held picture, a change of the row while held |
| `*-res2x-map` | the full-screen map (output resolution) over a 2x game |
| `*-res2x-movie` | a movie frame is unscaled |
| `*-res2x-turbo` | `turbo on -> 1x` and `turbo off -> 2x` in the log; the capture after turbo off equals the steady 2x capture (no stale target) |
| `*-res2x-row` | the Options rows: values, persistence, the clamp, the greyed turbo row |

The 2x references use the **window grab** (`DW3_REPLAY_XSHOT`) because the PS1-display capture
(`Draw_StoreImage`) is the nearest downsample of the scaled picture and would hide the thing
being tested; they live in their own refs folder (`refs/res2x/`). GPU rasterization of slanted
edges can differ by one sub-pixel across drivers, so the 2x family uses the runner's
per-channel tolerance (`replay_tests.py` line 51) with a small pixel-count budget, and is
tied to the lavapipe/Xvfb environment the other references already use. A Mesa unit test (like
`tools/present16_gpu_test.c`) renders axis-aligned quads at 1x, 2x and 3x and checks that each is
the 1x picture with N x N blocks: that is the claim "2D is identical", proven without a
recording. Not run in this step.

## 8. Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| Handheld 3x misses 60 fps in busy battles (no GPU number exists) | medium | phase 0 measures it; the per-mode clamp table; row text warns about battery |
| Nouveau and the dock change: GL objects lost, the new targets fail, or the driver rejects a size | low-medium | targets are recreated on the dock path already used for the mesh and the title overlay; on failure fall back to 1x with `dw3-res: targets failed, 1x` (as the gutter FBO does) |
| The partner view and the HUD look coarse next to a fine stage | certain (by design) | accepted in phases 1 to 3; phase 4 optional |
| The 3D layer is 3x sharp and the 2D sprites stay chunky: some will dislike the mix | medium | it is what the PC 3x does and the owner already saw it; default stays 1x |
| Stale or black frame at the turbo switch or while held under Options | medium | switch at the frame boundary; the held-battle replay; the turbo replay compares with the steady capture |
| Replay references on the 2x family drift with the Mesa version | medium | tolerance + pixel budget; family kept small; 1x pinned references are untouched |
| The PSY-Z fork change touches the 1x path | low | the 1x path is a branch on `internal_res <= 1`; the area sweep (rule 13) runs, no reference may change |
| Bilinear on the docked 1.5x blit softens polygon edges the user wanted crisp | low | nearest for integer ratios, bilinear only for non-integer; one constant to flip |
| GTE has no sub-pixel output, so the owner may expect the wobble to go away | medium | the doc and the row's help text say "smoother edges", not "PGXP"; the not-planned item above |
| Memory in applet mode is below the estimate | low | 11 MiB; phase 0 logs it before anything is promised |
| AGENTS.md rule 8: a value above what the machine can do | low | the clamp is logged, the row shows the effective value |

5. **PC.** Offer 1x to 3x on the PC too, or leave the PC at its single experiment value until the
   Switch part is done?
