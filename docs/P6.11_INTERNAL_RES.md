## Verdict

| Question | Answer |
|---|---|
| Feasible on the Switch at **2x**? | **Yes**, for the 3D battle (the only 3D layer the Switch draws on the GPU today). Estimated GPU cost 1-3 ms handheld and under 1.5 ms docked per 16.7 ms frame; memory 3 MiB. Estimate, not measured: the OLED has no GPU-time number yet. |
| At **3x**? | **Yes on paper, tight handheld.** Estimated 2-6 ms handheld worst case, 1-2.5 ms docked; memory 7 MiB with the display-sized targets proposed here (36 MiB with the PC layout, not recommended). A handheld cap at 2x stays available as a per-platform limit if the OLED run disagrees. |
| Field, menus, movies, title? | **Nothing to scale today, and not much to gain later** (investigated in [section 10](#10-field-menus-and-2d-investigation-2026-11-01); the owner asked for it on 2026-11-01). The Switch draws them with the CPU rasterizer at 1x. The field has no 3D model to refine (actors are 2D sprite frames; the only polygons are the dialogue windows and text), so a higher internal resolution would only make bigger blocks. Scaling on the CPU is out (3x is 9x the pixels). Putting the field on the GPU (P6.10) is a different goal (turbo speed, CPU time) that would make a field scale free as a by-product, but it costs weeks and buys no sharper picture by itself. |
| What the player gets | Smoother 3D edges and less shimmer in **battle**, and a battle picture that is 1:1 with the panel handheld (3x of the 426x240 widescreen picture is 1278x720). The vertices stay integer PS1 coordinates, so the polygon wobble stays. |
| Docked only? | **No.** Allow 1x/2x/3x in both modes, with a **per-mode clamp table set from the OLED measurement** (owner, 2026-11-01; [6.2](#62-the-measurement-rows-r0x)). The GPU is about 2.5x faster docked, but the TV is where the 4.5x output stretch shows the most, so both modes benefit. |
| Turbo idea ("Native res while turbo") | **Justified by the logs, not only by taste.** The battle mesh flushes every game frame in turbo (the P6.22 deferral does not cover battle), so at 4x the GPU would do 4x the fill at Nx. Drop to 1x while turbo is on, with both targets allocated up front. |
| Recommended build | Six phases, about 12 to 16 worker days, [below](#7-phased-build-plan). **Phase 0 is built (2026-11-01):** an OLED measurement NRO that logs GPU and CPU frame times at 1x/2x/3x, handheld and docked ([R0.x](#6-oled-test-rows)); the clamp table is filled from its numbers. |

What this changes in the roadmap text: the done-when of P6.11 says "the GTE/3D path renders above
native on PC and Switch ... and the 2D/UI layers and widescreen patches still match soft
rendering". On the Switch the 2D/UI layers match soft by construction (they are soft). The
"3D path" is the battle mesh. If P6.10 later moves the field to the GPU, its 2D quads need no
scaling. See [the owner answers](#9-owner-answers-and-open-questions) and [section 10](#10-field-menus-and-2d-investigation-2026-11-01).

## 1. What exists: the PC experiment

`DW3_PC_INTERNAL_RES=3` ([PC README](../platforms/pc/README.md)) calls
`Psyz_VideoSetInternalResolution(3)` in `platforms/pc/src/main.c` (it accepts only 3 today, and
prints `dw3-pc: experimental internal resolution 3x (960x720 for 320x240 content)`). The scaling
is in PSY-Z's `sdl3_gpu.c` (`vendor/psyz/psyz/src/platform/sdl3_gpu.c`); `sdl3_gl.c` has the same
design. The Switch does not use either file ([SWITCH_BACKEND](SWITCH_BACKEND.md)).

How it scales:

| Part | What PSY-Z does | Where |
|---|---|---|
| Vertices | **Not scaled in the data.** `Vertex` holds `short x, y` (`sdl3_draw.h`): integer PS1 screen coordinates, as the GTE and the game produced them. The scale is the **viewport** (`VRAM_W * n` by `VRAM_H * n`) and the scissor (`* n`). No GTE sub-pixel precision exists in this path; the rasterizer just samples the same integer triangles on a finer grid. | `DrawBatch` (about line 1921) |
| Render target | A second texture, `scaled_vram_render`, of `1024*n x 512*n` RGBA8, next to the native `vram_render`. | `CreateScaledVramTarget` |
| VRAM texture reads | Textures and CLUTs are still sampled from the **native** 1024x512 texture with `texelFetch`, so texels stay PS1 texels. | `psx.frag.glsl` |
| Coherence | After each batch the drawing area is nearest-downsampled back into the native VRAM (`SyncScaledVramToNative`), so anything that reads VRAM (the next frame's textures, `StoreImage`, the replay capture) sees a 1x picture. Writes by `LoadImage`, `ClearImage` and `MoveImage` are mirrored up with a nearest blit (`SyncNativeVramToScaled`). | lines 625 to 670 |
| Present | The display rectangle is blitted from the scaled target to the swapchain. | `PlatformBackend_Present` |
| Change at run time | `ApplyPendingInternalRes` at the next present: it **releases and creates** the scaled texture and re-blits all of VRAM. That is a one-time allocation hitch, which is why the turbo idea asks for both targets to exist up front. | line 722 |
| Limits | `PSYZ_INTERNAL_RES_MAX` 8, and `n` is lowered until `1024*n <= 16384`. | video.h, `AdjustInternalRes` |

What each layer does at 3x on the PC (the PC draws everything through this path):

| Layer | Result | Why |
|---|---|---|
| 3D polygons | Crisper edges, less crawl. Vertex wobble stays. | Same integer vertices on a finer grid. |
| 2D sprites, tiles, UI quads | Identical picture, N x N blocks. | The fragment shader fetches `floor(uv)` texels, so each texel becomes an N x N block. Axis-aligned quads at integer coordinates land on exact multiples of N: no half-pixel seams. |
| Slanted textured quads used as windows | Edge pattern differs from the PS1 rasterizer, by less than 1 PS1 pixel. | Same as the existing 1x GPU path; the difference shrinks with N. To be proven by the 2x replay family ([section 5](#5-replay-plan)). |
| Widescreen gutters (P6.1) | Work. The gutter texture is also `n` times larger (`GetGutterTarget`, `gutter_render_res`), and [P6.1_WIDESCREEN](P6.1_WIDESCREEN.md) records that it works with `DW3_PC_INTERNAL_RES`. | `sdl3_gpu.c` line 551 |
| Dithering | **Changes.** The shader indexes the 4x4 matrix with `gl_FragCoord & 3`, which is a fragment coordinate, so at N the pattern is N times finer than the PS1 one (smoother gradients, not the PS1 grid). Fix, if wanted: use `floor(gl_FragCoord / n) & 3`, so each PS1 pixel keeps its own value. Recommended: keep the finer one for the first cut (it is the natural look), and decide by eye on the OLED. | `psx.frag.glsl` line 42 |
| Movies | Unscaled. The 24-bit region goes through `rgb24_source` with `n = 1`. On the Switch the movie is converted to RGB555 and shown by the soft path. | `PlatformBackend_Present` |
| Native title and Options overlays, the full-screen map | Unrelated to the setting. They are host overlays drawn after the picture at output resolution (960x720 canvases on both hosts, [MENU_COMPOSITION_PLAN](MENU_COMPOSITION_PLAN.md); `nx_map_view.c`). The "retained canvas" is therefore independent of N. | `title_menu_overlay.c`, `nx_title_overlay.c` |
| 16-bit present (P6.22 pass 4) | Not involved: it is the path that uploads CPU VRAM as `R16UI`. The scaled target is RGBA8. | `nx_gpu.c` |
| `title_background_capture.c` | Only acts when `DW3_PC_INTERNAL_RES=3` (it reads the env var itself, and `title_menu_overlay.c` does the same for the window size). Both must be moved to the new setting in the build. | lines 119 and 274 |

Memory on the PC: the scaled texture is 8 MiB at 2x and 18 MiB at 3x, and the gutter texture is
the same size again (16 and 36 MiB). The PC test run below shows the resident set growing
by 18 and 33 MB.

## 2. What the Switch draws today

The Switch backend is native libnx ([SWITCH_BACKEND](SWITCH_BACKEND.md)), not the SDL3 GPU path:

| Layer | Drawn by | Resolution | Source |
|---|---|---|---|
| Field, menus, dialogue, HUD, title picture, movies (as RGB555) | PSY-Z CPU rasterizer into a 1024x512 RGB555 VRAM in RAM (`switch_gpu.c`), presented with an `R16UI` upload and a shader (P6.22 pass 4) | 1x, then stretched to 1280x720 (handheld) or 1920x1080 (docked) | `nx_gpu.c` `resolution_for_mode` |
| Battle 3D (`gpu-tex`, the default since preview.22) | GLES3 mesh FBO, 1024x512 RGBA8, plus a second one for the P6.1 gutters (`nx_mesh.c`); no depth buffer (painter's order from the OT) | 1x | `s_mesh_fbo`, `s_gutter_fbo` |
| Battle partner view, drawing areas smaller than the screen | Kept on the CPU rasterizer (`mesh_area_is_screen`) | 1x | P5.2 |
| Composite | The mesh is blitted to the output, then the CPU VRAM is drawn over it with a shader that drops black (`UI_FS`) | output | `dw3_nx_mesh_present` |
| Title menu and logo, Options, full-screen map | Native GL overlays | output | `nx_title_overlay.c`, `nx_map_view.c` |

Three consequences:

1. **The only thing a Switch internal resolution can scale is the battle mesh.** That is also the
   only 3D geometry on screen. The P6.22 profile of the field shows sprites, tiles and a few
   textured triangles for windows; none of it gains from a finer grid.
2. **The cost is in the mesh path only**, so the field, menus and turbo outside battle keep their
   present speed.
3. **Today's widescreen battle draws every batch twice** (`draw_batches` into the mesh FBO and
   again into the gutter FBO, `flush_locked`), and then blits the mesh FBO's display part over
   the gutter FBO's (`dw3_nx_mesh_present`). At Nx the second pass would double an Nx cost for
   nothing in the middle; it only needs the two side strips (see phase 2).

The output is stretched by the GPU: handheld 1280x720, docked 1920x1080. The 4:3 picture is
960x720 handheld (exactly 3x) and 1440x1080 docked (4.5x). The 16:9 widescreen picture
(53-pixel gutters, 426x240) is 3.005x handheld and 4.5x docked. So **3x is output-native handheld**
and 2x is a 1.5x stretch; docked, neither is an integer.

## 3. Numbers

### 3.1 PC measurement (2026-10-31)

Method: `build/pc/dw3-pc` (US, `a9c34c0`, only `main.c` patched locally to let the env var take 2
and 1; the patch is not in this PR), the recorded `us-two-battles.rec` (two forced battles, widescreen
on, the scenario's own env), Xvfb 1920x1080 with Mesa llvmpipe (`vulkan: No DRI3 support detected`:
Vulkan on the real GPU cannot present on Xvfb, so the "GPU" is the CPU), `nice -n 10`, one
`dw3-pc` at a time, `SDL_AUDIODRIVER=dummy`, 5000 frames to the end of the recording. The machine
was shared with other workers (load average 13 to 16), so absolute times move. The replay suite
was not run. Script and raw table: `tmp/evidence/20261031-p611-feasibility/` (git-ignored).

| Scale | Wall, 5000 frames (runs) | Per game frame | CPU time (user) | Resident set |
|---|---|---|---|---|
| 1x | 24.3, 24.4 s (33.1 s on the first, cold run) | 4.9 ms | 115 s | 204 MB |
| 2x | 42.7, 42.8, 44.2 s | 8.6 ms | 326 s | 222 MB |
| 3x | 67.5, 67.7, 68.7 s | 13.5 ms | 667 s | 237 MB |

Reading: the cost is **linear in pixels** (about +1.1 to 1.2 ms of wall per extra 1x of pixels,
about 14 ms of CPU, at both 2x and 3x), so the fill-rate is the cost and there is no big fixed
price per scale change. The absolute numbers say nothing about the Switch GPU: llvmpipe is a CPU
rasterizer. They support the shape of the estimate in 3.3, not its size. Turbo 4 or none made no
difference in the replay (it runs uncapped).

### 3.2 What the OLED logs already say

No log has a GPU time. What exists (handheld, 1280x720):

| Fact | Source |
|---|---|
| The battle mesh draws about 1300 triangles per game frame (69k to 80k per 60 frames) and costs the CPU about 0.25 to 0.45 ms per frame to submit (`flush_us` 14k to 26k per 60 frames). It runs at 60 fps (`frames_mesh=60`). | `tmp/evidence/2026-10-22-preview30-rc6-oled/dw3-234757.log`, `mesh dbg:` |
| At turbo 4x the same 60-frame window flushes the **same 79k triangles** with only 15 frames shown (`frames_mesh=15`): every game frame is drawn, not only the shown ones. The P6.22 pass-2 deferral covers the CPU rasterizer and says "Battle keeps the immediate path". So the GPU fill at 4x is 4x per second. | same log; `switch_gpu.c` line 767 |
| Battle at turbo ran about 180 to 190 game fps on the OLED (preview.25), against 70 to 80 in the field. | [P6.22](P6.22_FIELD_CPU.md), ROADMAP P6.10 |
| `present_us` is 5.6 to 12.5 ms per present while `swap_us` is only 0.5 to 0.6 ms, at 1x and at 4x, so the draw calls block (waiting for a free buffer) before the swap and `present_us` cannot be read as GPU cost. (Field scenes, preview.57, handheld.) | `tmp/evidence/20261031-ftp-console-logs/dw3.log`, `dw3.3.log`, `pace dbg:` |

So the 1x mesh path has headroom at 190 game fps, but **there is no measured GPU time**, and the
vsync hides it at 60 fps. Phase 0 fixes that with a turbo test (below): with "Native res while
turbo" off, the game fps at 4x in battle is the GPU's throughput at that scale.

### 3.3 Switch estimate

Inputs: the display-sized picture is 426x240 = 102 240 px at 16:9 (76 800 at 4:3). Overdraw in
battle is not measured; assume 2 to 4x (sky and floor planes plus models). The shader does two
dependent `texelFetch` (index word, then CLUT) for 4/8-bit textures, one for 16-bit, modulation
and dither. The Tegra X1 (Maxwell, 16 ROPs and 16 texture units) at the clocks the console sets
(published figures, not checked on this unit: handheld 307 to 460 MHz, docked 768 MHz; this port never changes them, rule 7) peaks at
about 4.9 Gtexel/s handheld and 12 Gtexel/s docked. At two fetches per fragment and a realistic
25 to 40 % efficiency (small triangles, blending, a driver-compiled integer shader), assume 0.6 to
1.0 Gfrag/s handheld and 1.5 to 2.4 Gfrag/s docked.

| Scale | Target (display-sized, with gutters) | Fragments per frame | GPU per frame handheld | GPU per frame docked | Bandwidth at 60 fps (about 16 B/frag) |
|---|---|---|---|---|---|
| 1x (today) | 426x240 | 0.2 to 0.4 M | 0.2 to 0.7 ms | 0.1 to 0.3 ms | under 0.4 GB/s |
| 2x | 852x480 | 0.8 to 1.6 M | 0.8 to 2.7 ms | 0.3 to 1.1 ms | 0.8 to 1.5 GB/s |
| 3x | 1278x720 | 1.8 to 3.7 M | 1.8 to 6.2 ms | 0.8 to 2.5 ms | 1.7 to 3.5 GB/s |

The shared memory bandwidth is about 21 to 25 GB/s, so 3x is 7 to 17 % of it at worst. Against
the 16.7 ms frame, 3x handheld uses 11 to 37 %; if the real efficiency is half of the low
assumption, it is still under one frame. The GPU works in parallel with the CPU thread, so the
budget is the GPU's alone. **This is an estimate with a factor of 2 of uncertainty in both
directions.** Battery and heat rise with the GPU load in handheld; that is for the owner to feel
(OLED row R7).

With the PC layout instead (a `1024*n x 512*n` target and an equally large gutter target, plus the
downsample blit to native after every batch) the same pixels cost more: 16 MiB at 2x and 36 MiB at
3x of render targets, plus a blit of up to `(320x240)*n*n` pixels per flush (0.7 M pixels at 3x).
That is the reason for the display-sized design below.

### 3.4 Memory

| Layout | 1x (today) | 2x | 3x |
|---|---|---|---|
| Mesh FBO + gutter FBO, VRAM-sized (the PC layout) | 2 + 2 MiB | 8 + 8 MiB | 18 + 18 MiB |
| **Proposed**: two display-sized wide targets (with the 53 px gutters) | n/a (the 1x pair below) | 1.6 + 1.6 MiB | 3.5 + 3.5 MiB |
| **Both** the 1x pair (VRAM-sized, as today) and the Nx pair, pre-allocated for the turbo switch | 4 MiB | 4 + 3.2 = 7.2 MiB | 4 + 7.0 = 11 MiB |

(RGBA8, 4 bytes per pixel; driver padding and tiling add a few percent.) The game's CPU-side VRAM
buffers stay as they are. How much GPU memory a homebrew in
applet mode may use is not documented in this repo; 11 MiB is small enough that the answer is
"fits" unless the console is already near its limit. Phase 0 logs it.

## 4. Design

### 4.1 Approach: which layers scale and which stay native

| Layer | Scales? | How |
|---|---|---|
| Battle 3D (mesh FBO) on the Switch | **Yes** | A display-sized RGBA8 target of `(display_w + 2*gutter) * n` by `display_h * n`. The vertex shader gets `u_scale = n` and the viewport and scissor are multiplied; the vertex data and the OT order are unchanged. There is no depth buffer, so nothing else is needed. |
| Battle 3D on the PC | **Yes** | The existing PSY-Z path (`scaled_vram_render`), with the changes in 4.4. |
| Field, menus, HUD, text, partner view, movies, title picture | **No** (native 1x) | CPU rasterizer on the Switch; on the PC they go through the same GPU path and are N x N blocks, which is visually identical. |
| Title menu, Options, full-screen map | Independent | Native overlays at output resolution. |
| Widescreen gutters | Follow the mesh | The wide target already contains them; the existing side-strip logic is kept at Nx. |

Output stage on the Switch: the mesh target is drawn to the output with **nearest at an integer
ratio and bilinear otherwise** (docked 1.5x for 3x; 2.25x for 2x), then the CPU VRAM layer is
drawn over it as today. The UI layer stays nearest, so text and sprites keep their pixel look
while the 3D behind them is finer. This is the same mix the PC 3x has.

Known look issue, to decide by eye: the **partner view** in the battle HUD (a 3D model in a
100x60 area) stays on the CPU rasterizer at 1x, so it will look coarser than the stage next to
it. Phase 4 can give it its own small Nx target; it is an optional polish.

### 4.2 Options rows (AGENTS.md rule 8)

Both are registry rows in the **Display** group, with `port_options.cfg` keys, label and message
line in the five languages. The next free registry indexes on `main` today are **28 and 29**
(`DW3_PORT_OPT_COUNT = 28` in `port/options/port_options.c`; take the next free ones when the
build starts, because D2 to D5 add rows first). Display holds 4 rows now
(`{0, 15, 22, 21}` in `port_options_groups.h`); two more make 6, which is the list's visible
count, so no scrolling until D5's Map scaler arrives.

| Row | Key | Values | Default | Applies | Notes |
|---|---|---|---|---|---|
| **Internal resolution** | `internal_res` | 0 = 1x (native), 1 = 2x, 2 = 3x | 0 (1x) | at once; the targets are allocated when the value changes, not per frame | Message line, English draft: "Smoother 3D in battle. Higher uses more battery." Per-platform limits: the PC offers 1x to 3x; the Switch offers 1x to 3x in both modes, with a clamp table (`handheld max`, `docked max`) that phase 0 sets from the OLED numbers. A value above the limit is clamped and logged. |
| **Native res while turbo** | `internal_res_turbo` | 0 = off, 1 = on | **1 (on)** | at once | Message line: "Fast-forward draws at 1x, then returns to your resolution." Greyed (and shown as 1x) when Internal resolution is 1x. |

Defaults: 1x keeps the original look (the replays and the OLED baseline do not move). Native res
while turbo defaults to on by the owner's request. Both rows are plain switches in the sense of
the registry: no new widget. The labels must fit the generator's 290 px (row label) and 236 px
(value) limits; "Internal resolution" and "Native res while turbo" are short enough, to be
confirmed by `tools/generate_pc_title_lettering.py` in the build.

Environment test aids (not options, per the rule): `DW3_INTERNAL_RES=1|2|3` forces the value for a
run (replaces `DW3_PC_INTERNAL_RES`, which stays as an alias on the PC for one release),
`DW3_INTERNAL_RES_TURBO=0|1`, and on the Switch `DW3_NX_TEST_ENV` accepts both.

### 4.3 Turbo: native resolution while fast-forward is on

Trigger: `dw3_port_turbo_speed() >= 2` (full fast-forward in the field, battle and results,
`port/options/turbo.c`). The menus' 1.5x turbo does not count; the Switch does not scale menus
anyway.

State machine, run once per game frame in `dw3_port_turbo_poll()` and applied **at the frame
boundary**, before the frame's first draw:

```
turbo off, scale N  --R3 to 2x/3x/4x-->  turbo on:  use 1x   log  dw3-res: turbo on -> 1x
turbo on            --R3 back to 1x-->   turbo off: use Nx   log  dw3-res: turbo off -> Nx
```

- **Both targets are allocated whenever the chosen scale is above 1x**: the 1x pair that exists
  today and the Nx pair of 3.4. The switch only changes which target the flush binds and which the
  present samples, plus one uniform. No allocation, no shader compile, no `glTexImage2D`: no
  hitch. The allocation happens when the Options row changes or at boot, and is logged once:
  `dw3-res: targets 3x 1278x720 x2 allocated in 1.2 ms (handheld)`.
- On the PC the PSY-Z change is to keep `scaled_vram_render` alive while `internal_res` is 1 for
  turbo, and make the change a variable flip plus one `SyncNativeVramToScaled` of the whole VRAM
  when it goes back up (a single blit of 1024x512, well under a millisecond on a GPU). Today
  `ApplyPendingInternalRes` frees and re-creates the texture, which is the hitch to avoid.
- On the Switch the mesh target is repainted by every battle frame, so the stale target needs no
  copy; the one case is a battle held under the Options screen (P9.7), where the held picture is
  in the old target: the switch waits until the next frame that draws, or re-presents the old
  target. Test case in the replay family.
- Logs, once per event, in the AGENTS.md rule 12 style: `dw3-res: set 2x (handheld)`,
  `dw3-res: clamp 3x -> 2x (handheld max)`, `dw3-res: turbo on -> 1x`, `dw3-res: turbo off -> 2x`,
  `dw3-res: targets ...`. The `mesh dbg:` line gains `res=N`.
- Honest note on the benefit: turbo outside battle has no mesh cost at all, so the row only
  matters in battle turbo. That is where the numbers show it matters (3.2).

**Also skip the mesh frames turbo never shows (owner, 2026-11-01: do both; phase 3).** The way P6.22
pass 2 does for the CPU rasterizer, the frames turbo will not show do not flush the battle mesh.
The mesh draws on the GPU into a target that every frame clears and repaints, so skipping three
of four frames looks safe; it needs the same care as pass 2 about what reads the target (the
encounter transition, `StoreImage`, a battle held under Options). If it works, turbo costs the
same GPU per second as 1x at any scale. The owner wants the row **default ON as well**: skipping
saves GPU work but not the CPU queueing, and the 1x switch is the safety net if a skipped-frame
case turns up. It needs no Options row of its own: it changes no picture (a skipped frame is never
shown), so it is host plumbing under rule 8 (B); the PR says so for the owner to confirm.

The phase 0 build already has the measurement form of it (`DW3_NX_MESH_SKIP=1`, or Minus+ZL+L with
the probe on): in `dw3_nx_gpu_skip_present` the queued triangles are dropped instead of flushed,
nothing else changes. It is a measurement aid, not the phase 3 code: it does not look at what else
reads the target. R0.4 compares `game_fps` with it on and off at 4x turbo and 1x/2x/3x.

### 4.4 Other changes the build needs

- **PSY-Z (the `Larbaco/psyz` fork, a submodule bump called out in the commit):** the up-front
  allocation and variable flip above; lower the `AdjustInternalRes` cap to what the row offers;
  optionally the dither coordinate (`floor(gl_FragCoord / n)`); make `Psyz_VideoSetInternalResolution`
  callable before the window exists (it already defers to the next present).
- **PC:** replace the `main.c` env parsing (3 only) and the two `getenv("DW3_PC_INTERNAL_RES")`
  reads (`title_background_capture.c`, `title_menu_overlay.c`) with the port setting; the 1280x720
  3x window sizing becomes "when the setting is 3x and the window was not resized by the user".
- **Switch:** `nx_mesh.c` scale uniform, new targets, gutter pass restricted to the two side strips,
  `dw3_nx_mesh_present` blit filter, `nx_gpu.c` dock/handheld recreate (the EGL context is
  rebuilt on a dock change and drops every GL object, so the targets are recreated with the new
  mode's clamp and logged again), the `mem dbg` line gains the target bytes. **Phase 0 has these
  parts in test-aid form** (VRAM-sized `1024*N x 512*N` targets instead of the display-sized pair,
  see [6.1](#61-the-phase-0-measurement-nro-built-2026-11-01)); `mesh dbg:` has `res=N` and `mem dbg:`
  has `mesh_tgt=` already.
- **`port/`:** the two rows, the cfg keys, the turbo hook (`dw3_port_res_*`), the five-language
  strings. A new `port/options/internal_res.c`, platform-independent; the platforms provide

### 4.5 Dither: a finer grid at higher resolution (owner, 2026-11-01)

The owner chose the **finer grid**, not the PS1 grid. What that means in the shader, and what the
build does about it:

- The mesh fragment shader (and PSY-Z's `psx.frag.glsl`) looks the 4x4 PS1 dither matrix up with the
  fragment coordinate, `gl_FragCoord & 3`. At Nx the target has N times the fragments, so the
  pattern repeats every 4/N PS1 pixels: a **finer grid by construction**. Each PS1 pixel's
  footprint (N x N fragments) holds N^2 different thresholds instead of one, so a gradient dithers
  inside a PS1 pixel (smoother, less visible pattern) while the average colour of the PS1 pixel is
  the same as on the PS1. The amplitude (offsets -4 to +3 before the quantisation to 5 bits) is
  unchanged.
- At **1x** nothing changes: the coordinate is the PS1 pixel, the pattern is the PS1 pattern, the
  replays stay pinned.
- At **3x** the matrix period (4 fragments) does not divide the PS1 pixel (3 fragments), so the
  pattern is not aligned to PS1 pixel boundaries. That is harmless for an ordered pattern, and the
  look is what the owner already saw on the PC at 3x. If the 4x4 shows a visible texture at 3x, a
  denser matrix (8x8 Bayer) is the fix; it is not planned and would be a phase 4 item decided by
  eye.
- The PS1-grid variant (`floor(gl_FragCoord / n) & 3`, one matrix cell per PS1 pixel) is kept only
  as an A/B test aid: the phase 0 shader has the uniform `u_ditherDiv` (1.0 = fine, N = PS1 grid,
  `DW3_RES_DITHER=ps1`), and the same one-line change exists for PSY-Z's PC shader. It has **no
  Options row**: the setting that changes the picture is Internal resolution itself, and at 1x the
  two are identical (rule 8).
- Checks: the 1x family must not move; the 2x references (window grabs, [section 5](#5-replay-plan))
  include the dither and are deterministic on lavapipe; OLED row R8 is the by-eye A/B.
- The gutter pass draws shifted by `gutter_px - area_x0`, so its matrix phase differs from the
  centre's by a few fragments (also at 1x today). Not a regression and not visible; noted so
  nobody chases it.

| Field | Meaning |
|---|---|
| `mode`, `out` | `handheld` or `docked`, and the surface (1280x720, 1920x1080) |

| `mesh_up_us` | CPU time to upload the VRAM sample texture before the draws (dirty box only) |
| `mesh_gpu_us`, `mesh_gpu_n` | **GPU time of a frame's mesh draws, the gutter pass included**, and the frames it was read for |
| `pres_cpu_us`, `pres_gpu_us` | CPU and GPU time of the present of a shown frame (upload, mesh blit, UI draw; not the swap) |
| `raster_us` | CPU time of the software rasterizer at a present (`sync_us` of `pace dbg:` per shown frame): **the field's CPU raster cost** |
| `swap_us` | time inside `eglSwapBuffers` (the wait for the display) |
| `skip_n`, `skip_us` | frames turbo did not show, and what their skip path cost |
| `busy_pct` | 100 * (window time - swap time) / window time |
| `q_drop`, `disjoint` | queries dropped (ring full) and windows the driver flagged as disjoint: both should be 0, or the GPU figures are suspect |

Other lines the rows read: `dw3-res-probe: targets res=N size=WxH gutter_target=0|1 bytes=...

## 10. Field, menus and 2D investigation (2026-11-01)

Asked by the owner on 2026-11-01: could the **field, menus and 2D** gain anything from a higher internal
resolution on the Switch, and at what cost? Candidates named: (A) a GPU path for the field
rasterizer, (B) scaling only the 3D partner and NPC models in the field, (C) sub-pixel sprite placement.
Method: code reading ([ARCHITECTURE](ARCHITECTURE.md), `switch_gpu.c`, the decomp's field camera and
actors), the P6.22 field profiler on the PC (`-DDW3_PC_FIELD_PROF=ON`, US, which feeds every `Draw_*`
call to a shadow copy of the Switch's CPU rasterizer) over ten recorded scenarios (the opening and a
field walk, the Digimon lab, the gym, the card album, the shops, the Items screen and the field menu,
and two forced battles for contrast), and the OLED `pace dbg:` windows already in the logs
(preview.57, handheld, field and menus). The PC machine was loaded, so its absolute times are high;
the primitive counts and pixel areas are exact and do not move with load.

### 10.1 What the field and the menus draw

Per game frame, mean over the windows of each scenario (`kpx` is the bounding-box area of the
primitives, thousands of pixels; `us` is the PC time in the shadow rasterizer):

| Scenario (US) | Windows | Sprites (`sprt`) | Rectangles (`tile`) | Textured polys (`pft`) | Gouraud textured polys (`pgt`) | Rasterizer, median |
|---|---|---|---|---|---|---|
| Opening scenes (`newgame-field`) | 280 | 68 prims, 294 kpx | 1.8, 77 kpx | 13.3, 29 kpx | 0 | 2.0 ms |
| Field walk | 320 | 66 prims, 287 kpx | 1.9, 79 kpx | 12.2, 27 kpx | 0 | 2.0 ms |
| Field menu screens | 132 | 326 prims, 461 kpx | 1.4, 19 kpx | 4.8, 68 kpx | 1.5, 0 kpx | 2.3 ms |
| Items screen | 65 | 300 prims, 426 kpx | 1.0, 35 kpx | 6.1, 136 kpx | 3.2, 0 kpx | 2.3 ms |
| Digimon lab / gym / card album / shop | 13 to 20 each | 274 to 343 prims, 471 to 478 kpx | 0.1 to 0.2, 18 to 28 kpx | 0.5 to 1.9, 1 to 4 kpx | 0 | 2.2 to 2.6 ms |
| *Battle (for contrast)* | 83 | 85 prims, 194 kpx | 1.3, 74 kpx | **148 prims, 6027 kpx** | **169, 30 kpx** | 3.1 ms (p95 10.4) |

Facts that follow:

1. **The field has no 3D geometry.** Over 600 windows of the opening and the field walk, Gouraud polygons
   (`pg`, `pgt`) are 0 per frame. The only polygons are 12 to 13 small textured ones per frame (the
   dialogue window and the text glyphs, 27 to 29 kpx in all) and half a flat one. The map is 128x128
   8-bit CLUT sprites, the actors and their shadows are sprites too (11 to 12 small ones, P6.22).
   Menus are the same: sprites for backgrounds and icons (300 to 340 per frame, 430 to 480 kpx, about
   5x the 4:3 screen) and a few window quads. **Only battle uses the GTE and 3D polygons**, which is
   what the mesh layer already takes.
2. **A sprite at 2x or 3x is the same picture with bigger blocks** (P6.11 section 1): the texel is
   fetched at `floor(uv)`. So there is nothing for a higher internal resolution to refine in the
   field, the menus, the title or the movies, with a CPU rasterizer or a GPU one.
3. **The CPU rasterizer is the cost of these scenes**: 2.0 to 2.6 ms per game frame on the PC, about
   97 % of the frame ([P6.22](P6.22_FIELD_CPU.md)). On the OLED (turbo logs, `sync_us` per shown frame,
   handheld) it is a median of 2.5 ms at 2x (p95 3.6, worst 6.9) and 1.9 ms at 4x (p95 7.5). At 1x the
   field already holds 60 fps and the rasterizer runs inside the draw calls, so it shows in `other_us`
   rather than `sync_us`; R0.3 logs it as `raster_us` with the new probe.
   At 1x, `present_us` is about 11 to 12 ms per frame in the same logs, which is the wait for the display
   after `eglSwapBuffers` (the logs show `swap_us` at 0.5 ms), so **no existing log says what the GPU
   costs**; the probe's `pres_gpu_us` does.

### 10.2 Candidate A: a GPU path for the field rasterizer (P6.10)

What it is: a second implementation of PSY-Z's `Draw_*` contract in GLES3 for every primitive the field
and menus use (rectangle, sprite, flat and textured polygon, line, `LoadImage`/`StoreImage`/`MoveImage`/
`ClearImage`), so the field draws like the battle already does. PSY-Z's own `sdl3_gl.c` and
`sdl3_gpu.c` already do all of it on the PC (the mesh shader of `nx_mesh.c` was adapted from them),
and the PC replays pass with them, so the shaders are not research; the port to the Switch is.

| | |
|---|---|
| What it needs | All the primitive kinds and the four semi-transparency modes with a correct destination (VRAM is 5-bit and the mask bit, STP, is part of the blend); CLUT, 4-bit and 8-bit sampling; texture windows; the dither; drawing area and offset; the P6.1 gutter planes (CPU side today: `GetGutterPlaneRaw`); a GPU copy of the 1024x512 VRAM kept coherent with `LoadImage` and friends (the mesh path's dirty-box upload is the start of it); **read-backs** for the readers of VRAM (`StoreImage` and `MoveImage` in the encounter transition, the title background capture, `GetVram` users), each a `glReadPixels` stall of about a millisecond; the P6.22 pass 2 deferral redone for the GPU (frames turbo does not show); the 315 replay references again under Ryubing's GPU. |
| Known risk | preview.9 sent field triangles to the mesh and showed severe artifacts (blue stripe column, rug blobs, missing walls, neon outlines); the mesh shader has no semi-transparency destination and drops black as transparent ([ROADMAP P6.10](ROADMAP.md)). |
| Effort | **15 to 25 worker days** and at least two OLED rounds (an estimate: the contract is wide and the exactness bar is "0 differing pixels" on 315 scenarios; the P6.22 passes show each CPU-side change alone cost days). |
| What it buys | The CPU raster time goes away: 2.0 to 2.6 ms per game frame on the PC and about 2 to 4 ms per shown frame on the OLED become the submit of 60 to 340 draws (the battle mesh submits 1300 triangles for 0.3 to 0.45 ms, so well under that). **Turbo in the field** would reach battle's 180 to 190 game fps instead of the 160 to 240 expected after P6.22. The VRAM upload and the present stay. |
| What it costs on the GPU | The field's fill is about 370 kpx per frame at 1x (sprites plus rectangles), 480 kpx in menus: an upper bound (bounding boxes before clipping; P6.22 measured 3.0 to 3.5 times the screen painted). With the section 3.3 throughput (0.6 to 1.0 Gfrag/s handheld, 1.5 to 2.4 docked): **0.4 to 0.8 ms at 1x, 1.5 to 3 ms at 2x, 3 to 7 ms at 3x handheld** (0.2 to 0.3, 0.6 to 1.3, 1.4 to 3 ms docked). Same order as the battle at the same scale. Estimates with the same factor-of-2 error as section 3.3; R0.1 and R0.3 will bound them (`pres_gpu_us` is the upload, blit and one full-screen draw). |
| What a scale would then be | Free for the code (a viewport multiplier, as the mesh), but the picture is the same with bigger blocks; nothing is sharper. The cost would be GPU time and battery for no visible gain, except in the output stretch (10.5). |

**Verdict A: P6.10 is about turbo and CPU time, not about resolution.** It is worth deciding on those
grounds alone (2.5 ms of the field frame, a possible 190 fps field turbo). If it is ever built, an
internal-resolution scale in the field is a one-line follow-up, but there is no reason to build P6.10
for it.

### 10.3 Candidate B: scaling only the 3D partner and NPC models in the field

**There are none.** The profile above shows no 3D primitive in the field, in the opening scenes or in
any menu: the partner Digimon, the NPCs and the player are sprite frames loaded into VRAM (the
"actor frames and CLUT rows loaded every few frames" of [P6.22](P6.22_FIELD_CPU.md)) and drawn as
`SPRT`s; the decomp's field actors (`src/field/field_mode/actor.c`) carry a tile position and a z, no
model. The 3D models of the game are the battle ones (`include/battle/battle_mode/model.h`), already on
the mesh path, plus the partner view in the battle HUD (the 100x60 area the CPU rasterizer keeps,
section 4.1: its own Nx target is the optional phase 4 polish). I did not walk every stage of the game:
the ten scenarios cover the opening, one large field, the lab, the gym, the card album, both shops, and the
field menu and Items; a special cutscene with a model, if one exists, would show as `pg`/`pgt` in a
profile run of it (`DW3_PC_FIELD_PROF`, 5 minutes per scenario). **Verdict B: nothing to do** unless the
owner knows a scene with a 3D model outside battle.

### 10.4 Candidate C: sub-pixel sprite placement

The idea: at 3x a sprite could sit on a third of a PS1 pixel, so slow movement and scrolling would be
smoother. Findings:

- The data path is integer. `SPRT`, `TILE` and polygon packets hold `s16` x and y; the decomp's field
  camera is an `s32` pixel centre that follows `target->tile` and pans in integer steps (`delta /= 4`,
  `/= 2`, `= 1`, `src/field/field_mode/camera.c`); actors have a tile position, and only `z` has
  fractional bits (`z >> 8`). **No fractional position exists to expose**, so a renderer alone cannot
  do it (unlike PGXP, where the GTE computes a sub-pixel value that is thrown away).
- It would need fractional camera and actor positions added to the game logic (decomp patches per
  actor type and the camera), a side channel from there to the draw (the packets have no room: the
  GPU contract would need float positions), and a GPU path for the field (A) to use them. Every one of
  those is replay-visible and changes how the game moves.
- The gain is small: the field scrolls at 60 Hz in whole-pixel steps, and a PS1 pixel is 3 output pixels
  handheld; a sub-pixel step would help only slow pans of under 1 pixel per frame.

**Verdict C: not recommended.** Cost: A (15 to 25 days) plus 10 or more days of game-logic work
and replay churn for a gain nobody asked for. Same bucket as the not-planned PGXP item of section 7.

### 10.5 What would improve the 2D picture on the Switch, cheaply

The 2D layer is drawn at the output with **nearest** sampling. Handheld, 960x720 of the 1280x720 panel
is exactly 3x, so it is already sharp. **Docked** the stretch is 4.5x: a PS1 pixel is 4 or 5 output pixels
wide, so rows and columns alternate in width, which is the visible roughness of the 2D on a TV. A
sharp-bilinear scaler (an integer nearest step followed by a short bilinear edge) is one shader on the
present of the CPU VRAM layer, costs well under 1 ms of GPU time, needs no new render path and does not touch the
game or the replays. The project already has the scalers for the full-screen map (`nearest`, `sharp`,
`lanczos2`, `fsr1`, `bilinear`, D5) and lists a "CRT/sharp" host option for Phase 10
([PORT_OPTIONS](PORT_OPTIONS.md)). It would be a Display row of its own (rule 8), a separate item and not
part of P6.11.

### 10.6 Recommendation

1. **Keep P6.11 on the battle 3D**, and rewrite its done-when that way when the owner agrees: "a scale
   setting in the Port options; the battle mesh renders above native on PC and Switch with both discs;
   the 2D/UI layers and widescreen patches still match soft rendering". The field, menus, title and
   movies stay at 1x by construction.
2. **Do not build a field scale.** The field has no 3D to refine (B), sub-pixel placement does not exist
   in the data (C), and a GPU field (A) would give bigger blocks.
3. **Decide P6.10 on its own merits** (CPU time and turbo, 15 to 25 days), not for resolution. If the
   owner wants it, the internal-resolution code of phase 2 is reusable by it.
4. **For a sharper 2D picture, especially docked, open a separate small item**: a sharp-bilinear (or
   integer-plus-edge) output filter row, about 2 to 3 worker days, no replay impact.
5. Fill the field's GPU-cost bounds from **R0.3** before any P6.10 decision: `pres_gpu_us` and
   `raster_us` at 1x, handheld and docked.

## 11. As built: phases 1 to 3 (2026-11-01)

What the build does, where it differs from the design above, and what was and was not checked. The sections
above are kept as designed; this one is what the code is.

### 11.1 Rows and policy (phase 1)

* Registry rows **30 `internal_res`** (stored 0 = 1x, 1 = 2x, 2 = 3x; the file holds the number, `internal_res=1` is 2x) and
  **31 `internal_res_turbo`** (0 / 1, default 1), the 2nd and 3rd rows of Display, which now has eight rows and scrolls.
  Neither is locked in game. Row 29 is the PT-BR loader's Text language (P6.7), which landed first, so these rows are 30 and 31 and Text language stays the last row of Display. The overlay's lock mask was 32 bits with the Cheats lock at bit 30 and the in-game mark at 31; it is **64 bits** now (rows 0..61, Cheats bit 62, mark bit 63, game API ABI 7), tested in `locked_art_main.c`. Labels and message lines in EN and FR/DE/IT/ES drafts (`tools/generate_pc_title_lettering.py`), the
  Options help page in five languages. **Differs from 4.2:** Native res while turbo is **not greyed** at 1x: it also drives the
  skip of unshown mesh frames, which works at 1x, so the player can always turn it off.
* `port/options/internal_res.c` (platform independent) holds the policy and `port_internal_res.h` the four host functions
  (`dw3_platform_max_internal_res`, `_apply_internal_res(active, reserve)`, `_set_mesh_skip`, `_res_mode`). It runs once per game
  frame at the end of `dw3_port_turbo_poll()`, before the frame's first draw, and on every row change (`po_save`). It logs
  `dw3-res: set Nx (mode)`, `dw3-res: clamp Nx -> Mx (mode max)` (once per request, limit and mode), `dw3-res: turbo on -> 1x`
  and `dw3-res: turbo off -> Nx` (only when the target is above 1x and Native res while turbo is ON). Unit test:
  `tools/tests/test_internal_res.py`.
* **PC:** `platforms/pc/src/pc_internal_res.c` maps it to PSY-Z (`Psyz_VideoReserveInternalResolution` then
  `Psyz_VideoSetInternalResolution`). The `DW3_PC_INTERNAL_RES=3` code in `main.c` (3 only) is gone; `DW3_INTERNAL_RES=1|2|3` pins a
  run and the old variable is an alias for one release. The two other reads (`title_background_capture.c`, the 1280x720 window in
  `title_menu_overlay.c`) now follow the row's 3x; the window is resized only when it is smaller than 1280x720.
* **PSY-Z (fork branch `p6.11-internal-res`, one fork PR, merge with a merge commit, not squashed):** the new
  `Psyz_VideoReserveInternalResolution(n)` keeps the scaled VRAM target (and the scaled gutter target, in its own slot) allocated while
  the multiplier is 1, so the turbo switch is one whole-VRAM upscale blit instead of free + create. A reserve asked for before the
  window exists is made at the first present. The 1x path without a reserve is unchanged. The GL backend, PSP and the PS1 test target accept the call and ignore it. The dither
  matrix is indexed by the fragment already (finer at Nx), so the shader did not change.
  **Not done, harmless:** the canvas textures of the PS1-layout path are still re-created on a multiplier change (they are only used when
  the game leaves the native layout).
* The PC replays all run at 1x: the runner removes the three new variables and the 2x family is
  [P6.15](P6.15_REPLAY_TESTS.md#p611-internal-resolution-pinned-at-1x-and-the-2x-family).

### 11.2 Switch mesh scale (phase 2)

* **Layout (differs from the design):** the Nx targets are **VRAM-sized** (`1024*N x 512*N` RGBA8, mesh + gutter), the layout phase 0
  measured, not the display-sized pair of 3.4. The display-sized pair needs the drawing-area-to-target mapping (the battle draws in
  two buffers at different VRAM positions, ClearImage rects and the held picture all assume the VRAM layout); it is left for a follow-up
  once the OLED numbers say memory matters. Cost: 2x adds 16 MiB and 3x 36 MiB on top of the 4 MiB 1x pair, **only while the row asks for
  2x or 3x** (the log line `dw3-res: targets Nx ... bytes=` and `mem dbg: mesh_tgt=` say how much). If the allocation fails the host
  stays at 1x and logs `dw3-res: targets Nx failed, 1x`.
* `nx_mesh.c` keeps two sets of targets: the 1x set made at init exactly as before, and the Nx set made when the row (or the dock
  context after a rebuild) asks for it and kept while turbo can switch back. `dw3_nx_mesh_apply_res(active, reserve)` allocates
  the Nx set for `max(active, reserve)` and picks the active set; with a battle held under Options everything waits, because the held
  picture lives in the old set. Switching sets changes four GL handles and a few flags: no allocation, no shader compile, no
  `glTexImage2D`. The first frame on a set always draws.
* **Gutters at Nx:** the gutter pass draws the left and the right strip only (two scissors); the display part is blitted over the
  middle at the present anyway. At 1x the single wide pass is unchanged.
* **Clamp table:** `platforms/switch/psyz_backend/nx_res_clamp.h`, `DW3_NX_RES_MAX_HANDHELD` and `DW3_NX_RES_MAX_DOCKED`, both 2 until the OLED
  run. Read every frame, so a dock change applies the other limit. `tools/res_probe_summary.py` ends with the two lines to paste.
* The phase 0 aids that remain: the probe (`DW3_NX_RES_PROBE`, its chord to cycle the scale, `DW3_NX_MESH_FILTER`, `DW3_RES_DITHER=ps1`).
  `DW3_NX_MESH_SCALE` is gone (the row and `DW3_INTERNAL_RES` replace it); `DW3_NX_MESH_SKIP` stays a measurement aid.

### 11.3 Turbo (phase 3)

* **Native res while turbo:** fast-forward on (`dw3_port_turbo_speed() >= 2`: field, battle and the report; the menus' 1.5x and a
  held battle do not count) and the row ON: active 1x, the Nx set (or PSY-Z's scaled target) kept. Off: back to the chosen value.
* **Skipped mesh frames, with the row ON:** `dw3_port_turbo_poll()` works out whether the frame now starting is one `dw3_port_turbo_present_due()`
  will skip (`dw3_port_turbo_frame_will_skip()`, the same credit arithmetic on a copy) and tells the host before the frame draws. A skipped frame
  draws **nothing** into the mesh targets (no clear, no enqueue, no flush), so they keep the last *shown* frame. That is what makes it safe: a
  battle held under Options right after a skipped frame shows a complete picture, a mispredicted frame (turbo changed mid-frame) shows the
  previous mesh for one frame instead of an empty one, and `s_content_before_hold` still says the battle had content. The first frame after a
  set switch never skips. Game state is untouched: only the drawing is skipped (same RNG, same timers); the CPU rasterizer's own deferral (P6.22)
  is unchanged. Logs: `dw3-res: mesh skip on ...`, `mesh skip off (N frames skipped)`, and `skip=1` in the probe line.
* Not skipped on the PC (PSY-Z draws everything on its GPU path; there is no CPU queue to save).
