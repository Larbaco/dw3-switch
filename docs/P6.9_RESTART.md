# P6.9 in-process game restart

Controls, physical mappings, and diagnostic chord overlap: [HOTKEYS.md](HOTKEYS.md).

The title Port options shell exposes **Restart hotkey**, OFF by default. It is
saved with the other Port options since P9.4 (`port_options.cfg`, see
[PORT_OPTIONS.md](PORT_OPTIONS.md#persistence)), so enabling it once keeps it
across launches. Enable it from the title shell, then hold the PS1 logical buttons **L1 + R1 + Start + Select**.
On PC's keyboard map this is Q + R + Enter + Backspace. Switch uses the same
logical pad buttons.

`port/options/restart.c` owns the chord, opt-in check, and P5.3
`memcard_host_flush_all()` call. A flush error cancels the restart and leaves
the current game running. A successful flush asks the existing game loop to
reset its in-memory `GAME` state, discard the active mode task, hide the
native title overlay, and continue through the same `dw3_game_main()` call. It does
not repeat PSY-Z, CD, audio, heap, pad, or graphics initialization, and it
does not format or edit save data.

## Return to title from the field menu (P6.27)

The field menu has a last row, Return to title (always there, whatever the Restart hotkey setting). Cross on
it opens a Yes / No window (cursor on No); Yes calls
`dw3_port_restart_request()` and the next `dw3_port_restart_poll()` (right after
the pad update, as for the chord) runs the shared `restart_perform()`: the same
`memcard_host_flush_all()`, the same cancel on a failed flush, the same options /
overlay reset and the same in-process reset of `GAME`, the mode and the overlay.
Nothing of the reset was copied. The window is
[PORT_OPTIONS.md](PORT_OPTIONS.md#quit-and-return-to-title-p627-p628); the title
menu's Quit game (P6.28) is documented there too. Replay `us/eu-return-title`
(patch `0124` makes `DW3_START_MODE` apply on the boot only so the reset can leave
the forced field) show a restart from the field on both discs: the title (US) and the
language select followed by the title (EU). That covers "restart in the field"
that the 2026-10-15 notes below list as not automated; restart after a battle and
after a save written by the game is still open.

## The fade to black (preview.42 follow-up)

Owner report (preview.41, OLED): choosing TITLE SCREEN in the field showed the
picture at 4:3 for a moment before the title. The log said why: the reset drops
the mode task with no final draw, the field's last frame stays on screen while
the title loads (about six frames on the PC), and the widescreen gutters switch
off the moment the mode file changes (`dw3-widescreen: gutter 0 px per side (was
53; 4:3 picture) mode file 0x1c1 frame N`), so that old frame was shown squeezed
into 4:3 until the title backdrop switched the gutters on again. The OLED log of
preview.43 (US) shows it: `gutter 0 px per side (was 53; 4:3 picture) mode file 0x1c1
frame 32751`, back to `53 px (16:9)` at frame 32757, six frames of 4:3. The same
pattern at boot (frames 1 to 8, before any picture) and after the intro movie
(695 to 821, the movie itself) is expected and not covered by the fade.

Now `restart.c` fades through black (both the chord and the field menu):

1. `RF_OUT`, 20 frames: the overlay draws a black quad over the whole picture with
   a rising level (`port_screen_fade.h`; Switch: the overlay program with `u_sub` 1
   and `u_alpha` = level; PC SDL3 GPU: one quad per level sampling a 64 x 1 black
   ramp). The field is still 16:9 and plays on under it.
2. Black: the reset runs (`restart_perform`, unchanged) at the first full-black
   frame. The screen stays black until the new screen is drawing: the title backdrop
   (`dw3_port_widescreen_new_screen_ready`; EU: the language select, file 0x165) and
   at least 4 frames, at most 90 (widescreen off: no gutter signal). The gutter switch to 0 happens here, unseen.
3. `RF_IN`, 15 frames: fades in on the title or the language select.

A save being written cancels before any fade (`restart_begin`), as it did before.
Nothing in the game's code changes (no patch: `dw3_port_restart_poll` already ran
after the pad update). Log lines, in order: `fading to black before the reset`,
`screen is black after N frames; resetting now`, `saves flushed`, the
`dw3-widescreen: gutter 0 px` line, `new screen ready after N black frames; fading
in`, `fade finished, N frames from the request`. PC replay `us-return-title`
screenshots every third frame from 1872 show: the 16:9 field darkening, black, then
the title appearing at 16:9 and fading in; no 4:3 frame.

## Boot target after restart

Restart re-runs `newGame()`, so it lands where a cold host boot lands. US goes
to the title. EU goes to the language selection (`CNTY_SEL`) with `LANGUAGE`
cleared, and the player chooses a language again. This matches a real PS1
reset (which returns to the country select) and means a language change needs
no host relaunch. It is not "skip to title with the old language".

The native title overlay (Switch GLES / PC SDL3 GPU: menu plaques, logo
texture, edge-fade level) is only hidden by title-task draws, and the title
task is discarded on restart. Before the fix, an EU restart from the title left
the overlay's active flags set while the mode became `CNTY_SEL`, so the title
menu and logo drew on top of the language screen (owner report, preview.26).
`dw3_port_title_overlay_reset()` now clears the overlay state as part of the
restart.

## Validation

existing runtime as read-only input and an empty memcard directory under
`/dev/shm`. The title shell enabled the setting; the chord produced
`saves flushed; returning to title in-process`, followed by the title mode
entry again. Host startup and `dw3_game_main()` entry did not repeat. The
options state-machine test confirms OFF by default and that the setting can
be enabled. The PC `dw3-pc` target linked successfully.

P6.9 remains open until the Switch build and hardware chord are validated
(an OLED retest). The save-then-Continue and battle checks that were open here
are now covered on the PC build, see
[2026-10-25 replay validation](#2026-10-25-pc-replay-validation-us-and-eu)
below. The opt-in setting is persisted by P9.4. A restart does not re-read the
option file: the registry is host-owned and stays as it is in RAM, which
already equals the file because every change is written when it is made.

### 2026-10-25 PC replay validation, US and EU

Method: the PC build (`dw3-pc`, sdl3_gpu on lavapipe) on a private Xvfb per
scenario, driven by P6.15 replay recordings ([P6.15_REPLAY_TESTS.md](P6.15_REPLAY_TESTS.md)),
the US and the EU disc (EU in English), cheats compiled in, a fresh memory
card directory and a fresh option file per scenario. The option file seeds
`restart_hotkey=1`; the recordings press the chord as the logical mask
`0x0C09` (L1 + R1 + Start + Select) for five frames. Each scenario is 10-100 s
of wall time and 1500-4700 game frames. Not covered: the Switch hardware
chord (OLED), other EU languages than English, a restart during a save write.

Test hooks (PC only, nothing changes when unset): `DW3_START_MODE` boots into a
mode. Since patch `0124` (from the P6.27 work) it applies on the boot's
`newGame()` only, so a restart reaches the real boot screen (US title, EU
language select). Patch `0127` adds `DW3_START_MODE_EVERY=1`, which brings back
the re-entry: every `newGame()`, so every restart, honours `DW3_START_MODE`
again. `restart-battle-again`, `restart-in-battle-redo` and
`restart-before-battle` use it to test a second forced battle or field on a
reset `GAME`; the others test the boot screen after a restart.

| Scenario (US and EU) | What it does | Result |
|---|---|---|
| `restart-after-battle` | forced battle, Tech, report, back in the field, chord, boot screen, title menu | pass, both discs. US: PRESS START then New Game / Options / Load Game. EU: a clean SELECT LANGUAGE (no title plaques or logo drawn over it, the #162 fix holds), English, title, Start / Options / Continue |
| `restart-battle-again` | the same with `DW3_START_MODE_EVERY`: the restart re-enters the forced battle | pass, both discs. The second battle plays and ends like the first (`WFIGHTMN_endBattle result=1` twice, report, field). US: the field after the second battle is byte-identical to the first |
| `restart-in-battle` | chord while a technique message is on screen | pass, both discs. The chord is **allowed in a battle** (`port/options/restart.c` polls in the main loop in every mode; no mode is excluded): `FIGHTSTG_start`, the restart line, no battle end, then the boot screen and the title menu |
| `restart-in-battle-redo` | chord mid-battle, then the whole forced battle again | pass, both discs: the second battle starts with the command menu and ends won, report and field follow. See the RNG note below |
| `restart-before-battle` | restart in a random-battle field, then walk with the P6.20 `battle_now` hook | pass, both discs. The restart line, then `dw3-cheats: battle now`, then `FIGHTSTG_start`: a battle after a restart starts normally |
| `restart-save-continue` | save screen over the field (slot 1, YES, save), chord, boot screen, Load Game / Continue, slot 1, execute | pass, both discs. `STGMCARD_writeSave port=0 slot=0 status=1` before the restart; after it the slot picker shows the block (Junior, South Sector, play time), `STGMCARD_loadSave ok port=0 slot=0 progress=6`, and the field (`0x233`, Bulk Swamp) loads |
| `restart-newgame` | New Game, the opening's TV news, chord, New Game again, the same news | pass, both discs. The `news` captures before and after the restart are **byte-identical**, so nothing from the first New Game leaks into the second |

The save in `restart-save-continue` is written by the game's own memory-card
screen and read back by its own Load Game / Continue path in the same process
after the restart, through the P5.3 flat-save host. The restart flushes the
host's dirty slots first (`dw3-port-restart: saves flushed` comes after the
`writeSave` line in the log).

**Findings.**

- No save is lost, no state leaked into the next game, and no crash or hang
  in 14 scenarios (US and EU).
- The restart does not reseed the RNG (`RANDOM.seed(0)` runs only at the
  cold boot, the restart path calls `newGame()` only). Who moves first in the
  next forced battle therefore depends on the frame of the chord: a mid-battle
  restart at frame 600 on the US disc and at 637 or 700 on the EU disc gave the
  enemy the first move ("Kunemon Attack!" instead of the command menu), at 650
  both discs show the menu. This is consistent with the RNG phase and is not a
  state leak: moving the chord by a few frames changes it, nothing else does.
  A real reset would start from the same seed, but the first move also depends
  on the frame count since boot, so no fixed outcome is lost. Not changed.
- `BATTLE_SETUP.gauges` carry over from battle to battle, and only the
  title's New Game / Continue empties them (`clearGauges`). A decomp patch
  that cleared them on restart was tried (as `0128`) and did **not** change
  the enemy-first start above, so it was dropped; the gauges are not the cause
  and the title empties them on every real path out of a restart.
- Restart does not re-init the sound system, the file cache or the heap.
  Nothing showed a problem: after a mid-battle restart the log shows the boot
  screen starting its own exclusive sequence (`SsSepPlay ... exclusive=1`)
  and key-ons, and the runs end without a crash or a hang. The audio itself
  was not listened to (dummy audio driver), and the heap was not inspected.
