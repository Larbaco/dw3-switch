pause menu and from the title menu, like P6.30. It tells the player where to go
next and what to do, from the story progress the game already keeps. It only
reads game state; it never writes it, and the save format does not change.

## Owner decisions

Owner answers of 2026-10-28 (they replace the open questions of the P6.35 goal
note):

1. **Spoilers are opt-in, per area.** Each area has a spoiler sub-area that the
   player opens only if lost. It is hidden by default and needs an explicit
   reveal. Nothing spoiler-heavy is shown by just opening the screen.
2. **Current step, with browsing.** The screen shows the current step, derived
   from the story progress, and offers a way to browse other steps and
   chapters.
3. **Side content is included.** Optional quests, recruits, items and the like
   are in the walkthrough, clearly marked as optional.
4. **Agents draft, the owner reviews.** Agents write the text; the owner reviews
   it before it ships. Nothing unreviewed is released.
5. **All base-game languages at launch (2026-10-28).** The walkthrough (and the
   P6.30 help) exist at launch in English, and on the EU disc also French,
   German, Italian and Spanish; pt-BR comes later with P6.7. See Q3.

Earlier P6.30 decisions that apply here too (2026-10-27): it opens from the
pause menu and the title menu; everything is offline, no links; a page may
scroll; there is no Brazilian Portuguese first, pt-BR arrives with the P6.7
language packs ("it should have Portuguese when we add that language"), so the
text tables must be translatable from day one.

## 1. Mapping game state to a step

All citations are in `vendor/dw3_decomp` (the pinned submodule) unless marked
`port/`.

### 1.1 The story counter: `GAME.progress`

- `GAME.progress` is an `s32` at offset `0x263C` of `GameState`
  (`include/engine/game_state.h:497`). It is the main-story counter: scripts
  assign literal values to it, from 0 at the start up to `0x29` in the stage
  scripts that set it. Examples:
  `src/field/stages/kusanagi_city/wstag780.c:615` sets 0,
  `kusanagi_city/wstag785.c:276` sets 1, `asuka_city/wstag225.c:150` sets 2,
  `asuka_city/wstag212.c:163` sets 3, `central_sector/wstag200.c:41` sets 4,
  `east_sector/wstag420.c:41` sets 5, `east_sector/wstag410.c:13` sets 6;
  later ones such as `asuka_city/wstag310.c:719` (0x27) and
  `amaterasu_city/wstag311.c:496` (0x28) close the first half. Which area the
  player is in at each value is to be confirmed in phase 1 by replay, not
  assumed from the stage folder names.
- Conditions in scripts test it with `PROGRESS(n)`
  (`include/engine/game_state.h:68`, handled by `checkProgress`,
  `src/engine/game/events.c:320`) and with ranges in `PROGRESS_RANGES`
  (`src/engine/game/events.c:772`, read by `checkProgressRange`,
  `events.c:180`). The ranges are the best existing evidence of the **chapter
  boundaries** the scripts care about (for example `{0x04, 0x17}`,
  `{0x18, 0x25}`, `{0x27, 0x2A}`; the `0x63` upper bounds mean "to the end").
- `GAME.progress` is used in 261 places in `src/` outside the debug code, so
  the value is the primary key of the step table.
- Special values: the debug stage select treats `0x8000` as 0
  (`src/debug/stage_select/stage_select.c:824`); the walkthrough treats any
  value outside the table as "unknown step" (section 1.5).
- The European build has an **extra chapter** at `FIELD_PROGRESS_EXTRA = 0x2D`
  whose stages are `FIELDSTG_extraStages` (WSTAG920 to WSTAG974)
  (`include/field/field_map.h:251`; users in
  `src/field/field_mode/field.c:740` and following). It is the main US/EU
  difference of the data (section 2.4).
- The game's own map screen already buckets `progress` into five stages
  (`< 7`, `< 0xF`, `< 0x1B`, `< 0x1E`, else), which pick the town list
  (`src/menus/field_menu/map_screen.c:250`, `STSTATUS_townLists` at
  `src/menus/field_menu/helpers.c:352`, `STSTATUS_getTowns` at
  `helpers.c:9`). Those five buckets are a free sanity check for the chapter
  table: a table that disagrees with them needs a reason.

### 1.2 Which half of the game and which area

- `STSTATUS_getGameHalf()` (`src/menus/field_menu/helpers.c:172`) returns 0 for
  field maps below `0x270`, 1 from `0x270`, and -1 from `0x2D7` and outside the
  field, using `GAME.fieldMode` (`game_state.h:484`).
- `STSTATUS_getArea()` (`helpers.c:178`) maps the current field mode to a map
  area through `STSTATUS_mapAreas` (`helpers.c:377`). This gives the "you are
  here" area, which the screen uses to open the matching area chapter first.
- `STSTATUS_getVisitedAreas()` (`helpers.c:186`) reads, per area, the flag
  `0x2000 + map low byte` through `FLAGS_00.checkCondition(..., 1)`
  (`helpers.c:202`). The port already uses the same flags to draw the revealed
  map (`port/map_view/map_view.c:185`).

### 1.3 Event flags (for side content and finer steps)

- Event flags live in `FLAGS_00` (`game_state.h:47`, `bits[4]`) and in the byte
  arrays `GAME.flags02` to `GAME.flags40` (`game_state.h:500` onward), addressed
  by `FLAG(group, id)` (`game_state.h:67`). **The array sizes differ between
  US and EU** (US `flags02[0xD]`, EU `flags02[0x12]`, both at `0x2644`;
  `game_state.h:505` against `:533`), so the walkthrough never reads the arrays
  by raw offset. It asks the game's own evaluator,
  `FLAGS_00.checkCondition(code, value)` (`game_state.h:51`), the same call the
  scripts and `STSTATUS_getVisitedAreas` make. That keeps one code path for US
  and EU and cannot disagree with the game.
- Story events that fire at a progress value while a flag is clear are listed
  in `FIELDSTG_progressEvents` (`src/field/field_mode/data/fieldstg.c:1328`,
  type `ProgressEvent`, `include/field/field_mode.h:332`:
  `{progress, flag, condition, script, nextScript}`). The flags `0x400` to
  `0x40F` there are candidates for "this milestone is done" checks.
- Items, party and money are plain fields: `GAME.items[]`, `GAME.party[]`,
  `GAME.partners[]`, `GAME.money` (`game_state.h:487` to `:496`); item codes in
  conditions use `ITEM(kind, id)` (`game_state.h:75`) and cards `CARD(id)`
  (`:77`). Side-content "done" checks use these (recruit owned, item held, flag
  set).

### 1.4 Reading it from the port

The screen runs in the port (`port/walkthrough/`, new) and reads `GAME` and
`FLAGS_00` the way `port/map_view/map_view.c` does. It reads once when the
screen opens and again when the player returns to the step list (not per
frame), and logs the result (section 8).

Reading rules:

- Read-only. No call that applies an action (`applyAction`, `applyActions`).
- `checkCondition` is called only with codes taken from the table, never with
  computed ones, and only while the game is in a state where the flags are
  valid (field, menus). On the title menu with no loaded game, `GAME` is not a
  save: the screen opens in **browse mode** (section 3.5).
- Open question Q1: does the title menu have a loaded save to read from while
  Options is open? Verify in phase 1.

### 1.5 Resolving the current step

```
step = last row of STEPS (ordered) whose from_progress <= GAME.progress
       and whose unlock conditions all hold
```

- Steps are ordered by `progress`, then by an `order` within the same value.
- A step may carry **sub-conditions** (flags) when one `progress` value covers
  several things to do; the first step whose `done` condition is not yet true
  is the current one.
- No match (progress below the table, a value the table does not know, or the
  `0x8000` debug value): show "Step not recognised" and open the chapter list.
  Never guess.
- EU-only rows carry `region = EU` and are skipped on US.

## 2. Data format

### 2.1 Principles

- **Logic and text are separate.** The step table holds ids and conditions; a
  text table holds strings keyed by id. Changing a sentence never touches a
  condition, and a translation never touches logic.
- Both live in the repo as plain, reviewable, diffable files. No game data is
  in them (AGENTS.md: nothing derived from the disc in git).
- A host test validates the tables (section 8), so a typo in an id fails CI.

### 2.2 Step table (logic)

One row per step, a C table in `port/walkthrough/walkthrough_steps.c` (the port
keeps its data as C tables; if a text format is preferred, a small script
generates the C table and the generated file is checked in next to its source).

| Field | Meaning |
|---|---|
| `id` | Stable string id, for example `ch01.s03`. Never reused or renumbered; the text tables key on it |
| `chapter` | Chapter id (`ch01`) |
| `area` | Area id the step happens in (opens the right area and groups the spoilers) |
| `kind` | `MAIN` or `SIDE` |
| `category` | SIDE only: quest, recruit, item, card, mini-game, other |
| `region` | `ALL`, `US` or `EU` |
| `from_progress` | Smallest `GAME.progress` where it can be current (MAIN) |
| `to_progress` | Largest value, or -1 (MAIN), from the observed script ranges |
| `unlock` | Condition list of `(code, value)` pairs in the game's own encoding (`PROGRESS(n)`, `FLAG(g, i)`, `ITEM(k, i)`, `CARD(i)`), or none |
| `done` | Condition list that means the step is finished (SIDE status and sub-steps) |
| `order` | Position inside a chapter |

Using the game's own code encoding (`game_state.h:58`) means a row can be
checked against the scripts by grepping the same codes, and the evaluator is the
game's `checkCondition`, not new logic.

### 2.3 Text table (strings)

Keyed by step id and a **layer**:

| Layer | Content | Visible |
|---|---|---|
| `title` | Short name of the step (a few words) | Always |
| `goal` | One or two sentences: where to go and what to do next, no puzzle answers | Always, for the current step and browsed steps |
| `help` | Spoiler sub-area text: details, how-to, boss or puzzle solution | Only after the explicit reveal (section 4) |

Strings are stored per language in `port/walkthrough/text/<lang>.txt`
(`en`, later `fr`, `de`, `it`, `es`, `pt-BR`), one `key = value` per line, with
the key `step_id.layer` (for example `ch01.s03.goal`). Translation readiness
(P6.7):

- No sentence is built by concatenation; whole sentences, with `{name}`
  placeholders only where a name must be inserted.
- No text is embedded in the table of section 2.2.
- A missing key in a language falls back to English and logs it once
  (`dw3-walkthrough: text fallback <key> (<lang>)`), so a partial translation
  works and is visible.
- Proper names (characters, places, items) are short, may match the game's
  names so the player can find them, and are not copied from the disc script in
  bulk. The name list is a separate small table so each language can match its
  own game text.
- A text length budget per layer is part of the table validator (section 8) so
  nothing overflows the plaque.

Open question Q2 (section 9): names from a table, or from the game's text banks
at runtime.

### 2.4 US and EU differences

- `region` on a row restricts it. The known case is the EU extra chapter
  (`FIELD_PROGRESS_EXTRA`, `0x2D`), EU only.
- The flag arrays have different sizes in the two builds (section 1.3); flag
  codes are validated per region by the host test against the decomp headers of
  that region, because a flag id can exist in EU and not in US.
- The EU build has five languages; US has English. The text table is keyed by
  language, and a US row has no `fr/de/it/es` text (open question Q3).
- Every phase is verified on both builds (AGENTS.md owner rule 5).

## 3. UI flow and controls

The screen follows the title-menu identity, as the other Options sub-screens do
([TITLE_MENU_DESIGN](TITLE_MENU_DESIGN.md),
[PORT_OPTIONS](PORT_OPTIONS.md#groups-and-sub-screens-p99)): dimmed backdrop,
navy plaques with steel bevels and amber rails, a lit rail and short halo on the
focused plaque, warm lettering with a one pixel shadow. It uses the same header
plaque, message strip and two-button hint row, and it reuses the P6.30 page
engine (text wrapping, scroll, language fallback; the text file syntax, qualifiers
and tokens are in [P6.30_HELP](P6.30_HELP.md#4-text-table-format)). The Walkthrough group flips
to `built = 1` in `port/include/port_options_groups.h` (the `built` field, line
28) when the screen exists.

### 3.1 Screens

1. **Current step page** (the landing page, when a game is loaded). Header
   plaque: the chapter name. Body: the step title and its `goal`. A line below
   says how many steps are left in the chapter. Side content available now
   shows as a count ("2 optional things here"), not as text.
2. **Chapter list.** All chapters in order. Chapters past the player's progress
   show only a number and a "not reached" mark; the player can still open them
   (decision 2: browsing), with a one-time notice that later chapters may spoil
   the story (open question Q4).
3. **Step list** of one chapter: main steps, then the optional block (section 5).
4. **Step page** for any step: title, `goal`, and the reveal control for `help`
   (section 4).

### 3.2 Controls

As on the Options screen: Up / Down move the cursor; Confirm (Cross, Circle)
opens or reveals; Back (Triangle, X on the Switch) goes up one level and closes
the screen from the top level; L1 / R1 jump to the previous / next step (or
chapter on the chapter list); Up / Down scroll a long page when the cursor is on
the text; a held direction repeats like the other lists. The hint row names the
buttons of the current screen.

### 3.3 Scrolling

A page may scroll (owner, 2026-10-27). A scroll indicator (two small arrows on
the plaque's rail) shows when more text exists. The cursor never leaves the
reveal control while the text scrolls.

### 3.4 Entry points

- Pause menu and title menu, through Options. In game the screen opens on the
  chapter of the player's current area (section 1.2) with the current step
  highlighted.
- On the title menu the screen opens in browse mode unless Q1 resolves to "a
  save is available".

### 3.5 Browse mode and unknown state

When there is no loaded game, or the step is not recognised, the landing page is
the chapter list with a message strip line ("Pick a chapter to read"). No
current-step claim is made.

## 4. Spoiler reveal UX

Decision 1: each area has a spoiler sub-area, hidden by default.

- Every step page has two parts. The visible part (`goal`) is written to be
  safe: where to go and what to do next, without puzzle answers, boss
  weaknesses, hidden-item spots or later plot. The hidden part (`help`) is the
  area's spoiler sub-area.
- The hidden part shows as a **closed plaque** labelled "Stuck? Show the
  answer", with a short line that says what is inside in general terms ("how to
  solve this room"), never the content.
- Opening it takes **two actions**: Confirm on the plaque, then Confirm on a
  confirmation plaque ("This shows how to continue. Show it?  Yes / No", cursor
  starts on No). This prevents opening by a stray press.
- Once opened, the text stays open while the player is on that step; leaving the
  step closes it again. Nothing is remembered between visits and nothing is
  written to the save or the config. A hold-to-reveal variant is not used,
  because a long page must scroll while visible.
- The **area spoiler sub-area**: the chapter list also has, per area, a "Whole
  area" entry that opens the area's full spoiler page (all `help` text of the
  area, plus anything that spans several steps, such as the order of rooms). It
  sits behind the same two-step reveal.
- The landing page never shows `help`, even when the cursor sits on the reveal
  plaque.
- Open question Q5: an Options row "Remember revealed answers" (default off)?

## 5. Side content structure

Decision 3: side content is included and marked optional.

- Rows with `kind = SIDE` sit in the same chapter and area as the main steps
  they belong to, in a block after the main steps under a plaque "Optional". The
  mark is the word plus a different accent than the main amber, so it does not
  depend on colour alone.
- Categories (the `category` field, each with its own label in the text table):
  optional quest, recruit (a Digimon that can join), item or equipment
  location, card, mini-game, other. The list is confirmed against what the
  decomp shows per area (items and cards have codes: `game_state.h:75` to `:77`).
- Status: a SIDE row shows "done" when its `done` condition holds (recruit
  owned, item held, flag set). A row with no safe way to read "done" shows no
  status rather than a guess.
- Availability: a SIDE row is listed only when its `unlock` condition holds or
  its chapter has been reached; it never reveals a recruit or an item the player
  could not have met yet. Browsing ahead follows the same rule as main steps
  (section 3.1).
- Side `help` is behind the same spoiler reveal. Item and recruit locations are
  `help`, not `goal`; `goal` only says that the thing exists in this area.
- Missable content: a SIDE row that can be lost for good gets a warning line in
  its `goal` ("Cannot be done again later"), written only after the fact is
  confirmed.

## 7. Text authoring and review workflow

Decision 4: agents draft, the owner reviews before it ships.

1. **Research** (agent). Read the decomp for the step: stage scripts,
   `GAME.progress` assignments, flags and items involved, with file and line.
   Kept in the PR description as the evidence for the step table, not in the
   repo.
2. **Draft** (agent). Write the step rows and the English text from that
   evidence, in the agent's own words. Short sentences, no answers in `goal`.
3. **Verify** (agent). Play the step on PC with the replay harness
   ([P6.15_REPLAY_TESTS](P6.15_REPLAY_TESTS.md)) or read the script closely, and
   record what was confirmed in the PR. An unverified claim is marked
   `TODO(verify)` and cannot be in a shipped build; the validator fails on that
   marker in a release build.
4. **Review** (owner). The PR for an area is text-focused: the diff holds the
   step table and the text file, plus a generated reading copy (the steps in
   order with `goal` and `help` side by side) so the owner reads prose, not
   code. The owner approves, edits or rejects each step; corrections are
   commits on the same PR.
5. **Ship.** Only reviewed areas go into a release build. Each step carries a
   `reviewed` marker set by the owner's approval commit, which a release build
   requires; a tester build may show unreviewed text tagged "(draft)".

**Copyright.** All text is original writing for this port. It is not copied,
closely paraphrased or translated from any external walkthrough, FAQ or wiki
(GameFAQs and similar), and not copied from the game's disc script beyond short
names. The task given to every drafting agent says so, the text PR carries a
checkbox "written from the decomp and play, not from external guides", and the
owner's review includes spot checks. When the decomp does not tell the agent
enough, the agent plays the step instead of looking it up.

## 8. Test plan

### 8.1 Host / unit (CI)

- Table validator: every `id` is unique; every text key exists for `en`; the
  MAIN `from_progress`/`to_progress` ranges are ordered and non-overlapping per
  chapter; every condition code decodes with the macros of `game_state.h`;
  EU-only rows are absent from the US table; length budget per layer; no
  `TODO(verify)` or missing `reviewed` marker in a release build.
- Resolver test with fake `GAME.progress` and flags: the first and last value of
  each chapter, a value below the table, an unknown value, `0x8000`, and EU
  `0x2D` on US (must say "not recognised", not crash).
- Doc link test: `python3 tools/check_doc_links.py` (run by
  `tools/tests/test_doc_links.py`) for this doc.

### 8.2 PC replays

With the replay harness, load a save (or script to a point) at each of a few
progress values and check the step the screen shows. Initial set, one per phase 1
boundary: `GAME.progress` 0 (new game), 2, 4, and the first value after the first
area. For each: open Options, then Walkthrough, and log the result. Also covered:
the spoiler is closed on entry; the two-step reveal opens it; Back from the step
page closes it; a long page scrolls; opened from the title menu with no save it
shows the chapter list. Run on US and EU.

### 8.3 OLED checks (owner)

AGENTS.md rule 12: each item names the `dw3.log` lines that prove it, so the
owner only reports feel and looks. Proposed lines, once per event, not per frame:

| Check | Log proof |
|---|---|
| Screen opened | `dw3-walkthrough: open (from pause\|title, region US\|EU, language L, progress N)` |
| Current step resolved | `dw3-walkthrough: step <id> (progress N, chapter C, area A)` |
| Not recognised | `dw3-walkthrough: step not recognised (progress N)` |

| Closed | `dw3-walkthrough: closed after N ms` |

## 9. Open questions for the owner

- **Q1.** On the title menu, is a loaded save available while Options is open?
  If not, the screen is browse-only there. (Verified in code in phase 1; decide
  whether browse-only on the title menu is acceptable.)
- **Q2.** Names of characters, places and items: a separate name table in the

  languages, which favours reading names from the game's own text banks for
  places, items and Digimon (they already exist in all five languages) over a

- **Q4.** Browsing chapters ahead of the player's progress: a one-time notice
  (as proposed) or a confirmation on each later chapter?
- **Q5.** Remember revealed answers between visits (an Options row, default
  off), or always close them again (as proposed)?
- **Q6.** Also show the current step outside the Options sub-screen, for example
  as a one-line hint in the pause menu? (Out of scope here; a separate item.)
- **Q7.** Chapter names: neutral ones written by the agent ("Chapter 1: ..."), or

### Resolver

`dw3_wt_resolve(state, &result)`: among the MAIN rows that apply to the region
and cover `progress`, the current step is the first whose `unlock` holds and
whose `done` does not (if all are done, the last offered). Statuses:
`WT_OK`, `WT_BELOW` (below the table), `WT_ABOVE` (a valid value the table does
not cover yet, so every progress from 5 on today, and the EU `0x2D`),
`WT_UNKNOWN` (negative, above `0x63`, the `0x8000` debug value) and
`WT_NO_MATCH` (a gap, or no row offered). Anything but `WT_OK` is "step not
recognised"; the resolver never guesses. SIDE rows never decide the current
step. The half (`STSTATUS_getGameHalf`) and the area are carried in the state
and logged; phase 1 does not use them to choose the row.

The log line (AGENTS.md rule 12), once per change, never per frame:

```
dw3-walkthrough: progress P half H area A -> chapter C step S (rule R) [probe mode 0xM]
```

Rules: `progress` (the progress value alone decided), `progress+flag` (an
`unlock` or `done` condition decided), `all-done`, and for no step
`below-table`, `above-table`, `unknown`, `gap`, `no-row-offered`.

### What the player sees

  player can have met it (`from_progress`); an unreached area shows `Not reached yet`.

  coming` ("The walkthrough covers the first chapter for now...") and every `ch01` step and area
  is reached, so the list shows them all.

  walkthrough from the list.
