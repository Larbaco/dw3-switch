## 1. Current flow (as-is)

### 1.1 Entry points

- The field menu (`createFieldMenu`, `engine/menu/field_menu.c`) lists the
  rows. Choosing one stores `FIELD_MENU_CHOICE.option` / `.extra`, runs the
  block dissolve and loads the `STSTATUS` overlay (US `0x1F9`, EU `0x207`)
  (doc: P6.33 1.1). `STSTATUS_runScreens` (`menu.c`) opens the screen from
  `STSTATUS_screens[extra][option]` and recreates the field menu when it
  closes (read).
- The port adds an OPTIONS row at the end (patches `0123`, `0160`, doc), so the
  field menu has up to eight rows. Row order and labels come from
  `FIELD_MENU_OPTIONS` (read in patch `0160`); the screen order is Items, Sort,
  Map, Techniques, Status, Card folders (second row set only) (doc: P6.33 1.1).

### 1.2 Items screen (`item_screen.c`, `item_list.c`)

| Step | What happens | Code |
|---|---|---|
| Option list | Five rows. Up/Down move, Cross opens the list (or shows an "empty" help line), Triangle closes | `STSTATUS_chooseItemList`, lists from `STSTATUS_itemLists = {1, 0x80000002, 0x80000003, 0x80000004, 0}` (read) |
| Item list | Two columns, 16 per page; L1 / R1 turn pages; the info panel shows the item, its help line, the equipped and owned counts | `STSTATUS_runItemList` state 2, `STSTATUS_moveItemListCursor` (read) |
| Cross | **Only** when `panel->list == 0` and `ITEM_USE_MENU` is set: `SOUND_SELECT`, go on to the partner step. Every other list, and a consumable without the flag: no branch, no sound, no state change | `item_list.c` lines 201 to 210 (read) |
| Partner step | The partner pages open; Up/Down choose the member; Cross calls `STSTATUS_useItem` and goes to substate `0x64`; Triangle goes back to the list | `STSTATUS_chooseItemMember` (read) |
| Back | `STSTATUS_leaveItemList` sends the flow to the partner step (`setSubstate(0x14)`) when `itemIndex >= 0`, back to the options at `-1` | `item_screen.c` 598 (read) |

Which of the five options holds weapons, armor and accessories is not
re-derived here: the owner's B19 test and the `us/eu-items-select-equip`
replay use the second option for weapons (doc). The exact kind-to-option map
is **unverified**; phase 1 must read it from `ITEM_FUNCS.list` and the item
kinds before relying on it.

### 1.3 Status > Equipment (`status_screen.c`, `equip_panel.c`)

1. Status row, `STSTATUS_chooseStatusMember`: Up/Down over the party pages
   (`screen->member`), Cross confirms (doc: P6.33 1.3).
2. `STSTATUS_runStatusChoice` step 5: two rows, row 0 Digivolve, row 1
   Equipment. Up/Down set `screen->option`; Cross goes to step 10; Triangle
   goes back to the member list (read, `status_screen.c` 557 to 640).
3. `STSTATUS_chooseEquipSlot`: six slots, Up/Down; Cross builds the list
   (`STSTATUS_slotLists = {6, 7, 5, 5, 4, 4}`: head kind, body kind, two weapon
   slots, two accessory slots, read), "none" first, then what the partner
   `canEquip`, then the rest; Triangle closes the panel (read, 268 to 312).
   Patch `0128` adds ZL / ZR here to change `panel->partner` (doc).
4. `STSTATUS_closeEquipSlots` sets `cursor = 0; scroll = 0` and the list opens
   at "none" (read, 314).
5. `STSTATUS_chooseEquipItem`: eight rows, L1 / R1 page by 8, stats preview
   through `previewStats(screen, slot, item)`; Cross on an item the partner
   `canEquip` calls `STSTATUS_equip` and goes to substate `0x14` (list and slot
   panel fade out, back to the slot list); Triangle restores the preview and
   goes to `0x14` (read, 363 to 457).
6. `STSTATUS_canEquip(partner, slot, item)` checks only the partner bit in
   `weapon.partners` and the hand kind against slots 2 and 3. It does **not**
   check that the item kind fits the slot: that is done by which list the
   slot opens (read, `helpers.c` 83 to 102). A new entry path must therefore
   choose the slot itself.
7. `STSTATUS_equip(partner, slot, item)` moves the counts between
   `GAME.items` and `GAME.equippedItems`, returns the old item to the bag,
   clears slots 2 and 3 for kind 7 (both hands), and swaps within the group
   for kind 8 (read, `helpers.c` 107 to 168). It is the only writer; every new
   path must go through it.

## 2. Problems

Numbering continues P6.33 section 2 (items 1 to 9 there stay valid; 1, 2, 5, 6
are partly solved by `0128` or open for phases 2 to 3).

1. **Equipment in the Items menu is a dead end** (P6.34 trigger). The item is
   listed, described, counted, and Cross is silent. A new player reads it as a
   bug.
2. **Equipping needs a different screen and four choices**: Status, member,
   Equipment, slot, then the item. From the Items list that is a full exit.
3. **Every equip fades the list and the panel out and back in**, and the list
   reopens on "none", not on the item just worn (P6.33 items 5 and 6).
4. **Moving an item between Digimon is manual** (unequip on A, equip on B)
   because worn items are not in the bag (P6.33 item 3).
5. **The bag is split across two screens** that do not know each other
   (Items lists it, Equipment shows only one slot's candidates).
6. **"Use item" asks for a partner and closes the list every time**
   (P6.33 item 8; owner decision 6 asks for the partner change without
   closing).
7. **The options and their order feel odd** (owner, 2026-10-27). The report is
   not specific. Candidates, all (unverified as the cause): the Status question
   puts Digivolve above Equipment although equipping is the common action; the
   field menu puts Items, Sort and Status apart while all three touch the bag;
   the equipment lists sit among the consumables in the Items option list.
   See owner question 8.
8. **The ZL / ZR cycle has no Options row** (the window is full at nine rows),
   so it is invisible and cannot be turned off from the game.
9. **No help text names the buttons.** The equip panel has no free text line
   (P6.33 phase 1 status), and the P6.30 Help has no page for these menus.

## 3. Principles

- Game widgets only, in phases 1 to 4: no new panel, no host-drawn layer. The
  layout then follows `0076` in 16:9 and is the PS1 layout in 4:3, as the owner
  required (decision 7, side list dropped).
- Every state change goes through `STSTATUS_canEquip` and `STSTATUS_equip`.
  No new writer of `GAME.items`, `GAME.equippedItems`, `PartnerStats.equip`.
  No save change. Menu structures (`ItemScreen.items`, `ItemList.items`,
  `EquipPanel.items`) are caches rebuilt on open; after any equip they are
  rebuilt or the flow leaves them through a path that rebuilds them.
- Buttons are logical: `PAD_CROSS` confirm, `PAD_TRIANGLE` cancel, `PAD_SQUARE`,
  `PAD_L2`, `PAD_R2`. Text never hard-codes "A", "B", "ZL" or "ZR": it asks the
  controls module for the current physical name (P9.8 / P10.6 API, name
  **unverified**; until it lands the help page uses the PS names).
- Each behavior is a file key, on by default only once approved; with the key
  at 0 the code path is the original game and replay references match the PS1
  frames. Keys get an Options row in a new **Menus** group (phase 5) instead of
  staying file-only.
- Text: prefer the game's own strings (already in five languages on EU). Any
  new string exists in EN, FR, DE, IT, ES at launch (table in 7). The US disc
  has English only; the port strings still ship all five, selected by the same
  language the port already uses for Options (doc: PORT_OPTIONS).
- Turbo: result messages and holds count game frames, not wall time (as the
  game's own timers do). Cross is consumed by a substate change in the same
  frame, so 1.5x cannot double-fire it.

## 4. Proposed flow and phases

Smallest shippable first. Each phase is its own PR with its own key, patch,
scenarios and OLED items. Order is by owner value and risk.

### Phase 0: decisions

Owner answers to section 10. No code. Done when questions 1 to 4 and 8 are
answered (the others have a usable default).

### Phase 1: equip from the Items menu (smallest, the trigger)

Flow: Items > equipment option > list; **Cross on a weapon, armor or accessory
opens the partner step** the consumables already use; the partner the item can
go on is chosen with Up/Down; **Cross equips**; the result line says what was
worn and what returned to the bag; the flow returns to the list, rebuilt.

Details:

- Hook 1, `STSTATUS_runItemList` state 2, `item_list.c`: where patch `0180`
  logs today, when the key is on and the item is equipment, play `SOUND_SELECT`,
  set `itemIndex`, `item`, call `STSTATUS_showItemHelp(screen, -1)` and
  `substate++`, exactly the consumable path. The existing `STSTATUS_leaveItemList`
  then sends the flow to substate `0x14` (read).
- Hook 2, `STSTATUS_chooseItemMember`, `item_screen.c`: on Cross, if the item is
  equipment, call a port function instead of `STSTATUS_useItem`:
  `dw3_port_items_equip_from_items(partner, item, &slot)`. It refuses with the
  game's cursor sound when `STSTATUS_canEquip` is 0 (partner not in the mask),
  without leaving the step. Otherwise it picks the slot, calls
  `STSTATUS_equip`, and the flow continues in the same result substate (`0x64`
  and following) with a different help string.
- Slot rule, a pure function in `port/items_menu/` (unit test, no game
  structs). From the slot lists (read) and `EQUIP_KIND_*`
  (`engine/game_state.h`, read): kind 4 head: slot 0; kind 5 body: slot 1;
  kind 1 right hand: slot 2; kind 2 left hand: slot 3; kind 3 either hand: the
  first empty of 2 and 3, else slot 2; kind 7 both hands: slots 2 and 3
  (`STSTATUS_equip` fills both); kind 6 and 8 accessories: the first empty of
  4 and 5, else slot 4 (kind 8 replaces the same group, as `STSTATUS_equip`
  does). Whether the item kinds in the Items option lists match
  `STSTATUS_equipKinds` for every item is **unverified**; the slot function
  logs `rule=unmapped` and does nothing for a kind it does not know, and the
  scenario walks every kind present in the test bag.
- The partner step shows portraits only. Partners that cannot equip are not
  greyed (no new art): Cross is refused with a log line and no state change.
  A greyed marker is an option only if the page draw can be reused
  (**unverified**; see question 4).
- After the equip, the stale caches matter: `GAME.items[item]` dropped, so the
  item may leave the list. The flow must reopen through the existing
  `STSTATUS_reopenItemList` path, which has to be read to confirm it calls
  `ITEM_FUNCS.list` again (**unverified**); if it does not, the hook rebuilds
  `screen->items` and `screen->itemCount` before reopening and clamps the
  cursor.
- Key: `items_equip_from_items`, default 1 once approved (starts at 0 in the
  PR if the owner has not answered question 1). With 0, patch `0180`'s log runs
  as today.
- Patch: one, `0188` (`item_list.c`, `item_screen.c`), plus policy and strings
  in `port/items_menu/`.

### Phase 2: equip without the long round trip (P6.33 phase 3)

Today each equip fades the list and slot panel out (substate `0x14`) and the next
open resets `cursor` and `scroll` (read). Proposal: after Cross, skip the
fades and return to `STSTATUS_chooseEquipSlot` directly with the slot cursor
unchanged (needs the item list's rebuild: counts changed, old item back in the
bag, scroll bar range). Reopening the list on the **equipped row** (not "none")
is a separate small hook in `STSTATUS_closeEquipSlots` / `STSTATUS_enterEquipList`.
Keys `items_equip_stays` (default 1 once approved) and the list opens on the
current item. Patch `0190` (`equip_panel.c`; `0189` was taken by P51). Decision between "stay in the
list" and "back to the slot list" is question 6.

### Phase 3: whole bag, move between Digimon (P6.33 phase 2)

Square on the equip item list cycles the filter: this slot (as now), all
weapons, all armor and accessories, worn by others (decision 2, bag proposal).
Rows worn by another partner carry a note naming the wearer; Cross does
`STSTATUS_equip(other, slot, 0)` then `STSTATUS_equip(me, slot, item)`. One
count line shows the bag count of the shown kind and per row the worn-elsewhere
count (`GAME.equippedItems`). Filling uses `STSTATUS_listItems` with another
list index; no new panel. Patch `0192` (`equip_panel.c` only; built, see section 14). Key
`items_bag_view`. The same move can be offered in the Items-menu partner step
of phase 1 for an item that exists only as "worn": **not proposed**, because
worn items are not in the Items lists (read: they are in `equippedItems`, not
`items`).

### Phase 4: Items screen quality (P6.33 phase 4, the rest)

"Use item" returns to the list after use instead of closing it, so three
potions on three partners are not three round trips (decision 6); the partner
step keeps its Up/Down choice and may also take ZL / ZR with the same
`dw3_port_items_partner_next` helper as `0128`. Patch `0193`
(`item_screen.c`). Key `items_use_stays`. The "Items link to Equipment" jump of
P6.33 phase 4 is **superseded by phase 1** (the player equips from the Items
menu, so the jump is not needed); question 9 asks to confirm.

### Phase 5: Menus group, order and help

- A **Menus** group in Options (the P9.9 sub-screen style, drawn by the port:
  dimmed title, plaque rows, the same cursor and message line) with one row per
  key: Equip from Items, Partner switch, Equip stays, Bag view, Use stays. This
  also gives `items_partner_switch` its missing row (problem 8). Rows are
  disabled in game only if a key must not change mid-menu; these can change
  anywhere, since the hooks read the key per press. Whether a new group needs a
  hook beyond `port/options/` is **unverified**; none is expected.
- Order, only after question 8: a table-only reorder (Status question rows, or
  field menu rows) behind `menu_order`. Not built until the owner says which
  order feels right. If built, patch `0194`. The reorder must keep the saved
  field-menu cursor (`FIELD_MENU_CHOICE.option`) consistent, which is
  **unverified**.
- A **Help page** "Items and equipment" in the Help group (page engine,
  `port/help/text/<lang>.txt`): the flow in four lines, with the buttons by
  their current physical names. It ships with the five languages like every
  Help page (P6.30 rule).

## 9. Risks

| Risk | Mitigation |
|---|---|
| Stale menu caches after an equip (`ItemScreen.items`, `ItemList.items`, `EquipPanel.items`) cause a wrong cursor or a ghost row | rebuild through the reopen path; `list rebuilt` log; scenario equips the last unit of a stack |

### 12.1 The "unverified" points phase 1 depended on

| Point | Result | Where |
|---|---|---|
| Option-to-kind map | Option 0 of the Items screen is list 1 (usable); options 1, 2, 3 are `ITEM_LISTS[2..4]`: weapons, armor, accessories (`STSTATUS_itemLists = {1, 0x80000002, 0x80000003, 0x80000004, 0}`, `ITEM_LISTS = {KEY, USABLE, WEAPON, ARMOR, ACCESSORY}`). **The list is not the equip kind.** `ItemInfo.kind` (the list) and `record->weapon.kind` (the slot rule) differ: the weapons list holds kinds 3 (92), 7 (23) and **4 head (8 items)**; the armor list holds 4 (34), 5 (26) and **2 left hand (17 shields)**; the accessories list holds 6 (24) and 8 (44). Kind 1 (right hand) is used by no item. So the slot is chosen from the record kind, never from the option | `engine/game/items.c` tables, counted by a script over `WEAPON_DATA`, `ARMOR_DATA`, `ACCESSORY_DATA` and `ITEMS` |
| Is the list rebuilt after an equip | Yes. The used-item path rebuilds it itself: `STSTATUS_confirmItemUsed` calls `ITEM_FUNCS.list(STSTATUS_itemLists[option], screen->items)`, then `STSTATUS_reopenItemList` creates the list again on `screen->item` (`STSTATUS_createItemList` re-fills it with `STSTATUS_fillItemList`). Phase 1 reuses substates `0x64` / `0x65` and needs no rebuild of its own; one log line reports the count and the cursor | `item_screen.c`, `item_list.c`; log `list rebuilt` |

Worn items are therefore in the Items lists. Cross on such an item has nothing to equip: phase 1 refuses it (`reason=not-in-bag`, no sound change) | `engine/game/items.c` `listItems` |
| Glyph coverage for the EU strings | The game's text window takes bytes, not Latin-1. Glyphs (byte - 4 indexes the sheet): digits 4..13, A to Z 14..39, a to z 40..65, then kana, and only `? ! ~` and a mid dot at 229..233; **no period, apostrophe or accent among the glyphs**. ## 13. Phase 2 built (2026-10-29): equip stays on the slot list

Patch `0190`, key `items_equip_stays` (default 1, file-only, `DW3_ITEMS_EQUIP_STAYS=0`
for a run), `equip_panel.c` and `port/items_menu/`. Built by an agent after the
orchestrator told it to proceed with the section 10 defaults, **so Q6 is an
orchestrator default pending owner confirmation, not an owner answer**: back to
the slot list without fades, slot cursor kept, the list opens on the equipped
row. The other questions are as in section 12.

### 13.1 Findings

* **What the round trip is** (read, `equip_panel.c`): entering the list runs
  substates 10 to 15 (slots and title out, slot item and list in, four 10-frame
  `PanelAnim` fades, set in `STSTATUS_updateEquipPanel`); Cross on an item goes
  to `0x14` to `0x16` (list and slot item out), then substate 0 to 3 (title and
  slots in). Nothing else is reset: `panel->slot` and the slot cursor window
  survive, so "cursor kept on the slot" costs nothing.
* **Shortening, not skipping.** The fades are in game code outside the decomp's C
  (`STSTATUS_startFade`, `STSTATUS_updateFade` are asm). Rather than bypass the
  state machine, the patch sets the four `PanelAnim.duration` to 1 for the return
  and restores 10 when `STSTATUS_chooseEquipSlot` runs again. Measured on the PC
  build, US and EU: the panel is back on the slot list **9 frames** after Cross
  (`equip-stays ... frames=9`). The entry fades (slot list to item list) are
  untouched; Triangle (cancel) is unchanged and takes the long way back.
* **The worn item is usually not in the list.** `STSTATUS_slotLists` have no "all"
  flag, so `listItems` returns only items with a copy in the bag
  (`GAME.items > 0`); an item worn from a single copy is absent, and the list opens
  on "none" as in the original. With a spare copy (the replay bag has three of
  each) the list opens on that row: cursor, stat preview, help line and scroll bar
  (US: follows the item; EU: follows the page) are set for it, and a list longer
  than eight rows is scrolled so that three rows show above it.
* **Cursor at rest after a reopen.** In both flows (key on and off, and in the
  pre-patch build) the list cursor arrow is not drawn when the list is reopened
  until the cursor first moves (screenshots 220 frames after Cross, US). This is
  the original game's behavior (the `Cursor` task swings its arrow and the
  reopened window comes back without it); phase 2 does not change it. The row is
  still logged in `list-open`, and the arrow shows after the first Up or Down.

## 14. Phase 3 built (2026-10-29): the whole bag and moving an item between Digimon

Patch `0192`, key `items_bag_view` (default 1, file-only, `DW3_ITEMS_BAG_VIEW=0`
for a run), `equip_panel.c` and `port/items_menu/`. Built by an agent after the
orchestrator said to proceed with the recommended defaults, so **the P6.33
decisions it implements (2: the whole bag; 3: move between Digimon, a note
naming the wearer) are the owner's, but every detail below is an orchestrator
default pending confirmation**: filter order, titles, where the note goes, who
counts as "others", what happens to the vacated slot, and the five-language
drafts.

### 14.1 What it does

In Status > Equipment, in the item list (after Cross on a slot), **Square**
cycles the filter and wraps:

| Filter | Rows | Title (EN) |
|---|---|---|
| 0 this slot | the original list (no title change) | the slot's name |
| 1 all weapons | `ITEM_FUNCS.list(2)`: every weapon-list item in the bag, the ones that fit this slot first | `All weapons N` |
| 2 all armor and gear | `list(3)` then `list(4)`: armor and accessories in the bag, the ones that fit first | `Armor and gear N` |
| 3 worn by others | one row per item another **party member** wears that fits this slot and this Digimon can wear | `Worn by others N` |

`N` is the row count without "None". The cursor goes to "None" on every change,
the stat preview shows the slot emptied (as when the list opens), the scroll bar
is rebuilt for the new count (123 weapons, 145 armor and accessories in the test
bag, so a long list is normal) and the filter returns to 0 each time the list is
opened from the slot list. Rows that do not fit are grey and Cross does nothing
on them, exactly as in the original list (the filters 1 and 2 are a browsing
view of the whole bag; filter 0 and 3 are where equipping and moving happen).

In filter 3 the count column shows how many copies the others wear (not the bag
count), and the line under the help text reads `Worn by <name>` for the chosen
row (in the five languages; it replaces the weapon-kind line of slots 2 and 3
while that filter is shown). Cross takes the item from its wearer
(`STSTATUS_equip(wearer, wearer_slot, 0)`) and puts it on this Digimon
(`STSTATUS_equip`, which returns whatever was in this slot to the bag); the
phase 2 return to the slot list follows. The vacated slot stays empty; the
displaced item goes to the bag, it is not handed to the other Digimon. A
two-handed weapon is one row. `STSTATUS_equip` remains the only writer of
`GAME.items`, `GAME.equippedItems` and `PartnerStats.equip`.

### 14.2 Findings

* **Most weapons are not shareable.** The partner mask (`WeaponData.partners`)
  of most weapons names one Digimon (a few name two, `0xC0`), so the
  worn-by-others list of a weapon slot is usually empty for everyone else: the
  weapon the replay's first Digimon wore (item 132) was not a row for the
  third. The move matters for armor and accessories (masks like `0xFF`); the
  replay uses the first accessory slot. Items the other Digimon wears but this
  one cannot wear are not rows (not greyed): `STSTATUS_canEquip` gates the list.
* **"Others" are the current party** (`screen->count` members). Digimon that are
  not in the party (the farm) are not reachable from this screen, so their items
  cannot be moved here.
* The "none" row stays first in every filter. Cross on it unequips this slot as
  before.
* The list rows are `TextWindow`s that keep their text when the count shrinks,
  so the cycle hides all eight rows before refilling. The scroll bar of the old
  list is killed (`state = 3`) and the pointer cleared; the original code leaves
  the pointer of a closed bar in `windows->scrollBar`, which this patch never
  reads.
* Square is not used by any Status screen in the original game. With the
  Nintendo layout it is Y (the P6.12 remap moves it with the other buttons).
