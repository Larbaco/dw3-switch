# P5.2 — Battle mesh on GLES (approach A)

Status: ticked on `main` (2026-10-15) after owner OLED feedback. With
`gpu-tex` the battle sky is fixed and battle runs above 60 fps easily, on
both the US and EU discs. Field was already near 60 Hz. The done-when
(no frame over 16.7 ms, docked and handheld) has no recorded per-mode
frame-time numbers, so it rests on that qualitative report. Owner follow-ups
still open: MonMon's eye artifact, geometry passing in front of the camera
during the idle orbit, and an FPS drop when the Port options selection
changes. Owner-approved approach A.
**preview.9 regressed** (FPS + field graphics); gate + dirty sample upload
follow-up was the recovery path (see below). Soft battle was the default after
all-black FBO dumps. **The flat-blue GPU battle has a root cause and a fix
(see "Flat-blue GPU battle — root cause" below). After #114 merged, the owner
reported that GPU battle rendering works well in-game. The owner later requested gpu-tex as the default; the
preview.22 follow-up implements that request with the known sky limitation
documented below.** For alternatives beyond re-enabling
full textured mesh, see [P5.2_BATTLE_GPU_IDEAS.md](P5.2_BATTLE_GPU_IDEAS.md).

## `gpu-tex` default (2026-10-14, preview.22 OLED feedback)

Battle now cold-boots in `gpu-tex` (`DW3_NX_MESH_SOFT_BATTLE` is OFF by
default; `-DDW3_NX_MESH_SOFT_BATTLE=ON` or `DW3_MESH_SOFT=1` seeds soft).
The owner's blocking finding, the **missing Digimon picture in the
right-hand panel**, was the partner view (`FIGHTSTG_updatePartnerView`):
a 3D model drawn in its own 100×60 layer beside the menus. Its triangles
went to the mesh FBO, and the present draws CPU VRAM (the panel) over the
whole FBO. `switch_gpu.c` now keeps triangles drawn into a drawing area
smaller than the screen (`mesh_area_is_screen`) on the software path, in
OT order like soft, and flushes queued mesh triangles when the drawing
area changes (the scissor is applied at flush). Ryubing US and EU: the
stage renders and the partner picture shows beside Fight/Tech.

### preview.25 OLED feedback (2026-10-14)

The following are source-level fixes for the owner report. Visual acceptance
in-game (portrait eyes, HUD after battle, and title after battle/save/restart)
is pending; builds and unit tests alone do not establish that acceptance.

- **Artefacts in the partner's eyes.** The UI composite (`UI_FS` in
  `nx_gpu.c`) discards black CPU VRAM so the mesh FBO shows through, and
  the partner view's black pixels (the pupils) went with it, showing the
  battle stage behind. A black texel the game draws is 0x8000 (0x0000 is
  transparent and never drawn), so the VRAM pack now carries bit 15 in
  alpha, and inside the partner view's drawing area (noted by
  `switch_gpu.c` when it keeps that view's triangles on the software
  path, `dw3_nx_mesh_note_soft_view`) black with bit 15 stays. Elsewhere
  the old rule holds: additive effects drawn black with bit 15 must not
  turn into black boxes over the stage.
- **Dark debug HUD after a battle; black title menu and logo after a
  restart that follows a battle.** `set_blend` left the last batch's
  blend equation current. A subtractive batch (the battle fade-out) left
  `GL_FUNC_REVERSE_SUBTRACT`, so every later blended overlay subtracted
  itself from the frame. The mesh flush now restores `GL_FUNC_ADD` and
  disables blending, and both overlays set the equation themselves.
- **Idle camera moving wrong.** Not a renderer issue: see
  `GsSetRefView2` in [P3_GPU_GLITCHES](P3_GPU_GLITCHES.md#gssetrefview2-super-preview25-feedback-2026-10-14).

Open, pre-existing (same on `main` in `gpu-tex`, Ryubing): on the
cliff/sky battle stage the mesh FBO has opaque black where the sky dome
(`POLY_FT4` 0x2C, 4bpp tpage 640,0, CLUT at 672,255) samples index 0,
whose CLUT colour is 0x0000 (transparent: soft skips it and the blue
background shows). `MESH_FS` returns `vec4(0)` for a 0x0000 texel, which
with the mesh's blending enabled should leave the FBO untouched, so the
shader is probably sampling a different texel or CLUT entry than soft
does there; not root-caused yet. Soft (Minus+ZL+ZR) draws that sky
correctly.

## Flat-blue GPU battle — root cause (2026-10-13)

Symptom (preview.10 / preview.18 OLED, PR #89): `gpu-solid` and `gpu-tex`
show a flat stage-blue (≈ 59,115,233) field with the HUD on top, while
`tris_flush` is huge. PR #89's DIAG runs proved present, FBO and packet
vertices all work (cyan/green markers; `gpu-tex` under `mesh_only_diag`
showed the 3D). What it did not identify is **what painted the blue over
the mesh**.

Cause, end to end:

1. `FIGHTSTG_fadeStage` / `prepareStageModel`
   (`vendor/dw3_decomp/src/battle/battle_mode/stage.c`) call
   `SCREEN_LAYER->setBgColor`, which sets `isbg = 1`
   (`src/engine/gfx/layer.c` `layerSetBgColor`); the layer's DR_ENV is
   built with `SetDrawEnv` (`layer.c:146`).
2. PSY-Z `SetDrawEnv` (`vendor/psyz/decomp/src/libgpu/sys.c`, `isbg`
   block) encodes the background clear as an **opaque GP0 `0x60` TILE**
   over the clip rect (`rect = clip - ofs`), not a `0x02` fill. So it
   never reaches `Draw_ClearImage`; it goes through `Draw_PushPrim`.
3. `try_push_mesh_poly` only takes triangle polys, so the TILE fell to
   `software_rasterizer.push_prim` and filled the CPU VRAM draw area with
   the stage colour (logged as rgb555 `7,14,29`).
4. The mesh+ui present (`nx_gpu.c`) blits the mesh FBO, then the CPU VRAM
   with a discard of **exact black only**. The whole draw area was blue,
   so the blue layer covered the correctly rendered 3D. During the fade-in
   the colour is `1,1,1` → rgb555 0 (black), which is why some captures
   looked black instead of blue.
5. The mesh FBO itself was never cleared between frames (only a `0x02`
   `Draw_ClearImage` cleared it), so stale triangles accumulated.

Fix (`switch_gpu.c` `try_mesh_bg_fill`): in GPU battle modes an opaque
`0x60` TILE that covers the whole drawing area flushes queued triangles
(OT order), clears the CPU VRAM area to 0 (transparent for the composite)
and fills the mesh FBO with the 15-bit colour
(`dw3_nx_mesh_fill_bg`, which also marks the frame as mesh content). An
opaque full-area rect overwrites every earlier pixel in both layers, so
this is exact. Smaller tiles (UI boxes), mask-check draws, soft modes and
the field are untouched. Log: `nx_mesh: bg fill -> FBO rect=… rgb555=…`.

Evidence (Ryubing, headless Xvfb, forced encounter 1 = Pharaohmon vs
Kotemon, `gpu-tex`, raw runs under `/tmp/dw3-battle-gpu-rca-runs/`):

| Build | Screen | CPU VRAM display dump | Mesh FBO dump |
|---|---|---|---|
| `main` + test env | flat blue + HUD (owner's symptom) | 76800/76800 non-black (fill) | 75844/76800 non-black, stage + both fighters |
| fix | stage + fighters + HUD | 7590/76800 non-black (HUD only) | same 3D |
| soft (reference) | stage + fighters + HUD | — | — |

The fixed `gpu-tex` frame differs from soft only in rasterization edges,
idle-animation phase and the ordering limitation below.

Ruled out along the way: shader compile/link, FBO completeness, present
band / viewport (PR #89 cyan/magenta markers), packet vertex transform
(PR #89 green solids), texture/CLUT sampling (the FBO dump above is
textured and correct), dFdx/dFdy UV drift. The preview.10 "all black"
dump was a 21-triangle prologue frame during the black fade, not evidence
that fragments write nothing.

Known limitation (unchanged design): CPU VRAM is always composited on top
of the mesh, so a soft 2D primitive that the OT draws *under* a later
triangle still shows on top (e.g. the sparkle dots inside the black spirit
gauge under the enemy plate), and true-black UI texels are transparent.

## Sample upload: dirty rect (2026-10-13)

`Draw_LoadImage` / `Draw_ClearImage` / `Draw_MoveImage` now record the
written VRAM rect (`dw3_nx_mesh_mark_vram_dirty_rect`); the next flush
packs and uploads only the union box instead of the full 1024×512
(≈2 MB). Wrapping transfers still mark everything. In the Ryubing fight
`mesh dbg:` showed 0–8 uploads of 64–512 texels per 60 frames (CLUT
updates) where `main` re-uploaded the whole VRAM on most frames.
`mesh dbg:` now also prints `uploads=` and `upload_px=`. The
`mesh gpu: … tris flushed` log line is limited to once per 100k triangles
(it was written to `dw3.log` on every battle frame).

## Ryubing battle recipe

Ryubing cannot pass an environment to a homebrew NRO, so a development
NRO bakes one in with the CMake string `DW3_NX_TEST_ENV` (comma-separated
`K=V`, empty by default, applied with `setenv` at the top of `main`):

```bash
# custom build dir; same docker image as tools/build_switch_game.sh
cmake ... -DDW3_NX_MESH_SOFT_BATTLE=OFF -DDW3_NX_DUMP_VRAM=ON \
  -DDW3_NX_DEBUG_MESH=ON \
  "-DDW3_NX_TEST_ENV=DW3_START_MODE=0x600,DW3_FORCE_ENCOUNTER=1,DW3_MESH_SOFT=0,DW3_DUMP_MIN_PRIMS=30000"
```

`DW3_START_MODE=0x600` boots straight into battle after `newGame`,
`DW3_MESH_SOFT=0|1` seeds `gpu-tex` or `soft`, and `DW3_DUMP_MIN_PRIMS`
delays the one-shot dump (`dump_vram_display.ppm`, `dump_mesh_fbo.ppm`) to
a steady Fight frame; in GPU modes the dump now waits for a mesh+ui
present. Run it with the isolated-SD Ryubing harness (Xvfb, dummy audio,
restore trap) and read `INFOF` lines from the guest `dw3.log`. Never set
`DW3_NX_TEST_ENV` for a release or preview NRO.

## Problem

OLED `v0.6.5-preview.8` (map preload): field sits near 60 Hz
(`frame dt us` mean ~1000279 per 60 VSyncs). Battle Fight-menu idle is
about 46 Hz (mean ~1293264 across three fights). PC `sdl3_gpu` draws the
same scene without `RasterTriangle` (~1.6 ms CPU, VSync-bound). Switch
still routes every `Draw_PushPrim` through PSY-Z's software rasterizer and
presents RGB555 via GLES.

PC census (Fight menu, see agent note `battle-pc.txt`): ~1115 clipped
textured triangles / frame, ~347k bbox pixels; software fill alone is on
the order of ~5 ms on that desktop.

## Decision

**Route battle mesh triangles (POLY_GT / POLY_FT and other OT triangle
polys that today call `RasterTriangle`) through a GLES3 path on Switch.
Keep sprites / tiles / lines on the software VRAM path and the existing
RGB555 present blit.**

This mirrors PC `sdl3_gpu` / `sdl3_gl` packet handling without rewriting
`RasterTriangle` and without patching upstream PSY-Z.

**Gate (post-preview.9):** mesh enqueue is allowed only while the tracked
mode overlay file is `FILE_FIGHTSTG` (US `0x159` / EU `0x167`), via
`dw3_overlay_current_mode_file()`. Field and every other mode keep the
full software path and the opaque present blit.

## Layering

```
Draw_PushPrim (switch_gpu.c)
  ├─ triangle poly + FIGHTSTG mode → nx_mesh enqueue → flush into mesh FBO
  └─ else (field / menus / sprites / …) → software_rasterizer → CPU VRAM

Psyz_VideoVSync present (nx_gpu.c)
  1. letterbox clear
  2. if mesh had content: blit mesh FBO, then CPU VRAM with zero-color discard
  3. else: opaque CPU VRAM blit (preview.8 behaviour)
  4. eglSwapBuffers
```

- Textures / CLUTs stay in CPU VRAM (`Draw_LoadImage`); the mesh flush
  uploads that VRAM as a sample texture (RGB555 with STP in alpha).
  Upload runs only when VRAM is marked dirty (Load/Clear/Move), not on
  every OT flush, and covers only the dirty box.
- `Draw_ClearImage` clears both CPU VRAM and the matching mesh FBO rect
  (battle only).
- The DRAWENV background fill (opaque `0x60` TILE over the drawing area)
  clears CPU VRAM to 0 and fills the mesh FBO in GPU battle modes (see the
  root-cause section).
- Ordering assumption for battle: mesh then UI in the OT. Interleaved
  sprite-over-mesh mid-OT is a known risk (document if seen).

## preview.9 OLED regression (2026-10-11)

Tag `v0.6.5-preview.9` @ `042986f` (game tip `973daf3` #69). Mesh path
**did** activate (`nx_mesh: GLES3 mesh FBO ready`, `mesh gpu:` lines).

| Scene | preview.8 | preview.9 | Notes |
|---|---|---|---|
| Field steady | ~1000279 (~60 Hz) | ~1436113 (~41.8 Hz) | ~1.44× slower |
| Battle Fight-menu idle | ~1293264 (~46 Hz) | ~2931384 (~20.5 Hz) | ~2.27× slower |

**Root cause (field):** `try_push_mesh_poly` accepted any OT triangle
(`code & TRIANGLE`), including field interiors. Field also uses POLY_GT /
POLY_FT. That meant:

1. ~1000 mesh tris / field frame (nxlink counter deltas ~1008).
2. Each flush packed+uploaded full **1024×512** CPU VRAM as RGBA8
   (`upload_sample_vram` in `nx_mesh.c`).
3. Present composited mesh + **black-discard UI** over the software blit,
   which punches through cleared / zero texels and destroys field draws.

**Visual defects on field (owner OLED photo, Asuka clinic/inn interior):**

1. Thick vertical blue/cyan stripe column on the far left.
2. Large dark grey/black oval blobs on the teal rug.
3. Missing upper wall/ceiling → flat black/blue voids.
4. Sharp horizontal blue lines from the right edge.
5. Bright yellow/teal rectangular outline on the floor.
6. Thin bright cyan vertical line by the stairs.
7. Solid blue geometric blocks around room edges / background.

Sprites near the counter looked intact — consistent with “3D OT via mesh +
discard composite” vs software 2D. Preview.8 did not show this.

**Battle slowdown:** same full-VRAM upload path on every flush, plus discard
composite, without removing enough software work to win. Fight-menu idle
got worse, not better.

Photo / notes (not in git): Cursor project
`notes/preview9-oled.txt`, `notes/preview9-regress.txt`, asset
`image-ed2a6f18-3a0a-44bd-8d94-08d97f43a6bb.png`.

## Recovery (this follow-up)

1. **FIGHTSTG gate** — field returns to software `RasterTriangle` + opaque
   present (preview.8 field look / target ~60 Hz).
2. **Dirty sample upload** — skip full VRAM pack when VRAM unchanged since
   the last upload (helps Fight-menu idle).
3. Discard pending mesh when leaving battle so no stale composite.

Battle 60 Hz and GLES field parity remain open. If gated battle is still
slower than preview.8 software, prefer keeping the gate and further
upload/batch work — or temporarily leave mesh off for a preview — rather
than re-enabling field mesh.

## Image fidelity (known diffs)

| Area | Expectation |
|---|---|
| 4-bit CLUT + gouraud | Aimed at playable match via ES3 shader (from PSY-Z `sdl3_gl`) |
| Dither | Env bit + AUTO/OFF; may differ slightly from software |
| Semi-transparency / ABR | Approx with GLES blend; subtractive ABR is best-effort |
| UI / sprites | Unchanged software path |
| Zero-color discard | UI overlay drops `(pix & 0x7FFF) == 0`; rare true-black UI texels can punch through to mesh |
| Field | Must not use mesh until a dedicated field path is correct |

## Out of scope (this change)

Overclock, CD/tile pacing, movie/XA, save rewrite, empty-bbox skip as the
main fix, rewriting the whole PSY-Z software rasterizer, upstream PSY-Z PR,
field GLES mesh parity.

## Fallback

If the EGL ES3 context or mesh program fails to init, `Draw_PushPrim`
keeps the full software path (pre-change behaviour). Non-FIGHTSTG modes
always use that path even when mesh init succeeds.

### Soft battle escape (default ON)

`DW3_NX_MESH_SOFT_BATTLE` (CMake, **default ON**) keeps the FIGHTSTG gate
but forces OT triangles through software `RasterTriangle` and the opaque
VRAM present. Boot / mode changes log
`nx_mesh: battle_mode=soft` (GLES mesh off).

- Re-enable GLES mesh for triage: configure with
  `-DDW3_NX_MESH_SOFT_BATTLE=OFF` (or runtime `DW3_MESH_SOFT=0` if the
  environment is visible to the NRO — seeds `gpu-tex`).
- Force software even when the CMake default is off: `DW3_MESH_SOFT=1`.
- **Runtime A/B (OLED):** edge chord **Minus + ZL + ZR** cycles
  `soft` → `soft+bbox` (stub=soft) → `gpu-solid` (NOTEXTURE vertex colour) →
  `gpu-tex` → … Field never uses mesh. HUD shows `battle=…` when the
  debug overlay is on. See [DEBUG_OVERLAY.md](DEBUG_OVERLAY.md) and
  [P5.2_BATTLE_GPU_IDEAS.md](P5.2_BATTLE_GPU_IDEAS.md).

Use soft battle for recovery previews until a mesh FBO dump shows
`mesh_nonblack > 0` on a steady Fight-menu frame.

## preview.10 dump finding (2026-10-11)

Tag tip `bf41482` (#74) + FIGHTSTG gate. FTP PPMs verified all-black
(`nonblack=0/76800` for both `dump_vram_display.ppm` and
`dump_mesh_fbo.ppm`, 320×240).

| Observation | Meaning |
|---|---|
| Field `tris_enq=0` / `frames_blit` | Gate OK |
| First `present path: mesh+ui` at **21** tris | Dump fired on prologue frame |
| Later `tris_flush` tens of thousands / 60f, `frames_mesh=60` | Mesh enqueue/flush “works” |
| `mesh_nonblack=0` and `vram_nonblack=0` on display rect `0,256` | Mesh FBO display band empty; CPU VRAM band empty (expected if 3D skipped software) |
| Owner solid blue (earlier) | Likely `ClearImage` colour left in the FBO / present while textured fragments output zero; dump captured black prologue or black clear |

**Root cause (present), superseded 2026-10-13:** mesh+ui composites a black
(or clear-only) mesh FBO and black-discards UI, so the fight picture never
reaches the opaque blit. The real cause is the software-filled DRAWENV
background covering the FBO; see "Flat-blue GPU battle — root cause".
Huge `tris_flush` only proves vertices were submitted, not that texels
survived the ES3 sample path.

**Dump fixes:** defer until `prims_flushed ≥ 2000`, `glFinish` before
`glReadPixels`, also write `dump_mesh_fbo_y0.ppm` (other double-buffer
band), dump on soft FIGHTSTG opaque presents too.

**Mesh hardening (when soft is OFF):** nearest UV without `dFdx`/`dFdy`;
mark sample VRAM dirty on FIGHTSTG enter.

## Nxlink mesh debug

For OLED FPS / path triage after the FIGHTSTG gate, build
`./tools/build_switch_game.sh --nxlink` (stdio + sampled `mesh dbg:` summary).
Expect field windows with `tris_enq≈0` / `frames_blit`. With soft battle
