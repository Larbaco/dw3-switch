# P6.15 Regression replay tests

One command replays recorded pad input on the US build and the EU build and
diffs checkpoint screenshots against references. Since the second version it
goes past the title menu (new game, opening, first field, map transitions, a
17-20 minute soak) and gives crash, hang and memory verdicts that are
separate from the image diff. A second runner replays the same recordings on
the Switch build inside Ryubing.

```bash
# once: build the PC host for both discs (separate trees, see docs/P3_EU_BUILD.md)
tools/replay_tests.sh --build --update   # build, run, write references
tools/replay_tests.sh --quick            # title menus only (the original set, ~1 min)
tools/replay_tests.sh --single --launcher PATH  # P6.24: the title recordings through the region launcher (only US, only EU, both)
tools/replay_tests.sh                    # + gameplay scenarios (~6 min per scenario, 3 in parallel)
tools/replay_tests.sh --soak             # + the 15-20 min soak scenarios (~16 min each)
tools/replay_tests.sh --twice            # run each scenario twice; captures must be identical
tools/replay_tests.sh --only us-field-walk --only eu-field-walk
tools/replay_tests.sh --list
```

Needs `Xvfb`, ImageMagick `import`, and `python3-pil`. Every scenario gets its
own Xvfb on a free display (`-displayfd`, 1280x960); your real display is
never touched. Useful flags: `--only <scenario>`, `--jobs N` (default 3),
`--stall SECS`, `--timeout SECS`, `--no-turbo`, `--refs DIR`, `--out DIR`,
`--bin-us/--bin-eu PATH`, `--runtime-us/--runtime-eu DIR`, `--scen-dir DIR`.
Relative paths are resolved from the directory where the command is started.
Unknown `--only` names, missing checkpoints, duplicate checkpoint names, and
checkpoint frames outside `1..UINT_MAX` or not strictly increasing are errors.
Defaults: binaries `build/pc/dw3-pc` and `build/pc-eu/dw3-pc` (or `--build`),
runtimes `runtime/{us,eu}` then `~/.cache/dw3-switch/runtime/{us,eu}`
(own-disc, see `docs/DISC_SETUP.md`), references
`~/.cache/dw3-switch/replay-refs`, results `tmp/replay/<timestamp>/`
(per-scenario captures, timestamped run logs, `report.txt`, diff images).

## Design

| Decision | Choice | Why |
|---|---|---|
| Targets | PC host (`dw3-pc`, sdl3_gpu/lavapipe) under Xvfb for the picture diff; the Switch build in Ryubing for a log-only check (`tools/replay_ryubing.sh`) | The PC host is deterministic and headless. Ryubing has no pixel-stable output (its window, scaling filter and HUD move), so it is judged on the guest log only. |
| Input layer | Host libpad adapter `port/psyz_missing/psyz_pad_host.c`, keyed by the `PadChkVsync` count (game frame); the parser is `port/replay/dw3_replay.c` | Independent of host speed, Xvfb timing, turbo and emulator speed. No decomp edits. PC and Switch read the same `.rec` through the same parser. |
| Hook | PC: `DW3_REPLAY=<rec>` replays, `DW3_REPLAY_RECORD=<rec>` records the real pad. Switch: compile-time `-DDW3_NX_REPLAY=ON`, file `sdmc:/switch/dw3/replay.rec`. Everything unset / flag off = no behavior change | Off by default; release builds cannot replay (see Switch replay build). While recording, `DW3_AUTO_PAD` is ignored. |
| Checkpoints | `shot <frame> <name>` lines in the recording; the host writes the capture at that frame | Fixed frame numbers, named in the recording itself. |
| Capture | Per checkpoint: `<name>.ppm` (PS1 display frame from PSY-Z) and `<name>.png` (the whole Xvfb window, which includes the host title overlays) | The title logo/menu are PC GPU overlays that are not in the PSY-Z frame; the window grab sees them. The game thread is blocked in the hook while `import` runs, so the last presented frame is stable. |
| Compare | Per-channel tolerance 8/255; fail above 0.1% differing pixels (~1230 px of 1280x960); diff image = ref / capture / red mask | Two runs on this machine are byte-identical (0 px). The slack is for another Mesa/GPU driver, which moves some edge pixels by a few levels. One changed menu label is about 5000 px, so a real change stays well above the threshold. The cost: a single flipped pixel passes. |
| References | `~/.cache/dw3-switch/replay-refs`, outside git, generated with `--update` | They are captures of copyrighted output. `--update` rejects a reference directory inside the repository and refuses to write references from a run whose process failed. Never commit references. Only `.rec` pad logs and scripts are committed. |
| State | Fresh temp memory-card dir and fresh option-file dir (`DW3_CONFIG_DIR`, P9.4) per scenario; the phases of one scenario share them. Ryubing: the runner also deletes `port_options.cfg` from the root's SD at the start of each scenario | Same start state every run; a later phase can restart the process on the first phase's card. |
| RNG | Nothing to seed | The game RNG is a fixed table walked by an index, seeded to 0 at boot (`vendor/dw3_decomp/src/engine/system/main.c`, `random.c`). No host entropy feeds it; host clocks in `cdfs.c`/`memcard_host.c` only time log lines. A scenario is therefore a pure function of the pad frames. |
| Fast-forward | Gameplay scenarios run with `DW3_TURBO=4` (P6.4) | It only changes pacing, and only in field/fight modes. `--no-turbo` drops it; the replay is frame-keyed, so captures are identical either way (checked, see Results). |

Recording format (`tools/replay/scenarios/*.rec`, generated by
`tools/replay/gen_scenarios.py`, or recorded by hand with
`DW3_REPLAY_RECORD`):

```
pad  <frame> <hexmask>   hold this raw mask from this frame (START 0x8, UP 0x10, RIGHT 0x20,
                         DOWN 0x40, LEFT 0x80, TRIANGLE 0x1000, CROSS 0x4000)
shot <frame> <name>      checkpoint
end  <frame>             exit(0) at this frame
```

P6.18 added four manifest fields: `cfg` (keys the runner writes into the
fresh `port_options.cfg` before the first phase, so the option file reader is
part of the test; Ryubing writes the same file to the SD root), `env` (extra
environment for the PC run, such as `DW3_START_MODE`; the Ryubing runner skips
those scenarios), `forbid_log` (a regex that must not match the phase's log) and
`log_only` (the recording has no `shot` lines and there are no reference
captures: the verdicts are the process, the overlay markers and the log lines).

The scenario list (phases, tier, expected overlay-restore markers, timeouts)
is `tools/replay/manifest.py`; `gen_scenarios.py` builds every recording from
it, and the unit tests fail if a committed `.rec` differs from the generator.

### How the gameplay recordings work

The new-game opening is scripted and every box advances on Cross, so a fixed
Cross cadence (one tap every 30 game frames from frame 800 US / 900 EU) from
the menu reaches the first field with control after about 16400 game frames
on both discs. Name entry and the starter pack take the defaults (account
name `AAAAAAAA`, Balanced Pack). The opening contains a movie (around frame
14400-14900); no checkpoint is taken there (PSY-Z's captured frame is garbled
for RGB24 movie frames). From frame 16700 the player has control in the
Asuka City main lobby and the recordings walk with the d-pad. The frame
numbers were measured on the PC build; a failing early checkpoint means the
opening changed length.

Overlay markers: the log's `dw3: overlay restore file=0x... kind=mode|sub`
lines (US ids 0x1c1 title, 0x158 field, 0x1da/0x1db Kusanagi, 0x1f8 name
entry, 0x1c7 Login Room, 0x1c5 lobby; EU 0x165/0x1d0, 0x166, 0x1e9/0x1ea,
0x206, 0x1d6, 0x1d4) are checked as an ordered subsequence per scenario
(`expect_restore` in the manifest), and any `kind=unknown` fails. Both the PC
and the Ryubing runner use the same expectation.

Strict overlay restores (patch 0061): a replay run (PC: `DW3_REPLAY` is set;
Switch: the `DW3_NX_REPLAY` build) aborts on the first failed overlay
restore, after the `kind=unknown UNKNOWN` marker, a `dw3: ERROR overlay
restore failed` line and a `dw3: FATAL` line, so it shows up as a `CRASH`
(SIGABRT) at the point of failure instead of a run that goes on with an
overlay whose state was never reset. `DW3_OVERLAY_STRICT=0` turns that off
for a manual run. The PC runner removes `DW3_OVERLAY_STRICT` and the P3
debug aids (`DW3_START_MODE`, `DW3_FORCE_*`, `DW3_AUTO_DOOR_*`) from the
inherited environment; a scenario sets them only through its manifest `env`.

## Verdicts

Each process run gets a verdict that is separate from the image diff:

| Verdict | Meaning |
|---|---|
| `CRASH` | killed by a signal (the signal and the last game frame are in the detail); Ryubing: "Unhandled exception" / "Invalid memory access" in the emulator log or a non-empty guest `crash_report.txt` |
| `EXIT` | non-zero exit status |
| `HANG` | no game-frame progress for `--stall` seconds (default 120 on PC, 600 in Ryubing). Progress is the `dw3-replay: frame N` heartbeat (every 600 game frames) and the checkpoint lines |
| `TIMEOUT` | the per-phase wall-clock limit (`timeout` in the manifest, `--timeout`) |
| `NOEND` | exited 0 before reaching the recording's `end` frame |
| `FAIL` (markers) | overlay restore sequence differs or `kind=unknown` |
| `FAIL` (memory) | soak only, see below |

A failed phase stops the scenario (later phases depend on it) and the
checkpoints it did not reach are reported as missing captures, so a crash is
not reported as a pile of image diffs.

Memory sanity (soak). The PC host has nothing like P5.1's `mem dbg:` line, so
the runner samples the process RSS every 5 s (`/proc/<pid>/status`, tagged
with the last game frame) and, for the window from `rss_from_frame` (20000,
after the opening) on, splits the samples into four equal chunks. The
scenario FAILS when the chunk medians rise strictly chunk over chunk
(monotonic growth) AND the last median is more than **48 MiB** above the first.
The threshold is a first guess, set well above run-to-run noise (the PC
host's RSS wobbles by a few MiB) and below anything a real leak over 17
minutes of door trips would hide under; see Results for what the soak
measured. Fewer than 8 samples in the window is reported, not failed. Non-soak
scenarios report their RSS peak as `INFO`.

## Switch replay build

`sdmc:/switch/dw3/replay.rec` is read by a build configured with
`-DDW3_NX_REPLAY=ON` (`tools/build_switch_game.sh --replay`). The design
choices:

- **Compile-time, not file-triggered.** A release NRO must never replay
  because a stray file sits on the SD card, so the whole path (the file
  name, the log lines, the stderr routing) only exists when the flag is on.
  Default and release builds have none of it. The replay NRO is built in its
  own tree (`build/switch[-eu][-nxlink]-replay/`) and named
  `dw3-switch[-nxlink]-replay.nro`, its NACP name ends in "replay", and the
  boot log prints `dw3: REPLAY BUILD`. `tools/build_switch_game.sh` refuses
  to mix up the cache of a replay and a normal configure.
- **Same code path as the PC.** `psyz_pad_host.c` (already linked by both
  hosts) calls the shared `port/replay/dw3_replay.c` parser from
  `PadChkVsync` and publishes the masks through `Psyz_PadsSet`, keyed by the
  same game-frame counter. It overrides whatever the real controller
  (or its absence) put in the pad buffer each game frame.
- **Output.** `replay shot <frame> <name>` per checkpoint, `replay begin`,
  `replay end <frame>`, the `dw3-replay: frame N` heartbeat, then `exit(0)`
  (which also flushes the memory card). In the replay build `boot_main.c`
  calls `consoleDebugInit(debugDevice_SVC)` (unless nxlink owns stderr) so the
  game's `fprintf(stderr, ...)` markers (overlay restores, `FIELDSTG_pickStage`)
  also reach `svcOutputDebugString`; the lines that `psyz_log` already sends
  appear twice in the emulator log, which is harmless.
- **No pixel checks.** Checkpoints are log lines only. The Ryubing runner
  grabs the screen at each line as informational evidence and never compares
  it.

## Ryubing runner

```bash
tools/replay_ryubing.sh --build --quick            # builds both replay NROs (docker), title scenarios
tools/replay_ryubing.sh --version us --only us-field-walk
tools/replay_ryubing.sh --soak                     # + the soak (80+ minutes in Ryubing)
```

`tools/replay_ryubing.sh` (`tools/replay/ryubing.py`) builds or takes the
replay NRO (`--build`, `--nro-us/--nro-eu`; default is the `--nxlink --replay`
build, which adds the `mem dbg:` samples and the debug HUD; `--no-nxlink` for
the plain one), prepares its **own** Ryubing data roots under
`/mnt/cabal/tmp/dw3-p615-ryu/{us,eu}` (`--root-base`; keys, config and
profiles copied once from a read-only seed root, `--seed-root`, plus the owner
runtime without a memory card), and runs
`DOTNET_ROOT=$HOME/.dotnet Ryujinx -r <root> --use-main-config <nro>` on a
private Xvfb. It never touches `~/.config/Ryujinx/Config.json` or another
agent's root. For every scenario it wipes the root's memory card, copies the
phase recording to `sdcard/switch/dw3/replay.rec`, reads the Ryujinx output
(`OutputDebugString` lines) while the run goes, and stops the emulator after
`replay end`. Verdict, per phase:

1. no `Unhandled exception` / `Invalid memory access` and no guest crash report;
2. every `replay shot` line of the recording, in order, and `replay end`;
3. the overlay restore markers match the scenario's sequence, none unknown;
4. with an nxlink build, the `mem dbg:` high-water marks (heap, file cache,
   libc) grow by at most 512 KiB (libc: 768 KiB, see below) between the 60%
   point of the run and its end;
5. no game-frame progress for 600 s is a HANG (the JIT makes the first minute
   slow).

**libc limit 768 KiB (2026-10-25).** The smoke test of main 50bbd74 (P6.22
pass 2, #263) failed `eu-volume-persist` and `eu-pacing-persist` with a libc
high-water step of +565K/+601K after the 60% mark (heap and file cache +0K).
It is not #263: the 256 KiB RGB555 pack table is a static array (BSS, not in
`mallinfo`), and the deferred-draw queue only runs when turbo is on, which
these scenarios never use. Three runs of both scenarios on each build, EU,
Ryubing: main failed 2 of 12 mem checks (volume p1 +565K twice), the parent
ca7e784 failed 1 of 12 (volume p2 +601K); the smoke test's own parent rerun

Root cause, confirmed by the separate investigation
([BALLOON_NULL_ACTOR.md](BALLOON_NULL_ACTOR.md)): the walk ends at the
Digital World bridge gate ("Oh yeah! I need my partner Digimon data!",
WSTAG210 script30), which sends the balloon close `0x326` twice; the second
one creates a balloon that goes INIT to DONE with a NULL actor. That is also
the preview.29 US crash in Ryubing. Patch `0058` fixed it on both hosts.

Regression coverage, all passing with the patch: `us-repro-balloon` (this
lobby walk) and `us/eu-bridge-partner-gate` (the root-cause path; the build
without the patch dies with SIGSEGV between `gate` and `dialogue` on both
discs, shown as a `CRASH` process verdict and missing captures). Ryubing,
replay NRO built from the tree with the patch: `us-repro-balloon` went from
`CRASH` to `PASS` (716 s, same 7 checkpoint lines, `replay end`, flat `mem dbg:`).

## Not covered (open under P6.15)

- **Battle by pad input from a new game.** `us/eu-two-battles` cover two
  real battles (techniques, win, report, return to the field) but start them
  with the P3.3 dev hooks, and only on the PC. From a new game a battle is
  not reached yet. The opening ends in the Asuka City lobby /
  Login Room hub. The Account Clerk says to "retrieve your Digimon data at
  the lobby", and the route out of the arrival point leads down to the Digital
  World bridge gate, where the hero is stopped ("I need my partner Digimon
  data", the `us/eu-bridge-partner-gate` scenarios, which used to crash on the
  balloon bug). Getting the partner needs the lobby counter and a few more
  scripted steps that were not explored: the gate pods did not react to Cross
  or d-pad in 2400 frames of trying, and the Start menu (and
  Triangle/Circle/Square/Select) does nothing in the hub, so there is no
  flee/fight to script yet. Four random 4500-frame lobby walks produced no
  other overlay change. Scripted `DW3_FORCE_ENCOUNTER` (P3.3) is a dev hook,
  not pad input, and the Switch replay NRO cannot set it per phase.
- **Save and load round trip.** Saving needs the field Start menu or a save
  point, and neither was reachable in the hub. `*-load-menu`
  covers the card-access half on an empty card. A save made with the dev
  hooks (`DW3_START_MODE=0x2D7 DW3_FORCE_MENU=0xC00:0x80000000
  DW3_FORCE_MCARD_SAVE=1`) wrote `save0.bin`, but the title Load screen then
  listed no data (`LV--`, "There is no data."), so it was not usable as a
  fixture. The two-phase mechanism itself (one memory-card directory shared
  by the phases of a scenario, the second phase restarting the process on it)
  is implemented and unit-tested with a stub binary
  (`tools/tests/test_replay.py`), ready for a `*-save-load` scenario once a
  save is reachable.
- **Other EU languages in the gameplay scenarios.** `eu-newgame-field` and
  `eu-field-walk` are English only. The title scenarios still cover all five
  languages. The opening is the same script in every language and only the
  text differs, so French/German/Italian/Spanish variants would need only a
  different language-select prefix, but each costs ~5 minutes per run.
- Movies. PSY-Z's captured frame is garbled for RGB24 movie frames in this
  setup, and the scenarios skip the movie with Start/Cross, with no
  checkpoint inside it. FMV and audio are not checked at all
  (`SDL_AUDIODRIVER=dummy`).
- Cross-machine references. The threshold is a guess for other drivers, not
  measured; references made on one machine have not been tried on another.
- A single changed pixel is below the picture threshold by design.
- Timing of the opening: the Cross cadence and the checkpoint frames were
  tuned on this build; if the opening changes length the recordings need new
  frame numbers. A failing `news`/`name-entry`/`lobby` checkpoint is the
  signal.
- Ryubing: pictures are never compared, and the soak there takes more than an
  hour. No CI job (needs the owner's discs).

### Running it nightly (not installed)

No CI job runs this, because it needs the owner's discs and a runtime tree.
A self-hosted runner or a cron job on the owner's machine could run, from a
worktree with both PC builds and `runtime/{us,eu}` in place:

```bash
tools/replay_tests.sh --soak --jobs 4 --out /mnt/cabal/tmp/replay-nightly || \
  echo "P6.15 replay failed, see report.txt in the newest results dir"
tools/replay_ryubing.sh --quick     # optional, adds the Switch build
```

The exit status is 0 only when every check passed, so a plain cron mail or a
`workflow_dispatch` job on a self-hosted runner with the `runtime` and
`replay-refs` directories on the runner is enough. References have to be
generated on that machine (`--update`) before the first run.
