# P6.30 Technical help and the shared page engine: design

Status: **phases 1 to 4 built** (2026-10-28, first PR): the page engine, the
glyph atlas, the Help sub-screen (PC and Switch code paths, reached from the title
Options, the field menu OPTIONS row and the battle Options), the ten pages of the
English draft (`port/help/text/en.txt`, **draft, owner review pending**), tests and PC
replays on US and EU. **Not yet checked on a Switch OLED** (OLED_TEST_PLAN H1 to H8).
The base-game languages other than English are **TODO stubs** that fall back to
English with a log line; a validator warns while they are stubs
(section 11). Phase 5 (translations, pt-BR) and phase 6 (the release gate in CI,
the doc-drift check) are open. Goal note: [ROADMAP P6.30](ROADMAP.md#phase-6-goal-notes). Order:
[Priority](ROADMAP.md#priority) Tier 2 item 3, after P9.9 (the Options group
frame) and the [controls bundle](CONTROLS_BUNDLE.md).

The technical help is an **Options sub-screen** (the hidden "Help" group of
[PORT_OPTIONS](PORT_OPTIONS.md#groups-and-sub-screens-p99)). It is a short book
of pages: controls, port hotkeys, turbo, the Options rows, saves, widescreen,
map view and mods, logs and bug reports, a FAQ. It only reads text and a few
facts about the running build; it never writes game state, and it needs no
network.

The same page engine also serves the
[P6.35 walkthrough](P6.35_WALKTHROUGH.md). Sections 2 to 5 define the engine so
that both books share one parser, one wrapper, one scroller and one drawing
path, and differ only in the structure of their data.

## 1. Owner decisions and constraints

   the EU disc French, German, Italian and Spanish); only pt-BR waits for P6.7.
   See Q3 in section 10.

Constraints carried over from the goal note and from AGENTS.md:

- Only what is confirmed. Items not yet checked on a Switch OLED carry a visible
  tag (`!unv`, section 4.3) so the help does not claim more than the docs do.
- Screenshots only from the owner-approved set; the help has none.
- The text comes from the same facts as [PLAYER_GUIDE](PLAYER_GUIDE.md) and
  [HOTKEYS](HOTKEYS.md). Section 8 says how the drift between them is caught.

  any external guide.
- The Cheats screen is **not** described in the help. The owner wants it
  undiscoverable on a normal install ([PORT_OPTIONS](PORT_OPTIONS.md#groups-and-sub-screens-p99),
  "Grouping is a proposal"); it stays in the PLAYER_GUIDE only.

## 2. Page and section model

One generic model, two books.

```
Book            "help" or "walkthrough"; owns its structure and its entry screen
 Page           a title, a short blurb, an ordered list of blocks
  Block         one of: h (heading), p (paragraph), li (list item),
                row (two columns "left | right"), note, warn, q / a (FAQ pair)
```

- A **section** is a heading block plus the blocks until the next heading. There
  is no deeper nesting: the screen is a console menu, not a manual.
- A **page** is one scrollable text panel. A **page list** (the Help group's own
  list, in the Options plaque style, six visible, scrolling like the other
  lists) shows the pages of the book by title, with the blurb in the message
  strip. Confirm opens a page.
- Blocks wrap to the panel width; `li` gets a bullet and a hanging indent, `row`
  gets two columns (left wraps in about 60 percent of the width, right at the
  rest), `note` and `warn` get a bar at the left (`warn` in the warm accent;
  they never rely on colour alone, the word-free bar shape differs) and `q` is
  drawn in the lit lettering with `a` below it, indented.
- The walkthrough maps its layers to blocks: `title` is the page title, `goal`
  is a `p` block, and `help` (the spoiler layer) is a `p` block that the
  walkthrough wraps in its own reveal plaque
  ([P6.35 section 4](P6.35_WALKTHROUGH.md)). The reveal plaque, the step logic
  and the chapter list stay in `port/walkthrough/`; the engine does not know
  about spoilers.

What is shared and what is not:

| Shared (new `port/pages/`) | Help only (`port/help/`) | Walkthrough only (`port/walkthrough/`) |
|---|---|---|
| Text file parser and the key table | Page list (order from the English file) | Step table, resolver, chapter list |
| Qualifier filtering (region, platform, unverified) | Entry from the Options group | Reveal plaque and its two-step confirm |
| Token resolver (`{btn:..}`, `{path:..}`, `{build:..}`) | Help-only tokens (none planned) | Name placeholders (`{name}`) |
| Language fallback and its log line | | Per-step fallback accounting |
| Wrap, layout, scroll state, scroll indicator | | |
| Drawing of the panel in the overlay art | | |
| Validator (ids, tokens, budgets, glyph coverage) | Help validator rules | Step table validator |

The engine is pure C with a width callback (it asks "how wide is this string in
pixels"), so the host tests run it with a fixed-width fake metric and no
renderer. The drawing sits next to the Options art
(`platforms/pc/src/title_overlay_art.c` and the shared overlay path the Switch
GLES build also uses), so PC and Switch draw alike.

## 3. Screen, scrolling and controls

### 3.1 Visual identity

The Help screens use the title menu's identity, as the other Options
sub-screens do ([TITLE_MENU_DESIGN](TITLE_MENU_DESIGN.md)): the dimmed backdrop
(deeper over the field or a battle), navy plaques with steel bevels and amber
rails, a lit rail and short halo on the focused plaque, warm lettering with a
one pixel shadow.

- **Page list:** the standard Options list of plaques. Title as the plaque
  label, blurb in the message strip, hints `Open`, `Back`.
- **Page:** a header plaque with the page title; one large navy **text plaque**
  under it for the body; the message strip shows the page position (`3 / 10`) and the hint row shows
  `Scroll` and `Back`. The body uses one text size and a lighter lettering than
  the plaque labels so a page reads as text, not as a menu.
- The panel and strip metrics come from the same helpers as the Options
  sub-screens; nothing new in the art vocabulary.

### 3.2 Scrolling

A page is laid out once, at open, into lines. The panel shows `N` lines
(`N` = the plaque height divided by the line height). If the page is longer:

- Up / Down scroll one line, with the same held-direction repeat as the lists.
- Left / Right scroll by one screenful (a page up / page down).
- An amber arrow above and below the panel shows that more text exists, the
  same arrows the lists use. At the top or the end the arrow disappears.
- L1 / R1 go to the previous / next page of the book. This is the same
  "sibling" meaning as in the walkthrough (L1 / R1 jump to the previous / next
  step), so a player learns one rule.
- Triangle goes back to the page list; from the list it closes the group (the
  usual Options behaviour).
- Cross and Circle do nothing on a page of the help (there is nothing to
  confirm); the walkthrough uses them for its reveal.

A page that fits shows no arrows and Up / Down do nothing (and play no sound,
as with the other lists).

### 3.3 Sound

As on the Options screen: cursor sound for Up / Down while they move, the
cancel sound for Back, the choice sound when a page opens. No sound for a
scroll that hits an end.

### 3.4 Printed button names until P10.6

Pages never write "B" or "X" as plain words in the text. They use tokens
(section 4.4), so the page follows the active layout and map without a
re-edit. Until the glyph work of
[P10.6](CONTROLS_BUNDLE.md) exists, the resolver returns **plain names** in
square brackets (`[B]`, `[R3]`, `[L] [R] [+] [-]`), the same names the Options
hints use today (B Change, X Back). On PC the names are the keyboard keys
(`[X]`, `[2]`) from [HOTKEYS](HOTKEYS.md). Behind the resolver there is one
function, `dw3_btn_name(ps_button)` from the controls bundle (see
[CONTROLS_BUNDLE section 3](CONTROLS_BUNDLE.md)); when P10.6 lands, the engine
asks the same function for a glyph id instead of a string and the text is
unchanged. If a token names a button with no source (unmapped under a custom
remap), it renders `[?]` and logs once (section 6).

## 4. Text table format

### 4.1 Choice: a line-based text file, one per language

Text lives in `port/help/text/<lang>.txt` (`en.txt` now; `fr`, `de`, `it`, `es`,
`pt-BR` later) and the walkthrough uses the same format in
`port/walkthrough/text/<lang>.txt` (as P6.35 section 2.3 already proposes).

Why a plain `key = value` text file and not JSON or a C table:

- Same shape P6.35 already chose, so the engine has **one** parser.
- No quoting or escaping noise, so a reviewer and a translator read prose; a
  diff shows exactly the sentence that changed.
- Comments are allowed (JSON has none), which the draft uses for the status and
  the format legend.
- It needs about 120 lines of C to parse and no third-party code; the repo
  already has a tiny JSON subset parser for mods, but help text is not JSON-shaped.
- The file is embedded into the build by a generator (section 4.6), so the
  runtime has no file to find on the SD card and no path to get wrong.

### 4.2 Syntax

```
# comment
@format = 1                       header lines: format, book, lang, status
key [qualifier ...] = value       one entry per line, UTF-8
```

- `key` is `help.<page>.<kind>[.<n>]`. Kinds: `title`, `blurb`, `h`, `p`, `li`,
  `row`, `note`, `warn`, `q`, `a`. A `row` value is `left | right`.
- **Order.** The order of the **English** file is the page order and the block
  order. Another language carries the same keys and the engine takes the order
  from English, so a translator cannot reorder pages and a missing key is
  visible.
- **Escapes:** `\n` forced line break, `{{` and `}}` literal braces. There is no
  other markup: a paragraph is one line and the engine wraps it.
- **No concatenation.** Whole sentences only; a translator reorders words
  around a token freely. A name inserted at run time is a token, never glued.
- **Header `@status`:** `draft, owner review pending` today. The validator
  fails a release build whose file still says draft (section 8), as P6.35 does
  with its `reviewed` marker. A tester build shows `(draft)` in the page
  title.

### 4.3 Qualifiers: region, platform, status

A qualifier follows the key and filters the entry at load time:

| Qualifier | Meaning |
|---|---|
| `@us`, `@eu` | Only on that region's build (the build knows its region) |
| `@switch`, `@pc` | Only on that host |
| `!unv` | Not yet checked on a Switch OLED. The block is drawn with a small `(unverified)` tag (a word, not only a colour) |

Several qualifiers may be combined (`@switch !unv`). Two entries with the same
key and different qualifiers are the way to write different text per region
(for instance the setup lines: one `@us`, one `@eu`). A key with no matching
entry on this build is simply absent; a page with no blocks left is hidden from
the list. The `!unv` tag is removed from the text file by the PR that lands the
OLED confirmation, so the help follows the ROADMAP.

### 4.4 Tokens

`{kind:name}` is replaced when the page is laid out (at open), never stored:

| Token | Result |
|---|---|
| `{btn:cross}` ... `{btn:r3}`, `{btn:dpad}` | The physical button that produces that PS1 button under the active map and layout (P6.12, P9.8). Plain `[B]` now, a glyph after P10.6 |
| `{ps:cross}` | The PS1 name, for the rare place where it matters |
| `{chord:restart}` | The restart chord built from the four buttons' names (`[L] + [R] + [+] + [-]`) |
| `{path:root}` | The runtime root: `sdmc:/switch/dw3/` on the Switch, the runtime folder on PC |
| `{path:memcard}` | The memcard folder actually in use for this run (per-profile on the Switch) |
| `{build:version}`, `{build:region}` | Version string and `US` / `EU`, for the bug report page |

Unknown token names render `[?name]` and log once; the validator fails the
build on an unknown token in any shipped file. Tokens, not text, carry every
fact that depends on the run, so the English file is correct in any layout.

### 4.5 Translation readiness (P6.7)

- Missing key in a language falls back to English; the engine logs
  `dw3-pages: text fallback <book> <key> (<lang>)` once per key. A partial
  translation works and is visible in the log.
- A language file may also contain qualifiers. A translator keeps them.
- Length budget: titles and blurbs are measured in pixels with the real metric
  (page title at plaque width, blurb at the message-strip width, the same
  330 / 690 px limits the generator already enforces for the Options lettering).
  Body text has no hard limit: it scrolls, but a validator warning fires above
  120 lines on a page.
- pt-BR needs Latin-1 accents. The glyph atlas (4.6) covers Latin-1, which also
  covers FR, DE, IT and ES, so no new rendering work comes with the language.

### 4.6 Rendering the text: a baked glyph atlas, not pre-baked pages

Today the Options text is lettering generated at build time with DejaVu Sans
(`tools/generate_pc_title_lettering.py`) because it is a closed set of short
strings and the game needs no font at run time. A help page is open text, in
several languages, so baking each page as an image would multiply the data and
block translation by anyone without the generator. The design:

- A generator (a sibling of the lettering one) bakes **one glyph atlas** for the
  body size: DejaVu Sans, Latin-1 plus the few symbols the text uses (bullet,
  arrows, brackets), anti-aliased, with advance widths, into a generated `.inc`
  checked in. The game still needs no font file or Python at run time.
- The engine lays out text with the atlas advances (the width callback) and the
  overlay blits glyph quads, like it does for the retained plaques.
- The text files are embedded as C string tables by the same generator, so the
  validator can check every character against the atlas at build time ("glyph
  not in atlas") and a missing letter fails CI, not the console.

This is the biggest open technical item (Q1, section 10): atlas size and the
texture budget on the Switch.

## 5. Entry points

All through the existing Options screen; no new global input.

| From | Path | Notes |
|---|---|---|
| Title menu | Options, Help | The title menu has a fixed number of plaques (four, five with an auto-save); a Help plaque there would change that layout, so the entry is through Options (Q2) |
| Pause menu (the field menu) | OPTIONS row, Help | Opens over the field; the game waits behind it, music keeps playing |
| Battle | Select at the command menu, Help | The battle stands still, as for Options. Pages that need the field (none) would be greyed |

The Help group flips `built = 1` in `port/include/port_options_groups.h` when
the first page exists (the placeholder `DW3_OPTGRP_HELP` is already there). It
has no rows of its own (like Cheats it is a screen), so the group's row count is
0 and `port_options.c` hands over to `port/help/` the way it does for the
Cheats screen; the group is listed always (it is not secret, unlike Cheats).
Group name, blurb and the Open / Back hints exist in the five EU languages in
the Options lettering; the page titles and body are English only until the
packs (Q3).

No new pad shortcut is added; every free button is accounted for in
[HOTKEYS](HOTKEYS.md) and [P6.32 section 7.5](P6.32_MAP_ZOOM.md#75-free-buttons-in-the-field-for-a-future-field-hotkey).

## 6. Logs (AGENTS.md rule 12)

The engine logs its own events with `dw3-pages:`, once per event, never per
frame; the books log theirs with `dw3-help:` (and P6.35 keeps `dw3-walkthrough:`).

| Event | Line |
|---|---|
| Text loaded | `dw3-pages: text help en loaded (N keys, M qualified, K filtered out for US\|EU/switch\|pc, B bytes)` |
| Fallback | `dw3-pages: text fallback help <key> (<lang>)` |
| Token problem | `dw3-pages: token <name> unresolved, drawn as [?name]` (once per name) |
| Token resolved (first use per token per open) | `dw3-pages: token {btn:cross} -> "B" (layout playstation, glyphs off)` |
| Help opened | `dw3-help: open (from title\|field\|battle, region US\|EU, platform switch\|pc, language L, N pages)` |
| Page opened | `dw3-help: page <id> (from list\|prev\|next, N lines, panel M lines, unverified blocks U)` |
| Reached the end | `dw3-help: page <id> end reached (line L of N)` (once per open of a page) |
| Page closed | `dw3-help: page <id> closed after T ms (read to line L of N)` |
| Help closed | `dw3-help: closed after T ms (pages opened P)` |
| Timing | `dw3-help: first frame T ms after open`, `dw3-help: layout <id> N lines in T us` |

These let the owner report only feel and looks: the lines prove which page was
opened, from where, in which region and language, how far it was read, and that
no token or key was missing.

## 8. Test plan

### 8.1 Host / unit (CI)

- Parser: header, comments, qualifiers, escapes, duplicate keys with different
  qualifiers, a bad line (missing `=`, unknown kind) is an error with the line
  number.
- Qualifier filter on a 2 x 2 matrix (US / EU, Switch / PC): the right entry is
  chosen; a page with no block left is hidden.
- Token resolver: every `{btn:*}` for the default map, a remapped map (once
  P6.12 exists), PC keyboard names; unknown token; `{{`.
- Wrap and scroll with a fixed-width metric: words longer than the line, `row`
  columns, the last line, scroll clamp, page up / down, a page that fits.
- Validator on the real `en.txt`: every key has a kind and a known page, the
  token names exist, every character is in the atlas, blurbs and titles fit,
  every non-English key exists in English, the build fails a release when
  `@status` says draft.
- Doc drift check: a small script extracts the controls and hotkeys facts the
  help restates (button names, defaults, file names, the log rotation count)
  and compares them with HOTKEYS.md, PLAYER_GUIDE.md and `port_options.c`
  defaults, so a changed default fails CI instead of drifting (phase 6).
- `python3 tools/check_doc_links.py` and `tools/tests/test_doc_links.py` for
  this document.

### 8.2 PC replays (US and EU)

With the replay harness ([P6.15_REPLAY_TESTS](P6.15_REPLAY_TESTS.md)):
title, Options, Help, each page, scroll to the end and back, L1 / R1 between
pages, Back to the list and out; the same from the field menu OPTIONS and from
a battle. Reference frames: the page list, the top of Controls, the end of
Saves (scrolled). Check the `@us`/`@eu` pages (Setup) differ by region, and that
a missing key falls back with the log line (a test language file with one key
removed).

### 8.3 OLED checks (owner)

New items go in [OLED_TEST_PLAN](OLED_TEST_PLAN.md) with the lines that prove
them:

| Check | What the owner looks at | Proof in `dw3.log` |
|---|---|---|
| H1 Open from the title | Help plaque in the Options list, the page list matches the title menu style | `dw3-help: open (from title, ...)`, `dw3-help: first frame T ms after open` |
| H2 Open from the field menu and a battle | The game waits behind it, music keeps playing | `dw3-help: open (from field, ...)`, `open (from battle, ...)` |
| H3 Reading and scrolling | The text is readable at arm's length on the OLED in handheld and docked, arrows show, Up / Down and Left / Right scroll | `dw3-help: page <id> (... N lines, panel M lines ...)`, `end reached` |
| H4 Button names | The names on the Controls and Hotkeys pages match the console | `dw3-pages: token {btn:r3} -> "R3" ...` and similar |
| H5 Region pages | The Setup page shows only the lines of this disc | `dw3-pages: text help en loaded (... filtered out ...)` |
| H6 Unverified tags | `(unverified)` shows where expected | `dw3-help: page <id> (... unverified blocks U)` |
| H7 No missing text | No `[?]` anywhere | no `dw3-pages: token ... unresolved`, no `text fallback` in English |

The report states the method, the display used and the time played (AGENTS.md
rule 8).

## 9. Draft text and review workflow

The first draft is [`port/help/text/en.txt`](../port/help/text/en.txt), marked
**draft, owner review pending**. It covers the ten pages: Setup, Controls, Port
hotkeys, Turbo, Options explained, Saves, Widescreen, Map view and mods, Logs
and bug reports, FAQ. Every sentence restates a fact from the repo docs; the
file header lists them.

Workflow, as for P6.35: an agent drafts, the owner reviews, nothing ships
unreviewed. The review PR shows the text file; a generated reading copy (pages
in order with default button names and both regions) is part of phase 1 so the
owner reads prose, not keys.

Things the draft deliberately leaves out, for the owner to confirm:

- the Cheats screen (see section 1);
- developer environment variables (`DW3_TURBO`, `DW3_WIDESCREEN`, `DW3_AUTO_PAD`)
  and the Switch diagnostic chords (debug HUD, battle renderer);
- unbuilt features (button remap, glyphs, the single-build launcher, the save
  editor) until they land, so the help never describes a screen that is not
  there. When P6.12 lands, a Controls-remap page is added in the same PR.

Facts the draft states that the owner should check against the hardware:

- the per-profile save path and the legacy copy (P6.26, OLED item E5 open);
- cross-region import (open on hardware);
- map view and the map pack (B16 partial, B17 pending);
- crash panel wording (checked on emulator).

These blocks carry `!unv` so the help shows the caveat.

**Resolved 2026-10-28 (owner decision):** the map view closes with the game's cancel button
(Triangle, Switch X; it follows the P6.12 remap). HOTKEYS.md, OLED_TEST_PLAN B16, the
P6.32 doc and `port/help/text/en.txt` now all say so; Square only opens the view.

## 10. Open questions for the owner

*Applied in the first PR (the defaults, plus the owner's answer to Q3): Q1 the atlas
(195,264 bytes of coverage, three faces, section 11), Q2 through Options, Q3 fallback
and stubs now, Q4 not mentioned, Q5 `(unverified)` tags shown, Q6 both texts kept.*


Each has a recommended default; the plan proceeds on the default unless the
owner says otherwise.

- **Q1. Text rendering budget.** A baked body-size glyph atlas (Latin-1, one
  size, DejaVu Sans) plus runtime layout, as in section 4.6, against baking each
  page as an image. *Recommended: the atlas. Phase 2 reports its size (expected
  well under 1 MB of RGBA) before any further work.*
- **Q2. Title menu entry.** Reach Help through Options (as designed) or add a
  separate Help plaque to the title menu. *Recommended: through Options. The
  title plaques are a fixed set, four or five depending on the auto-save, and
  "the main menu too" is satisfied by Options being on it.*
- **Q3. Languages at launch. ANSWERED by the owner, 2026-10-28:** the help must
  exist **at launch in every language the base game already has**: English (US
  and EU), plus French, German, Italian and Spanish on the EU disc. pt-BR comes
  later with P6.7. This replaces the earlier recommendation ("English only with
  a note"). Consequences: the five text files (`en`, `fr`, `de`, `it`, `es`) are
  a launch requirement, not a P6.7 follow-up; translation is a work item of the
  help phases (agents draft, the owner reviews, as for the walkthrough); a
  missing key still falls back to English with the logged line (section 4), but
  a release may not ship a language file that is partial. The page text keeps
  the `{btn:...}` placeholders, so button names need no translation work. The
  language shown is the EU disc's in-game language (US: English).
- **Q4. Cheats in the help.** *Recommended: not mentioned, so the screen stays
  hidden.*
- **Q5. Detail of the unverified items.** Show `(unverified)` tags to players, or
  keep unverified facts out of the help until the OLED confirms them.
  *Recommended: tags, because the player is told the truth and the text is ready
  the day the check passes.*
- **Q6. Doc source.** The help and the PLAYER_GUIDE restate the same facts. *Recommended:
  keep both, and add the drift check of phase 6 rather than generate one from the
  other, since the guide has links and long tables that do not fit a console
  panel.*

### What the screen is

The help is its own full 960x720 RGBA layer (2,764,800 bytes), composed on the CPU from
the view `port/help/help.c` keeps (the page list, or the visible lines of a page) with
the title menu's plaques, header, message strip, hints and amber arrows. The host draws
it **instead of** the Options layer while it is open and releases the texture (and the
art frees the canvas) when it closes. **The Options cache, its prewarmed layers and its
compose times are not touched**: the group list gains one plaque (Help) and nothing else
in the open or group-open path changes. Compose of the help layer (desktop CPU) is
about 5 to 6 ms for the list and a page; the Switch will be slower, so every compose over
20 ms is logged (`dw3-help: panel composed in N us`).

Deviations from the design above:

- **Own layer, not an Options sub-layer.** Section 3.1 said the page reuses the Options
  helpers; it does reuse the art (plaque sprites, strip, arrows, button caps), but not the
  cache. The cost is a 2.7 MB texture and canvas while the help is open (released after).
- **Screen words** (Open, Back, Scroll, Pages, Page, the `(unverified)` and `(draft)`
  tags) are text keys `help.ui.str.<name>` of the same file (kind `str`, never a block), so
  they translate with the pages. The group name Help and its message line are authored
  lettering in the five EU languages (generator `tools/generate_pc_title_lettering.py`).
- **Hints**: the page list shows `Open` and `Back` with the button caps; a page shows
  `[D-pad] Scroll`, `[L][R] Pages` and `Back`. Scroll is hidden when the page fits.
- **Scroll**: a screenful is the panel less one line (13 - 1 = 12 lines), so one line of
  context stays. No `[?name]` token appears in the shipped English (checked in CI).
- **Layout width**: the body is 712 px wide, 13 lines of 30 px on the 960x720 canvas, about
  60 characters a line; the longest English page (the FAQ) is 51 lines.
- **Draft tag**: while `@status` says draft the page title shows `(draft)`.
- **`{build:version}`** is the NRO version on the Switch (`DW3_NRO_VERSION_STR`), `dev` on
  PC. **`{path:root}`** is the config folder without its region folder; **`{path:memcard}`**
  is the memcard folder in use.

### Languages (owner decision 2026-10-28)

The help has to exist in every base-game language at launch. The mechanism came first
with `fr.txt`, `de.txt`, `es.txt`, `it.txt` as stubs (headers only, status `todo stub`);
**the four texts are now drafted, see [section 12](#12-translations-machine-drafted)**.
The rest of this paragraph describes the stub and partial-file behaviour, which stays
(and has a unit test). Opening the help on an EU disc set to French shows the
English pages and logs one line (`dw3-pages: text fallback help * (fr): the language file
has no keys yet (stub), English shown`); a partial file logs one line per missing key. The
language of the text is the Options lettering's (the EU disc's in-game language; the US
disc is English). `python3 tools/generate_help_assets.py --check` and the CI test
`tools/tests/test_help.py` **warn** (a pytest warning, `P6.30 launch gap`) while a language is a
stub; `--release` and the release gate fail on it, so a release cannot ship a partial
language. pt-BR is not in the list: it comes with the game language of P6.7.

## 12. Translations (machine-drafted)

**Status: FR, DE, IT and ES drafted by an AI agent, needs native review.** The owner
approved the English and cannot read the other languages; the rule is that they exist
at launch on the EU disc (Q3), so they ship as drafts. Each file says so in its header
and in `@status = draft, machine-drafted, needs native review`. Nobody who speaks the
language has read them yet. Treat every sentence as a candidate, not as final text.

How they were written:

- **Same keys.** Every key, qualifier (`@us`, `@eu`, `@switch`, `@pc`, `!unv`) and token
  (`{btn:..}`, `{path:..}`, `{chord:..}`, `{build:..}`) is exactly that of `en.txt`, in the
  same order (checked: 152 keys per language). Only the prose changed. No text was copied
  from any outside guide or wiki.
- **The game's own words.** The field menu of the EU disc is read from the replay
  captures of each language: OBJETS / TRIER / CARTE / TECHNIQUES / STATUT / OPTIONS /
  RETOUR TITRE (FR), ITEMS / SORTIEREN / KARTE / TECHNIK / STATUS / OPTIONEN / TITELBILD
  (DE), OGGETTI / ORDINA / MAPPA / TECNICHE / STATO / OPZIONI / TORNA AL TITOLO (IT),
  ARTICULOS / ORDENAR / MAPA / TECNICAS / ESTADO / OPCIONES / VOLVER AL INICIO (ES). The
  title plaques (Commencer / Start / Inizia / Comenzar, Charger / Laden / Carica /
  Cargar, Continuer / Weiter / Continua / Continuar, Quitter / Beenden / Esci / Salir) and
  every Options group and row name come from the port's own lettering table
  (`tools/generate_pc_title_lettering.py`), so the help names a row exactly as the
  Options screen draws it. The PlayStation button names are the usual ones of each
  language (Croix, Rond, Triangle, Carre; Kreuz, Kreis, Dreieck, Quadrat; Croce,
  Cerchio, Triangolo, Quadrato; Cruz, Circulo, Triangulo, Cuadrado).
- **Words kept in English.** The port's own on-screen words that exist only in English
  (the crash panel's "The last run crashed.", the map's "BUILDING", "MOD 4X", the scalers
  "Nearest", "Lanczos2" and "FSR 1"), file names, log prefixes and the values ON / OFF are
  quoted as the game draws them.
- **Voice.** French uses "vous"; German, Italian and Spanish use the informal "du", "tu",
  "tu", like the port's lettering table. A native reviewer may want to unify this.

Glyphs: the atlas has Latin-1 plus the dashes, curly quotes, bullet and ellipsis; every
accent, the eszett, the inverted marks and the guillemets of the four languages are in
it. The one letter outside it is the French ligature oe, which the texts avoid by never
using a word that needs it. `generate_help_assets.py --check` fails on any other
character. No glyph was added.

Fit: the validator measures titles and blurbs in pixels with the atlas advances. Review of
the first PC captures found that a long title plus the draft tag ("(brouillon)", "(borrador)")
overflowed the page plaque (Spanish FAQ and Options at 485 and 467 px; French 421 px touched
the edges), so `generate_help_assets.py` now also fails a drafted fr/de/it/es title whose
width with the tag is over 410 px, and those titles were shortened (ES "FAQ", "Las Opciones",
"Registros, bugs"; FR "Les Options", "Journaux, bugs"; IT "Opzioni spiegate"; DE "Karte und
Mods", "Logs und Fehler"). Four blurbs were shortened too (FR turbo, IT turbo and map, ES
map). The page engine wraps the rest; `test_translated_pages_fit` lays out all 10 pages of
the four languages on PC and Switch and fails on an unresolved token, a layout overflow
(`cannot be laid out`) or a page more than 1.5 times the English length plus 4 lines.

Tests: `tools/tests/test_help.py` (validator for all five files, the real French pages,
stub and partial fallback still tested with inline text), `tools/replay/` scenarios
`eu-help-fr|de|it|es` (page list, Controls, Options explained, in the language; no
`dw3-pages: text fallback` line allowed).

Terms not confirmed from the game: the EU names of the Equipment panel ("panneau
d'equipement", "Ausruestungsfenster", "pannello equipaggiamento", "panel de equipo" are
descriptions, the disc's own heading was seen only as FR "Equiper"), of the battle
command menu and technique list, and of "Digimon" screens other than the field menu's.
They are plain words, not labels the reader must match, but a reviewer with the disc
should compare them.

Open: native review of all four files; the doc-drift check; pt-BR with P6.7.

PC replays (EU build, 2 jobs): `eu-help-fr|de|it|es` PASS (process, log lines, overlay markers; `dw3-help: open (from title, region EU, platform pc, language <l>, 10 pages)`, `dw3-pages: text help <l> loaded (152 keys, 13 qualified, 4 filtered out, N bytes)`, `dw3-help: page controls (from list, 34 lines ...)` and `page options (from list, 55 to 58 lines ...)`, no `text fallback`). Their references are new by design (the old `eu-help-fr` ones showed the English stub); they were refreshed in a private `DW3_REPLAY_REFS`, looked at, and only those four scenarios were copied to the shared refs. The English help scenarios (`eu-help-title|field|battle`) differ from the shared refs in the picture checks, with `en.txt`, `help.c` and the page engine unchanged by this work (the shared refs predate other merged UI changes, for example #346); refresh them in their own change.
