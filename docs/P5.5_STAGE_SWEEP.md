# P5.5 Stage sweep on hardware

One opt-in run that loads every stage of the game, one after the other, and
logs what happened to each. The owner runs it once on the OLED (US, then EU),
sends `dw3.log`, and the log alone says which stages load and return. It is
P3.8's PC sweep ([P3.8_STAGES](P3.8_STAGES.md)) moved inside the game, so it
needs no environment, no `stage_sweep.py` and no recording.

Status (2026-10-28): built; PC sweep **237/237 ok on US and on EU**; OLED run
**pending** (item G9 of the [OLED test plan](OLED_TEST_PLAN.md)).

## Turn it on

The sweep exists in builds that have the Cheats screen (CMake `DW3_CHEATS`,
default ON, so every preview). A `--no-cheats` build does not contain it.
It is **off** unless the region's `port_options.cfg`
(`sdmc:/switch/dw3/us/port_options.cfg`, or `eu/`; the file the other file-only
keys use) holds:

```
stage_sweep=1
```

| Key | Meaning |
|---|---|
| `stage_sweep=1` | run, or continue the run a crash cut short |
| `stage_sweep=2` | start from the beginning (forget the progress file) |
| `stage_sweep=0` / absent | off (default) |
| `stage_sweep_frames=N` | frames each stage runs before it is left, 30 to 3600, default 90 |

The keys are file-only (no row on the Options screen) and are kept when the
Options screen rewrites the file. The Cheats master switch is not needed: the
sweep changes no game data. **Set the key back to 0 (or delete the line) when
you are done**; a finished sweep does not run again by itself (below), but the
line otherwise stays armed.

PC (test aids, not read on the Switch): `DW3_STAGE_SWEEP=1|2`,
`DW3_STAGE_SWEEP_ONLY=0x200,0x206` (a subset), `DW3_STAGE_SWEEP_FRAMES`,
`DW3_STAGE_SWEEP_DIR` (progress file folder), `DW3_STAGE_SWEEP_EXIT=1` (end the
process at the summary), `DW3_STAGE_SWEEP_HANG_MS`.

## What it does

From the first frame of the boot mode:

1. Requests the debug stage select (`STAGSLCT`, mode `0x1500`) and waits for
   it, 30 frames.
2. Requests a stage mode from the table (`requestMode(mode, 0)`, as the P3.8
   sweep and the stage select do), seeding the party first (`setParty(0)`).
3. Waits for that mode (20 s), lets it run `stage_sweep_frames` game frames
   (a frame is one pass of the mode task: the stage's loader, its tasks and
   its draw have all run), takes the free game heap.
4. Requests the stage select again and waits for it (20 s).
5. Logs one line, then the next stage.

The 237 stages are the loadable `FIELDSTG_stages` modes, in table order
(`port/sweep/stage_list.inc`, generated by `tools/gen_sweep_stages.py` from the
decomp; US and EU list the same modes and stages, a unit test keeps the file
current). `WSTAG460` (mode `0x236`) is **skipped**: it is a weak stub in every
build (P3.8: `updateWanderer` faults when the real object is linked), so the
log says `skipped` for it. The EU extra chapter's stages
(`FIELDSTG_extraStages`, `GAME.progress` = extra) are **not** in the set; they
need the chapter's progress and are a follow-up.

It never writes a save: the auto-save is held off while the sweep runs, the
memory card screen is never opened, and the stage select ignores its cursor.
The progress file is the only thing it writes (below).

## Log lines

Prefix `dw3-sweep:`. In `sdmc:/switch/dw3/dw3.log` (the PC log has the source
position before it).

```
dw3-sweep: stage sweep on (key stage_sweep=1, 238 stages in the table, 90 frames each, progress file sdmc:/switch/dw3/us/stage_sweep.txt)
dw3-sweep: stage WSTAG460 skipped: WSTAG460 is a weak stub in every build (...)
dw3-sweep: stage WSTAG200 (mode 0x200) begin
dw3-sweep: stage WSTAG200 ok in 359 ms (frames 90, mem free 7473820, load 10 ms)
dw3-sweep: stage WSTAG2xx FAILED: <reason>
dw3-sweep: done 236/237 ok, failed: WSTAG2xx (<reason>); skipped: WSTAG460
```

`ok in N ms` is the time from the request to the return to the stage select;
`load` is the time to the first frame of the stage; `mem free` is the game
heap's free bytes when the stage had run its frames (the arena is 8 MiB, so
about 7.4 MB free is the PC baseline); `frames` is the dwell. A `begin` line
comes before every stage, so a `dw3: null-guard hit: <site>` line (nxlink
builds; once per site per run) belongs to the stage whose `begin` precedes it.

Failure reasons:

| Reason | Meaning |
|---|---|
| `timeout: mode 0x.. not reached in 20 s (game is in mode 0x..)` | the request did not take (the game stayed in another mode) |
| `left the stage for mode 0x.. after N frames` | the stage sent the game elsewhere by itself |
| `did not return to the stage select (game is in mode 0x..)` | the stage ran but would not go back |
| `hang: no game frame for 45 s` | a watchdog thread saw the game stop; it logs, records and ends the process |
| `crash or hang in the previous run (see crash_report.txt)` | a `begin` with no result: the previous run died inside this stage; this launch reports it |

`ABORTED: the stage select (mode 0x1500) was not reached in 20 s` ends the run
when the game cannot get back to the select at all; the summary then says
`not run: N`.

## Resume after a crash

`sdmc:/switch/dw3/<us|eu>/stage_sweep.txt` (beside `port_options.cfg`, so US
and EU each keep their own) gets one line
per event, opened and closed each time: `begin 0x2xx`, `ok 0x2xx <ms>, mem
free <n>`, `fail 0x2xx <reason>`, `skip ...`, and `done` at the end.

- A crash (the Switch writes `crash_report.txt`, [P5.4](P5.4_CRASH.md)) or a
  HOME-menu Close leaves a `begin` with no result. Start the NRO again: the
  new run logs `stage WSTAGxxx FAILED: crash or hang in the previous run`,
  records it, and **continues with the next stage**. Stages already `ok` are
  not run again (`resuming: N stage(s) already ok in an earlier run`).
- A hang is turned into the same record by the watchdog (45 s without a game
  frame), and the process ends so the relaunch continues. (Putting the console
  to sleep for more than 45 s mid-stage counts as a hang; relaunch and go on.)
- After `done` the file stays, and a later launch with `stage_sweep=1` logs
  `the previous sweep is complete; not running again` plus the old summary and
  does nothing. `stage_sweep=2` (or deleting `stage_sweep.txt`) starts over.
- Keep `crash_report.txt` before each relaunch (rule 9 of AGENTS.md); the
  failure line names the stage, the report names the function.

The Switch keeps 5 runs of `dw3.log` (`dw3.log` to `dw3.4.log`); a sweep that
crashed several times spans several files. `grep dw3-sweep dw3*.log` gives it
all.

## Tests

- `tools/tests/test_stage_sweep.py` + `stage_sweep_main.c`: the state machine
  against a fake game (all ok, stuck request, no return, stage that leaves,
  crash and resume, hang and watchdog, subset, off by default, a finished
  sweep not rerun) and the table against the decomp.
- Replay scenarios `us-stage-sweep` and `eu-stage-sweep` (P6.15, `log_only`,
  no references): five stages from the boot, `done 5/5 ok`, no autosave line,
  no null-guard hit, the process ends itself.
- Full PC run (`DW3_STAGE_SWEEP=1`, Xvfb, about 3 min): see Results.

## Results

PC host, own disc, Xvfb, 90 frames per stage, 2026-10-28:

| Version | Result |
|---|---|
| US | `done 237/237 ok, failed: none; skipped: WSTAG460`; no null-guard hit |
| EU | `done 237/237 ok, failed: none; skipped: WSTAG460`; no null-guard hit |
| Resume | a run killed mid-sweep, relaunched: the stage it was in is reported `crash or hang in the previous run`, the rest ran (179 `ok` lines in the second run) |

The PC result matches P3.8 (237/237 PASS). A PC pass says the stage loads,
runs 90 frames and returns; it says nothing about the Switch-only faults
(64-bit pointers on AArch64 with a real MMU, memory, the file cache), which is
what the OLED run is for. Ryubing: see below.
