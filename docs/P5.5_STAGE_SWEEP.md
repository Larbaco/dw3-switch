# P5.5 Stage sweep on hardware

One opt-in run that loads every stage of the game, one after the other, and
logs what happened to each. The owner runs it once on the OLED (US, then EU),
sends `dw3.log`, and the log alone says which stages load and return. It is
P3.8's PC sweep ([P3.8_STAGES](P3.8_STAGES.md)) moved inside the game, so it
needs no environment, no `stage_sweep.py` and no recording.

Status (2026-10-30): built; PC sweep **238/238 ok on US and on EU** (it was
237/237 with `WSTAG460` skipped until [the gap below](#the-wstag460-gap-2026-10-30)
was closed); OLED G10 passed on the 237 of 2026-10-28 / 29, a rerun for the 238th
stage is open (item G10 of the [OLED test plan](OLED_TEST_PLAN.md)).

## Turn it on

The sweep exists in builds that have the Cheats screen (CMake `DW3_CHEATS`,
default ON, so every preview). A `--no-cheats` build does not contain it.
It is **off** unless the region's `port_options.cfg`
(`sdmc:/switch/dw3/us/port_options.cfg`, or `eu/`; the file the other file-only
keys use) holds:

```
stage_sweep=1
```

| Key | Meaning |
|---|---|
| `stage_sweep=1` | run, or continue the run a crash cut short |
| `stage_sweep=2` | start from the beginning (forget the progress file) |
| `stage_sweep=0` / absent | off (default) |

Put the key in the **region's** file (`us/` or `eu/`), **not the top-level**
`sdmc:/switch/dw3/port_options.cfg` (the region picker's file): the sweep never reads
it there. When it finds `stage_sweep` set in the top-level file it logs once
`dw3-sweep: stage_sweep found in <top-level file>, ignored; put it in <region file>` and
changes nothing (P51 item 7, owner preview.51: the key sat in the wrong file and no sweep
ran).
| `stage_sweep_frames=N` | frames each stage runs before it is left, 30 to 3600, default 90 |

The keys are file-only (no row on the Options screen) and are kept when the
Options screen rewrites the file. The Cheats master switch is not needed: the
sweep changes no game data. **Set the key back to 0 (or delete the line) when
you are done**; a finished sweep does not run again by itself (below), but the
line otherwise stays armed.

PC (test aids, not read on the Switch): `DW3_STAGE_SWEEP=1|2`,
`DW3_STAGE_SWEEP_ONLY=0x200,0x206` (a subset), `DW3_STAGE_SWEEP_FRAMES`,
`DW3_STAGE_SWEEP_DIR` (progress file folder), `DW3_STAGE_SWEEP_EXIT=1` (end the
process at the summary), `DW3_STAGE_SWEEP_HANG_MS`.

## What it does

From the first frame of the boot mode:

1. Requests the debug stage select (`STAGSLCT`, mode `0x1500`) and waits for
   it, 30 frames.
2. Requests a stage mode from the table (`requestMode(mode, 0)`, as the P3.8
   sweep and the stage select do), seeding the party first (`setParty(0)`).
3. Waits for that mode (20 s), lets it run `stage_sweep_frames` game frames
   (a frame is one pass of the mode task: the stage's loader, its tasks and
   its draw have all run), takes the free game heap.
4. Requests the stage select again and waits for it (20 s).
5. Logs one line, then the next stage.

The 238 stages are the `FIELDSTG_stages` modes, in table order
(`port/sweep/stage_list.inc`, generated by `tools/gen_sweep_stages.py` from the
decomp; US and EU list the same modes and stages, a unit test keeps the file
current). Nothing is skipped now: `WSTAG460` (mode `0x236`) was, as "a weak stub
in every build", until patch `0197` linked it. The skip mechanism
(`sw_skip_reason`) stays, empty. The EU extra chapter's stages
(`FIELDSTG_extraStages`, `GAME.progress` = extra) are **not** in the set; they
need the chapter's progress. They are covered by the replay scenarios
`eu-extra-stage-*` and a by-hand run of all 55 (below).

It never writes a save: the auto-save is held off while the sweep runs, the
memory card screen is never opened, and the stage select ignores its cursor.
The progress file is the only thing it writes (below).

## Log lines

Prefix `dw3-sweep:`. In `sdmc:/switch/dw3/dw3.log` (the PC log has the source
position before it).

```
dw3-sweep: stage sweep on (key stage_sweep=1, 238 stages in the table, 90 frames each, progress file sdmc:/switch/dw3/us/stage_sweep.txt)
dw3-sweep: stage WSTAGxxx skipped: <reason>          (none is skipped now)
dw3-sweep: stage WSTAG200 (mode 0x200) begin
dw3-sweep: stage WSTAG200 ok in 359 ms (frames 90, mem free 7473820, load 10 ms)
dw3-sweep: stage WSTAG2xx FAILED: <reason>
dw3-sweep: done 237/238 ok, failed: WSTAG2xx (<reason>)
```

`ok in N ms` is the time from the request to the return to the stage select;
`load` is the time to the first frame of the stage; `mem free` is the game
heap's free bytes when the stage had run its frames (the arena is 8 MiB, so
about 7.4 MB free is the PC baseline); `frames` is the dwell. A `begin` line
comes before every stage, so a `dw3: null-guard hit: <site>` line (nxlink
builds; once per site per run) belongs to the stage whose `begin` precedes it.

Failure reasons:

| Reason | Meaning |
|---|---|
| `timeout: mode 0x.. not reached in 20 s (game is in mode 0x..)` | the request did not take (the game stayed in another mode) |
| `left the stage for mode 0x.. after N frames` | the stage sent the game elsewhere by itself |
| `did not return to the stage select (game is in mode 0x..)` | the stage ran but would not go back |
| `hang: no game frame for 45 s` | a watchdog thread saw the game stop; it logs, records and ends the process |
| `crash or hang in the previous run (see crash_report.txt)` | a `begin` with no result: the previous run died inside this stage; this launch reports it |

`ABORTED: the stage select (mode 0x1500) was not reached in 20 s` ends the run
when the game cannot get back to the select at all; the summary then says
`not run: N`.

## Resume after a crash

`sdmc:/switch/dw3/<us|eu>/stage_sweep.txt` (beside `port_options.cfg`, so US
and EU each keep their own) gets one line
per event, opened and closed each time: `begin 0x2xx`, `ok 0x2xx <ms>, mem
free <n>`, `fail 0x2xx <reason>`, `skip ...`, and `done` at the end.

- A crash (the Switch writes `crash_report.txt`, [P5.4](P5.4_CRASH.md)) or a
  HOME-menu Close leaves a `begin` with no result. Start the NRO again: the
  new run logs `stage WSTAGxxx FAILED: crash or hang in the previous run`,
  records it, and **continues with the next stage**. Stages already `ok` are
  not run again (`resuming: N stage(s) already ok in an earlier run`).
- A hang is turned into the same record by the watchdog (45 s without a game
  frame), and the process ends so the relaunch continues. (Putting the console
  to sleep for more than 45 s mid-stage counts as a hang; relaunch and go on.)
- After `done` the file stays, and a later launch with `stage_sweep=1` logs
  `the previous sweep is complete; not running again` plus the old summary and
  does nothing. `stage_sweep=2` (or deleting `stage_sweep.txt`) starts over.
- Keep `crash_report.txt` before each relaunch (rule 9 of AGENTS.md); the
  failure line names the stage, the report names the function.

The Switch keeps 5 runs of `dw3.log` (`dw3.log` to `dw3.4.log`); a sweep that
crashed several times spans several files. `grep dw3-sweep dw3*.log` gives it
all.

## The `WSTAG460` gap (2026-10-30)

Found by the P6.35 slice 2 replay probe (#376): a probe that boots the
Reliability Spot (mode `0x236`, `WSTAG460`) aborted in strict mode with
`overlay restore file=0x355 kind=unknown UNKNOWN`, and its scenario `pe` had been
moved to the Main Lobby. The sweep never saw it because it skipped that stage on
purpose, so "237/237" (also on the OLED, G10) counted every stage but this one.

**Root cause.** Two gaps, one hiding the other.

1. The host's overlay tables (`port/overlays/overlay_table_{us,eu}.c`, written
   by hand, no generator) had no row for the stage's file (US `0x355` = 853, EU
   `0x364` = 868), and the stage object was not linked (a weak stub in
   `stage_stubs.c`: `WSTAG460_startStage` returns NULL). P3.8 skipped the stage
   because linking it faulted.
2. That fault is the second gap: `updateWanderer` (`wstag460.c`) finds its map
   object by `StageTile.anim == tileAnim`, and the stage creates seven wanderers
   for the animations 1 to 7, but the stage's object table has no animation 4. The
   fourth wanderer keeps `tile` NULL and writes `tile->visible`, `->clutRow`,
   `->x`, `->y` every frame. On the PS1 that is a write into low RAM; on a 64-bit
   host it is a SEGV on the first frame. Patch `0197` gives such a wanderer a spare
   tile that nothing draws (`DW3_NULL_GUARD_HIT("wstag460.wanderer-no-object")`).

**Real play.** Not only the replay probe. The stage is on the story path: at
progress `0xE` (chapter 3, step 5, the Digi-Egg of Sincerity) the Southern
Sector's `WSTAG455` event 360 ends with `SCRIPT_LEAVE(0x236, ...)`, and event 370 in
the Reliability Spot (`endEvent370`) sets progress `0xF` and gives the DE
Sincerity. Before the fix that `SCRIPT_LEAVE` loaded a stage with no overlay row
and a NULL start function: the PC build faults on the first frame (non-strict
`SIGSEGV`, strict `abort`), and the Switch build is the same code and the same
tables (`platforms/switch` links `port/`), so a player on either build could not
get past progress `0xE`. The replay scenario `us|eu-stage-0x236` walks that
transition. (The Switch build in Ryubing, below.)

**Other stages missing the same way.** Compared with `config/{us,eu}/stages.txt`
(every stage file of each disc) and `FIELDSTG_stages` / `FIELDSTG_extraStages`:

| Region | Stage files | Missing from the table | After this change |
|---|---|---|---|
| US | 239 | 1: `WSTAG460` | 0 |
| EU | 294 | 56: `WSTAG460` and the 55 of the extra chapter (`WSTAG920` to `WSTAG974`, modes 624 to 750, picked while `GAME.progress` is `0x2D`, set by `endEvent1500` in `WSTAG780`) | 0 |

The extra chapter was documented as "weak-stubbed for link" (P3_EU_BUILD,
SINGLE_BUILD): on the EU disc, past the ending, every one of those modes loaded
as an unknown overlay with a NULL start function. They are linked now, EU only
(the US game cannot compile them, they use `LANGUAGE`), with their sections bound
by `overlay_sections_eu_extra.c`. The one stage that needed more than the table
rows is `WSTAG924` (the extra chapter's Digimon Lab): its `stageColor` lives in
`wstag924_head.c`, a file of its own on the PS1 so that GCC lays the jump tables
out as the matching build; the host packs one object per stage, so patch `0197`
includes the head file under `PORT_HOST`. All 55 were booted by hand on the EU
PC build (`DW3_START_MODE=<mode> DW3_PROGRESS=45`, strict overlay restore, 600
frames at turbo 4, the replay's idle recording): 55 of 55 exit 0 with the stage
file the extra table names and no restore error. The scenarios `eu-extra-stage-920`,
`-924`, `-949` and `-974` keep four of them (the first, the one with the head
file, one in the middle, the last). Adding the extra chapter to the sweep itself
(a second pass at progress `0x2D`) is still open: the sweep seeds the party, not
the progress.

**Test.** `tools/tests/test_overlay_table_stages.py` fails when a stage of
`config/<region>/stages.txt` has no file id (equal to `FIELDSTG`'s), enum slot, name,
descriptor row, section binding, `dw3_host_stage`, linked-list entry or host
object in `port/`, when the enum and the descriptor array are out of step (the
array is positional), when two stages share a file id, or when the US table has a
stage of the extra chapter. There are no exceptions to list. Other overlays that
are not field stages (`WFIGHTTS`, `SOUNDTST`, `SHOCKTST`) are not in these lists
and still go through the weak-stub path of `port/overlays/README.md`.
