# P6.33 Items menu usability redesign (design proposal)

Status: **in progress** (owner answers recorded 2026-10-26; phase 1 partner
cycle built, see section 4). The survey and options below are dated 2026-10-24
and come from reading the source. Roadmap entry: [ROADMAP.md](ROADMAP.md) (P6.33). The layout
and open transition of the same menu are P6.1 (patches `0075`, `0076`, see
[P6.1_WIDESCREEN.md](P6.1_WIDESCREEN.md#items-menu-field-menu-2026-10-24)).

Owner request (2026-10-24, translated):

- when equipping, be able to switch between Digimon without leaving;
- see the items in the bag;
- and similar usability fixes ("etc.").

## 1. Survey of the current code

Read-only, `vendor/dw3_decomp` at `b9caa6cf9648ec331762cacfc7256f5d97d81e0a`
(the pin in `port/patches/DECOMP_PIN`). Paths are under
`vendor/dw3_decomp/src/menus/field_menu/` unless noted. US and EU share the
source; the only version split seen in this menu is the scroll bar position in
`STSTATUS_chooseEquipItem` (`#if VERSION_US`).

### 1.1 Which mode and overlay

The "Items menu" is not one screen. The field menu (`createFieldMenu`,
`engine/menu/field_menu.c`, running inside `FIELDSTG`) lists the options.
Picking one runs the block dissolve and `requestMode(MODE_STATUS)`, which loads
the overlay **`STSTATUS`** (US `0x1F9`, EU `0x207`;
`include/menus/field_menu.h`). Its main task `STSTATUS_createMenu` /
`STSTATUS_updateMenu` (`menu.c`) calls `STSTATUS_runScreens`, which opens the
screen picked in `FIELD_MENU_CHOICE` from the table `STSTATUS_screens[2][7]`
(`helpers.c`): Items, Sort, Map, Techniques, **Status**, Card folders (second
row only), Demo. When the screen closes it recreates the field menu
(`createFieldMenu`).

Two screens matter for the request:

| Screen | Created by | Task and structs |
|---|---|---|
| **Items** (first option) | `STSTATUS_createItemScreen` (`item_screen.c`) | `ItemScreen`, `ItemScreenWindows`, plus `ItemList` / `ItemListWindows` for the list panel (`item_list.c`) |
| **Status** (fifth option) | `STSTATUS_createStatusScreen` (`status_screen.c`) | `StatsScreen`, `StatsScreenWindows`, plus the `EquipPanel` (`equip_panel.c`) or the `DigivolvePanel` (`digivolve_panel.c`) |

**Equipping is in the Status screen, not in Items.** The Items screen only
lists, shows and uses items. So "switch Digimon while equipping" is a Status
screen change, and "see the bag" can be done in either.

### 1.2 Functions

- Items screen: `STSTATUS_runItemScreen` is a `switch` on `screen->substate`
  (0 start; 1-6 open the 1, 2 or 3 partner pages; `0x0A`
  `STSTATUS_chooseItemList`; `0x0B`-`0x10` open and leave the list;
  `0x14`-`0x1E` the "use on which partner" step, `STSTATUS_chooseItemMember`,
  which calls `STSTATUS_useItem`; `0x64`-`0x6F` the result and option locks;
  `0x32`-`0x38` close). `STSTATUS_drawItemScreen` draws portraits and cursors;
  `STSTATUS_updateItemScreen` is the task.
- Item list panel: `STSTATUS_createItemList`, `STSTATUS_fillItemList`
  (in `tech_screen.c`), `STSTATUS_runItemList`, `STSTATUS_moveItemListCursor`
  (L1 / R1 turn the 16-item pages), `STSTATUS_drawItemList`,
  `STSTATUS_refreshItemList`.
- Status screen: `STSTATUS_runStatusScreen` (a `switch` on `substate`:
  `STSTATUS_chooseStatusMember`, `STSTATUS_openStatusPanel`,
  `STSTATUS_waitStatusPanel`, the close steps), `STSTATUS_runStatusChoice`
  (the Digivolve / Equipment question, with its fades),
  `STSTATUS_showChosenPage`, `STSTATUS_showPartnerSlots`,
  `STSTATUS_showPartnerEquipment`, `STSTATUS_showPartnerStats`, and
  `STSTATUS_previewStats(screen, slot, item)` (computes the stats with an item
  in a slot by saving and restoring `PartnerStats.equip`).
- Equip panel (`equip_panel.c`): `STSTATUS_createEquipPanel` (reads
  `GAME.funcs.getPartyMember(screen->member)` once into `panel->partner`),
  `STSTATUS_runEquipPanel` (substates: 0-2 open, 3 `STSTATUS_chooseEquipSlot`,
  `0x0A`-`0x0E` open the list, 15 `STSTATUS_chooseEquipItem`, `0x14`-`0x16`
  close the list and return to the slots, `0x32`-`0x34` close the panel),
  `STSTATUS_showEquipList`, `STSTATUS_showEquipItem`, `STSTATUS_drawEquipPanel`.
- Rules and mutation (`helpers.c`): `STSTATUS_listItems` (lists 0-4 are
  `ITEM_FUNCS.list`; 5, 6 and 7 are the equipment lists), `STSTATUS_canEquip(
  partner, slot, item)`, `STSTATUS_equip(partner, slot, item)`. The panels call
  them through `STSTATUS_data.funcs`, a function table, so a hook can wrap them.

### 1.3 How the equip flow and partner selection work today

From the field, with 2 or 3 partners in the party (`screen->count`):

1. Field menu: Start, pick **Status**. Block dissolve, load `STSTATUS`.
2. `STSTATUS_chooseStatusMember`: Up/Down over the partner pages, Cross
   confirms. `screen->member` is the party index.
3. `STSTATUS_runStatusChoice` step 5: the two-row question (row 0 Digivolve,
   row 1 Equipment), Up/Down then Cross. Triangle goes back to step 2. Only the
   chosen partner's page, slots and stats are shown.
4. `STSTATUS_createEquipPanel` captures the partner once. Slot list
   (`STSTATUS_chooseEquipSlot`, 6 slots, Up/Down; Cross opens the item list;
   Triangle closes the panel).
5. Item list for the slot (`STSTATUS_chooseEquipItem`): 8 rows, "none" first,
   then items this partner can equip, then the rest in grey; L1 / R1 scroll a
   page of 8 (only with 9 or more rows); the stats panel previews the item;
   Cross equips (`STSTATUS_equip`) and goes to substate `0x14` (the list and
   the slot item panel close and fade out; the slot list is shown again);
   Triangle goes back without equipping.
6. Leaving: Triangle on the slot list closes the equip panel (`0x32`);
   `STSTATUS_waitStatusPanel` returns to the question (`counter = 1`); Triangle
   there goes back to the partner list (`runStatusChoice` step 12 with
   `counter != 0` sets substate 0).

No step changes `panel->partner` after creation. L1 / R1 are read only for
page scrolling in the item list. No screen of `src/menus/field_menu/` reads
Square, Circle, L2 or R2 (grep, 2026-10-24).

### 1.4 Item and bag data

- `GAME.items[0x193]` (`s8`, counts up to 99) is the **bag**.
  `GAME.equippedItems[0x193]` (`s8`) counts items that are worn.
  `PartnerStats.equip[6]` (`s16`, `PartnerEquip`) holds each partner's six
  slots (`include/engine/game_state.h`). `STSTATUS_equip` moves counts between
  the two arrays (old item `equippedItems--`, `items++`; new item the reverse)
  and handles the two-handed pair (slots 2 and 3) and the armour/accessory
  group swap. An item worn by Digimon A is therefore **not in the bag** and
  does not appear in B's list.
- `ItemInfo` (`price`, `sellPrice`, `kind` `ITEM_KIND_*`, `type`) and the
  per-type record `ItemData` (`weapon.partners` is a bitmask of the partners
  that can equip it, `weapon.kind` the hand kind), read with
  `ITEM_FUNCS.get(id)`.
- `ITEM_FUNCS.list(type, out)` fills an `s16[0x194]` with the ids of a kind that
  have a count (`STSTATUS_itemLists = {1, 0x80000002, 0x80000003, 0x80000004,
  0}`: the five lists of the Items screen; `STSTATUS_slotLists = {6, 7, 5, 5,
  4, 4}`: the list of each equipment slot). The menus keep their own copies:
  `ItemScreen.items[0x194]`, `ItemList.items` and `bag`, `EquipPanel.items` and
  `owned`. They are rebuilt on open and never saved, so **the save does not
  depend on any menu structure**.
- Item use (`STSTATUS_useItem`) writes `PartnerStats.stats[]` and
  `GAME.items[item]--`, with `RANDOM.next()` for the stat items.

### 1.5 Where it draws

Everything is drawn by the game through its own widgets in `STSTATUS`, on
`screen->layer`, at fixed 320x240 positions: `SpriteDrawer`, `TextWindow`,
`Cursor`, `ScrollBar` and `PanelAnim` fades. The background is
`STSTATUS_drawBackground` (sprite `0x1D`, 96 px pattern, drawn twice more for
the gutters by patch `0053`); the portraits are drawn by
`STSTATUS_drawItemScreen` / `STSTATUS_drawStatusScreen`; the list panel by
`STSTATUS_drawItemList`; the equip panel by `STSTATUS_drawEquipPanel`. Text
window positions and strings come from `STSTATUS_layout[]` (`helpers.c`).
Panels open with a horizontal scale about a pivot, so a new panel needs its own
fade.

## 2. Pain points

Counted as extra presses and screen changes on the flow above.

1. **Equipping a second Digimon means leaving and re-entering.** From the slot
   list of A: Triangle (close slots), Triangle (question), Down, Cross (member
   B), Down, Cross (Equipment), then the panel fades in again. About 6 presses
   and three panel open/close animations before B's slot list is usable. With
   three partners, every comparison costs this.
2. **The partner is fixed at panel creation** (`panel->partner`). L1 / R1 only
   scroll pages, so nothing changes the partner in place.
3. **An item worn by another Digimon is invisible.** To move a weapon from A to
   B the player opens A, chooses "none", backs out, opens B, then equips it.
   `STSTATUS_equip` already handles the counts; the menu does not offer it.
4. **The bag is not shown while equipping.** The item list shows the name and
   `x N` (`windows->rows[i].count`, from `GAME.items`) only for the chosen
   slot's candidates. There is no whole-bag view and no view of what the other
   partners wear.
5. **Every equip closes the item list.** After Cross in
   `STSTATUS_chooseEquipItem` the panel goes to substate `0x14` (list and slot
   item panel fade out). Equipping weapon, armour and accessory is three
   round trips, each with two panel fades in and out.
6. **The cursor is lost.** `STSTATUS_closeEquipSlots` sets `panel->cursor = 0;
   panel->scroll = 0`, so the list always opens at the top (the "none" row),
   not at the item just equipped.
7. **The Items screen has no link to equipment.** It shows the chosen item's
   equipped and owned counts, but for equipment the player has to leave and go
   Status, member, Equipment.
8. **"Use item" asks for a partner for every use**
   (`STSTATUS_chooseItemMember`), and the list closes to ask. Using three
   potions on three partners is three round trips.
9. **Grey items give no reason** (partner mask or hand kind). Minor.

The "etc." in the request is read as 3 to 9. Question 4 asks the owner.

## 3. Proposal options

All options keep the **save format unchanged**: no new field in `GAME`,
`PartnerStats` or the memory card block. New state (which partner the panel
shows, a cached bag summary) lives in the menu's task structs, which are
rebuilt on each open. Each option sits behind a Port option (key in
`port_options.cfg`, P9.4), **off by default**, so the default build is
bit-identical to the PS1 behaviour. Every equip goes through
`STSTATUS_canEquip` and `STSTATUS_equip`, so the rules and the count
bookkeeping cannot differ from the game's.

### Option A: reuse the game's widgets (least invasive)

- **Partner cycle on the equip panel.** A hook in `STSTATUS_chooseEquipSlot`
  reads a new button and moves `panel->partner` and `screen->member` to the
  previous or next party member (wrapping), then calls the functions the
  question step already uses to refresh (`STSTATUS_showChosenPage`,
  `STSTATUS_showPartnerSlots`, `STSTATUS_showPartnerEquipment`,
  `STSTATUS_showPartnerStats`). The slot cursor stays on the same slot. Proposed
  button: **L2 / R2** (ZL / ZR on the Switch), which no field menu screen
  reads. L1 / R1 stay as the page scroll in the item list.
- **Bag view.** The game already draws `x N` per row. Add one summary line from
  a game text window (`TextWindow::setNumber`), for example the bag count of the
  slot's kind, and next to the row count the number worn elsewhere
  (`GAME.equippedItems[item]`). No new art.
- **Move an item between Digimon.** List items worn by another partner (from
  `getPartnerStats(p)->equip`) as extra rows marked with that partner; Cross
  does `STSTATUS_equip(other, slot, 0)` then `STSTATUS_equip(me, slot, item)`.
- **Equip stays.** Do not take substate `0x14` after Cross; keep the cursor on
  the equipped row.

| Aspect | Option A |
|---|---|
| Patch scope | one patch (a second one if the move rows are split out): hooks in `equip_panel.c` (`STSTATUS_chooseEquipSlot`, `STSTATUS_chooseEquipItem`, the return substates) and one helper in `status_screen.c`; policy in a new `port/items_menu/` (as `port/battle_menu/` for P7.9) |
| Save and state risk | none in the file. In memory only `STSTATUS_equip` writes `GAME.items`, `GAME.equippedItems`, `PartnerStats.equip`, as today. Care: switch only between frames, never inside `STSTATUS_previewStats` (it holds a temporary copy of `PartnerStats.equip`); restore the preview (`previewStats(-1, 0)`) before a switch |
| Widescreen (P6.1) | no new layout: the game's panels already follow `0076`. New text windows use the same `DW3_MENU_LEFT` / `DW3_MENU_RIGHT` anchors, and sit at the PS1 position with widescreen off |
| Controls and glyphs (P9.8, P10.6) | L2 / R2 are free in this overlay. HOTKEYS.md has no L2 / R2 chord (restart is L1+R1+Start+Select, fast-forward is R3 in field and battle only, Options is Select). No face button is used, so P9.8 does not change them. The help text needs the button name; until P10.6 it is plain text per language (EU has five), after it the glyph for ZL / ZR or L2 / R2. HOTKEYS.md gets a row |
| Replay tests | new scenarios `us/eu-items-equip-switch`, built like `menu-screens` (its checkpoints `status-equip`, `status-equip-list` already reach the panel; `tools/replay/gen_scenarios.py`) with `DW3_FORCE_ITEMS` and a party of 2 to 3, pressing R2 then L2, equipping, and a `dw3:` log line with the counts to check in `expect_log`. Default off: `us/eu-menu-screens` and `items-screen` must still pass unchanged |

### Option B: bag list and partner row (moderate)

Option A plus a **bag list next to the slot list** (a small `ItemList`-style
panel of the slot's kind, always visible while choosing a slot) and a
**partner row** at the top of the equip panel (small portraits of the party, the
current one highlighted, drawn like `STSTATUS_drawStatusScreen`'s). The Items
screen also gets an "Equip" shortcut: Square on an equipment item in the list
opens the Status screen's equip panel for that item's slot.

| Aspect | Option B |
|---|---|
| Patch scope | two or three patches: equip panel layout (new `STSTATUS_layout[]` entries and fades), the partner row, the Items to Status jump (`item_list.c`, `menu.c`: set `FIELD_MENU_CHOICE` and `screen->member`, close one task and open the other in the order `STSTATUS_runScreens` expects) |
| Save and state risk | none in the file. More in-memory coupling: two screens' tasks hand over state; growing `EquipPanel` is fine, since it is a task allocation (`createTask(..., sizeof(EquipPanel), ...)`) and not saved |
| Widescreen | the layout is 320 wide and the equip panel already fills it, so a side list needs space: move the stats panel or shrink the list (4 rows). Needs a 4:3 variant, or it becomes 16:9-only, which ties a usability feature to the Widescreen option |
| Controls and glyphs | as A, plus Square in the Items list (free today). Square is PC `Z`, Switch `Y`; unchanged by P9.8 |
| Replay tests | as A, plus new layout checkpoints in 16:9 and 4:3 (`widescreen=0`), and the default Items and Status checkpoints unchanged |

### Option C: port-drawn panel in the 16:9 gutters (most invasive)

A host-drawn panel (not game widgets) with the whole bag, the party's equipment
and an equip action, drawn by the port in `port/ui/` with the host font, fed
from `GAME.items`, `GAME.equippedItems` and `PartnerStats.equip`, with its own
cursor driven by the pad.

| Aspect | Option C |
|---|---|
| Patch scope | a per-frame hook in `STSTATUS` to draw and read the pad; a `port/ui/` panel module; a pad shim so the game's menu does not react to the same presses (the screens read `PAD_*` themselves) |
| Save and state risk | the panel would call `STSTATUS_equip` while the game's screens hold copies (`EquipPanel.items`, `ItemList.bag`, the preview state), so the open lists go stale; every action must rebuild them. Highest risk of the three, still no change to the file |
| Widescreen | the gutter is 53 px per side (426 px picture) and exists only in 16:9, too narrow for item names. The panel would overlay game panels or use a small host font, and it is absent with widescreen off or on a 4:3 display, so it cannot be the only way to do it |
| Controls and glyphs | needs a focus switch between the game menu and the panel; a new chord may not use A or B (P9.8) nor the restart chord; glyphs are port-drawn and can follow P9.8 and P10.6 directly |
| Replay tests | the panel is host-drawn, so frame checkpoints cover it, but only against references from the patched build (nothing of the PS1 to compare); input scripts must name the focus switch |

## 4. Recommendation and phased plan

**Option A, in phases; do not start B or C until the owner has used A on the
OLED.** A solves the two stated problems (switch Digimon, see the bag) with the
game's own widgets and layout, so the 16:9 work of `0076` carries over; it
keeps the save and the default bit-identical; and the existing replay machinery
can test it. C does not fit a 53 px gutter and has to take over the game's
input. B needs layout that is easier to judge once A is on the device.

| Phase | Scope | Done when |
|---|---|---|
| 0. Decide and measure (done 2026-10-26) | answers in section 5; record the baseline press and fade count of section 2 from a Status replay; confirm L2 / R2 reach the overlay on the Switch (`nx_input.c`) and on the PC keyboard map | button and bag content chosen by the owner; baseline written here |
| 1. Partner cycle | hook in `STSTATUS_chooseEquipSlot`, refresh helper in `status_screen.c`, Port option `items_partner_switch` (**on by default**, answer 5), ZL / ZR (answer 1), help line | the owner changes partner on the slot list without leaving on US and EU with 2 and 3 partners; page, slots and stats refresh; switching alone changes no count in `GAME`; with the option off `us/eu-menu-screens` and `items-screen` match the PS1 frames, and with it on they match after review of the references; the new scenario passes |

Bag view and moves | summary line, worn-elsewhere count, rows for items worn by other partners with the two-step `STSTATUS_equip` | an item moves between Digimon from the item list; `GAME.items` and `equippedItems` equal those of a manual unequip and equip run; the swap scenario passes on US and EU |

### Phase 1 status (2026-10-26)

Built: patch `0128`, `port/items_menu/`, key `items_partner_switch` (file-only,
default 1: the Options window is full at nine rows, so there is no row), ZL / ZR
on the slot list, replay `us/eu-items-equip-switch[-43]`. ZL / ZR reach the
overlay: the Switch backend maps `HidNpadButton_ZL` / `ZR` to `PADL2` / `PADR2`
(`platforms/switch/psyz_backend/nx_input.c`) and the PC keyboard map has them as
W / E ([HOTKEYS.md](HOTKEYS.md)). No help line was added: the equip panel has
no free text line in which the five EU languages could show the button names;
the buttons are in HOTKEYS.md and the release notes (a line drawn by the port
is the job of P10.6 glyphs).

Phase 3 was **not** built in the same PR. "Equip stays" as worded (keep the
item list open after Cross) does not give "three slots without a re-open": the
three slots (weapon, armour, accessory) have three different lists, so staying
in one list only helps repeated equips of the same slot. What costs time today
is the full close and re-open animation of the list and the panel after each
Cross and the cursor reset to "none" (pain points 5 and 6). Doing it properly
means rebuilding `panel->items` after `STSTATUS_equip` (counts changed, the old
item is back in the bag, `canEquip` of the rest changed), hiding rows beyond a
shorter count, resizing the scroll bar across the 8/9 row limit and
re-previewing the stats. That is more than a small hook; it needs its own patch
(`0129`) and a decision between "stay in the list" and "go straight back to the
slot list without the fades".

The eight questions of the first draft were answered on 2026-10-26.

Consequences for the plan:

- Option B's side bag list does not fit 4:3 (the equip panel already fills the
  320 px). **It is dropped**: no side list is built. The partner row of B is
  also not built; the partner cycle (ZL / ZR) plus the stats panel already
  show who is selected. Anything added must work with `widescreen=0` and in
  16:9 with the same layout (the game's panels already follow `0076`).
- Phase 4 (Items link and partner change in "use item") is now wanted, not
  "only if asked".
- Default on means the default build is no longer bit-identical to the PS1 in
  this menu. The replay references of the screens must be checked. The only
  expected change is the new help line, and only if a help line is added.
- Phase 1 reads ZL / ZR with a new key only on the slot list, so other screens
  are untouched.

### Bag proposal (answer to question 2, for the owner to accept or change)

"The whole bag" in the terms of options A and B, without a side list:

1. **Equip item list shows the whole equipment bag, not only the slot's kind.**
   Today the list for a slot shows that slot's candidates, then the rest of the
   same kind in grey. Proposal (phase 2): Square on the list cycles the filter
   *this slot*, *all weapons*, *all armour and accessories*, *worn by
   others*. The game's own rows are reused (name and `x N`), only the filling
   function changes (`STSTATUS_listItems` with another list index). No new
   panel, so it is the same in 4:3 and 16:9.
2. **Count line.** One game text line shows the bag count of the shown kind
   and, per row, the number worn elsewhere (`GAME.equippedItems[item]`), so
   the whole bag is readable at a glance.
3. **Worn-by-others rows** (answer 3) are part of the same list, each with a
   note naming the wearer (Cross moves it).
4. **Consumables and key items** are the Items screen, which already lists the
   whole bag in five lists. Phase 4 links the two screens (Square on an
   equipment item opens Equipment for that item's slot, and a way back), so the
   whole bag is two presses away from either screen.

If the owner prefers a single view, the alternative is option B's side list in
16:9 only, which is not recommended because of answer 7.
