## Encounter rate

### How the game starts a random battle

All of it is in `vendor/dw3_decomp/src/field/field_mode/battle.c`:

1. The player's footsteps. `FIELDSTG_playStepSounds` (`actor_control.c`) runs
   while the hero walks; every 8th frame it plays the footstep and, when the
   caller allows battles (`canBattle`), calls **`FIELDSTG_checkBattle`**, a
   function pointer that is `FIELDSTG_countBattleSteps` (`data/fieldstg.c`).
2. **`FIELDSTG_countBattleSteps`** does nothing unless the stage has an area
   map (`FIELDSTG_map.files[FIELD_MAP_AREAS]`) and a `FieldBattles` list, no
   battle is starting, and the field is not busy, acting or frozen. It reads
   the area under the hero (cell value 1..4), takes that area's `BattleList`,
   and subtracts its rate from `GAME.battleSteps`:
   `rate = FIELDSTG_battleRates[list->count]`, the table
   `{2000, 3, 4, 6, 9, 18}`.
3. At `GAME.battleSteps <= 0` it starts **`FIELDSTG_startAreaBattle`** (one of
   the list's eight battles, `RANDOM.next() & 7`), but only if
   `BATTLE_SETUP.randomBattles != 0` (a debug flag of the stage select that is
   on in a normal game), and then rolls the next countdown with
   **`FIELDSTG_rollBattleSteps`**: `value = RANDOM.next() % 2304`; under 0x100
   the countdown is `value`, otherwise `(value + 0x100) / 2` (0x100 to 0x4FF).
   The first countdown is set when a game starts (`state.c`: `(RANDOM & 0x1FF)
   + 0x200`).
4. `FIELDSTG_startBattle` -> `FIELDSTG_startEncounter` fills `BATTLE_SETUP`
   and leaves for `MODE_BATTLE`.

So a random battle is a countdown of footsteps, at 3 to 18 per step against a
countdown of 0 to 1279. Everything else that starts a battle does not use this
countdown:

| Path | Function | Used by |
|---|---|---|
| Event battle | `FIELDSTG_startEventBattle(index)` (`battle.c`), through `FIELDSTG_battleFuncs`; the field action `EVENT_BATTLE(id)` (0x7400 + id, `events.c`) | story events, scripted fights, the gauge (`gauge.c`) and the hidden spots (`hidden_spots.c`) |
| Stage event 9000 | `FIELDSTG_startEventBattle5` (`field.c`) | the end-of-area fights of 16 stages |
| The battle itself | `FIELDSTG_startBattle` | all of the above and `FIELDSTG_startAreaBattle` |

### Design (patch 0062)

`FIELDSTG_countBattleSteps` asks the port what one footstep costs, after it
has read the area's rate and before it subtracts it
(`dw3_port_pacing_encounter_step`, `port/pacing/pacing.c`; the arithmetic is the
pure `dw3_pacing_scale_rate`, `pacing_policy.c`):

* **1x** (default): the rate unchanged. The countdown, the RNG calls and the
  battle are the same as in a build without the patch.
* **0.5x**: half the rate. An odd rate keeps its remainder (`carry`) for the
  next footstep, so over any number of footsteps the countdown falls by
  exactly half of what 1x takes off (the unit test checks 1000 footsteps for
  each rate in the table).
* **OFF**: the footstep is ignored: no countdown, no roll, no battle.
* **An area with the rate 2000** (`BattleList.count` 0, the table's first
  entry) is left alone in every mode. 2000 is more than a countdown can ever
  hold (at most 1279), so such an area starts its battle on the first footstep:
  the map forces it, it is not a random encounter. The random areas use 3 to 18
  (`DW3_PACING_FORCED_RATE` is 1000).

The port also logs, through `psyz_log` (PC stderr, Switch `dw3.log`):

* `dw3-pacing: random battle after N footstep(s) (encounter rate X)` when a
  random battle starts;
* `dw3-pacing: encounters off: N footstep(s) in battle areas ignored` for the
  first footstep and then every 32nd while OFF;
* `dw3-pacing: map-forced area battle on the first footstep (not affected by the
  encounter rate)` for the rate 2000 areas.

### Encounter rate above 1x (owner request after rc4)

Two more values, **1.5x** and **2x**, so the player can also fight more.
Nothing in the decomp changes: patch 0062 already lets the port return any
step for the footstep, and 0.5x / OFF only used two of the answers.

* **Stored values** (`encounter_rate` in `port_options.cfg`): 0 = 1x, 1 = 0.5x,
  2 = OFF as before, and **3 = 1.5x, 4 = 2x**. They are not renumbered, so a
  file from a P6.18 build keeps its meaning (the unit tests load each of
  0..4, write the file back and read it again; 5 and up are invalid and fall
  back to 1x with the usual log line; `DW3_ENCOUNTER_RATE` accepts 0..4).
* **The order on the screen** is not the stored order: **OFF, 0.5x, 1x, 1.5x,
  2x**, so Left goes towards "fewer" and Right towards "more" with the default
  in the middle. Left / Right step along it and stop at the ends. **Confirm
  steps up and wraps: 1x -> 1.5x -> 2x -> OFF -> 0.5x -> 1x**. The mapping
  position <-> stored value is a four-line table in `port_options.c`
  (`po_encounter_order`); the overlay and the file only ever see the stored
  value. A file written with 1 (0.5x) or 2 (OFF) steps from where it is.
* **Scaling** (`dw3_pacing_scale_rate`): 2x subtracts `2 * rate`; 1.5x
  subtracts `(3 * rate + carry) / 2` and keeps the odd half step as the carry,
  exactly like 0.5x. So over any number of footsteps the countdown falls by
  exactly one and a half (two) times what 1x takes off: the unit test checks
  1000 footsteps for every rate of the table (`3 4 6 9 18`), and also that the
  carry of one mode is dropped when the mode changes. The first countdown of
  a game is rolled by the game and is the same at every rate, so the
  footsteps to the first battle are 102 at 1x, **68 at 1.5x and 51 at 2x** in
  the replay (two thirds and a half). The area's rate is read first, so the
  random areas (3..18) scale and the countdown is never started by the scaling
  itself.
* **Map-forced areas** (the rate 2000 entry) and scripted battles are untouched
  in every mode, as in P6.18's first pass: `rate >= DW3_PACING_FORCED_RATE`
  returns before any scaling (unit test for 1.5x and 2x, including the edge
  999 -> 1998 against 1000 -> 1000).
* **Lettering and help:** `1.5x` is a new word (`opt_15x` in
  `tools/generate_pc_title_lettering.py`; `2x` already existed for
  Fast-forward). The message line of the row reads "Random battles only: OFF
  to 2x. Story battles stay." (634 px, inside the 696 px message box; it was
  "Random battles only; story and boss battles stay."). The cache test renders
  stored values 0..4 of the row from every cursor row.

### What was rejected

| Idea | Why not |
|---|---|
| Set the rate to 0 (OFF) in `FIELDSTG_battleRates` | `FIELDSTG_rollBattleSteps` can roll a countdown of 0 (`value < 0x100`), and `0 - 0 <= 0` starts a battle on the next footstep. The skip has to be before the comparison. |
| Clear `BATTLE_SETUP.randomBattles` | It only gates the start: the countdown would still run, roll and consume RNG. It is also the stage select's debug flag. |
| Change the countdown after a battle (`rollBattleSteps`) | Same rate for the whole walk is simpler to explain ("half as often") and the footsteps stay comparable; and OFF still needs the skip. |
| Scale `FIELDSTG_battleRates` | The table is shared by all areas and has the special 2000 entry. |
| Renumber the encounter values to the screen order (0 OFF .. 4 2x) | An option file written by a P6.18 build (`encounter_rate=1` is 0.5x, `=2` is OFF) would silently change meaning. The order lives in the screen only. |

### Why OFF cannot break a story or boss battle

OFF returns from `FIELDSTG_countBattleSteps` and from nothing else.
`FIELDSTG_startEventBattle`, `FIELDSTG_startEventBattle5`, the gauge and
hidden-spot calls, and `FIELDSTG_startBattle` are not touched (the patch is one
hook inside the countdown function and one log call). A map-forced area is
handled in the policy (rate >= 1000 is returned unchanged in every mode), and
the unit test covers it for OFF, 0.5x and 1x.

How it was verified:

* **Scripted battle with OFF** (`us-encounter-off-event`, `eu-encounter-off-event`):
  `DW3_FORCE_NPC_ACTION=0x7400` runs the field action `EVENT_BATTLE(0)`, the
  path the events use, on the Bulk Swamp field with OFF. The battle starts
  (`FIGHTSTG_start`, the FIGHTSTG / WFIGHTMN / STFGTREP / FIELDSTG overlay
  restores in order) and no `random battle` line appears.
* **Random battle with OFF** never starts (below).
* Map-forced areas: `tools/tests/test_pacing.py`.

## Text speed

### How a message is typed

All text is a `TextWindow` (`engine/text/text_window.c`). A typed window has a
**type delay**: `textWindowSetTypeDelay(win, delay)` sets `typeDelay` and
`visibleEnd = 0`; `updateTextWindow` adds one character to `visibleEnd` every
`typeDelay + 1` frames, and `textWindowDraw` draws the visible part and runs the
control codes. Every dialogue box (`createTalkBox`), message box
(`createMessageBox`), battle report line, gym result, name-entry welcome and
list-menu message calls it with **6**, one character every 7 frames; the area
name banner (`banner.c`) types at 5. The control codes are part of the text, not of the typing: a
wait for a button (code 2, window state 2 substate 1), a page break (code 3)
and a pause of N frames (code 6, state 2 substate 0). A full page scrolls when
the next line would be the fourth (`textCodeNewLine`). Cross while a window
types calls `textWindowShowPage`, which makes the rest of the current page
visible at once, up to the next wait, page break or fourth line.

### Design (patch 0063)

* **Normal** (default): nothing changes.
* **Fast**: `textWindowSetTypeDelay` turns a delay of 6 into 2 (one character
  every 3 frames, 2.3x). Other delays are left alone (the area name banner types at
  5, see "The 103-frame pages") and 0 stays 0.
* **Instant**: the same delay, and `updateTextWindow` calls
  `textWindowShowPage` as soon as a page has started (fewer than 3 characters of
  it shown), so the page appears at once, exactly as if the player pressed Cross
  on its first frame. It still stops where Cross stops: at a wait for a button
  (the "next" arrow), at a page break and at the page's last line; a pause code
  still pauses; Cross still works. A longer text that scrolls (a fourth line) used
  to type the new line at the fast delay; since patch 0068 the scrolled line is
  held and shown whole (next section). Since 2026-10-24 Instant also turns the
  area name banner's delay 5 into 2, so the same reveal shows its two names
  whole ("Instant and the area name banner").

The port logs `dw3-pacing: text page typed in N frame(s) (text speed X)` when a
dialogue window reaches a wait or the end (the frames it was typing, plus the
frame it finished), once per page.

### Instant and scrolled lines (patch 0068, after the rc4 OLED log)

The owner's EU log of rc4 at Instant (`2026-10-22-preview30-rc4-oled/dw3.log`)
had 27 `text page typed in N frame(s)` lines: 19 of 1-2 frames, and 8 of 103
(five times), 67 (twice) and 127 (once) frames. The first reading of those 8
(this section as first written, patch 0068) was "a line that scrolls in a long
text, typed at 3 frames per character: `3n + 1` frames", because 103, 67 and 127
are all `3n + 1`. **That reading was wrong for those 8 lines**: they are
`6n + 1` as well (17, 11 and 21 characters at 6 frames), and they are the area
name banner, see the next section. The scroll itself is real, was reproduced and
is fixed, which is what this section and patch 0068 are about.

What the game does: the message window shows two lines of a three line text.
When the text goes on, `textCodeNewLine` finds the page full and **scrolls**:
the window moves up one line and the new line is typed from its first
character. The Instant reveal of patch 0063 only fires on the first frames of
a page (`shown <= 2`), so the scrolled line was typed at the fast delay: 3
frames per character, a 34 character line in 103 frames. Waits for a button
and pauses are not the cause: they stop typing and the log counts typing
frames only.

Reproduced on the PC build, US and EU, with `text_speed=2` and the opening's
dialogue (the same recording as `*-newgame-field`): before the patch four pages
took 53, 50, 32 and 4 frames, and an instrumented build (not committed) showed
each of them with 3 to 5 scrolls (`start` moving) and `delay=2`, no other
slow page of the opening. The owner's first random battle and aftermath were
run too (`DW3_START_MODE=0x233`, the walk to the battle after 102 footsteps in
both discs, a forced win and the report, then mashing Cross): the report pages
are 1, 1 and 2 frames and nothing slow follows. Patch 0068 also added the log
line `slow Instant page with no scroll hold (N frames): reveal missed it` for an
Instant page that took more than 24 frames and had no scroll hold: the rc6 log is
what it found, next section.

**Fix (patch 0068).** With Text speed Instant, `textCodeNewLine` asks the port
what to do when the page is full (`dw3_port_pacing_text_scroll`):

* it **holds** the full page for `DW3_PACING_SCROLL_HOLD` = 12 frames (0.2 s):
  the function returns `0x8000` without scrolling, the same stop it uses after a
  scroll, so the window shows what it showed and meets the newline code again
  next frame. Without a hold the lines on screen would be replaced three frames
  after the reveal and could not be read;
* then it **scrolls** as the game does and calls `textWindowShowPage`, so the
  new line is on screen whole.

A scrolled line now costs the hold, 12 frames, whatever its length (103 -> 12
for a 34 character line); a short line that used to take about 10 frames takes
12. Normal and Fast (and the windows that do not type at the fast dialogue
delay: the banner, delay 0) get 0 from the port and run the game's own code,
unchanged. Waits for a button, page breaks and Cross are not touched. Each
scroll logs `dw3-pacing: text scroll N after a hold of 12 frame(s) (text speed
instant)`. Measured on the opening (US and EU): the four scrolling pages take
66, 66, 40 and 40 frames (3 to 5 scrolls of 12-13 frames) instead of 53, 50, 32
and 4. The pages with no scroll are unchanged (23 of 1 frame and 46 of 2
frames in both runs). A screenshot series of a three line text shows the lines
appearing whole, one per scroll, with nothing glitched.

The hold is a compromise: a text with many lines between two waits appears one
line every 0.2 s at Instant, which is quick to read but never faster than the
player can press Cross at Normal or Fast. A shorter hold is a one-line change
(`DW3_PACING_SCROLL_HOLD` in `port_pacing.h`).

### The 103-frame pages: the area name banner (rc4 and rc6 OLED logs)

The rc6 log (`/mnt/cabal/tmp/dw3-preview30-rc6-out/dw3.log`, EU, built from main
`1fc5bfc`, Instant, Encounter rate 2x, turbo used) has 20 random battles and,
after 19 of them, **one** `text page typed in 103 frame(s)` (15 times) or `in 73
frame(s)` (4 times), each followed by the new diagnostic `slow Instant page with
no scroll hold ... reveal missed it`, and never a `text scroll` line. The pages
before it are the report: 1 and 2 frames (exp, money, item), as on the PC.
Reading the log around the lines gives the real place of the slow page:

```
dw3-widescreen: gutter 0 px per side        <- report screen (4:3), turbo 1x
text page typed in 1 frame(s)               <- report page
text page typed in 2 frame(s)               <- report page
dw3-widescreen: gutter 53 px per side       <- back in the field, turbo 4x
text page typed in 103 frame(s)             <- ~3 s later
slow Instant page with no scroll hold (103 frames): reveal missed it
dw3-pacing: random battle after 37 footstep(s)
```

So the slow "page" is not in the report and not a scrolled line: it is on the
first seconds of the **field after the battle**. What the field opens there is
`FIELDSTG_createBanner` (`field/field_mode/banner.c`): the area name banner,
which freezes the hero while it plays. `FIELDSTG_showAreaName` creates two text
windows (the area name and the place name) and types them at **delay 5**, not 6.
Patch 0063 leaves every delay but 6 alone on purpose (the banner is an animation
timed to its boxes, see "What was rejected"), so the banner types at 6 frames
per character in every Text speed: `103 = 6 * 17 + 1`, `73 = 6 * 12 + 1` (a
place name of 17 and an area name of 12 characters), and in the rc4 log `67 = 6 *
11 + 1` ("Bulk Swamp" is 11) and `127 = 6 * 21 + 1`.

Why the pacing log saw them. The port times dialogue windows by remembering their
address (`Tracked` in `port/pacing/pacing.c`, four slots) and reports a page when
the window finishes. The game frees a text window with the page that used it and
gives the same address to the next window, which after a battle is a banner
window. The slot of the freed report window was never dropped, so the banner window
was timed as a dialogue window: its 103 typing frames were logged as a page
that took 103 frames, and, at Instant, flagged as a reveal that missed. Nothing
was typed slowly that Text speed was supposed to speed up.

Reproduced on the PC build, US and EU (the Switch heap hands the address back by
itself after a battle report; on the PC it needs a bigger table, so the
scenario sets `DW3_PACING_TRACKED=256`, a debug aid that keeps every dialogue
window instead of the last four): the opening and the door tour of the lobby and
the Login Room at Instant open the banner after many dialogue windows. **Before
the fix** (`us-banner-instant`, `eu-banner-instant`, the port code without the
untracking): 4 lines `text page typed in 67 frame(s)` and 4 `slow Instant page
with no scroll hold (67 frames)` per disc, the scenario fails. **After**: none,
the two scenarios pass. The unit test (`tools/tests/pacing_main.c`) has the same
sequence by hand: a report page on an address, a banner at delay 5 on the same
address, 103 typing frames, silence. The existing replays never saw it because
they use the four-slot table and the PC heap does not hand a report window's
address to the banner.

**Fix (port only, no decomp patch).** `dw3_port_pacing_text_delay`, which
patch 0063 calls for every `setTypeDelay`, now forgets the window at that address
when the delay is not 6, and logs `dw3-pacing: text typed at delay 5 is not a
dialogue page (area name banner): text speed leaves it alone` once per banner
window. Nothing the game does changes, in any Text speed.

**The banner was left as the game has it** (until 2026-10-24: at Instant its
names are now shown whole, see the next section; Normal and Fast still type
it). It is not text the Text speed row was made for, and the numbers say a
speed-up would be small. Measured on the PC (EU,
no turbo, no input, `Bulk Swamp` / `South Sector`: 11 and 13 characters): the
text types in 66 and 78 frames while the ten boxes stretch (they are all open by
about frame 60), the banner waits for both windows to finish
(`FIELDSTG_updateBanner` substate 4), holds 60 frames and wipes out in 15, so it
closes about 140 frames after it starts (2.3 s at 60 fps, hero frozen). Typing at
the fast delay or showing the names whole would end it about 20 frames (13
characters) to 45 frames (the 17 character place name of the rc6 log) earlier,
0.3 to 0.7 s; the 60 frame hold and the boxes would stay. If the owner wants the
freeze after a battle shorter, that is a decision about the banner's own timing
and is listed in the roadmap (P6.18); this change does not touch it.

### Instant and the area name banner (preview.31-rc1)

Text speed Instant, the post-battle text still runs slowly". Measured on the PC
build at Instant, with frame-stamped prints of the report's and the banner's
states (a scratch build, not committed), the forced Kotemon vs Kunemon battle
(`<v>-p77-battle`, Cross every 30 frames):

  (`DW3_FORCE_ENCOUNTER=38`, +39 exp). The rest of the report is the game's own

* **The banner was the text that still typed.** Right after the report the field
  opens the area name banner, which types its two names at delay 5 in every Text
  speed (6 frames per character) and waits for both before its 60-tick hold.

| Area banner after the battle (`Kusanagi City` / `Street Corner`) | Before | After (Instant) |
|---|---|---|
| US: banner, open to closed (game ticks, 1/60 s) | 160 | **126** |
| US: of which waiting for the names after the boxes were done | 35 | **1** |
| EU: banner, open to closed (game ticks) | 180 | **140** |
| EU: of which waiting for the names after the boxes | 42 | **1** |

**Change (port only, `port/pacing`).** `dw3_pacing_scale_delay` turns the

so the reveal of patch 0063 (`textWindowShowPage` at the start of a page, as
Cross does) shows each name whole. The banner's boxes, its 60-tick hold and its
wipe keep the game's timing, so the banner still opens and closes as before,
only without the wait for the typing (0.6 to 0.7 s per banner). The banner is
still never timed as a dialogue page (the untracking of the rc6 fix stays), and
its log line now says `... (area name banner): shown whole (text speed
instant)` instead of `... text speed leaves it alone`. Normal and Fast type it
as the game does: at Normal the captures of the banner are byte-identical
before and after (7 checkpoints, US). The banner also opens at map changes, and
there too its names now appear whole at Instant.

**Checks.** `tools/tests/test_pacing.py` (delay 5 -> 2 at Instant only, the
reveal fires for it, the glue logs `shown whole`, the banner's address is still
never timed or held); replay `us/eu-postbattle-instant` (turbo 4x and Instant:
both banner lines say `shown whole`, `leaves it alone` and `slow Instant page`
are forbidden, the report's pages show in 1-2 frames) and
`us/eu-postbattle-normal` (no turbo, Normal: `leaves it alone` twice, `shown
whole` forbidden). `*-banner-instant` still passes (its regex matches both

### What was rejected

| Idea | Why not |
|---|---|
| Reveal the scrolled line with no hold | The page is full: the next newline code scrolls within a frame, so a text of several lines races to its last line and the first lines are never readable. |
| Instant as type delay 0 (what the game uses for plain windows) | The whole text is drawn in the first frame and the page-full scroll (`textCodeNewLine`) then runs once per frame, so a text of four or more lines without waits would race to its last lines before they can be read. `textWindowShowPage` stops at the page. |
| Scale every delay | The area name banner types at delay 5 together with its ten boxes. Its length is the longer of its typing and its boxes, then 60 frames of hold: speeding the typing alone would save 0.3 to 0.7 s of a 2.3 s banner (numbers in "The 103-frame pages"). Left as the game has it at Normal and Fast; since the rc1 feedback Instant shows its names whole (the only other delay Instant touches). |
| Shorten the banner's 60-tick hold or its boxes at Instant | That is the banner's own animation, not text; a shorter hold would need its own option (P6.18 owner's call). |
| Show the banner's names only once its boxes are done | Needs a decomp patch in `banner.c`, and the game already shows the first letters before the boxes; names whole from the first frame look the same as the game's start, only complete. |
| Track every typed window in the port (any delay) and log the banner as a page | The banner is not a page of text; timing it that way is what produced the rc6 "103 frame" lines. Dialogue windows (delay 6) are tracked, anything else is forgotten at its `setTypeDelay`. |
| Skip the wait for a button | It would break input-driven dialogue. Waits and pauses are never touched. |
| A flag byte in the window (the unused `unusedC4`) to remember Instant | The delay value (2) is only ever given by this patch, so no per-window state is needed. |

## Faster battle animations: deferred

There is no clean single knob. The battle has its own time base,
`FIGHTSTG_battle.frames` (`battle_mode/speed.c`, `FIGHTSTG_countFrames`; its
mode 3 is "twice as many frames"), but only part of the battle reads it: the
model keyframes, sprite animation, move tasks, face and battle sound timers.
The rest reads `GFX.funcs.getFrameTime()` directly: the battle script's waits
(`battle_script.c`), the camera, the HUD tweens, entrances, hit effects, lights
and the digimon change. Scaling `frames` alone would run the animations at 2x
while the script still waits at 1x (idle gaps, and hit effects that no longer
line up with the animation they belong to). Scaling `getFrameTime` in battle
mode would speed everything up, but that is a fast-forward and overlaps P6.4
(R3 already runs a battle at 2x to 4x, and the row picks the speed). A
dedicated "battle speed" would be a new, separately tuned feature and is not
done here. It can land later as a P7.4 item.

## Limits (honest list)

* **Text speed** changes only the windows that type at delay 6, which is every
  dialogue, message box and report line of the game, and, at Instant only, the
  area name banner's delay 5 (its names are shown whole; its boxes and hold are
  the game's). A window the decomp types with another delay keeps it.
* **Instant** was not run against every text of every bank: it is the same
  call as the player pressing Cross on a page, and the waits, pauses and page
  breaks are control codes it does not skip, but a text that relies on the
  typing time for its pacing without a wait (a pause is honoured; a text that
  just types on) reads faster. The first dialogue of the opening was checked
  by screenshot. A text that scrolls shows one new line every 12 frames
  (patch 0068); a scroll the Instant code does not see (a window with another
  delay) keeps the game's own timing.
* **Encounter rate** changes the countdown of the random areas only. The
  number of footsteps to the next battle is still random (the game's own roll),
  at half the speed under 0.5x. The Options screen is only reachable from the
  title, so the rate cannot change in the middle of a walk.
* **Not covered**: a long play-through (no save reaches a random battle by pad
  input alone, so the field was entered directly with `DW3_START_MODE`, which
  the Switch build has no environment for); the other four EU languages' text
  (the typing mechanism is language-independent, the replays ran the English
  one); the OLED.
* **Two PC-only scenario groups.** The encounter scenarios need
  `DW3_START_MODE` / `DW3_PROGRESS` and run only on the PC build; the text and
  persistence scenarios run on the Switch build in Ryubing too.
* **Battle animations** are not implemented (above).
