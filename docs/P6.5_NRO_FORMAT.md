# P6.5 NRO format notes (FW 23.x baseline)

Research note for the release packaging baseline (P6.5). Question: does
firmware 23.0.0's NRO format work change require anything from our
`switch-release.yml` / `tools/build_switch_game.sh` flow? Written
2026-10-16 from the sources listed below; no builds were run (NTFS
worktree, no Docker here). Verdict up front: **nothing to change in CI or
the build**; the ~8.9 MB uncompressed game `.nro` stays exactly as the
toolchain emits it. Details and evidence follow.

## NRO0 format facts

`switchbrew` now documents the NRO0 file as (`nn::ro::detail::NroHeader`):

- A 0x10-byte prefix at file offset 0 (`RocrtHeader`), then the `NRO0`
  signature at 0x10, Version, Size, Flags, the .text/.ro/.data descriptors,
  and the BSS size inside the 0x70-byte NroHeader. The previously reserved
  slot at NroHeader offset 0x3C becomes `[23.0.0+]` `AdditionalHeaderOffset`.
- `RocrtHeader` is the historical NroStart that `elf2nro` always wrote as
  zeros. It only matters to the official `nn::ro` service (it locates the
  module header). [17.0.0+] widened one of its fields; homebrew loaders
  never read it. There is no record — through Atmosphere releases up to
  1.12.x — of a NRO0 layout break requiring rebuilt binaries: NROs from
  years-old `elf2nro` output keep launching on 17.0.0+ consoles.
- Homebrew asset (`ASET`, version 0) section at file offset
  `{NroHeader.Size}`: icon (256x256 JPEG), NACP (0x4000), optionally
  romfs. `switchbrew` points at `switch-tools` as the reference
  implementation of exactly this section.

FW 23.0.0 additions, marked `[23.0.0+]` on the wiki page:

- `Flags` bit 1 = `Compress`.
- `NroHeader` offset 0x3C = `AdditionalHeaderOffset`, pointing at a new
  `AdditionalNroHeader` (`NRA0`) with `CompressedSize` and a hash region.
- Atmosphere's 1.12.0 notes confirm the mechanism from the loader side:
  Atmosphere's `ro` sysmodule "was updated to reflect the latest official
  behavior. NROs can now be lz4 frame compressed."

So: the 23.0.0 `NRA0`/`Compress` path is an **optional, opt-in compression
feature** in the official module loader, not a new baseline header. An
uncompressed NRO0 has no `AdditionalHeaderOffset`, no `Compress` flag, and
is the same byte layout homebrew has shipped since 2017.

## What our toolchain emits

`elf2nro` (switch-tools master) writes:

- A zeroed 0x10-byte `NroStart` (the `RocrtHeader` prefix).
- `NroHeader` with magic `NRO0`, `version = 0`, and
  `flags = aligned_header << 0` only. There is no code for `NRA0`,
  `AdditionalHeaderOffset`, or compression anywhere in the source; the
  repo's last commit is 2024-10-23, so FW 22-23 support has not been
  (and does not need to be) added there.
- Segments are copied uncompressed. (LZ4 appears in `elf2nso` for the
  separate NSO format, which official ExeFS binaries use — not our NRO
  path, and unrelated to the 23.0.0 NRO0 feature.)
- The `ASET` asset section with icon/NACP/romfs from
  `--icon/--nacp/--romfs` options.

Our build calls this binary twice:

- `platforms/switch/CMakeLists.txt` uses the devkitPro toolchain macros
  `nx_generate_nacp` + `nx_create_nro` (NACP + ICON, no romfs). The devkitA64
  image is `devkitpro/devkita64:latest` via `tools/build_switch_game.sh`
  (and `tools/dk.sh`), which today is the `20260219` image tag.
- `platforms/switch/Makefile` (CI job `switch`, the `host_hello` sample)
  uses libnx `switch_rules`, whose `%.nro` rule is `elf2nro $< $@` plus our
  `--nacp=` override. That pass is only the sample, not the game image.

Both entry points therefore produce the identical classic uncompressed
NRO0 + ASET layout. The 23.0.0 compression step has no homebrew
implementation: `switch-tools` (2026 master) cannot emit `NRA0` NROs, so
the toolchain in our image can never set `Compress` or
`AdditionalHeaderOffset` on its own.

## Loader expectations (hbmenu / hbl / Atmosphere / Sphaira)

- Atmosphere 1.12.0 added FW 23.0.0 support; 1.12.1 (2026-10-16) still
  bundles hbl 2.4.5 + hbmenu 3.6.1. The release notes describe 23.x kernel/
  service changes (42-bit address space, ShadowStack, c-ares DNS in
  `dns.mitm`, BatchRead storage in `fs.mitm`) and the `ro` lz4 feature.
  Nothing requires homebrew NROs to be compressed or to carry any new
  header.
- `nx-hbloader` v2.4.5's changelog highlights HOS 21.x compatibility; no
  NRO0 format change since. `nx-hbmenu` v3.6.1's newest user-visible
  change is a warning for homebrew using an old launch ABI — a libnx
  runtime concern, not a file-format one.
- Sphaira (hbmenu replacement by iTotalJustice) launches `.nro` files and
  installs forwarders from them; it consumes the same classic NRO0 +
  ASET layout, which is all toolchains currently produce.

Consequence for us: the uncompressed path remains the only guaranteed
supported path across hbmenu, Sphaira and Atmosphere on 23.x, and it is
what we already ship. The only Atmosphere-related requirement for users
is Atmosphere 1.12.x+ when the console runs FW 23.0.0 (stated in
Atmosphere's own notes; worth one line the next time
`platforms/switch/release/README.txt` is refreshed).

## Answers to the research questions

1. **Does devkitA64 auto-emit the 23.0.0 `NRA0` header / Compress flag?**
   No. `elf2nro` master (last commit 2024-10-23, image = what CI uses)
   only knows `flags` bit 0 (`AlignedHeader`) and writes every segment
   uncompressed. `NRA0`/`Compress` exists only on compressed NROs; the
   compressing step is lz4-framing before load and is exclusive to the
   official 23.0.0 `nn::ro` chain (mirrored by Atmosphere's `ro`). No
   homebrew packer in our image triggers it.

2. **Anything to change in CI/build for FW 23?** No change required.
   The release and CI `.nro`s are uncompressed classic NRO0 files with an
   ASET section, which every current launcher accepts; Atmosphere 1.12.x
   keeps that contract on 23.0.0. The release install notes could gain
   one line for FW 23 consoles (Atmosphere >= 1.12.x) at the next README
   refresh; that is release text, not a build change. CI keeps
   `devkitpro/devkita64:latest` (= `20260219` as of 2026-10-16); if build
   reproducibility is ever needed, pinning the digest
   (`sha256:1fc388c3...` for that tag) is the option, and that is a tree-
   wide policy call, not a FW 23 fix.

3. **Is compressed NRO worth it at ~8.9 MB?** No. Sizes would likely drop
   well under the original (code + rodata compressed, unmeasured), but we
   cannot produce it (`switch-tools` has no NRO0 compressor), homebrew
   loaders only legitimately support the uncompressed layout today, and
   the artifact is a small SD-card download either way. Revisit only if
   `switch-tools` ever implements it and hbl/Sphaira document support.

4. **Assets section story unchanged?** Yes. ASET v0 with icon + NACP
   (+ optional romfs) matches what `nx_create_nro(ICON, NACP)`
   produces; we ship no romfs because game data is extracted from the
   owner's disc to `sdmc:/switch/dw3/us` / `eu/` at first boot. The NACP
   23.x additions sit at offsets >= 0x3448 inside the same 0x4000 field
   and touch nothing we set (display_version at 0x3060 stays the hbmenu
   version source, see `tools/dw3_nro_version.py` and the checks in
   `tools/build_switch_game.sh` / `switch-release.yml`).

## Limits of this note

No FW 23.0.0 console was available here; loader-side statements come from
release notes and the current wiki page, and hardware acceptance stays
with the normal OLED preview checks. `switch-tools`, `libnx`, `hbl`,
`hbmenu` or Atmosphere changing their NRO contract would invalidate the
verdict — the wiki page and the linked release notes are the fast
re-check.
