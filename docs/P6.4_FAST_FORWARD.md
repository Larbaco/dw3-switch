# P6.4 fast-forward ("turbo")

**Status (2026-10-24): done.** Owner confirmed on the OLED, 2026-10-24.

Fast-forward runs the game 2x, 3x or 4x while it is on, for grinding,
walking the map and battles. It is a port addition with no PS1 equivalent.

## Using it

| Action | Switch | PC gamepad | PC keyboard (PSY-Z map) |
|---|---|---|---|
| Fast-forward on / off | Right stick click (R3) | Right stick click (R3) | **2** |
| Pick 2x / 3x / 4x / OFF | Title → Options → Fast-forward | same | same |

- The Port options row reads `Fast-forward: 2x (R3)` by default. Confirm on
  it cycles 2x → 3x → 4x → OFF. OFF disables R3 completely.
- The game always starts at normal speed; R3 turns fast-forward on, a second
  press turns it off. Holding R3 toggles once.
- It only speeds up the **field** (`FIELDSTG`), **battle** (`FIGHTSTG`) and
  **battle report** (`STFGTREP`, the results screen after a won battle; since
  2026-10-24, see [Battle report](#battle-report-preview31-rc1-oled)) modes.
  Title, movies, menus that load as their own mode (the field menu's screens,
  `STSTATUS`, included), the memory card screen and the card game always run
  at normal speed. Fast-forward stays armed across them and resumes when the
  field or a battle comes back.
- Music and sound effects play faster too: the sequencer ticks once per game
  frame, as on the PS1.
- The row value (OFF / 2x / 3x / 4x) is saved in `port_options.cfg` (P9.4),
  like the other Port options rows. Whether R3 is *currently* on is not: the
  game always starts at normal speed and R3 arms it.
- `DW3_TURBO=2|3|4` in the environment starts the game with fast-forward on
  at that speed (test runs); `DW3_TURBO=0` sets the row to OFF.

R3 is free: the decomp never reads `PAD_L3`/`PAD_R3`, and a PS1 digital pad
has no stick buttons. It is also clear of the Switch diagnostic chords
(Minus + ZL + ZR) and the P6.9 restart chord (L1 + R1 + Start + Select).

## How it works

`port/options/turbo.c` owns the policy: the R3 toggle, the speed from the
Port options row, and the field / battle / report check through
`dw3_overlay_current_mode_file()` (US 0x158/0x159/0x1C2, EU
0x166/0x167/0x1D1). Patch
`0051-PORT_HOST-p64-fast-forward-poll.patch` calls `dw3_port_turbo_poll()`
once per frame after `PAD.update()`. The hosts ask
`dw3_port_turbo_speed()` every vsync and pace from it:

- **Switch** (`platforms/switch/psyz_backend/nx_gpu.c`): `Psyz_VideoVSync(0)`
  presents one game frame in `speed`. The skipped frames do not upload VRAM
  or swap, so nothing waits on the display; the battle mesh layer still
  flushes and resets per frame so the next shown frame starts from the same
  state. The CPU rasterizer still draws every frame, so the real speed on
  hardware is "up to" the setting. No CPU/GPU clock change (the owner does
  not overclock the Switch).
- **PC** (`platforms/pc/src/main.c`): while fast-forward runs, PSY-Z is put
  in `PSYZ_VSYNC_LIMITLESS` and the vsync pump paces each frame to `speed`
  times the base rate from `Psyz_VideoStats()` (59.94 Hz NTSC, 50 Hz PAL).
  Every frame is still presented. The previous vsync mode comes back when
  fast-forward stops. If the PC cannot keep up, the pacer drops its
  schedule instead of sprinting afterwards.

No game state, timer or RNG changes: the game simply runs more frames per
second, the same frames it would run at 1x.

## Validation

- `tools/tests/test_turbo.py`: the R3 toggle, field / battle / report
  gating (the field menu screens stay at 1x), speed from the option, OFF
  disabling R3, `DW3_TURBO`.
- `tools/tests/test_port_options.py`: default 2x and the 2x → 3x → 4x →
  OFF cycle.
- Builds: PC `sdl3_gpu` US and EU; Switch game `.nro` US and EU.

In-game, 2026-10-14, commit 0b94858, owner's machine on private Xvfb
displays, US and EU discs (evidence outside Git in
`tmp/evidence/p64-turbo/`):

- **PC** (`sdl3_gpu`, game frames per second read from PSY-Z's frame
  counter; Xvfb has no driver vsync, so the 1x baseline used PSY-Z's own
  limiter):

  | | US | EU |
  |---|---|---|
  | Field 1x | 60 | 50 |
  | Field 2x (R3) | 120 | 100 |
  | Field 3x (`DW3_TURBO=3`) | 180 | 150 |
  | Field 4x | 218–220 (Xvfb ceiling ~211 uncapped) | 200 |
  | Battle 2x | 120 | 100 |

  R3 off returns to 60/50 and on again to 2x. Title and opening movie stay
  at 1x with `DW3_TURBO=3`. The Status menu (its own mode) drops to 1x and
  2x resumes back in the field.
- **Ryujinx** (US and EU): `dw3-turbo: speed 2x` in the field, R3 toggles,
  clean picture in field, field menu, Status and battle (mesh path), no
  crash. Ryujinx is CPU-bound on that machine, so the measured gain was
  small (field: 60 game frames in ~1.40 s at 1x vs ~1.30 s at 2x). The
  present skip works, but the CPU rasterizer dominates; the real gain on
  the Switch has to be measured on the OLED.
- On the Switch title, R3 logs nothing (the native title overlay consumes
  the pad); harmless, since the title always runs at 1x.

## Battle report (preview.31-rc1 OLED)

Owner feedback (2026-10-24, preview.31-rc1, OLED): "even with turbo on and
Text speed Instant, the post-battle text still runs slowly".

**Cause.** The battle report (exp, money, item, level ups) is its own mode,
`STFGTREP` (US file 0x1C2, EU 0x1D1), loaded between `FIGHTSTG` and the
field. The gate above only accepted the field and battle mode files, so with
R3 on the game ran 4x through the battle, dropped to 1x for the whole report
and went back to 4x in the field. The OLED logs show it (rc6:
`dw3-turbo: speed 1x` right after the report's `gutter 0 px` line, `speed 4x`
again in the field), and so does the PC: `speed 1x` at `STFGTREP_start`. The
report's text itself was already instant at Instant (pages logged in 1-2
frames); what still crawled was the screen around it at 1x, and then the
area name banner of the field (its names typed at the game's speed in every
Text speed, see [P6.18](P6.18_PACING.md#instant-and-the-area-name-banner-preview31-rc1)).

**Fix.** `STFGTREP` is the third mode file of the gate (`turbo.c`). Nothing
else changes: the report runs the same game frames (84 on the US forced
battle, 101 on the EU one, before and after), only more of them per second.
The win jingle plays in the report (`SEP loop count 127 seq=1 tr=14`); like
the battle music it now plays at the turbo speed while R3 is on, and the
report does not wait for it (the jingle loops until the field's music stops
it), so no wait of the game depends on it. Turbo off: unchanged. The field
menu's screens (`STSTATUS`) still run at 1x.

**Checks.** `tools/tests/test_turbo.py` (the report keeps the speed, the
field menu screens do not); replay `us/eu-postbattle-instant` (turbo 4x and
Instant: `speed 1x` between `STFGTREP_start` and `STFGTREP return` is
forbidden; fails on a build without the fix) and `us/eu-postbattle-normal`
(no turbo: no turbo line at all); `us/eu-victory-music` still passes (the
jingle between `STFGTREP_start` and `STFGTREP return`). Evidence:
`tmp/evidence/20261024-postbattle-text/`.

**OLED check.** Win a battle with R3 on (4x): the results screen (panels
sliding in, the exp roll, the level-up blink, the fade out) runs at the same
speed as the battle; `dw3.log` has no `dw3-turbo: speed 1x` between the
battle and the field unless R3 was pressed. The win jingle plays sped up with
the rest, as the battle music does. R3 off: the report as before.

## Field FPS depends on what is on screen (rc8 OLED)

On the OLED (US disc, preview.30-rc8, no log) the owner walked inside the
Forest inn: at the bottom corner of the room the FPS reads 120+, at the top it
drops to about 80, and the owner expects the same in other places. It is a
HUD reading, not a benchmark, and the turbo setting was not stated. The room
and the game logic are the same, only the camera and what is visible change,
so the cost of a field frame depends on the on-screen content (visible
geometry, sprites and tiles: raster and draw cost). That is consistent with
the rc7 log reading that the field is bound by game logic plus the CPU raster
per frame (the measured rc7 numbers are in "New Game opening, measured from
the rc7 log" below, about 13.7 ms of CPU per field frame, and the P6.10
reasoning), and it adds that this cost is not fixed: it moves with the camera.
It is not proof: the rc8 reading has no counters or log.

For the P6.22 measurement, use this as an A/B: the same room, the same disc and
turbo setting, standing at the bottom corner and then at the top for about
10 s each, and compare `frame dt us=`, `mesh dbg:` (`flush_us`, `upload_us`,
`present_us`, `frames_blit`, `soft`) and `mem dbg:` between the two positions.
Only the camera changes, so any difference is on-screen cost. Then repeat in
one other room or map.

## Deferred field raster skipping (preview.25 feedback)

The owner validated R3 turbo on the EU OLED: about 180 fps in battle at
2x, versus 70–80 fps in the field. This is feedback, not a new performance
measurement. Switch still rasterizes every game frame and skips only
presents. PR #146 proposed dropping display-buffer draws too, but the
field encounter transition copies VRAM `(0,0,320,240)` with `MoveImage`
(`FIELDSTG_playBattleTransition`) to use it as a transition texture. A
dropped buffer can therefore be sampled even when no present shows it.
Keep this optimization deferred until framebuffer readbacks/copies are
preserved and field-to-battle transitions pass at 2x/3x/4x.

### New Game opening, measured from the rc7 log (2026-10-23)

First numbers for P6.22, from the `dw3.log` of the owner's second rc7 run
(`dw3_ponte.log`, US disc, OLED handheld, nxlink build, a New Game played
through the opening, the lobby and the bridge walk; 15734 lines, not
committed). Each sample is one `frame dt` window of 60 vsync pumps, which is
60 game frames, with the `mesh dbg:` line of the same window
(`frames_blit` / `frames_mesh` count presented frames, `present_us` is the
window total). The log does not mark scenes, so these are all the windows of
the session, not only the opening: the opening, the lobby and the walks
cannot be told apart in it. One window of 9391087230 us (the console slept)
is left out.

| Windows | N | Time | Game frames per second (weighted) | Spread (p10 to p90) | Median window | Presents per window | `present_us` |
|---|---|---|---|---|---|---|---|
| Turbo 4x, field and event scenes (CPU raster, `frames_blit`) | 4998 | 4396 s | **68.2** | 63 to 74 (best window 85) | 863 ms | 15 (every 4th frame) | 42 ms |
| Turbo 4x, one battle (GPU mesh, `frames_mesh`) | 26 | 8 s | **190** | 171 to 235 | 300 ms | 15 | 46 ms |
| 1x, field and event | 72 | 90 s | 48 (transitions and the movie drag it down) | 36 to 60 | 1054 ms | 59 | 168 ms |

Reading, as hypotheses to confirm, not conclusions:

- **Turbo 4x in the field and in scripted scenes runs at about 1.1x, not 4x**:
  68 game frames per second against the 240 the 4x setting asks for on the
  US disc (28 %). The best window of the whole session reached 85. In the same
  run and at the same setting a battle reaches about 190 (79 %), so the bound
  is in the field/event path, not in the turbo gate or in a global wait.
- **It is not the present.** `present_us` is the sum over the window: 42 ms
  for 15 presents (about 2.8 ms each, the same as 1x: 168 ms for 59), under
  5 % of the 863 ms window. About 820 ms are left for 60 game frames, which
  is **about 13.7 ms of CPU per game frame** in the field (with the raster
  drawing every frame), against about 4.2 ms in the battle window
  (300 ms - 46 ms over 60). A fixed 13.7 ms per frame caps the rate near
  70 fps whatever the setting, which is exactly what the owner sees. This
  points at candidate (1) of P6.22 (game logic plus the software raster per
  emulated frame) and away from the present path; skipping presents, which
  is all turbo does on the Switch today, cannot help.
- The 1x field windows are not comfortable either: the median is 1054 ms per
  60 frames (57 fps), 31 of 72 windows are at 1.0 s and 19 at 1.1 s, and a
  tail of transitions is slower, so the field sits at its budget even at
  normal speed. That fits a CPU-bound frame.
- Text typing is cheap in game frames: 107 of 111 pages were typed in 1 or 2
  frames with Text speed Instant (4 took 40 or 66 frames, not examined).
- Not in the log: which scene each window is (no `mode=` or overlay lines in
  the sampled stretch), a split of game logic against raster per frame, and
  whether the turbo gate (field and battle mode files only) misses any of
  these scenes. `soft=` is 0 in every window, so the CPU raster of the field
  is the normal path and not the mesh fallback. The next step is still
  (a)/(b) of P6.22: a PC replay of the opening at `DW3_TURBO=4` that times
  logic against raster per scene.
