# P6.22 Where a field frame's CPU time goes

Measured 2026-10-24 on the PC build, as a proxy for the Switch. Goal of
P6.22 ([ROADMAP](ROADMAP.md#phase-6-goal-notes)): turbo at 4x reaches only
about 68 game fps in the field and scripted scenes on the OLED (rc7 log,
about 13.7 ms of CPU per game frame), against about 190 in battle.

## Result

- **The CPU rasterizer is about 97 % of a field frame.** It is PSY-Z's
  `sdl3_software.c`, which the Switch draws everything outside battle with
  (`switch_gpu.c`). In the field and the scripted scenes of the New Game
  opening it costs 2.2-2.6 ms per game frame on the PC, against about 60-70 us
  for all the game logic, the OT walk and the pad and sound code together.
- **Most of that is rectangles.** The map is drawn as 128x128 8-bit CLUT
  sprites, plus a full-screen clear (a 320x240 TILE, wider with the gutters).
  Textured triangles (the dialogue window and text) are about 10 %.
- **Top against bottom of the Forest Inn is fill, not logic.** The same 29
  map sprites and 47-48 primitives are drawn at both spots, but at the top the
  camera shows more of the map: 184 000 sprite pixels per frame against
  142 000 at the bottom, where a large part of the screen is the black void
  below the floor that no map block covers. +29 % pixels gives +29 % raster
  time; the game logic is the same (66 against 63 us).
- **Implemented:** a faster CPU rasterizer in PSY-Z (`dw3-soft-raster-fast`,
  `2f931d8`), same pixels: 4.0-5.4x less raster time in field, menu and
  scripted scenes, 0 differing pixels in 154 605 frames of 18 US and EU
  replays and in 6 million random operations over the full GP0 ranges.
- **Expected on the OLED:** the field at 4x from about 68 game fps to roughly
  160-240 (the 4x target is 240 US, 200 EU). This is an estimate from the PC
  (below), not a measurement; the OLED check is open.

## Method

The PC host draws with SDL_GPU, so the Switch's rasterizer does not run there.
The profiler build (`-DDW3_PC_FIELD_PROF=ON`, `platforms/pc/src/field_prof.c`,
off by default) wraps the `Draw_*` contract at link time and feeds every call
to the PC renderer and to a shadow copy of `sdl3_software.c`, with the same
gutter bookkeeping as `switch_gpu.c`. Nothing the PC shows or the game does
changes: the replay captures of the profiler build match the references (222
checks, 0 failed). Every 60 game frames it prints a `dw3-prof:` line:

| Field | Meaning |
|---|---|
| `cpu_us` | the game thread's CPU per frame (`CLOCK_THREAD_CPUTIME_ID`) |
| `soft_us` | the shadow CPU rasterizer, per primitive kind (`tile`, `sprt`, `pf`, `pg`, `pft`, `pgt`, `line`, `img`: count / bounding-box kilopixels / us) |
| `pcgpu_us`, `vsync_cpu_us` | the PC's own renderer and present (PC only, not on the Switch) |
| `game_us` | the rest: decomp logic, OT walk and packet dispatch, pad, sound sequencer |
| `load_kb` | `LoadImage` bytes per frame (VRAM uploads) |
| `mix_us_per_s` | the SPU mixer's CPU per second of audio (its own thread) |

`DW3_PROF_SAMPLE=<file>` samples the game thread (SIGPROF on its CPU clock)
for a function-level split; `DW3_SOFT_TRACE=<file>` writes a binary trace of
every `Draw_*` call, and `DW3_SOFT_HASH=<file>` a hash of the shadow VRAM per
frame. `tools/soft_raster_bench.sh` replays a trace through the current
rasterizer and a reference revision built into the same binary, times both
per primitive kind and compares VRAM and the gutter planes after every frame
(`--fuzz N` does the same with random primitives). `perf` is not usable on this
desktop (`perf_event_paranoid` 4).

Runs: PC US and EU, Release (GCC 13, `-O3`), Xvfb, `DW3_TURBO=4`, driven by
replay recordings: the Forest Inn with `DW3_START_MODE=0x223 DW3_PROGRESS=6`
(stage WSTAG360) and a walk to the top and to the bottom of the room, and the
P6.15 scenarios. The desktop was shared with other jobs, so absolute times
move by tens of percent between runs; the bench interleaves old and new, so
its ratios are the stable numbers. Evidence (logs, tables, scripts,
screenshots; not committed):
`tmp/evidence/2026-10-24-p622-field-cpu/`.

## Cost per game frame (PC, before the change)

Forest Inn, US, median of 60-frame windows standing still:

| | Top (upper floor) | Bottom (below the counter) |
|---|---|---|
| Game thread CPU | 2006 us | 1595 us |
| CPU rasterizer | **1782 us** (89 %) | **1379 us** (86 %) |
| - sprites | 1400 us, 191 kpx, 41 prims | 986 us, 150 kpx, 41 prims |
| - full-screen clear (TILE) | 343 us | 333 us |
| - textured polygons | 42 us | 60 us |
| Game logic + OT + pad + sound | 66 us (3 %) | 63 us (4 %) |
| PC renderer and present (PC only) | 157 us | 152 us |
| VRAM uploads | 0 KB (map preloaded) | 0 KB |

A sampler run in the same room (frames 400-2000) gives the same split: 90 %
of the game thread in the rasterizer (`SampleTexture` 32 %, `WritePixel` 24 %,
`RasterSprite` 22 %, `ShadeTexel` 20 % of it), 3 % game code (of which the OT
walk, `Psyz_GpuExeque`, is about a sixth), 7 % the PC's own renderer.

New Game opening, US, one serial run (mean per frame per stage):

| Stage | Game thread | Rasterizer | Game logic |
|---|---|---|---|
| Kusanagi street (WSTAG780) | 2829 us | 2571 us | 68 us |
| Online Center (WSTAG785) | 2434 us | 2194 us | 64 us |
| Name entry (STPLNMET) | 4002 us | 3802 us | 78 us |
| Chamber Room (WSTAG790) | 2616 us | 2382 us | 61 us |
| Main lobby | 2594 us | 2350 us | 76 us |

Within the rasterizer (bench, whole `us-newgame-field` trace, 16 825 frames):
sprites 1637 us, full-screen clear 322 us, textured polygons 194 us, the rest
under 20 us. The map sprites are 8-bit CLUT, opaque, at the neutral color
(128, 128, 128), without texture window: 58-68 % of all rectangle pixels.
Overdraw: 3.5x the 4:3 screen area painted per frame at the top of the inn,
3.0x at the bottom, the clear included.

Audio: the SPU mixer costs 13.4-14.6 ms of CPU per second of audio on the PC
(1.4 % of a core). It runs on its own thread on both hosts; on the Switch
`nx_audio.c` creates it with `cpuid -2` (the process's default core, where the
game thread also runs) at a higher priority (0x20), so its share is taken from
the game thread's core.

## Top against bottom of the Forest Inn

The owner's rc8 reading (120+ fps at the bottom corner, about 80 at the top)
comes from fill. The trace of the two spots has the same primitives: one
full-screen clear, 29 map sprites (128x128 blocks and their cut-offs), 11-12
small actor and shadow sprites, 4 textured polygons. At the top six full
128x128 blocks are on screen (98 kpx) against four at the bottom (66 kpx): the
bottom view has a large black area below the floor, painted only by the clear.
The CPU cost of a sprite is per pixel, so the raster time follows the
on-screen map area. Game logic, primitive count and VRAM uploads do not change
between the two spots. With the rc7 calibration below, the old rasterizer
gives about 8.3 ms per frame (120 fps) at the bottom and about 10.5 ms (95 fps)
at the top, close to the owner's reading.

## From the PC to the OLED

The OLED (Cortex-A57 at the stock 1020 MHz) is slower than this PC per
thread. One calibration point: the rc7 OLED log gives 13.7 ms per field frame,
of which about 0.7 ms is the present (2.8 ms per present, one present every
fourth frame at 4x). The PC's Switch-relevant part of the same kind of frames
(rasterizer plus game logic) is about 2.45 ms, so the OLED is about 5.3x the
PC here. The new rasterizer brings the field to 0.5-0.9 ms of rasterizer plus
logic on the PC, which at 5.3x is 3.2-5.3 ms per frame on the OLED with the
present: about 190-300 game fps, so at the 4x cap in most places. The A57 does not scale uniformly (the old
code was division- and branch-bound, the new code is mostly loads and
stores), so the doc's planning range is 160-240 fps at 4x, capped by the 4x
target. The OLED check is open: the same A/B in the Forest Inn and the New
Game opening with `frame dt us=` and `mesh dbg:` lines on a `--nxlink`
build, US and EU.

## What changed

PSY-Z `sdl3_software.c` (branch `dw3-soft-raster-fast` on the Larbaco fork,
`80fa492` and the review fix `2f931d8` on top of `ef67c4a`), the Switch's
renderer for everything outside battle:

- Rectangles: each row is clipped once into up to three runs (left gutter,
  VRAM, right gutter) instead of `ClipX0`/`ClipX1` and `PixelPtr` per pixel;
  the texture row, the CLUT row and `ShadeTexel`'s modulation (a table per
  channel) are looked up once per rectangle; no division per pixel unless the
  horizontal grid scales; an opaque untextured rectangle without mask test is
  a fill, and an opaque textured one at the neutral color without texture
  window or mask test copies texels with the mask bit.
- Triangles: the edge functions step by a constant per column; a row ends at
  the first miss after a hit (each edge test passes on a half-line); texture
  coordinates and Gouraud colors step with an exact quotient and remainder
  instead of three to five 64-bit divisions per pixel; the texture page is
  decoded once; flat neutral undithered texels skip `ShadeTexel`.
- Pixels, their order and their values are unchanged, including texture reads
  of areas the same primitive writes.
- Review fix (`2f931d8`): `80fa492` relied on the row clamps for `PixelPtr`'s
  y test, but clamping to the area and then to VRAM leaves row 511 when the
  area starts at y >= 512 (a 10-bit GP0 E3 y that libgpu never sends), so a
  triangle drew that row where the old code drew nothing. Triangle rows are
  now limited to the area too. The reviewer's repro (area (0,600)-(1023,1023),
  `GP0 20ffffff 00000000 0000012c 02bc0000`) writes 81 px with `80fa492`
  and 0 px now, as `ef67c4a`. Rectangles already test each row.
