# P3.7 — Movie pacing diagnostics (StGetNext busy-wait)

Status: **investigation recorded; empty-poll gate landed on
`perf/stgetnext-ready-gate`.** No pump/pacing change, no sleep/yield.

## What the perf run showed

OLED perfdiag (PSY-Z `eb0393b`, pace correct at 150 sectors/s): in movie mode
`StGetNext` accounted for 61–79% of each 60-VSync window, with ~1.5M calls/s and
almost every call finding no sector due. Actual delivery stayed ~150 sectors/s.
MDEC/RGB24/present/swap were a small fraction. The nested pump microsecond
metric overflowed, so the *distribution* inside a window is not trustworthy;
the `StGetNext` call/wait counters and its outer wall-time were.

## Why the calls are empty

The game waits for the next movie frame in `STDWTITL_getNextFrame`
(`vendor/dw3_decomp/src/menus/title/movie.c`): `while (StGetNext(...) != 0)`,
up to 2,000 calls, inside a 2,000-iteration retry. Every call enters
`__wrap_StGetNext`, which pumps one paced step and then, when the read cursor
`StRingIdx3` holds neither a ready frame (`id 2`) nor the wrap sentinel
(`id 1`), scans every ring slot for one. At 150 sectors/s a frame is ready only
~every 60 ms, so ~99.99% of polls scan and find nothing.

Two costs sit on that empty path: the port wrapper's slot scan
(`platforms/switch/psyz_backend/nx_present.c`) and the pump's per-call clock
read inside `Psyz_CdPumpStream`. This change removes only the first, in the
Switch wrapper.

## The gate and why it is safe

`__wrap_StGetNext` now remembers a poll that scanned the whole ring clean,
keyed on `(StRingAddr, StRingSize, StRingIdx1, StRingIdx3)`, and returns
immediately while that key is unchanged. Ordering proof:

- `id 2` is written only by `data_ready_callback` (`c_004.c`), reached only from
  `StCdInterrupt` after it already ran `StRingIdx1++`.
- `id 1` is written only at `StCdInterrupt`'s wrap, immediately before
  `StRingIdx1 = 0` (reachable only with `StRingIdx1 > 0`).
- So a ready frame or sentinel cannot appear without moving `StRingIdx1`.
- One pump publishes at most `CD_PACE_CATCHUP` (8) sectors, and the ring holds
  32 slots, so between two consecutive polls the write cursor cannot leave and
  re-enter the same value. Two polls are one pump apart: the game only spins in
  `StGetNext` between them.
- `StFreeRing` and the body-resync reposition move `StRingIdx3`; the verdict is
  also dropped on a hand-off, on an unusable ring, and whenever the recovery
  path runs.
- Paths that only *remove* a ready/sentinel slot (`StClearRing`, the
  `StCdInterrupt` reset, the sentinel reset) cannot create a frame the gate
  would skip.

`dw3_stgetnext_gate_hit` refuses rings at or below `DW3_STGETNEXT_RING_MIN` (8),
so if a future change raised the catch-up cap or shrank the ring the gate stops
engaging rather than risk a stale verdict.

## What it does not do

The gate does not change the stream rate (the pace is wall-clock, unchanged),
frame delivery, XA sync, the MDEC handshake, `VSync`, Start-skip, or the
wrapper's return value. It does **not** make the movie smoother: a 15 fps
stream paced at 150 sectors/s is the intended behaviour. It removes redundant
empty-poll work, so the win is CPU/power/headroom, not frame rate.

## Remaining uncertainty / follow-up

- Whether the per-call monotonic clock read in `Psyz_CdPumpStream` is now the
  dominant empty-poll cost is unmeasured here; that is the next thing to profile
  if `StGetNext` is still hot. It is upstream-PSY-Z, so it needs its own change.
- The OLED `dt` up to 10.9M us/60 (~181 ms/frame, ~5.5 fps) is hard to
  reconcile with a sustained 150 sectors/s and should be re-bucketed with a
  64-bit timer before drawing conclusions from it.
- Do not add per-poll sleeps or yields: the 2,000x2,000 retry budget is a
  wall-time watchdog and a naive delay stretches it from ~2.7 s to hours.

## Tests

`tools/tests/test_stgetnext_gate.py` builds `tools/tests/stgetnext_gate_main.c`
against the real `platforms/switch/psyz_backend/stgetnext_gate.h` and asserts
the gated wrapper's return values, read cursor and ring bytes match the ungated
wrapper across empty polls, ready frames, body-same-head bail, body resync,
orphan drop, sentinel (with and without `StEndFrame`), a ready frame found by
scan, wrap, publish-then-poll invalidation, `StFreeRing` reposition, ring reset
and a deterministic stress run -- plus a slot-visit count proving the scan is
skipped, and the guard cases.
