# P3.7 — Movie pacing diagnostics (opening STR)

Status: **Investigation note** — no code change in this branch. It records the
measured evidence behind the current Switch movie-pacing finding so the next
workstream does not have to re-measure it. Companion to
[`P3.7_MOVIES.md`](P3.7_MOVIES.md).

The A/B below only changes the PSY-Z pin, so it isolates the STR pump change:

| Pin | Meaning |
|---|---|
| `eb0393b` (`dw3-str-pace`) | current pin — `Psyz_CdPumpStream` paced at 150 sectors/s (`docs/PSYZ.md`) |
| `8dbed91` | its parent — the pre-pace Switch backend build (no 150 sectors/s budget) |

## Console capture (perfdiag-2)

A diagnostic Switch build on the current paced pin observed the opening STR as
**42,542,976 bytes**, which is exactly `18,088 × 2,352` — a raw Mode2/Form2
extent. A nearby BIN was found in that same capture, so the form-2 restore path
had run.

**Conclusion (this capture only):** a missing Form2 restore does **not** explain
the pacing problem here. The form-2 restore is ruled out for this capture, not
for every configuration. This is a single diagnostic capture, not a sweep.

## PC rate A/B — same tree, same runtime, 55 s

Both runs used the same source tree and runtime; only the PSY-Z pin differs.

| Pin | Ring activity over 55 s | Result |
|---|---|---|
| `eb0393b` (paced) | **810 distinct frames** | ≈ **14.7 fps** — near the STR's own 15 fps authoring rate |
| `8dbed91` (pre-pace) | **5,970 ring drain events**; `frameCount` reached **642**, hit the last frame, and looped | ring drained far faster than the stream rate |

Frame **#30** framebuffer dumps were **identical** between the two pins, and the
output images did not differ at that sampled frame.

**Conclusion:** the pacing change is *necessary*; reverting to the pre-pace pin
is **not** a fix. Pre-pace pulls the whole ring ahead of real time and races to
the last frame instead of pacing to the 150 sectors/s target.

## OLED perfdiag-2 (Switch) — movie windows

Each window is 60 VSync samples during movie playback.

| Window | `dt` (µs) | fps |
|---|---|---|
| 1 | 4,200,000 | 14.2 |
| 2 | 10,900,000 | 5.5 |
| 3 | 7,800,000 | 7.7 |

Share of `dt`:

| Stage | Share of `dt` |
|---|---|
| `StGetNext` | **61–79%** |
| MDEC | 3–4% |
| RGB24 | ≈0.3% |
| present | 2.7–5.5% |
| swap | ≈0.4–1% |

Outside the movie windows the title returns to ≈60 Hz, so the cost is specific
to the movie wait loop, not a global frame-rate cap.

`StGetNext` ran at **≈1.5M calls/s**, and almost all of those were no-sector /
zero-budget waits, while sector **delivery held ≈150 sectors/s** — i.e. the
wait loop is spinning far more often than the paced delivery needs.

**Caveat (do not misread the log):** the nested `Psyz_CdPumpStream` microsecond
duration instrumentation **overflowed**, so its `us` values are **not usable**.
The call / wait / delivery counters and the outer `StGetNext` timing *were*
valid and are what the table above uses.

## Source investigation (game → pump call chain)

The wait path has no naive fixed sleep. It is:

```
STDWTITL_decodeNextFrame
  STDWTITL_getNextFrame                 (retry guard: 2000)
    while (StGetNext(...) != 0)         (retry guard: 2000)
      __wrap_StGetNext                  Switch backend resync / orphan-tail scan
        __real_StGetNext                PSY-Z StGetNext implementation
          Psyz_CdPumpStream             150 sectors/s pace budget
```

- The nested retry counters bound the wait to at most **~4,000,000 `StGetNext`
  attempts** (2000 × 2000) before the getter gives up. A naive added sleep
  would push against that watchdog.
- `Psyz_CdPumpStream` is also called from the **host VSync pump**, so the pump
  has two entry points and the ring cursor is shared.
- The same CD ring carries **XA audio and video** over one stream, so any
  blocking wait has to keep the audio pull alive.
- The Switch `__wrap_StGetNext` can walk the whole 32-slot ring on each
  non-empty poll, and the pace budget reads the monotonic clock per call, so a
  no-sector poll is not free.

### Options, lowest risk first (recommendation only — none implemented here)

1. **Reduce the per-poll no-op cost** in the `StGetNext` / pump path (the
   per-call clock read and the ring scan) and remeasure. Lowest risk; no
   behavior change to the CD timing.
2. **A bounded cooperative wait** (yield instead of spin) — would need the
   watchdog and the MDEC slice handshake re-tested.
3. **Move the pump to a thread** — higher risk: the ring cursor and the shared
   XA/video stream would need ownership rules.

## Read this with

The PC A/B points at **~150 sectors/s as the correct target**, and the Switch
path is dominated by the `StGetNext` busy-spin rather than by decode or
present. There is **no definitive fix** yet, and the numbers above come from
diagnostic builds.
