# P3.7 — Movie pacing diagnostics (opening STR)

Status: **Resolved in Ryubing; OLED-validated on preview.21 for frame rate and drops** — the pacing work below measured a busy-wait that turned
out to be a **symptom**, not the cost. The opening STR was dropping ~37% of
its frames in the producer; see *Root cause* and *Before / after*.
`fix/str-bridge-read-race`, instrumented by `DW3_NX_DEBUG_MOVIE`.
The historical measurements are kept in *Original investigation* below so the
next workstream does not have to re-measure them.

## Symptom, and why the busy-spin was a symptom

The opening FMV (`MOVIEOPN.STR`, authored **15 fps**, CD 2x = 150 sectors/s)
played far below its authored rate: **6.75 fps** on the OLED, **10.70 fps** in
Ryubing, ~15 fps on the PC host from the same game code.

The visible cost was a hot consumer: the game's `StGetNext` wait loop spun at
millions of polls per second, so PR #106 cached the empty-ring scan there and
cut the polls. It did not move the rate, because the consumer was polling for
a frame that had never been published.

The instrumented Ryubing baseline recorded 1128 handovers and 657 skipped
frame numbers: 1785 accounted frames, or 1.582 accounted frames per handover.
This supports producer-side frame loss; it is not an OLED ratio. The drop
path on a sector mismatch is the `secCount != Stsector_offset` arm in
`StCdInterrupt`: it calls `init_ring_status`, rewinds the ring write cursor
and consumes the sector, losing the partial frame until `secCount == 0`.

Ring backpressure cannot be ruled out from absent log messages: PSY-Z's
`libcd.c` writes those diagnostics to stderr, which Ryubing does not forward.
The FILE race is supported by source inspection, the synthetic read regression
and the instrumented before/after comparison below.

## Instrumentation

Both counters are cheap and stay in the tree (`DW3_NX_DEBUG_MOVIE=1`, default
on for `--nxlink` builds):

- `fc_skipped` — counted where the game takes a frame (`StGetNext` hand-over
  in the Switch present wrapper). If `frameCount` jumps by more than one
  between two handed-over frames, the difference is added. A `frameCount` that
  goes *backwards* is counted separately as `restarts`: typically a new
  playback, but that counter alone does not prove replay.
- `reads` / `read_overlap` — the STR bridge bumps `reads` on every read
  callback entry and `read_overlap` when an entry finds another bridge read
  already in flight. That check sits **before** the lock, so it keeps
  reporting contention after a fix.

`INFOF` (svcOutputDebugString) is used, not `stderr`: Ryubing does not forward
guest stdio, so `stderr` lines never appear in its log and their absence there
means nothing. `movie dbg:` and `frame dt us=` do appear.

## Root cause: a data race on the STR file bridge

`port/movies/str_stream.c` serves **two readers from one `FILE*`** with a
non-atomic open/seek/read:

- **video** — `StCdInterrupt` -> `CdReady` -> `CD_ready` -> `disk_read_cb`, on
  the game/main thread, holding no PSY-Z lock;
- **XA** — the audio thread's mixer -> `xa_pull_samples` (which holds
  `Psyz_AudioLock`) -> `xa_read_raw_sector` -> `disk_read_cb`.

The XA reader scans every sector, video sectors included, to find its 1-in-8
XA sectors, so it reads about as often as the video path. When the two
`fseek`+`fread` pairs interleave, the video path receives a sector the other
reader just seeked to. It is not the sector it asked for, so `secCount` no
longer matches, the ring resets, and the frame is dropped. The XA side gets
wrong sectors the same way.

A possible explanation for the ordering seen across hosts is that a Switch SD read goes through
fsp-srv IPC and takes long enough to lose the race often, Ryubing sits in
between, and a page-cached desktop read is short enough to almost always win.

Ruled out along the way: `StFinalSector` freezing the producer (the data-ready
callback clears it synchronously), MDEC-busy deferral (`MDEC_out` is
synchronous), `StFreeRing` (logging only),
and the PR #106 empty-scan gate (its counters stayed at zero).

## Fix

Hold PSY-Z's audio lock across every use of the bridge's file handles. That is
the lock the XA side already takes for its read, so the change only adds the
missing video side. It is recursive on every host (libnx `RMutex`,
`SDL_CreateMutex`, the PSP audio mutex), so the XA path's re-entry is safe, and
it is a no-op before audio init — when there is no audio thread to race with.

The audio thread may wait for a bridge file operation held by the video
thread. Its worst-case SD latency and audio underrun impact were not measured;
the audren buffer size (4 x 1024 frames, ~93 ms) does not establish that bound.

No pacing constant, no busy-wait behaviour, no PR #106 gate and no clock was
touched.

## Before / after (Claude Ryubing captures, same STR, 175 s run each)

Baseline: instrumented `97ef2ee`, capture `u8VZpx`. Final fixed run:
`ee0c363`, capture `8z1Teg`. These are the original author's emulator tests;
the independent emulator comparison is recorded below.

| Measure | Before | After |
|---|---|---|
| Movie windows (`frame dt us=`) | 8.91 - 9.90 fps | **14.991 - 15.009 fps** (30 complete handed=60 windows) |
| Decode rate (`DecDCTout frame done`) | 9.39 - 9.55 fps | **15.00 - 15.01 fps** |
| `fc_skipped` per 60-pump window | 31 - 41 | **0** |
| Frames lost in the run | 657 of 1785 (**36.8%**) | **0 of 1848** |
| Frames decoded in 175 s | stopped at #900 | #1800 — the whole 1776-frame movie |
| `read_overlap` per complete handed=60 window | 74.5 mean (18 windows) | 131.7 mean (30 windows) |
| Movie wall time | ~117 s for ~1068 frames | ~118 s for 1776 frames |

`read_overlap` went **up**, as expected: the contention is still there, it is
just serialized now instead of corrupting the read. Its counter sits before
the lock exactly so this stays visible.

All 30 complete `handed=60` windows in the final run held 14.991-15.009 fps.
The three partial boundary windows (`handed=21`, `15`, `12`) are excluded
from that rate. The earlier fixed capture `MUE1aV` had 1788 handovers and
is not the final run summarized here. Its mixed boundary rates are not
steady-state playback measurements.

OLED validation is recorded below. Image quality, audible synchronization,
console performance and worst-case SD read latency were not measured by this
fix's emulator counters.

## Independent emulator checkpoint (2026-10-13)

Paired runs used the same source/runtime STR input, Ryubing 1.3.339-canary,
Vulkan llvmpipe 20.1.2, firmware 20.5.0 and a private SD/profile. Audio used
SDL3 dummy. The runtime difference was the mutex: instrumented baseline
`97ef2ee` versus fixed `ee0c363`. Generated headers were prepared before
compilation; `d36faa9` subsequently makes that build order explicit.
Later documentation and header-comment changes do not change the runtime.

- Baseline, 175.14 s: logged windows sum to 1254 handovers, 529 skipped frame numbers and 1199
  read overlaps. Its 18 complete windows ran at 9.6864-11.3900 fps
  (median 10.5320). Two backwards `frameCount` transitions were recorded;
  those alone do not establish replay.
- Fixed, 175.22 s: logged windows sum to 1848 handovers, zero skips and
  4607 read overlaps. These sums exclude unlogged partial tails.
  All 30 complete `handed=60`, `restarts=0` windows ran at 14.9931-15.0064 fps. Decode milestones
  #300 to #1500 took 80.001 s; decoding reached #1800 after the complete
  1776-frame movie and replay.
- Start/Plus after 175 s exited the replay and returned to the title without
  a hang. The host regression suite passed: 85 passed, 2 skipped.

This independently confirms the frame-loss/rate fix in the emulator.
Dummy audio does not verify audible synchronization or listening quality;
OLED image quality and SD latency were not validated by these emulator
counters; see the OLED validation section.

## Reproduce

```bash
./tools/build_switch_game.sh --nxlink      # DW3_NX_DEBUG_MOVIE defaults on
```

In the guest log, one line per 60-pump window while a movie is active:

```
movie dbg: handed=<n> fc_skipped=<n> restarts=<n> reads=<n> read_overlap=<n>
```

A healthy movie is `fc_skipped=0` and a `frame dt us=` of ~4000000 in the
steady windows. `read_overlap > 0` is expected and does not mean corruption
once the lock is in.

Host regression: `tools/tests/test_str_stream_race.py` reproduces the race
outright — two threads reading interleaved LBAs from two synthetic extents,
asserting every sector returned matches the LBA requested.

## Original investigation (historical — it measured the symptom)

The A/B below only changes the PSY-Z pin, so it isolates the STR pump change:

| Pin | Meaning |
|---|---|
| `eb0393b` (`dw3-str-pace`) | `Psyz_CdPumpStream` paced at 150 sectors/s (`docs/PSYZ.md`) |
| `8dbed91` | its parent — the pre-pace Switch backend build (no 150 sectors/s budget) |

### Console capture (perfdiag-2)

A diagnostic Switch build on the paced pin observed the opening STR as
**42,542,976 bytes**, which is exactly `18,088 × 2,352` — a raw Mode2/Form2
extent. A nearby BIN was found in that same capture, so the form-2 restore
path had run.

**Conclusion (this capture only):** a missing Form2 restore does **not**
explain the pacing problem here. The form-2 restore is ruled out for this
capture, not for every configuration. This is a single diagnostic capture, not
a sweep.

### PC rate A/B — same tree, same runtime, 55 s

Both runs used the same source tree and runtime; only the PSY-Z pin differs.

| Pin | Ring activity over 55 s | Result |
|---|---|---|
| `eb0393b` (paced) | **810 distinct frames** | ≈ **14.7 fps** — near the STR's own 15 fps authoring rate |
| `8dbed91` (pre-pace) | **5,970 ring drain events**; `frameCount` reached **642**, hit the last frame, and looped | ring drained far faster than the stream rate |

Frame **#30** framebuffer dumps were **identical** between the two pins, and
the output images did not differ at that sampled frame.

**Conclusion:** the pacing change is *necessary*; reverting to the pre-pace pin
is **not** a fix. Pre-pace pulls the whole ring ahead of real time and races to
the last frame instead of pacing to the 150 sectors/s target. This still
holds — the race fix did not change the pace, only whether the paced frame
survived.

### OLED perfdiag-2 (Switch) — movie windows

Each window is 60 VSync samples during movie playback.

| Window | `dt` (µs) | fps |
|---|---|---|
| 1 | 4,200,000 | 14.2 |
| 2 | 10,900,000 | 5.5 |
| 3 | 7,800,000 | 7.7 |

Share of `dt`:

| Stage | Share of `dt` |
|---|---|
| `StGetNext` | **61–79%** |
| MDEC | 3–4% |
| RGB24 | ≈0.3% |
| present | 2.7–5.5% |
| swap | ≈0.4–1% |

Outside the movie windows the title returns to ≈60 Hz, so the cost is specific
to the movie wait loop, not a global frame-rate cap. Window 1 straddles the
movie's start, so it mixes pre-movie frames in and reads higher than the rate
during playback; windows 2-3 are steady-state playback.

`StGetNext` ran at **≈1.5M calls/s**, and almost all of those were no-sector /
zero-budget waits, while sector **delivery held ≈150 sectors/s** — i.e. the
wait loop was spinning for frames the producer had already discarded.

**Caveat (do not misread the log):** the nested `Psyz_CdPumpStream` microsecond
duration instrumentation **overflowed**, so its `us` values are **not usable**.
The call / wait / delivery counters and the outer `StGetNext` timing *were*
valid and are what the table above uses.

### Source investigation (game → pump call chain)

The wait path has no naive fixed sleep. It is:

```
STDWTITL_decodeNextFrame
  STDWTITL_getNextFrame                 (retry guard: 2000)
    while (StGetNext(...) != 0)         (retry guard: 2000)
      __wrap_StGetNext                  Switch backend resync / orphan-tail scan
        __real_StGetNext                PSY-Z StGetNext implementation
          Psyz_CdPumpStream             150 sectors/s pace budget
```

- The nested retry counters bound the wait to at most **~4,000,000 `StGetNext`
  attempts** (2000 × 2000) before the getter gives up. A naive added sleep
  would push against that watchdog.
- `Psyz_CdPumpStream` is also called from the **host VSync pump**, so the pump
  has two entry points and the ring cursor is shared.
- The same CD ring carries **XA audio and video** over one stream, so any
  blocking wait has to keep the audio pull alive.
- The Switch `__wrap_StGetNext` can walk the whole 32-slot ring on each
  non-empty poll, and the pace budget reads the monotonic clock per call, so a
  no-sector poll is not free.

### Options considered at the time

1. **Reduce the per-poll no-op cost** in the `StGetNext` / pump path — this is
   what PR #106 shipped (the empty-scan cache). It removed the poll cost and
   left the rate unchanged, which is what pointed at the producer.
2. **A bounded cooperative wait** (yield instead of spin) — still not done; the
   spin is no longer on the critical path now that frames are not dropped.
3. **Move the pump to a thread** — not done, and not needed for this fix.

## Read this with

The paced pin sets **~150 sectors/s as the correct target**; the paced
`StGetNext` cost was dominated by waiting for frames the bridge had discarded.
With the lock in place the movie holds the authored 15 fps in Ryubing, so the
busy-wait is now a wait for a legitimately paced stream rather than for a
replacement frame. A cooperative wait is still an option, not a need.
