# P10.4 Rumble — `PadSetAct` → hid HD rumble design

Status: **driver implemented on the `research/audio-hid` bridge,
hardware-unverified (2026-10-16)**. It follows
[P4.4_INPUT_STATUS.md](P4.4_INPUT_STATUS.md), where rumble was recorded
as "NOT implemented, NOT tested" — that note changed on this branch.

> The decomp's vibration path is complete and idle: `pollPadState` aligns
> actuators only when `PadGetState` reports `PadStateStable` (6), and
> `setVibration` writes the two motor intensities into `PAD.act` and calls
> `PadSetAct(port, PAD.act, 2)` every frame a motor runs. Until this
> change the host never reported actuators (`PadInfoAct` → 0) and
> `PadGetState` never left `PadStateFindCTP1` (2), so the game-side flags
> never set and `PadSetAct` was never called. This note documents the
> chain that lights it up with `hidSendVibrationValue` (dual linear
> resonant actuators, "HD rumble"), Lite-safe by construction.

## Game-side contract (facts from the decomp)

| Piece | Location | Behavior |
|---|---|---|
| Actuator alignment | `src/engine/pad/port.c::alignActuators` | `PadInfoAct(id, -1, 0)` (count) then `PadInfoAct(id, i, InfoActSub)`; stores `act & 1` per motor, then `PadSetActAlign(port, PAD.act[pad])` |
| Alignment trigger | `src/engine/pad/port.c::pollPadState` | only in the `PadStateStable` (6) case; sets `PAD_FLAG_ALIGNING`, then `PAD_FLAG_VIBRATION` on the next poll |
| Motor writes | `src/engine/pad/pad.c::setVibration(port, motor, time, value)` | `PAD.act[pad][motor & 1] = value` (u8, 0–255 + slot timers; `motor` 0/1) |
| Per-frame send | `src/engine/pad/pad.c::updateVibration` (called from `readPad`) | while any timer runs: `PadSetAct(id, PAD.act[pad], 2)` every frame; on expiry sets that motor byte back to 0 and sends once more |
| Non-analog fallback | `setVibration` else-branch | writes `PAD.act = {0x40, 0x01}` — shows the game treats byte 0 as PWM-able and byte 1 as on/off-ish; the DigitalShock handshake contracts above never fire there for us |
| Built-in test | `src/debug/vibration_test/vibration_test.c` (`SHOCKTST`, game mode `0x900`) | pattern/time/power editor driving `PAD.setVibration(0, motor, time, power)` for both motors |

**Key fact for scope:** retail mode never calls `setVibration`. Grep over
the decomp shows `src/debug/vibration_test/vibration_test.c` as the only
caller. So P10.4's "event tuning" cannot come from the decomp as-is;
in-game rumble events would be a *port-side addition* (a small
`port/patches/0051` emitting `PAD.setVibration` on battle hits), which is
a separate decision. The driver below is what any event source would
ride on.

## Shim chain (no `vendor/` changes)

```
decomp setVibration → PadSetAct [libpsyz NOT_IMPLEMENTED]
                    -Wl,--wrap=PadSetAct (Switch + PC link flags)
                    → __wrap_PadSetAct (port/psyz_missing/psyz_pad_host.c)
                    → Psyz_PadsSetAct  [weak in psyz_pad_host.c]
                        Switch: platforms/switch/psyz_backend/nx_rumble.c (strong)
                        PC:     weak no-op until an SDL one is added
```

Supporting changes in the shared adapter (used by both hosts):

- `PadInfoAct(port, actno, term)` — counts 2 actuators for a connected
  analog pad (`PSYZ_CTRL_ANALOG_PAD` = `0x73` is the kind a Switch pad is
  published as), else 0. Per-actuator table returns stable values whose
  low bit is 0, so the alignment seeds `PAD.act = {0, 0}` (idle), never
  the `0xFF` heap-fill value; only `act & 1` and the count are read by
  the decomp, so exact PSYQ act-IDs are not pinned here.
- `__wrap_PadGetState` — connected pads now hand off to `PadStateStable`
  (6) after a few polls, instead of `PadStateFindCTP1` forever. This is
  the real-DualShock handshake shape (Discon → FindPad → FindCTP1 →
  Stable stays) and it is what enables `alignActuators` and
  `PAD_FLAG_VIBRATION`. P4.4's walking/button behavior is unaffected:
  `pollPadState`/`readPad` treat any non-zero state as connected.
- `__wrap_PadSetAct` — forwards `(port, act[2], 2)` to the weak
  `Psyz_PadsSetAct`, unchanged for the DigitalShock-off case.
- `PadSetActAlign` still accepts (returns 1); it is the align ACK.

## Switch mapping (nx_rumble.c)

Target surface: libnx `hid` ("HD rumble" / linear resonant actuators):

- `hidInitializeVibrationDevices(handles[2], 2, id, style)` — 2 handles
  = left + right actuator group; id/style come from the live pad style
  (`dw3_nx_input_style_set`, `padGetStyleSet`): `NpadHandheld`-in-rails →
  `(HidNpadIdType_Handheld, HidNpadStyleTag_NpadHandheld)`, else
  `(HidNpadIdType_No1, FullKey/JoyDual)`.
- `hidIsVibrationPermitted` gate — when the system rumble switch is off,
  the hook logs once and stops sending (respects the system setting;
  `hidBeginPermitVibrationSession` would be the override knob if the
  owner ever asks for one).
- `hidSendVibrationValue(handle, &value)` for both handles with the same
  `HidVibrationValue` (PS1 motors are centered; left/right split is
  not signaled by the wire format).

Byte → HID mapping (first cut, verify with SHOCKTST):

| PS1 byte | Meaning on DualShock | HidVibrationValue |
|---|---|---|
| `act[0]` | motor 0 (small/fast) | `amp_high` = act[0]/255 · intensity, `freq_high` = 320.0f |
| `act[1]` | motor 1 (large/slow) | `amp_low` = act[1]/255 · intensity, `freq_low` = 160.0f |

`amp_*` floats 0–1; 160/320 Hz are the standard recommended frequencies.
If SHOCKTST on hardware shows the bands swapped (motor 0 buzzes deep
instead of short), swap the rows; that is a two-line fix. Amplitudes of 0
are still sent (once) so the motor stops and the system keep-alive
(\~120–160 ms after the last value, per homebrew reports and
switchbrew's HID notes — verify on device) does not mask a clean stop.

## Lite-safety (no actuators)

- Switch Lite handheld reports `NpadHandheld` but has no LRAs:
  `hidInitializeVibrationDevices` returns an error for that id/style.
  The hook treats *any* init failure for the handheld pair as
  "no hardware actuators", logs `nx_rumble: no actuators` once, and
  becomes a permanent no-op for that route (no per-call retry noise).
- Docked Lite + external Joy-Con/Pro pads would route through
  `HidNpadIdType_No1` (FullKey/JoyDual) instead, which is a valid
  route; only the handheld-route failure is permanent.

## Port options / gating

- Compile-in is unconditional (part of `psyz_backend/*.c`, CMake glob);
  runtime kill-switch is `DW3_NX_RUMBLE=0` (same env mechanism as
  `DW3_MESH_SOFT`). Default is **on** for the driver, because with the
  driver on, retail gameplay is inert anyway (no `setVibration` callers)
  — the only thing that can rumble is the SHOCKTST debug path.
- The Port options row (`Switch host: Rumble on/intensity` seed in
  [PORT_OPTIONS.md](PORT_OPTIONS.md)) lands via P9.5 once P9.4
  persistence exists; the env flag is the session-level stand-in.
- P10.4's "intensity" slider plugs into the `intensity` factor used by
  the mapping above; nothing else needs to change.

## What is NOT done here

- No PC (SDL) rumble; the weak forward makes the PC build behave exactly
  as before (vibration inert).
- No in-game rumble events (retail game has none; see the scope fact).
- No port-options row (P9.5 territory).
- Not verified on hardware; the OLED checks below are the record that
  closes P10.4's done-when alongside a Port options toggle or an explicit
  N/A decision for Lite (hardware lacks actuators → maps to the
  "marked N/A" branch in the roadmap).

## Hardware smoke plan (when a unit is in hand)

The retail game sends no vibration, so a plain play session cannot show
the driver. Two single-purpose probes exist for the session:

1. **Self-test define (recommended first):** build the owner's `.nro`
   with `-DDW3_NX_RUMBLE_SELFTEST` (dev/--nxlink builds only) — it pulses
   the mapped motors 3× about a second after boot. A silent-boot release
   never sets it.
2. **SHOCKTST (the decomp's own test):** on PC, `DW3_FORCE_STAGE=0x900`
   drives `requestMode(0x900, 0)` so the hidden vibration-test overlay
   runs (pattern/time/power editor per motor). On Switch the env does
   not travel through hbmenu, so reaching SHOCKTST needs either nxlink
   arg passing (verify once) or a small port-side mode-jump chord.
   Decision left to the owner; it is the only path that covers per-motor
   intensity and the band-order question in the mapping table.

On-device expectations either way:

- No `nx_rumble:` lines while nobody drives motors.
- With a probe active: `hud pad` unchanged; observed rumble on a
  Pro/Joy-Con pair; Switch Lite logs `nx_rumble: no actuators` once.
- Record via `tmp/evidence/…` (dated), then update this note + P10.4 in
  `docs/ROADMAP.md`.

Open question left to the owner: whether P10.4's done-when should add a
Switch debug chord that jumps to `SHOCKTST` (nothing in the port jumps
game modes today except the restart flow), or whether the boot
self-test define is enough; and whether the intensity Port options row
is wanted before anything ships.
