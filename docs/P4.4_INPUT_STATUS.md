# P4.4 Input — hid → PS1 pad, mode table, rumble status

Status: **host wiring implemented and headless-tested; not hardware-validated**
(2026-10-10).

> The ROADMAP checkbox for P4.4 stays open: its "done when" is title and field
> controls on **Switch hardware** with Joy-Con and Pro Controller, and no
> console was available in this session (emulator/CI only).

## Goal

Map libnx `hid`/`pad` to the PS1 pad wire frame so the decomp's pad path
(`src/engine/pad/`) sees the same bytes a DualShock would put in `PadData`,
including the digital/analog modes `PadInfoMode` / `PadSetMainMode` negotiate.

## Where the pieces live

| Piece | Location |
|---|---|
| Switch input source (`Psyz_PadsPoll`, hid → wire frame, button map) | `platforms/switch/psyz_backend/nx_input.c` |
| Portable libpad adapter (`PadInitDirect`, `PadGetState`, `PadInfoMode`, `PadSetMainMode`, …) | `port/psyz_missing/psyz_pad_host.c` |
| PSY-Q constants the decomp includes (`libpad.h` shim) | `port/include/libpad.h` |
| Headless check | `tools/pad_host_test.c`, `tools/tests/test_pad_host.py` |

The adapter is **shared with the PC host** (`platforms/pc/CMakeLists.txt`) — it
is not Switch-specific — so every change here must hold for both.

## Wire format (confirmed correct; unchanged)

PSY-Q's pad word lives in two active-low bytes of the 34-byte receive buffer:
wire byte 2 is the **high** byte (d-pad, Start/Select) and byte 3 the **low**
(d-pad/face, L1/R1/R2/L2), matching PSY-Z's `BuildPadFrame`
(`vendor/psyz/psyz/src/platform/sdl3_common.h`) and `UnpackPadBits`
(`libetc.c`). The decomp overlays `PadData.buttons` (a `u16`) on bytes 2–3
(`engine/pad/pad.h`), which is why `port/psyz_missing`'s `DW3_AUTO_PAD`
injection writes the mask in native little-endian order instead of wire order.
This was audited as correct and is left as-is.

Switch button map (`nx_input.c`, positional like a PS1 pad in hand):

| Switch | PS1 |
|---|---|
| B (south) | Cross (`PADRdown`) |
| A (east) | Circle (`PADRright`) |
| Y (west) | Square (`PADRleft`) |
| X (north) | Triangle (`PADRup`) |
| D-pad | D-pad |
| L / R | L1 / R1 |
| ZL / ZR | L2 / R2 |
| L3 / R3 (stick click) | `PADi` / `PADj` |
| + / − | Start / Select |

One stick only: it drives the PS1 **left** stick; the right one stays centred
(`0x80`). The Y axis is inverted so up is a lower byte value, which is what the
decomp's stick-to-d-pad thresholds expect (`slot->analog[3] <= STICK_LOW` →
up). This inversion is pre-existing and was **not** changed (it needs hardware
to confirm the sign).

## Controller mode contract (fixed)

`src/engine/pad/port.c` does, in `lockPadMode`:

```c
PadSetMainMode(id, PadInfoMode(id, InfoModeCurExOffs, 0), PAD_MODE_LOCKED);
```

`readPadButtons` / `readPad` / `setVibration` branch on
`PadInfoMode(id, InfoModeCurExID, 0)` against `PAD_ID_DIGITAL` (4) and
`PAD_ID_ANALOG` (7) (`engine/pad/pad.h`). The contract, taken from the header
the decomp compiles against — PSY-Z's `psyz/include/libetc.h` — is that
`InfoModeCurExOffs` is the **offset of the active mode in the controller mode
ID table**, and `PadSetMainMode`'s `offs` is the **table offset of the mode to
switch to** (with `lock` bit 1 = change the selector, bit 0 = lock it).

Before this change the adapter had a no-op `PadSetMainMode` (always returned 1)
and a hard-coded `InfoModeCurExOffs == 0`, so the mode the game thought it was
in could never change and half the contract was a lie. Now:

- The table is `{PSYZ_CTRL_DIGITAL_PAD (0x41), PSYZ_CTRL_ANALOG_PAD (0x73)}`.
  Their high nibbles are exactly 4 and 7, i.e. `PAD_ID_DIGITAL` /
  `PAD_ID_ANALOG`; `InfoModeCurExID` returns the kind's high nibble.
- `InfoModeCurExOffs` returns the active kind's table offset (0 or 1) and
  `InfoModeIdTable` returns the id at a requested offset (the pair the round
  trip needs).
- `PadSetMainMode` validates the port (connected) and the offset (in range),
  hands the selected kind to PSY-Z with `Psyz_PadsSetKind`, remembers the lock
  bit, and returns 1 accepted / 0 rejected. The platform backend rebuilds its
  frame from that kind on the next poll (PC `BuildPadFrame`, Switch
  `nx_input.c`), so the switch lands on the following `PadGetState` /
  `PadChkVsync`, as on a real controller.

PC regression check: with the default digital pad, `InfoModeCurExOffs` still
returns 0 and `PadSetMainMode` still returns 1 for a connected port, so no PC
code path changes; it now returns 0 only for the disconnected/out-of-range
cases where `lockPadMode` already short-circuits.

## Switch controller kind policy

- The Switch host reports **`PSYZ_CTRL_DIGITAL_PAD` by default** — the same
  default PSY-Z/libapi applies to every port. Buttons, d-pad and Start/Select
  cover the title and field controls the done-when asks for.
- **`PSYZ_CTRL_ANALOG_PAD` is the only alternative.** PSY-Z's
  `PSYZ_CTRL_ANALOG_STICK` (0x53, high nibble 5) is *not* recognised by the
  decomp, so `nx_input.c` normalises it to `ANALOG_PAD` before publishing (same
  wire layout, recognised id).
- Moving the port to analog (left stick drives the PS1 left stick, which the
  decomp turns into d-pad movement) is reachable through
  `PadSetMainMode` → `Psyz_PadsSetKind`; it remains opt-in until centring and
  dead-zone behavior are checked on hardware.
- **Switch OLED, preview.4 (2026-10-11):** nxlink log confirms a connected
  digital pad (`kind=0x41`) during field play. The owner reports navigating
  several maps and reaching battle; they also report the analog stick has no
  function. The controller model used was not recorded, analog mode was not
  selected/validated, and Joy-Con + Pro coverage is therefore still incomplete.

## Rumble (optional — NOT implemented, NOT tested)

- `PadSetAct` / `PadSetActAlign` remain `__wrap_` stubs that accept and do
  nothing; `PadInfoAct` returns 0, so no actuator list is ever reported.
- Stronger: `PadGetState` reports `PadStateFindCTP1` (2) for a connected pad and
  never `PadStateStable` (6), and `pollPadState` only aligns actuators in the
  `PadStateStable` case. So the decomp never sets `PAD_FLAG_VIBRATION` and
  `setVibration` returns 0 — the game's vibration path is inert on both hosts.
- HD rumble (`padSetVibration` on libnx) is therefore **not implemented and not
  tested**. It is P4.4-optional and tracked by P10.4.

## Tests

```bash
# focused (builds pad_host_test against the stub Psyz_Pads)
python3 -m pytest tools/tests/test_pad_host.py -q     # 2 passed
# full host-data suite
python3 -m pytest tools/tests -q                      # 33 passed, 1 skipped
# PC host regression gate for the shared adapter
cmake -S platforms/pc -B build/pc -G Ninja -DPSYZ_RENDERER=sdl3_gpu \
  -DSDL_X11_XSCRNSAVER=OFF
cmake --build build/pc -j"$(nproc)"                   # exit 0, dw3-pc linked
```

The PC host build is green with the modified adapter (`psyz_pad_host.c`
recompiled; 1506 targets, exit 0). It needs `vendor/psyz`'s nested submodules
`external/SDL` and `nugget` (for `port/CMakeLists.txt`'s `bsdec.c`)
initialised, and SDL configured with `-DSDL_X11_XSCRNSAVER=OFF` on this host.

The 1 skip is pre-existing (`test_cdfs.py`: owner `runtime/us` not present).
`tools/pad_host_test.c` now also asserts: `CurExID` 4/7 and `CurExOffs` 0/1 for
the digital/analog frames, the `InfoModeIdTable` entries, that
`PadSetMainMode(0, 1, LOCKED)` publishes `0x73`, that offset 0 publishes `0x41`,
and that a past-the-table offset and a disconnected port are rejected. The
`pad_host_test` unit is also compiled with `-Wall -Wextra -Werror`.

- **PC**: `./build/pc/dw3-pc` (window title `dw3-pc Phase 2`) — title and field
  respond to the pad; `DW3_AUTO_PAD=…` still injects scripted input. The
  adapter logs `dw3-pad: PadSetMainMode …` once.
- **Switch**: build the `.nro` on CI (`devkitpro/devkita64`) and launch from
  hbmenu; confirm title/field buttons, then move the port to analog and re-check
  walking before changing the default.
