# P4.4 Input — hid → PS1 pad, mode table, rumble status

Status: **ticked (2026-10-11).** Handheld Joy-Con and a Pro Controller
both walk with the left stick on the OLED. Rumble stays the P10.4 stub.

> The host publishes `PSYZ_CTRL_ANALOG_PAD` (`0x73`). The preview.5 boot
> log recorded handheld Joy-Con (`style=0x3`, `handheld=1`). The owner
> also tested a Pro Controller the same day. D-pad, buttons, Start and
> Select stay in the button word.

## Goal

Map libnx `hid`/`pad` to the PS1 pad wire frame so the decomp's pad path
(`src/engine/pad/`) sees the same bytes a DualShock would put in `PadData`,
including the digital/analog modes `PadInfoMode` / `PadSetMainMode` negotiate.

## Where the pieces live

| Piece | Location |
|---|---|
| Switch input source (`Psyz_PadsPoll`, hid → wire frame, button map) | `platforms/switch/psyz_backend/nx_input.c` |
| Left-stick scale, 8192 dead zone, kind rewrite (`0x41`/`0x53` → `0x73`) | `platforms/switch/psyz_backend/nx_stick.h` |
| Portable libpad adapter (`PadInitDirect`, `PadGetState`, `PadInfoMode`, `PadSetMainMode`, …) | `port/psyz_missing/psyz_pad_host.c` |

| Headless check | `tools/pad_host_test.c`, `tools/tests/test_pad_host.py` |

The adapter is **shared with the PC host** (`platforms/pc/CMakeLists.txt`) — it
is not Switch-specific — so every change here must hold for both.

## Wire format (confirmed correct; unchanged)

PSY-Q's pad word lives in two active-low bytes of the 34-byte receive buffer:
wire byte 2 is the **high** byte (d-pad, Start/Select) and byte 3 the **low**
(d-pad/face, L1/R1/R2/L2), matching PSY-Z's `BuildPadFrame`
(`vendor/psyz/psyz/src/platform/sdl3_common.h`) and `UnpackPadBits`
(`libetc.c`). The decomp overlays `PadData.buttons` (a `u16`) on bytes 2–3
(`engine/pad/pad.h`), which is why `port/psyz_missing`'s `DW3_AUTO_PAD`
injection writes the mask in native little-endian order instead of wire order.
This was audited as correct and is left as-is.

Switch button map (`nx_input.c`, positional like a PS1 pad in hand):

| Switch | PS1 |
|---|---|
| B (south) | Cross (`PADRdown`) |
| A (east) | Circle (`PADRright`) |
| Y (west) | Square (`PADRleft`) |
| X (north) | Triangle (`PADRup`) |
| D-pad | D-pad |
| L / R | L1 / R1 |
| ZL / ZR | L2 / R2 |
| L3 / R3 (stick click) | `PADi` / `PADj` |
| + / − | Start / Select |

The left stick drives the PS1 **left** stick (wire bytes 6 and 7, decomp
`analog[2]` / `analog[3]`). The right stick stays centred (`0x80`). libnx
stores that left stick in `PadState.sticks[0]` for a Joy-Con pair in the rails
(`NpadHandheld`), a Pro Controller (`NpadFullKey`), and a Joy-Con pair off the
rails (`NpadJoyDual`). `padInitializeDefault` reads player 1 and Handheld.
Handheld is sampled first, and a stick that is not exactly `(0, 0)` is kept.

libnx Y is positive upward. The host inverts it so up is a lower byte, which
is what `slot->analog[3] <= STICK_LOW` means. Preview.4 never left digital
mode, so this sign is still unchecked on hardware.

Centre dead zone: `|raw| < 8192` publishes as `0x80` (`DW3_NX_STICK_DEADZONE`
in `platforms/switch/psyz_backend/nx_stick.h`). 8192 is 25% of the calibrated
full scale (32767). The decomp still ignores a byte inside `(0x40, 0xC0)`,
about ±16512 raw counts, so drift under 8192 cannot walk, and a small tilt
past 8192 does not walk either. Walking starts at the same PS1 thresholds as
a DualShock left stick. D-pad, face buttons, Start and Select are the button
word in the same frame, so they still work while the stick sits at `0x80`.

## Controller mode contract (fixed)

`src/engine/pad/port.c` does, in `lockPadMode`:

```c
PadSetMainMode(id, PadInfoMode(id, InfoModeCurExOffs, 0), PAD_MODE_LOCKED);
```

`readPadButtons` / `readPad` / `setVibration` branch on
`PadInfoMode(id, InfoModeCurExID, 0)` against `PAD_ID_DIGITAL` (4) and
`PAD_ID_ANALOG` (7) (`engine/pad/pad.h`). The contract, taken from the header
the decomp compiles against — PSY-Z's `psyz/include/libetc.h` — is that
`InfoModeCurExOffs` is the **offset of the active mode in the controller mode
ID table**, and `PadSetMainMode`'s `offs` is the **table offset of the mode to
switch to** (with `lock` bit 1 = change the selector, bit 0 = lock it).

Before this change the adapter had a no-op `PadSetMainMode` (always returned 1)
and a hard-coded `InfoModeCurExOffs == 0`, so the mode the game thought it was
in could never change and half the contract was a lie. Now:

- The table is `{PSYZ_CTRL_DIGITAL_PAD (0x41), PSYZ_CTRL_ANALOG_PAD (0x73)}`.
  Their high nibbles are exactly 4 and 7, i.e. `PAD_ID_DIGITAL` /
  `PAD_ID_ANALOG`; `InfoModeCurExID` returns the kind's high nibble.
- `InfoModeCurExOffs` returns the active kind's table offset (0 or 1) and
  `InfoModeIdTable` returns the id at a requested offset (the pair the round
  trip needs).
- `PadSetMainMode` validates the port (connected) and the offset (in range),
  hands the selected kind to PSY-Z with `Psyz_PadsSetKind`, remembers the lock
  bit, and returns 1 accepted / 0 rejected. The platform backend rebuilds its
  frame from that kind on the next poll (PC `BuildPadFrame`, Switch
  `nx_input.c`), so the switch lands on the following `PadGetState` /
  `PadChkVsync`, as on a real controller.

PC regression check: with the default digital pad, `InfoModeCurExOffs` still
returns 0 and `PadSetMainMode` still returns 1 for a connected port, so no PC
code path changes; it now returns 0 only for the disconnected/out-of-range
cases where `lockPadMode` already short-circuits.

## Switch controller kind policy

- A connected Switch pad is published as **`PSYZ_CTRL_ANALOG_PAD` (`0x73`)**.
  PSY-Z/libapi still defaults the port to `PSYZ_CTRL_DIGITAL_PAD` (`0x41`).
  `dw3_nx_publish_kind` rewrites that, and `PSYZ_CTRL_ANALOG_STICK` (`0x53`),
  to `ANALOG_PAD` before the frame is stored. `0x53` has high nibble 5, which
  `readPadButtons` does not treat as analog. `0x73` does (high nibble 7).
- The button word is still filled in that analog frame. A centred stick adds
  no direction bits, so the d-pad, face buttons, Start and Select keep
  working.
- `PadSetMainMode` can still select digital. The next `Psyz_PadsPoll` publishes
  analog again, because that is the mode the left stick needs. Disconnect
  (`0xFF`) is not rewritten.
- **Switch OLED, preview.4 (2026-10-11):** nxlink showed `kind=0x41` while the
  owner walked maps and entered battle with the d-pad and buttons. The left
  stick did nothing. The controller model was not recorded.
- **Switch OLED, preview.5 (2026-10-11):** the boot log showed
  `kind=0x73 style=0x3 handheld=1 deadzone=8192`. Later the same day the
  owner confirmed the left stick works on that handheld Joy-Con
  (`NpadFullKey|NpadHandheld`) and on a Pro Controller. The one-shot log is
  `left stick kind=0x73 style=0x.. handheld=0|1 deadzone=8192`.
  `style` is libnx `HidNpadStyleTag`: `0x1` Pro (`NpadFullKey`), `0x2`
  Joy-Con pair in the rails (`NpadHandheld`), `0x4` Joy-Con pair off the
  rails (`NpadJoyDual`). `handheld=1` means the rails pad answered.

## Rumble (P10.4 — adapter + backend written, hardware-unverified)

- The actuator path now exists end to end in C, still waiting on a hardware
  listen (see `docs/P10.4_RUMBLE.md` smoke plan):
  - `PadGetState` returns `PadStateFindCTP1` (2) for the first 4 connected
    polls and then `PadStateStable` (6), so `pollPadState` starts the
    `alignActuators` cycle that sets `PAD_FLAG_VIBRATION` exactly like a real
    DualShock negotiation would.
  - `PadInfoAct` reports the 2-actuator table for an analog pad (`InfoActFunc`
    0x01/0x02, `InfoActSub` 0/0 so `PAD.act` stays idle after alignment,
    `InfoActSize` 2, `InfoActCurr` 60) and 0 for digital pads / bad indices.
  - `PadSetAct` forwards the 2-byte `PAD.act` array to the new weak hook
    `Psyz_PadsSetAct` (one-shot `dw3-pad: PadSetAct …` log on the first send);
    `PadSetActAlign` logs once and accepts.
- On the Switch, `psyz_backend/nx_rumble.c` implements the hook: it initializes
  both vibration routes once (handheld rails / Lite plus player 1 for docked),
  picks the route from the libnx style set per send, gates on
  `hidIsVibrationPermitted`, de-duplicates unchanged packets, and translates
  act[0] (small motor) → the 320 Hz band and act[1] (big motor) → the 160 Hz
  band (band order unverified). `DW3_NX_RUMBLE=0` disables it; the boot pulse
  diagnostic is compiled in with `-DDW3_NX_RUMBLE_SELFTEST`.
- The PC host keeps the weak idle default, so rumble stays silent there.
- **Not tested on hardware**: no devkitPro here, so nothing above has run on a
  real console; the next hardware session should do the SHOCKTST/self-test
  pulse from the P10.4 smoke plan.

- **PC**: `./build/pc/dw3-pc` (window title `dw3-pc Phase 2`) — title and field
  respond to the pad; `DW3_AUTO_PAD=…` still injects scripted input. The
  adapter logs `dw3-pad: PadSetMainMode …` once, and now also the one-shot
  `dw3-pad: port 0 stable …` and `dw3-pad: PadSetAct …` lines if the game ever
  drives the actuator path (SHOCKTST only, mode 0x900). Input stays silent
  rumble-wise: the weak `Psyz_PadsSetAct` default is idle on PC.
- **Switch**: build the `.nro` on CI (`devkitpro/devkita64`) and launch from
  hbmenu. With the stick centred, d-pad, face buttons, Start and Select should
  behave as in preview.4. Deflect the left stick past the decomp window and
  the player should walk. nxlink should show `kind=0x73`, the `left stick`
  line with `style` / `handheld`, then `vibration devices up`, the
  `dw3-pad: port 0 stable … (actuators aligned)` line, and — only when the
  game vibrates (SHOCKTST / battle) — the `dw3-pad: PadSetAct …` and
  `rumble act=…` lines from `nx_rumble`. For a pulse without SHOCKTST, build
  with `-DDW3_NX_RUMBLE_SELFTEST=ON` (P10.4 smoke plan in
  `docs/P10.4_RUMBLE.md`).
