# P7.7 Bug and text fixes

Status (2026-10-22): **partly done.** Two of the five listed bugs are real
bugs of the original game, are fixed and are verified on the US and EU PC
builds (not yet on the OLED). The other three could not be pinned to the
original game, so nothing was changed for them. The roadmap item stays open.

The list comes from the Harmony Beta v1.0 notes (rsigristc/dw2003-qol-patch,
README and CHANGELOG, read 2026-10-22) through
[COMMUNITY_QOL.md](COMMUNITY_QOL.md). Those notes give one line per fix and no
repro, and Harmony changes the PAL disc together with other mods (Flawe's item
kit, FastTravel, a Start-menu save), so a line of the list can describe a bug
of the mod chain and not of the stock disc. Every bug below was therefore looked
for in `vendor/dw3_decomp`, then reproduced (or not) on the unmodified US and
EU discs with the PC host.

| # | Listed bug | Original game? | Result |
|---|---|---|---|
| 1 | Picking / Snapping Claw on a KO'd enemy | Yes, US and EU | **Fixed**, patch `0066` |
| 2 | Active Digivolution name in battle | Yes, US and EU | **Fixed**, patch `0065` |
| 3 | Reward text "1IT" / "1EXP" | Not reproduced, US and EU in 6 languages | Skipped |
| 4 | Save label showing Asuka Inn | Not on the stock disc | Skipped |
| 5 | Square map glitch | Not on the stock disc | Skipped |

Patch `0064` is the test hooks the replay scenarios need (see
[Tests](#tests)); it changes nothing unless an environment variable is set.
See [PATCHES.md](PATCHES.md) for the series.

## Decision: fixes are always on, no Port option

AGENTS.md treats the decomp as upstream and wants the port to add options
where behaviour differs from the original. Both fixes are shipped **without a
Port option**, for these reasons:

- Bug 2 is a display bug. The text on screen was wrong (a Rookie name over a
  Champion), so "off" would only bring the wrong text back. A name the player
  typed at the Nickname Shop is kept (see below), so no player choice is lost.
- Bug 1 changes what a technique yields, so it is the nearest to a balance
  question. It was weighed and shipped on, because it does not change any
  number the game uses: the steal roll is made at the same moment with the
  same random numbers whether or not the hit kills (`FIGHTSTG_rollSteal` runs
  in `FIGHTSTG_startAction`, before the damage), the steal event spends no
  random number, and the item and its "Stole X!" message are exactly what the
  game gives when the same roll succeeds on a hit that does not kill. Without
  the fix a successful roll was thrown away with no message, the item stayed
  on the enemy and was only an ordinary drop (itemChance in 1024) afterwards.
  The fix therefore turns a lost, invisible success into the visible one the
  tech's own description promises; it cannot raise the steal chance.
- A file-only flag in `port_options.cfg` would have to extend the
  `dw3-options: saved ... (widescreen=... text_speed=...)` log line that many
  replay scenarios (and the Ryubing runner) match, for a behaviour nobody is
  expected to want off. If the owner wants the old claw back, the place for a
  flag is one condition in the `#if PORT_HOST` block of patch `0066`.

## 1. Picking Claw / Snapping Claw on a KO'd enemy

**Symptom.** The claws (techniques 127 and 128, `TECH_EFFECT_STEAL`; both on
both discs with identical `TechData`) are meant to take the enemy's item. When
the hit that carries the steal also knocks the enemy out, the item is never
taken and no "Stole ..." message is shown, even though the steal roll
succeeded. Harmony's wording: "Fix Picking Claw and Snapping Claw when an enemy
is KO'd".

**Root cause.** `FIGHTSTG_startAction` rolls the steal up front
(`FIGHTSTG_trySteal` -> `FIGHTSTG_rollSteal`) and only marks
`FIGHTSTG_action.effects[TECH_EFFECT_STEAL]`. The item moves into the bag in
`stealEnemyItem`, which is run by `FIGHTSTG_updateActionEvents`.
`FIGHTSTG_updateTechAction` (battle_mode/tech_action.c, substate 2) starts those
events only when `task->step == 0`, and `dealTechDamage` sets `step = 1` when the
hit leaves the enemy at 0 HP. A killing blow therefore skips every queued
effect, including a steal that already succeeded. (The partner's first
technique, `FIGHTSTG_updateFirstTech`, has the same skip but no partner has a
claw as `skills[0]`: only Growlmon, WarGrowlmon and Gallantmon know them, as
learned techniques, so only the Tech menu path was changed.)

**Fix** (`0066-PORT_HOST-p77-claw-steal-on-knockout.patch`). On a knocked-out
target, if the steal flag is set, clear every other effect (a poison or sleep
must not be applied to a fighter that is down), run the action events, then end
the action like the knock-out path does (new substate 10: no wake-up test, no
counter motion). The knock-out event stays queued and is handled by the battle
menu after the action task ends, so the order on screen is "68 damage!", "Stole
Balanced Pack!", "Defeated!", "Battle won!", and `stealEnemyItem` still sees the
fighter that was hit. A claw that misses, does not kill, or does not roll the
steal takes the old code path.

**Evidence** (PC host, both discs; the hooks of patch `0064` force the roll):

- Before: `DW3_FORCE_TECH=127 DW3_FORCE_HIT=1 DW3_FORCE_STEAL=1
  DW3_FORCE_ENEMY_ITEM=1 DW3_FORCE_ENEMY_HP=1` on the forced Kotemon vs Kunemon
  battle: "Kunemon 68 damage!", "Defeated!", "Battle won!", no steal. The same
  claw with `DW3_FORCE_ENEMY_HP=2000` shows "Stole Balanced Pack!".
- After: the same run logs `claw steal on a knocked-out enemy (tech 127)` and
  `steal item 1 from enemy slot 0 (hp 0)`, and shows the message between the
  damage and "Defeated!".
- Replay scenarios `us/eu-p77-claw-ko` (the fix), `us/eu-p77-claw-alive` (the
  old path, unchanged) and `us/eu-p77-ko-no-claw` (a technique without the steal
  effect that kills: no steal line, no knocked-out path). `us-p77-claw-ko` fails
  on a build without `0066`.
- Screens (not committed): `tmp/evidence/p77/claw-ko-{us,eu}-after.png`,
  `claw-ko-us-before.png`.

**Not covered.** The enemy's own claws never steal (`FIGHTSTG_rollSteal` returns
0 for the enemy side). No natural, unforced roll was played: the steal chance is
the game's own and is a few percent, so the hooks force the roll and the hit.

## 2. Active Digivolution name in battle

**Symptom.** A partner that fights as a Champion or higher (set up in the field
menu, or by the Digivolve command in the battle) still has its Rookie's name in
the battle HUD, over a model and messages that use the new name. Seen before
the fix on the PC build with a forced Dinohumon: the HUD reads "Kotemon".

**Root cause.** `FIGHTSTG_showFighterNames` (battle_mode/hud.c) draws the
partner's name from `GAME.partners[member].info.name`. `initNewGameData` copies
that string once from the Rookie's `nameId`, the Nickname Shop (STDGNAME) can
replace it, and nothing follows a digivolution. The window was also refreshed
only when the active slot changed, so a digivolution in battle
(`WFIGHTMN_digivolve` sets the fighter's id, the slot stays) could not update
it. The report screen ("Kotemon Level 9!") reads the same string; only the HUD
is in the Harmony note and in this fix.

**Fix** (`0065-PORT_HOST-p77-battle-hud-form-name.patch`). The HUD asks what the
fighter is now (`GET_DIGIMON(BattleFighter.id)`) and shows that Digimon's name
from the `TEXT_DIGIMON_NAMES` file the battle already loads, **but only while
`info.name` is still the Rookie's default string**. A nickname is kept whatever
the form, because the player chose it. `shown[0]` keys the slot and the Digimon
id, so the name follows a digivolution in battle. An unevolved partner has the
same string both ways, so a battle without digivolution is unchanged.

Names of the high forms do not fit the Rookie-sized space: the current HP number
is in the same row, and the longest names ("Imperialdramon MP", "MetalGarurumon",
"BK WarGreymon", "GuardiAngemon", about 70 to 91 px against 60) ran into it. A
name wider than 60 px is squeezed horizontally with the text window's own scale
(`setScale`, `setPivot`), which draws the glyphs as scaled quads. Names that fit
(every Rookie, "Dinohumon" 54 px) take the unscaled path.

**Evidence.** `us/eu-p77-hud-rookie` (Kotemon, 43 px, unchanged string),
`-hud-form` (Dinohumon, 54 px), `-hud-long` (MetalGarurumon, 84 px, squeezed),
`-hud-nickname` ("Spike" kept on a Dinohumon), and `eu-p77-hud-form-fr/it/de/es`
(the form's name read from each language's file, with the partner names
copied in that language: `DW3_LANGUAGE` is applied before the new game). Screens:
`tmp/evidence/p77/hud-before-after-us.png` (before: "Kotemon" over Dinohumon;
after, US and EU: "Dinohumon").

**Not covered.** A digivolution during the battle (the Digivolve command) was
not played: it needs a partner with learned slots, which the PC hooks do not set
up. The code path is the same key comparison, but the OLED check below should do
it once. The slight vertical blur of a squeezed name is also an OLED question.

## 3. Reward text "1IT" / "1EXP"  (skipped: not reproduced)

Harmony: "Correct battle reward text from "1IT"/"1EXP" to "BIT"/"EXP"" in the
"Visuals and fixes" section. Searched and tried:

- The report strings (`FGTRPT`, `USFGTRPT.BIN` and the five `xSFGTRPT.BIN`
  of the EU disc) decoded: "EXP gained", "BIT gained", the labels `EXP`, `LV` and
  the amount are inserted by `setNumber`. No string has a digit glyph where a
  letter belongs. A scan of every file of both discs for the glyph codes of
  "1IT" and "1EXP" (digit 1 is `0x05`, B is `0x0F`) finds nothing in
  `DAT/COUNTRY` (all text tables); the hits are in movie, model and stage
  data and are chance matches.
- Played on the PC build: forced battles with 6 EXP / 10 BIT and with 718 EXP /
  1490 BIT, on the US disc and on the EU disc in English, French, Italian, German
  and Spanish. The report shows "6 EXP", "10 BIT", "1490 BIT" and the header
  "718 EXP" correctly everywhere. The item adapters ("EXP Adapter", "BIT
  Adapter") and their descriptions are also right in all six text sets.

The most likely cause is the mod chain Harmony builds on (it rewrites item,
shop and battle texts and adds 1 BIT test items), not the stock text. No change
was made. If someone has a screenshot from an unmodified disc, the place to look
is the amount window of the report (`STFGTREP_*` windows of
`src/battle/report/`).

## 4. Save label showing Asuka Inn  (skipped: not on the stock disc)

Harmony: "Start-menu saves display the correct location instead of Asuka Inn".

The label of a save is two strings: the area (`TEXT_AREA_NAMES`, looked up by
the mode the player came from, `STGMCARD_prevModes`) and the place
(`TEXT_SHOP_NAMES`, `STGMCARD_places[mode & 0xFF]`, where the low byte of the
save mode 0xC00-0xC19 is the save point). Saving on the stock disc is only
possible at the 25 inns / towers / halls whose stage scripts leave for 0xC01 to
0xC19 (`SCRIPT_LEAVE(0xC0x)` in `field/stages`). Cross-checking all of them (28 stage
files, three of them the EU extra-chapter twins; stage, area from the mode table, place from `STGMCARD_places`) gives a place
that matches the stage each time (WSTAG430 Seiryu Tower -> "Seiryu Tower",
WSTAG470 Swamp Inn -> "Asuka Swamp Inn", ...), on the US disc and with the EU
tables in all six text sets.

"Asuka Inn" is place 43, which the table gives to **both** 0xC00 and 0xC01.
0xC01 is the real Asuka Inn. 0xC00 is the load/title mode, and no stage script
ever saves with it; a save made from any screen that is not one of the 25
(the debug stage select, or a Start-menu save, which the stock game does not
have) gets the Asuka Inn place and a blank area. That is what Harmony's
Start-menu save runs into. Seen on the PC build, US and EU, through the save
screen (`DW3_START_MODE=0xC00 DW3_START_MODE_ARG=0x80000000`): the slot shows
"Asuka Inn" with an empty area line, while `0xC02` shows "Seiryu Tower"
(screens in `tmp/evidence/p77/save-label-c00-us-eu-c02-us.png`, not committed).

Nothing to fix for the stock disc. The label of an in-game save from outside a
save point belongs to the in-game save menu (P6.14), which has to give mode
0xC00 a place of its own (and fill the area from the map's current stage).

## 5. Square map glitch  (skipped: not on the stock disc)

Harmony lists "Fix the map glitch when pressing Square during exploration" and,
separately, "Press Square during exploration to open the map ... Square switches
server maps" (Flawe's FastTravel). The stock game reads no Square in the field:
`PAD_SQUARE` appears only in the card game's hand pick, the text window's
wait-for-button codes and the debug tests, and the field and its Start menu
(`engine/menu/field_menu.c`, `FIELDSTG`) never test it. The map screen is part
of the Start menu (`menus/field_menu/map_screen.c`); it moves a cursor and
leaves on Triangle, and I found no fault in it.

Played on the PC build, both discs, in a random-battle field: a tap, a second
tap, a 60 frame hold, and Square with Circle. Nothing happens (no mode change,
no overlay restore; the frame is identical). Scenarios `us/eu-p77-square-field`
keep that as a check. The glitch is therefore in the FastTravel feature that
Harmony adds (P7.4), and has to be handled there.
