# P6.31 Auto-save (off by default)

Status (2026-10-25): **built, PC US and EU replays pass; owner OLED check open.**
Branch `feat/p6.31-autosave`. The owner was away, so every open question of the
[ROADMAP entry](ROADMAP.md#phase-6-goal-notes) was settled with the conservative
option and is marked **default chosen, owner can change** below.

## What it is

An Options row, **Auto-save**, with two values: **OFF** (the default) and **Each
area** ("On area change"). With it on, the first idle frame of every new field
area writes the game to the card slot the player last saved to or loaded from.
With it off nothing is read, written or logged; the game runs as it did before.

## What the card allows (why there is no auto slot)

The flat card file of a port ([P5.3_FLAT_SAVE.md](P5.3_FLAT_SAVE.md)) is 4 blocks,
`0x8000` bytes: a header sector, three icon sectors, the info section at `0x200`,
and three data slots from `0x300`, each `0x2700` bytes. They end at `0x7B00`.
`0x500` bytes are free, a fifth of a save. **There is no fourth slot**, and the
game's load screen (`STGMCARD`) lists exactly three. A separate auto slot would
need either a second card file the game cannot show (Continue could not load it
without a new screen) or a change to the load screen's layout. Neither is a
small, safe step, so the first slice writes into one of the three slots.

## Defaults chosen (owner can change)

|---|---|---|---|

No slot used yet in this run (a new game, or never saved or loaded): no auto-save | The card has no free slot (above). A "after each battle" value is one more row value |
| 3 | P6.20 cheat marks | **The auto-save is made, and carries the cheat mark** when a cheat changed the game: it calls the same `dw3_cheats_save_written` the game's own save does, so `save<N>.cheats` marks the slot, and a Continue of it keeps the game marked | The ROADMAP offered refusing or marking. Marking keeps the progress and still tells the truth; refusing would lose the area a cheat test needs saved |

More defaults chosen without the owner:

- **Where the game would save.** The hook sits in `openFieldMenu`, where the field menu
  may open: no event, no menu or inn, no talking or climbing, no area banner or
  fade (`FieldState.frozen`), no battle starting, and **`progress` of 4 or more**
  (before that the game's own field menu does not open, so the player cannot save
  there either). Only maps the save list knows (an area string exists for the
  mode: `STGMCARD_prevModes`, 239 modes) count.
- **Never over another game.** The slot's summary in the info section must carry
  the same player name, and its play time may not be longer than the game's now.
  A card that is not a DW3 card (magic or info checksum wrong), an empty slot, or
  another name or a longer play time refuses the auto-save and changes nothing.
  A new game or Return to title clears the target.
- **What is saved.** What `STGMCARD_fillSave` builds (the game's save bytes, the XOR
  checksum from byte 4, the region's version byte, the summary: name, area, place,
  money, play time, the party's levels and partners), with the mode, position and
  direction the field menu would record in `GameState.fieldMode / fieldPos /
  fieldDir`. These are written into a private copy: **`GAME` is not changed**, so
  a game with the option on plays exactly as with it off. The summary's place is
  string 43, the one the first save point shows (a generic place).
- **Rate.** One write per area change; no timer. A 32 KiB write to the SD card is
  one rename-atomic flat file write, the same the game's own save makes.
- **Language.** The row, its value and its message line are lettered in the five
  languages of the EU disc (English on the US disc), made by
  `tools/generate_pc_title_lettering.py` like the Cheats screen and the quit
  windows. The other eight rows are English on both discs, as before.

## The ninth row

The window was full at eight rows (38 px rows on a 42 px pitch, last row ends at
y 482, message rule at y 508). Auto-save is a ninth row: rows are now **34 px high
on a 38 px pitch**, first row at y 150 as before, last row ends at y 488, 20 px
above the message rule; labels, values, pointer and the focus box keep their size
(the focus box interior is 28 px, the pointer 26). The Cheats pages use the same
geometry (their replays are log-only); the Yes / No window keeps its own 38 px
row (`CHT_ROW_*`). Labels and values are drawn 2 px higher and the pointer 2 px
higher so a descender stays inside the row rectangle of the cache. The dirty-rectangle cache (`title_options_cache.c`) uses the same numbers;
`DW3_OPTIONS_MAX_DIRTY` stays 10. The Options references change (see the PR); the
P9.9 redesign still owns the real fix for the room (a tenth row will not fit).

## Design

| Piece | Where |
|---|---|
| Policy (`dw3_autosave_decide`, plain integers), the idle-frame state machine, target tracking, the write | `port/autosave/autosave.c`, `port/include/port_autosave.h` |
| Area string of a mode (copy of `STGMCARD_prevModes`, checked against the decomp by a test) | `port/autosave/autosave_areas.c` |
| The row | `port/options/port_options.c` (`DW3_PORT_OPT_AUTOSAVE` = 8, key `autosave`), overlay in `platforms/pc/src/title_overlay_art.c` |
| Game side: ask at the idle frame, build the snapshot | decomp patch `0140` (`field_mode/field.c`) |
| Game side: which slot the player used; title clears it | decomp patch `0141` (`memory_card/saves.c`, `title/menu.c`) |
| The player's version kept aside, test failure hook | `memcard_host_snapshot`, `memcard_host_test_fail_flush` in `port/memcard/memcard_host.c` |

Flow at an area change: `dw3_autosave_field_idle` (policy: option, field,
battle, busy, transition, baseline, same area, target) says go;
`autosaveField` builds the snapshot; `dw3_autosave_commit` re-reads the card,
checks it (DW3 card, same game), copies the player's version to `.pre-auto` if the
slot is still the player's, writes the slot and the info section in RAM, flushes
the file (rename-atomic), and marks the slot for the cheat sidecar. The first idle
frame after a load or a new game is only noted (the baseline): loading is not an
area change.

**Failure.** The flat save is written to `save<N>.bin.tmp` first and the old file
is removed only after the new one is complete (the P5.3 rule). If the copy for
`.pre-auto` cannot be made, nothing is written. If the flush fails, the old bytes
are put back in RAM and the file on disk is the old one; the card is not left
locked (the next MemCard call retries). The failure is logged
(`dw3-autosave: FAILED to write card ...`) and the game goes on; there is no
on-screen notice in this slice (open, below). Unit tests force the failure with
`memcard_host_test_fail_flush`, and, as a normal user, with a read-only card
folder.

Log lines (PC stderr, Switch `dw3.log`): `dw3-options: autosave=1 (...)` at boot
with the option on; `dw3-autosave: target is card P slot S (loaded|saved)`; `mode 0x..: not saved (<reason>)`;
`area change to mode 0x..: saving to card P slot S`; `your version of card P is
kept in saveP.bin.pre-auto`; `wrote card P slot S (area mode 0x.., #N)`;
`not saved: ...` or `FAILED ...`.

## OLED checklist (owner, US and EU builds from this PR)

1. Options now has nine rows: Auto-save last, OFF; the screen reads as before
   otherwise (row spacing is a little tighter). In French, German, Spanish and
   Italian discs the row's label and message are in that language.
2. Turn Auto-save on, leave, **load a save** with Continue, walk through a door:
   `dw3.log` shows `target is card ... (loaded)`, then `area change ...` and
   `wrote card ...`. Close the game, relaunch, Continue the same slot: you arrive
   in the new area, not where you saved. The slot's list entry shows the area you
   entered.
3. `save0.bin.pre-auto` (and `save1.bin.pre-auto` if you use card 2) exists next
   to `save0.bin` on the SD card after the first auto-save, and is your version.
4. Start a new game with the option on: nothing is written until you save once.
5. With it off, play as usual: no `dw3-autosave` line in the log.
6. Not covered by the PC replays: a real SD write failure, HOME during the write,
   and how long the write holds a frame on the SD card (the OLED log has no
   timing line yet; a feel check is enough).
